## 테스트는 무엇을 사는가

테스트는 돈(작성·유지 시간, CI 시간)을 내고 다음을 산다.

| 얻는 것 | 설명 |
|---|---|
| **회귀 방지** | 고친 버그가 다시 오지 않는다. 가장 직접적인 가치 |
| 설계 피드백 | 테스트하기 어려운 코드는 대개 결합이 강한 코드다 |
| 실행 가능한 문서 | "이 함수는 경계값에서 이렇게 동작한다" 가 코드로 남는다 |
| **변경 자신감** | 리팩터링·의존성 업그레이드·배포를 두려움 없이 |

반대로 비용은 이렇다.

| 비용 | 설명 |
|---|---|
| 작성 | 기능 코드만큼 또는 그 이상 |
| 실행 시간 | CI 가 느리면 피드백이 늦고, 사람들이 테스트를 덜 돌린다 |
| **유지** | 구현 세부에 묶인 테스트는 리팩터링마다 깨진다 (거짓 경보) |
| **플레이키** | 가끔 실패하는 테스트는 신뢰 자체를 무너뜨린다 — [노트 06](/testing/notes/06-e2e-flaky-management) |

좋은 테스트 전략 = **같은 신뢰를 가장 싸게 사는 배분**이다.

## 피라미드와 트로피

![테스트 피라미드와 트로피](/diagrams/test-pyramid-trophy.svg)

### 피라미드 (Mike Cohn, 2009)

```
        /\        E2E        — 적게: 느리고 깨지기 쉽다
       /  \       통합
      /____\      단위        — 많이: 빠르고 싸다
```

논리: 아래로 갈수록 빠르고 싸고 결정적이다. 그러니 대부분을 단위 테스트로, 위층은 꼭 필요한 만큼만.

### 트로피 (Kent C. Dodds, 2018)

```
       ___
      (E2E)        — 적게
    (  통합  )      — 가장 많이: 실제로 같이 동작하는지
     ( 단위 )       — 순수 로직만
    [ 정적 분석 ]   — 바닥: 타입·린트가 오타·타입 오류를 공짜로 잡는다
```

논리: 단위 테스트가 mock 투성이면 "mock 이 내가 설정한 대로 동작한다" 만 검증한다. 사용자에게 의미 있는 신뢰는 **여러 부품이 실제로 같이 돌 때** 나온다. 그리고 TypeScript 가 잡아 주는 버그는 테스트를 쓸 필요가 없다.

### 어느 쪽이 맞나

둘 다 맞다. 차이는 시대와 도구다. 피라미드가 나왔을 때는 DB·브라우저를 띄우는 테스트가 분 단위로 느렸다. 지금은 컨테이너로 진짜 Redis·Postgres 를 수 초에 띄울 수 있어서([통합 테스트와 컨테이너](/testing/notes/03-integration-containers)) 통합 테스트가 싸졌다. 결론:

- **순수 로직**(계산·변환·규칙) → 단위 테스트, 속성 기반 테스트로 넓게
- **경계를 넘는 동작**(DB 쿼리·캐시·큐·HTTP) → 진짜 의존성으로 통합 테스트
- **사용자 흐름의 핵심 몇 개** → E2E
- **오타·타입 오류** → 정적 분석에 맡긴다

## 층별 비교

| 층 | 범위 | 속도 | 실패 원인 찾기 | 신뢰도 | 이 사이트의 예 |
|---|---|---|---|---|---|
| 정적 분석 | 소스 전체 | 수 초 | 정확 | 타입·패턴 오류만 | `tsc --noEmit`, `eslint` |
| 단위 | 함수·클래스 | ms | 쉬움 | 로직 | `cardKey()`, `stripJosa()`, 요금 규칙 |
| 통합 | 모듈 + 실제 의존성 | 100ms~수 초 | 중간 | 경계 동작 | Redis 실험 전체 (`tests/experiments.test.ts`) |
| 계약 | 서비스 간 인터페이스 | 수 초 | 쉬움 | 호환성 | API 스키마 호환 검사 — [노트 04](/testing/notes/04-contract-testing) |
| E2E | 브라우저 → 서버 → DB | 수 초~분 | 어려움 | 사용자 흐름 | "노트 읽음 표시 → 첫 화면 진행률 증가" |

## "단위" 의 두 학파

| | 고립(mockist, 런던파) | 사회적(classicist, 디트로이트파) |
|---|---|---|
| 단위 | 클래스 하나 | 행동 하나 (여러 클래스가 협력해도 됨) |
| 협력자 | 전부 mock | 진짜 객체, 느리거나 외부인 것만 대역 |
| 장점 | 실패 위치가 정확, 설계를 강제 | 리팩터링에 강함 |
| 단점 | 구현 세부에 묶여 리팩터링마다 깨짐 | 실패 원인이 여러 곳일 수 있음 |

현대의 기본값은 **사회적 단위 테스트 + 프로세스 밖 의존성(DB·HTTP·시간)만 대역**이다. "내부 협력 객체를 mock 하면 테스트가 구현을 따라 굳는다" 가 가장 흔한 후회다.

## 테스트 대역 (test doubles)

| 대역 | 하는 일 | 예 |
|---|---|---|
| dummy | 자리만 채움, 안 쓰임 | 필수 인자 채우기 |
| **stub** | 정해진 값을 돌려줌 | `getUser()` 가 항상 고정 사용자 |
| spy | 호출을 기록 | 이메일이 몇 번 보내졌나 |
| **mock** | 기대하는 호출을 미리 정하고 검증 | `expect(repo.save).toHaveBeenCalledWith(...)` |
| **fake** | 가볍지만 진짜처럼 동작하는 구현 | 메모리 Map 으로 만든 저장소, 가짜 시계 |

fake 가 mock 보다 대개 낫다. 동작을 검증하므로 리팩터링에 강하다. 자세한 설계는 [단위 테스트 설계](/testing/notes/02-unit-test-design).

## 좋은 테스트의 조건 (FIRST + α)

| 조건 | 뜻 | 어기면 |
|---|---|---|
| **F**ast | 빠르다 | 아무도 안 돌린다 |
| **I**ndependent | 순서·다른 테스트와 무관 | 순서 의존 플레이키 |
| **R**epeatable | 언제 어디서나 같은 결과 (시간·난수·네트워크 통제) | 금요일에만 실패 |
| **S**elf-validating | 통과/실패가 자동 | 로그를 사람이 읽어야 함 |
| **T**imely | 코드와 함께 작성 | 나중에는 안 쓴다 |
| 실패가 명확 | 실패 메시지만으로 원인을 짐작 | `expected true, got false` |
| 행동을 검증 | 무엇을 하는지, 어떻게가 아니라 | 리팩터링마다 깨짐 |

## 커버리지에 대해

커버리지는 **테스트가 안 지나간 곳**을 알려 주는 데는 좋지만, 지나간 곳을 **검증했는지**는 알려 주지 않는다. 실험 [`test-mutation-mini`](/testing/lab/test-mutation-mini) 에서 return 문 커버리지 100% 인 테스트 3개가 돌연변이 8개 중 5개를 놓쳤다(뮤테이션 점수 38%). 경계값 5개를 더하니 100% 가 됐다. 커버리지 목표치(80%)를 강제하면 "실행만 하고 단언은 없는" 테스트가 늘어난다 — [뮤테이션 테스트](/testing/notes/07-mutation-testing-cost).

## 무엇을 테스트하지 않을까

- 프레임워크·라이브러리 자체 (React 가 렌더링하는지)
- 단순 위임·게터 (로직이 없는 코드)
- 자주 바뀌는 UI 세부 (픽셀·문구) — 스냅샷 테스트의 남용 주의
- 이미 타입이 보장하는 것

대신 **돈·권한·데이터 손실·한도**가 걸린 로직은 넓고 깊게 테스트한다.

## 예시로 보기 — 이 사이트의 테스트 구조

| 층 | 지금 | 비고 |
|---|---|---|
| 정적 분석 | `pnpm lint`, `tsc --noEmit` — CI 필수 | ✓ |
| 단위 | 거의 없음 | `searchSmart`, `stripJosa`, `cardKey`, 라이트너 상자 계산이 좋은 후보 |
| 통합 | `tests/experiments.test.ts` — Redis 실험 전체를 실제 Redis(CI 서비스 컨테이너)로 실행 | 실험 프레임워크의 `rec.check` 가 곧 단언 |
| 셸·코드 실험 | 헤드리스 러너 `scripts/run-*-lab.mts` | CI 에서는 안 돈다 (Docker·k8s 필요) |
| E2E | 없음 | 브라우저 흐름 몇 개가 후보 |

이 사이트는 우연히 **트로피 모양**이다. 실험 프레임워크(`Recorder` 의 `measure`/`check`)가 사실상 통합 테스트 프레임워크이고, 그 결과를 웹에서 보여 준다. 부족한 것은 순수 로직의 단위 테스트와 핵심 사용자 흐름의 E2E 다.

## 실전에서는 어디에 쓰이나 — 테스트 지도

> 테스트는 "배포해도 되나" 라는 질문에 사람 대신 답하는 장치다. 실무에서는 어느 층에 얼마나 투자할지(배분), 느리고 깨지는 테스트를 어떻게 관리할지(운영)가 기술 자체보다 더 자주 논의된다.

| 서비스·상황 | 이 주제의 어떤 부분이 | 더 읽기 |
|---|---|---|
| 핀테크 수수료·이자 계산 로직 | 시간·난수 주입, 경계값 표, fake 저장소로 결정적 단위 테스트 | [단위 테스트 설계](/testing/notes/02-unit-test-design) |
| 커머스 주문 저장·캐시·큐 연동 | 진짜 PostgreSQL·Redis 컨테이너로 SQL·원자성·TTL 검증 | [통합 테스트와 컨테이너](/testing/notes/03-integration-containers) |
| 마이크로서비스 수십 개의 독립 배포 | 소비자 주도 계약(Pact), 스키마 호환성 검사 | [계약 테스트](/testing/notes/04-contract-testing) |
| 레이트리미터·직렬화·CRDT 같은 까다로운 로직 | 속성 기반 테스트로 반례 자동 탐색·축소 | [속성 기반 테스트](/testing/notes/05-property-based-testing) |
| SaaS 가입·결제 핵심 여정 | Playwright E2E, 플레이키 격리·통과율 추적 | [E2E 와 플레이키 관리](/testing/notes/06-e2e-flaky-management) |
| CI 가 30분 넘게 걸리는 대형 저장소 | 뮤테이션 점수로 테스트 질 측정, 샤딩·영향 분석 | [뮤테이션 테스트와 비용](/testing/notes/07-mutation-testing-cost) |

**회사 규모에 따라**
- 스타트업: 타입·린트 + 핵심 로직 단위 테스트 + 결제 같은 몇 개 흐름의 E2E 로 시작한다. 커버리지 목표보다 "돈이 걸린 로직" 우선.
- 성장기: 컨테이너 통합 테스트가 표준이 되고, 서비스가 나뉘면서 계약 테스트와 CI 시간 문제가 등장한다.
- 대규모 조직: 플레이키 격리·소유자 지정·테스트별 통과율 대시보드를 운영하는 개발자 생산성(DevEx) 팀이 생기고, 영향 분석으로 PR 마다 필요한 테스트만 돌린다.

**이럴 땐 안 맞는다**
- 일주일 쓰고 버릴 프로토타입·일회성 스크립트: 테스트 비용을 회수할 시간이 없다. 타입 체크와 수동 확인으로 충분하다.
- 커버리지 수치 강제: 단언 없는 테스트만 늘어난다. 안 간 곳 찾기 용도로만 보고, 질은 뮤테이션 점수나 리뷰로 판단한다.

**누가 매일 만나나** — 백엔드·프론트엔드 개발자는 PR 마다 테스트를 쓰고 CI 실패를 조사할 때, QA·SDET 은 E2E 묶음과 테스트 전략을 설계할 때, 플랫폼 엔지니어는 CI 시간과 플레이키 비율을 관리할 때 만난다.

**면접·실무 단골 질문**
- Q. 피라미드와 트로피 중 무엇이 맞나? → 둘 다 "같은 신뢰를 가장 싸게" 라는 원칙. 컨테이너로 통합 테스트가 싸진 지금은 경계 동작은 통합, 순수 로직은 단위로 나눈다.
