## 커버리지는 무엇을 말하지 않나

| 지표 | 정의 | 100% 여도 놓치는 것 |
|---|---|---|
| 줄 커버리지 | 실행된 줄 비율 | 한 줄 안의 여러 조건, 단언 없는 실행 |
| 분기 커버리지 | if/else 각 방향 실행 비율 | `a && b` 에서 b 가 false 인 경우 |
| 조건(MC/DC) | 각 조건이 결과에 독립적으로 영향 | 경계값(29999 vs 30000), 잘못된 기대값 |

커버리지의 근본 한계는 **"실행됐다" 를 재지 "검증됐다" 를 재지 않는다**는 것이다. 단언이 하나도 없는 테스트도 커버리지 100% 를 만든다.

```ts
test("배송비", () => { shippingFee(60000, false); shippingFee(10000, false); shippingFee(40000, true); });
// 커버리지 100%, 단언 0개 — 무엇이든 통과한다
```

커버리지 목표치를 강제하면 이런 테스트가 늘어난다(굿하트의 법칙: 지표가 목표가 되면 좋은 지표가 아니게 된다). 커버리지는 **"테스트가 아예 안 간 곳"** 을 찾는 용도로 쓰고, 테스트의 질은 다른 방법으로 잰다.

## 뮤테이션 테스트의 원리

**코드에 작은 버그를 일부러 심고, 테스트가 그걸 잡는지** 본다.

![뮤테이션 테스트](/diagrams/test-mutation.svg)

```
1. 원본 코드에서 돌연변이(mutant) 를 만든다:  total >= 30000  →  total > 30000
2. 테스트 묶음을 돌린다
   - 하나라도 실패 → 돌연변이를 죽였다 (killed)  ✓ 테스트가 이 버그를 잡는다
   - 모두 통과    → 돌연변이가 살아남았다 (survived) ⚠ 테스트가 이 버그를 못 잡는다
3. 뮤테이션 점수 = 죽인 수 / (전체 − 동등 돌연변이)
```

### 돌연변이 연산자

| 범주 | 예 |
|---|---|
| 경계·비교 | `>=` → `>`, `<` → `<=`, `==` → `!=` |
| 논리 | `&&` → `\|\|`, `!x` → `x`, 조건을 `true`/`false` 로 |
| 산술 | `+` → `-`, `*` → `/`, `++` → `--` |
| 상수 | 숫자 ±1, 문자열을 `""` 로, 배열을 `[]` 로 |
| 문장 제거 | 함수 호출·return 문 삭제, 블록 비우기 |
| 반환값 | `return x` → `return null`/기본값 |

### 실측

실험 [`test-mutation-mini`](/testing/lab/test-mutation-mini) 은 이 과정을 수십 줄로 재현한다. 대상은 무료 배송 규칙:

```js
function shippingFee(total, isMember) {
  if (isMember && total >= 30000) return 0;
  if (total >= 50000) return 0;
  return 3000;
}
```

| 테스트 묶음 | return 문 커버리지 | 뮤테이션 점수 |
|---|---|---|
| 약한 묶음 3개: (60000,비회원), (10000,비회원), (40000,회원) | **100%** | **38%** (8개 중 3개) |
| + 경계값 5개: 30000/29999 회원, 50000/49999 비회원, 40000 비회원 | 100% | **100%** |

살아남았던 돌연변이 다섯 개:

| 살아남은 돌연변이 | 테스트에 빠진 질문 |
|---|---|
| `>= 30000` → `> 30000` | 회원이 **정확히 3만 원**이면? |
| `>= 50000` → `> 50000` | 비회원이 **정확히 5만 원**이면? |
| `isMember &&` → `isMember \|\|` | 비회원이 3만~5만 원이면? (회원 조건이 실제로 쓰이나) |
| `30000` → `3000` | 회원이 3천~3만 원이면? |
| `isMember &&` 삭제 | 비회원이 3만~5만 원이면? |

살아남은 돌연변이 목록은 **"다음에 쓸 테스트 목록"** 이다. 커버리지 보고서는 이 정보를 절대 주지 않는다.

### 동등 돌연변이

원본과 **의미가 같은** 돌연변이는 어떤 테스트로도 죽일 수 없다.

```js
for (let i = 0; i < n; i++)   →   for (let i = 0; i != n; i++)    // i 가 1씩 증가하면 같은 동작
return d > max ? max : d       →   return d >= max ? max : d       // d == max 일 때 둘 다 max
```

동등 돌연변이를 자동으로 판별하는 것은 일반적으로 불가능하다(정지 문제와 같은 부류). 사람이 보고 무시 목록에 넣는다. 그래서 뮤테이션 점수 100% 를 목표로 삼지 않고, **핵심 로직에서 살아남은 비동등 돌연변이를 0 으로** 를 목표로 한다.

## Stryker 로 실행하기

```bash
npm i -D @stryker-mutator/core @stryker-mutator/vitest-runner
npx stryker init
```

```json
// stryker.config.json
{
  "testRunner": "vitest",
  "mutate": ["src/lib/study.ts", "src/lib/search.ts", "!src/**/*.test.ts"],
  "coverageAnalysis": "perTest",
  "incremental": true,
  "thresholds": { "high": 80, "low": 60, "break": 50 }
}
```

| 설정 | 효과 |
|---|---|
| `mutate` | **핵심 로직만** — 전체에 돌리면 몇 시간 |
| `coverageAnalysis: perTest` | 돌연변이가 있는 줄을 실행하는 테스트만 돌린다 (수십 배 빠름) |
| `incremental` | 이전 결과를 저장해 바뀐 코드의 돌연변이만 다시 |
| `thresholds.break` | 점수가 이 아래면 실패 — CI 게이트 |

### 비용

돌연변이 수 × 테스트 묶음 실행 시간. 함수 하나에 돌연변이 수십 개, 파일 하나에 수백 개다. 그래서:

- 매 PR 에 전체를 돌리지 않는다 → **바뀐 파일만** (증분)
- 야간에 핵심 모듈 전체
- 대상은 **금액·권한·한도·상태 전이** 같은 버그 비용이 큰 로직

## 테스트 묶음의 비용 모델

테스트 하나의 평생 비용 = 작성 + (실행 시간 × 실행 횟수) + 유지(깨질 때마다 고치기) + **거짓 경보**(플레이키·구현 결합으로 인한 실패 조사).

| 테스트 유형 | 작성 | 실행 | 유지 | 거짓 경보 | 잡는 버그의 가치 |
|---|---|---|---|---|---|
| 순수 로직 단위 | 낮음 | ms | 낮음 | 거의 없음 | 로직 |
| mock 투성이 단위 | 중간 | ms | **높음** (구현 결합) | 높음 | 낮음 |
| 통합 (진짜 의존성) | 중간 | 수백 ms | 중간 | 낮음 | 높음 (경계) |
| E2E | 높음 | 수 초~분 | 높음 | **높음** (플레이키) | 높음 (여정) |

실험 [`test-flaky-detector`](/testing/lab/test-flaky-detector) 의 재시도 표가 숨은 비용을 보여 준다: 재시도는 실패율을 36% → 6% 로 낮췄지만 평균 실행 시간을 16ms → 27ms 로 늘렸다. 테스트 1만 개면 그 차이가 분 단위가 된다.

### 어떤 테스트를 지울까

- **한 번도 실패한 적 없고**, 같은 동작을 다른 테스트가 이미 검증 → 중복
- 구현을 바꿀 때마다 깨지고, 깨질 때 버그를 잡은 적이 없다 → 구현 결합
- 격리된 지 오래된 플레이키 → 고치거나 지운다 ([플레이키 관리](/testing/notes/06-e2e-flaky-management))
- 뮤테이션 테스트에서 **아무 돌연변이도 죽이지 않는** 테스트 → 단언이 없거나 의미 없다

## CI 실행 시간 최적화

| 기법 | 방법 | 효과 |
|---|---|---|
| 병렬 | 워커 여러 개 (`vitest --pool threads`) | 코어 수만큼 |
| **샤딩** | 테스트를 N 개 잡으로 나눔 (`--shard=1/4`), 매트릭스 | 잡 수만큼 |
| 실행 시간 기반 분배 | 지난 실행 시간으로 균등 분배 | 가장 느린 샤드가 병목이므로 |
| **영향 분석** | 바뀐 파일에 의존하는 테스트만 (`vitest --changed`, Nx/Turborepo affected) | PR 에서 크게 |
| 캐시 | 의존성·빌드 캐시, 테스트 결과 캐시 (입력 해시가 같으면 건너뜀) | |
| 빠른 실패 | 정적 분석 → 단위 → 통합 → E2E 순, 앞에서 실패하면 중단 | 피드백 시간 |
| 계층화 | PR: 영향받은 테스트 / main: 전체 / 야간: 뮤테이션·반복·E2E 전체 | |

자세한 GitHub Actions 설정은 [CI 성능](/github-actions/notes/06-ci-performance), 평가 CI 의 같은 계층화는 [평가 CI](/mlops/notes/07-eval-ci-prompt-regression).

## 실전에서는 어디에 쓰이나

> "커버리지 90% 인데 왜 버그가 새나" 라는 질문, 또는 "CI 가 너무 느린데 무엇을 줄이나" 라는 질문에서 이 노트가 쓰인다. 뮤테이션 테스트는 테스트의 질을 재고, 비용 모델은 테스트 묶음을 줄이고 배치하는 기준이 된다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 핀테크 수수료·한도 로직 | 커버리지는 높은데 경계 버그가 샘 | Stryker 를 핵심 모듈에만, 살아남은 돌연변이를 다음 테스트 목록으로 | 커버리지 목표 상향(단언 없는 테스트 증가) |
| 권한·접근 제어 코드 | 조건 하나 뒤집혀도 테스트가 통과 | AND 를 OR 로 바꾼 논리 돌연변이가 죽는지 확인 | 리뷰어 경험에 의존 |
| 대형 모노레포 CI | PR 피드백이 30분 이상 | 영향 분석(`--changed`, Nx·Turborepo affected) + 샤딩 + 빠른 실패 순서 | 러너만 증설 |
| 오래된 테스트 묶음 정리 | 유지비만 들고 버그를 못 잡는 테스트 | 돌연변이를 하나도 못 죽이는 테스트, 구현 결합 테스트를 삭제 후보로 | 무조건 유지 |
| 계층형 CI 운영 | 무거운 검사를 어디서 돌릴지 | PR: 영향 테스트 / main: 전체 / 야간: 뮤테이션·반복·E2E 전체 | 모든 검사를 매 PR 에 |

**이럴 땐 안 맞는다**
- 저장소 전체에 매 PR 뮤테이션 테스트: 돌연변이 수 × 묶음 실행 시간이라 몇 시간이 걸린다. 증분·핵심 모듈·야간으로 제한한다.
- 뮤테이션 점수 100% 목표: 동등 돌연변이는 원리상 못 죽인다. 핵심 로직에서 살아남은 비동등 돌연변이 0 을 목표로 한다.

**누가 매일 만나나** — 시니어 백엔드 개발자는 금액·권한 로직의 테스트 질을 점검할 때, 플랫폼·DevEx 엔지니어는 CI 실행 시간과 샤드 분배를 튜닝할 때 만난다.

**면접·실무 단골 질문**
- Q. 커버리지 100% 면 충분한가? → 실행 여부만 재고 검증 여부는 모른다. 뮤테이션 점수가 단언의 질을 보여 준다.
- Q. CI 를 빠르게 하는 방법은? → 빠른 실패 순서, 병렬·샤딩, 영향 분석, 캐시, 무거운 검사의 야간 분리.
