## 이벤트 스토밍 — 벽에 시간을 펼친다

이벤트 스토밍(Alberto Brandolini)은 도메인 전문가와 개발자가 큰 벽(또는 화이트보드 도구)에 **일어난 일**을 포스트잇으로 붙이며 도메인을 발견하는 워크숍이다. 색이 곧 문법이다.

| 색 (관례) | 요소 | 예 (주문 도메인) |
|---|---|---|
| 주황 | 도메인 이벤트 (과거형) | 주문됨, 결제 승인됨, 출고됨 |
| 파랑 | 명령 | 주문하기, 결제하기, 취소하기 |
| 노랑 (작은) | 행위자 | 고객, 상담원, 배송 시스템 |
| 노랑 (큰) | 집합 | 주문, 결제, 재고 |
| 보라 | 정책 (이벤트가 나면 명령을 낸다) | "결제 승인됨 → 출고 지시" |
| 초록 | 읽기 모델 | 주문 목록, 배송 추적 화면 |
| 분홍 | 외부 시스템 | PG사, 택배사 API |
| 빨강 | 핫스팟(질문·갈등) | "부분 취소는 누가 승인?" |

진행 순서는 보통 이렇다.

1. **혼돈의 탐색**: 각자 아는 이벤트를 마구 붙인다(과거형 동사).
2. **시간 정렬**: 왼쪽에서 오른쪽으로 시간순으로 놓는다. 중복·모순이 드러난다.
3. **명령과 행위자**: 각 이벤트를 일으킨 명령과 그 명령을 내린 사람을 붙인다.
4. **정책**: "~가 되면 ~한다" 자동 반응을 보라색으로.
5. **집합 찾기**: 같은 규칙으로 명령을 받아들이고 거절하는 덩어리를 묶는다.
6. **경계 긋기**: 언어가 바뀌는 지점(주문의 "상품" ≠ 재고의 "SKU")에서 컨텍스트를 나눈다.

```
[고객] 주문하기 ──▶ (주문) ──▶ 주문됨 ──▶ <정책: 재고 예약> ──▶ 재고 예약하기 ──▶ (재고) ──▶ 재고 예약됨
                                                                                      └─▶ 재고 부족함 ──▶ <정책: 주문 취소>
```

## 집합 — 일관성 경계

**집합(aggregate)** 은 "한 번의 명령으로 함께 일관되어야 하는 상태의 묶음" 이다. 이벤트 소싱에서는 **집합 하나 = 스트림 하나** 이고, 낙관적 동시성은 스트림 단위로 걸린다.

경계를 고르는 기준은 **불변식**이다.

| 불변식 | 같은 집합이어야 하나? |
|---|---|
| 계좌 잔액은 음수가 될 수 없다 | 예 — 잔액과 출금이 같은 스트림 |
| 주문 총액 = 줄 항목 합 | 예 — 주문과 줄 항목은 한 집합 |
| 상품 재고는 음수가 될 수 없다 | 재고 집합 안에서만 |
| 주문의 상품 재고가 있어야 한다 | **아니오** — 두 집합 사이는 사가·정책으로 결과적 일관성 |

> 규칙: **집합은 작게.** 큰 집합(예: "가게" 하나가 모든 주문을 포함)은 경합 지점이 된다. 실험 [es-optimistic-concurrency](/event-sourcing/lab/es-optimistic-concurrency) 에서 출금 20건이 같은 스트림을 두고 다투자 재시도가 55번 일어났다. 초당 수천 건이 한 스트림에 몰리면 재시도가 폭주한다. 인기 상품 재고 하나가 모든 주문을 받는다면 재고를 창고·슬롯별 스트림으로 쪼개는 식으로 경계를 다시 나눈다.

집합 간 참조는 **ID 로만** 한다. 주문 집합 안에 고객 집합 객체를 넣지 않고 `customerId` 만 둔다. 두 집합을 한 트랜잭션에서 바꾸려는 순간 경계가 잘못된 것이다 — 그때는 [사가](/event-sourcing/notes/07-sagas-operations)를 쓴다. 분산 트랜잭션을 피하는 이유는 [분산 시스템 노트 06](/distributed-systems/notes/06-transactions-coordination).

## 이벤트 이름 짓기

| 나쁜 이름 | 문제 | 좋은 이름 |
|---|---|---|
| `OrderUpdated` | 무엇이 왜 바뀌었는지 모른다 | `ShippingAddressChanged`, `OrderItemRemoved` |
| `CreateOrder` | 명령형 — 이벤트는 과거형 | `OrderPlaced` |
| `StatusChanged{status:3}` | 상태 코드 = 의도 손실 | `PaymentAuthorized`, `OrderCancelled{reason}` |
| `RowInserted` | 기술 용어 | 업무 용어 |
| `UserDidSomething` | 너무 일반적 | 구체적 사건 |

이름은 **도메인 전문가가 읽어도 이해되는 말**이어야 한다. "결제 승인됨" 은 회계 담당자가 이해하지만 "status=3" 은 아니다.

## 이벤트 스키마 — 데이터와 메타데이터

```json
{
  "id": "4f1c…",                     // 이벤트 고유 ID (소비자 멱등 키)
  "stream_id": "order-7731",         // 집합 ID
  "version": 4,                      // 스트림 안 순번 (낙관적 동시성)
  "type": "OrderItemRemoved",
  "schema": 2,                       // 데이터 스키마 버전 (업캐스팅용)
  "data": { "sku": "BK-102", "qty": 1, "reason": "out_of_stock" },
  "metadata": {
    "occurred_at": "2026-10-17T09:12:03Z",
    "actor": "user:331",             // 누가
    "correlation_id": "req-88f…",    // 이 업무 흐름 전체를 묶는 ID
    "causation_id": "evt-77a…",      // 이 이벤트를 직접 일으킨 메시지 ID
    "trace_id": "0af7651916cd43dd8448eb211c80319c"
  }
}
```

| 필드 | 쓰임 |
|---|---|
| `id` | 소비자가 중복을 걸러 내는 키 ([메시징 노트 04](/messaging/notes/04-delivery-guarantees-delay) 멱등 소비자) |
| `version` | `unique(stream_id, version)` 로 동시 변경 차단 |
| `schema` | 읽을 때 업캐스터 선택 ([노트 06](/event-sourcing/notes/06-schema-evolution)) |
| `correlation_id` | "주문 하나" 로 시작된 이벤트·명령 전체를 묶어 추적 |
| `causation_id` | 직접 원인 — 사가의 연쇄를 그래프로 그릴 수 있다 |
| `trace_id` | 관측 스택(Tempo)과 연결 |

## 이벤트 크기 — 너무 작게도, 너무 크게도 말자

- **너무 작다**: `FirstNameChanged`, `LastNameChanged`, `PhoneChanged` 가 화면 저장 한 번에 세 개 → 의도("연락처 수정")가 흩어진다. 하나의 사용자 의도 = 하나의 이벤트가 기본.
- **너무 크다**: `OrderSnapshotSaved{…전체 주문…}` → 사실상 상태 저장. 무엇이 바뀌었는지 비교해야 알 수 있다.
- **이벤트에 무엇을 담나**: 소비자가 그 이벤트만 보고 처리할 수 있을 만큼(fat event) vs ID 만 담고 조회하게(thin event). 외부 발행용은 대개 **필요한 사실을 담는 쪽**이 낫다 — 소비자가 조회하는 순간 결합과 경쟁 조건이 생긴다.

## 심화 — 집합 경계를 숫자로 검증하기

워크숍에서 그은 경계가 맞는지는 **경합**과 **수명**이라는 두 숫자로 확인할 수 있다.

### 경합 — 한 스트림에 얼마나 몰리나

한 스트림에 초당 λ 개 명령이 오고, 명령 하나가 "읽기 → 결정 → 쓰기" 에 w 초를 쓴다면, 내가 결정하는 동안 누군가 끼어들 확률은 대략 `1 − e^(−λ·w)` 다(도착이 무작위라는 단순 가정).

| 스트림 부하 λ | 처리 창 w | 충돌 확률(근사) | 판단 |
|---|---|---|---|
| 1/초 (개인 계좌) | 10ms | 약 1% | 문제없음 |
| 50/초 (인기 상품 재고) | 10ms | 약 39% | 재시도가 일상, 지연 꼬리가 길어짐 |
| 2,000/초 (한정판 오픈) | 10ms | 거의 100% | 경계를 다시 나눠야 함 |

목표는 `λ·w ≪ 0.1`. λ 를 줄이려면 집합을 쪼개고, w 를 줄이려면 로딩을 빠르게 한다([노트 05](/event-sourcing/notes/05-snapshots-performance)의 스냅샷·스트림 마감).

### 뜨거운 재고를 쪼개는 예

```
stock-BK102            (모든 주문이 한 스트림)          λ = 2,000/초
   ↓ 슬롯 8개로 분할
stock-BK102-slot-0 … stock-BK102-slot-7                  λ ≈ 250/초씩
   슬롯 선택 = hash(orderId) % 8,  초기 재고 800 → 슬롯당 100
```

대가도 분명하다. 슬롯 3 은 0 인데 슬롯 5 에 40 개가 남는 **조각화**가 생긴다. "슬롯이 비면 다른 슬롯을 한 번 더 시도" 또는 주기적인 `StockRebalanced` 이벤트로 옮긴다. 정확한 전체 재고는 이제 프로젝션(슬롯 합)으로만 보인다 — 일관성 경계를 좁힌 대가로 **전역 불변식 일부를 결과적 일관성으로** 바꾼 것이다.

### 수명 — 스트림이 얼마나 길어지나

| 집합 | 수명 동안 이벤트 수(예) | 판단 |
|---|---|---|
| 주문 | 5~30 | 이상적 |
| 장바구니 | 10~200 | 괜찮음 |
| 계좌(10년) | 수만 | 기간 마감 고려 |
| "가게" 전체 | 끝없음 | 경계 오류 |

## 이벤트 계약을 코드로 고정하기

이벤트 목록은 타입으로 닫아 두면 리듀서가 빠뜨린 경우를 컴파일러가 잡는다.

```ts
type OrderEvent =
  | { type: "OrderPlaced"; schema: 1; data: { orderId: string; customerId: string; lines: { sku: string; qty: number; unitPrice: number }[] } }
  | { type: "OrderItemRemoved"; schema: 2; data: { sku: string; qty: number; reason: "out_of_stock" | "customer_request" } }
  | { type: "OrderCancelled"; schema: 1; data: { reason: string; by: "customer" | "system" } };

function apply(s: OrderState, e: OrderEvent): OrderState {
  switch (e.type) {
    case "OrderPlaced": return { ...s, status: "placed", lines: e.data.lines };
    case "OrderItemRemoved": return { ...s, lines: s.lines.filter((l) => l.sku !== e.data.sku) };
    case "OrderCancelled": return { ...s, status: "cancelled" };
    default: { const _never: never = e; return s; }   // 새 이벤트를 추가하고 처리 안 하면 컴파일 에러
  }
}
```

`reason` 처럼 **업무상 이유**를 열거형으로 담아 두면 나중에 "품절 때문에 빠진 품목 비율" 같은 분석을 이벤트만으로 할 수 있다. 이유를 문자열 자유 입력으로 두면 그 분석은 불가능해진다.

## 모델링을 관측과 연결하기

좋은 이벤트 이름은 그대로 **메트릭 레이블과 로그 필드**가 된다.

| 신호 | 예 | 무엇을 알려 주나 |
|---|---|---|
| 카운터 | `es_events_appended_total{aggregate="order", type="OrderCancelled"}` | 취소율 급증 = 결제·재고 장애의 첫 증상인 경우가 많다 |
| 카운터 | `es_append_conflicts_total{aggregate="stock"}` | 경계가 너무 큰 집합 |
| 히스토그램 | `es_stream_length{aggregate}` | 수명이 끝나지 않는 집합 |
| 로그 필드 | `correlation_id`, `causation_id`, `stream_id`, `type` | 한 주문의 모든 일을 한 번에 조회 |

```
# Loki — 주문 하나로 시작된 흐름 전체를 시간순으로
{app=~"orders|payments|stock"} | json | correlation_id="req-88f"
```

`StatusChanged{status:3}` 같은 이름이었다면 대시보드에서 "3" 이 무엇인지 매번 해석해야 한다. 이벤트 이름이 곧 관측의 어휘다. 로그·트레이스 연결은 [관측성 노트 05](/observability/notes/05-logging-loki), [노트 06](/observability/notes/06-tracing-otel).

## 흔한 실수와 오해

- **"테이블 하나 = 집합 하나"**: 집합은 저장 구조가 아니라 **불변식**으로 정한다. 주문과 줄 항목은 테이블 두 개여도 집합 하나다.
- **CDC 이벤트 = 도메인 이벤트**: `orders 행 UPDATE` 는 기술 이벤트다. 왜 바뀌었는지(의도)가 없다.
- **거절도 전부 이벤트로 남긴다**: 거절된 명령은 일어나지 않은 일이다. 다만 "출금 거절" 이 업무상 감사 대상이면 `WithdrawalRejected` 를 **별도 감사 스트림**에 남긴다(집합 상태는 바꾸지 않는다).
- **이벤트에 계산 결과(잔액)를 넣는다**: 편하지만 리듀서와 어긋날 수 있다. 넣는다면 "참고용" 이고 재생은 리듀서로 한다.
- **내부 이벤트를 그대로 외부에 발행**: 내부 이름을 바꾸는 순간 소비자가 깨진다([노트 06](/event-sourcing/notes/06-schema-evolution)의 통합 이벤트).

## 스스로 점검

1. 인기 상품 재고 스트림에 초당 수천 건 명령이 몰린다. 경계를 어떻게 바꾸고, 무엇을 잃나? — 슬롯·창고별로 쪼개 경합을 나누고, 전체 재고 불변식은 결과적 일관성(프로젝션 합·재분배)으로 바뀐다.
2. 주문과 고객을 한 트랜잭션에서 바꿔야 한다는 요구가 나왔다. 무엇을 의심하나? — 경계 오류이거나 사가로 풀 업무. 집합 간 참조는 ID 로만.
3. `ContactInfoUpdated` 하나와 `PhoneChanged`·`EmailChanged` 셋 중 무엇을 고르나? — 사용자 의도 단위. 화면 저장 한 번이 의도라면 하나, 전화번호만 따로 인증하는 업무라면 따로.
4. correlation_id 없이 장애를 추적하면 무엇이 어려운가? — 서비스 경계를 넘는 연쇄(주문 → 재고 → 결제)를 시간·ID 추측으로 이어 붙여야 한다.

## 실전에서는 어디에 쓰이나

> 새 도메인을 설계하거나 CRUD 를 이벤트 기반으로 옮길 때, 무엇을 이벤트로 남기고 어디까지를 한 집합으로 묶을지 정하는 순간에 등장한다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 커머스 주문 도메인 킥오프 | 기획·운영·개발이 같은 흐름을 이해 | 이벤트 스토밍으로 이벤트·명령·정책·핫스팟을 벽에 펼침 | 요구사항 문서·ERD 부터 — 예외 흐름이 늦게 드러남 |
| 한정판 판매·티켓 오픈 | 뜨거운 재고 스트림의 경합 | 슬롯·창고별로 집합 분할, 전체 재고는 프로젝션 합 | 재고 한 행을 모두가 다툼 |
| 보험 청구·예약 시스템 | 업무 이유가 남는 감사 기록 | `OrderCancelled{reason}` 처럼 이유를 열거형으로 | `StatusChanged{status:3}` — 의도 손실 |
| 마이크로서비스 운영 | 서비스 경계를 넘는 흐름 추적 | correlation_id·causation_id·trace_id 메타데이터 | 시각·ID 추측으로 로그 잇기 |
| 운영 대시보드 | 이벤트 이름을 그대로 업무 지표로 | `es_events_appended_total{type}` 카운터 | 테이블 변경 수 집계 — 매번 해석 필요 |

**이럴 땐 안 맞는다**
- 행 변경을 그대로 옮긴 CDC 이벤트를 도메인 이벤트로 쓰는 것 — 의도가 없다. 도메인 이벤트가 필요하면 업무 언어로 다시 정의한다.
- 두 집합을 한 트랜잭션으로 바꿔야 한다는 요구를 큰 집합 하나로 푸는 것 — 경합 지점이 된다. 사가로 잇는다.

**누가 매일 만나나** — 백엔드·아키텍트가 기획자·도메인 전문가와 설계 워크숍을 할 때, 코드 리뷰에서 `XxxUpdated` 같은 이름을 잡아낼 때.

**면접·실무 단골 질문**
- Q. 집합 경계는 무엇으로 정하나? → 테이블 구조가 아니라 한 명령 안에서 지켜야 하는 불변식으로 정한다.
- Q. correlation_id 와 causation_id 는 어떻게 다른가? → 업무 흐름 전체를 묶는 ID 와, 이 이벤트를 직접 일으킨 메시지 ID. 둘이 있어야 사가 연쇄를 그래프로 그린다.
