## 왜 어려운가

상태 저장 시스템은 `ALTER TABLE` 하고 데이터를 변환하면 끝이다. 이벤트 스토어의 이벤트는 **과거의 사실**이라 고치지 않는 것이 원칙이고, 재생할 때마다 옛 이벤트를 새 코드가 읽어야 한다. 10년 된 시스템은 10년치 스키마를 모두 읽을 수 있어야 한다.

## 변경의 종류

| 변경 | 호환? | 처리 |
|---|---|---|
| 선택 필드 추가 (`memo?`) | 호환 | 읽을 때 기본값 |
| 필수 필드 추가 (`currency`) | **깨짐** | 업캐스터로 기본값 채우기 |
| 필드 이름 변경 (`amt` → `amount`) | 깨짐 | 업캐스터 |
| 필드 의미 변경 (단위 원 → 센트) | **위험** — 형은 같은데 뜻이 다름 | 새 이벤트 타입 또는 새 필드 |
| 이벤트 이름 변경 | 깨짐 | 타입 매핑 테이블 |
| 이벤트 분할 (`AddressChanged` → `StreetChanged` + `CityChanged`) | 깨짐 | 업캐스터가 1 → N |
| 이벤트 병합 | 깨짐 | 프로젝션 쪽에서 처리, 또는 복사·변환 |

> 규칙: **필드 의미는 바꾸지 않는다.** 단위·통화·시간대가 바뀌면 새 필드나 새 이벤트를 만든다. 형이 같아 테스트가 통과하는데 값만 100배 틀리는 사고가 가장 무섭다.

## 업캐스터 — 읽는 길목에서 변환

```ts
type Stored = { type: string; schema: number; data: any };

const upcasters: Record<string, Record<number, (d: any) => any>> = {
  MoneyDeposited: {
    1: (d) => ({ ...d, currency: "KRW" }),             // v1 → v2: 통화가 없던 시절은 모두 원화
    2: (d) => ({ ...d, amountMinor: d.amount * 100 }),  // v2 → v3 (예시)
  },
};

function upcast(e: Stored, target = LATEST[e.type]): Stored {
  let cur = e;
  while (cur.schema < target) {
    cur = { ...cur, data: upcasters[cur.type][cur.schema](cur.data), schema: cur.schema + 1 };
  }
  return cur;
}
```

- 업캐스터는 **순수 함수**다(외부 조회 금지). 재생 결과가 언제나 같아야 한다.
- 체인 방식(v1→v2→v3)이라 각 단계는 작게 유지된다.
- 리듀서·프로젝터는 **최신 스키마만 안다**. 옛 스키마 지식은 업캐스터에 모인다.

### 실측 — 업캐스터가 없으면

[es-upcasting](/event-sourcing/lab/es-upcasting) 의 스트림은 v1 이벤트 3개(통화 없음) 뒤에 v2 이벤트 3개(통화 있음)다.

| 재생 방식 | 결과 |
|---|---|
| v2 리듀서, 업캐스터 없음 | **실패** — `currency 없음: {"amount":5000}` |
| 검사를 뺀 "관대한" 리듀서 | `{ undefined: 5500, USD: 20, KRW: 1000 }` — 깨지지 않지만 **조용한 오염** |
| 업캐스터(v1 → currency="KRW") | `{ KRW: 6500, USD: 20 }` ✓ |

저장된 이벤트는 재생 전후로 한 바이트도 바뀌지 않았다. 관대한 리듀서 줄이 핵심 교훈이다. "필드가 없으면 그냥 넘어가자" 는 약한 스키마는 예외 대신 **틀린 데이터**를 만든다. 예외는 고치기 쉽고, 틀린 데이터는 몇 달 뒤 회계 감사에서 발견된다.

업캐스팅 비용도 쟀다. 메모리 안 이벤트 20만 개(절반이 v1)를 업캐스팅하며 재생하면 13.4ms, v2 만 10만 개 재생은 3.4ms 였다. 업캐스팅은 객체를 새로 만들므로 체인이 길고 이벤트가 많으면 재생 시간에 눈에 띄게 더해진다.

## 약한 스키마 vs 강한 스키마

| 방식 | 장점 | 단점 |
|---|---|---|
| 약한 스키마 (JSON, 관대한 읽기) | 필드 추가가 자유롭다 | 의미 오류가 조용히 지나간다 |
| 강한 스키마 (Avro/Protobuf + 레지스트리) | 호환성을 도구가 검사 | 진화 규칙을 지켜야 한다 |
| 혼합 | 내부 이벤트는 JSON + 업캐스터, 외부 발행 이벤트는 스키마 레지스트리 | 두 체계 |

외부로 발행하는 이벤트는 **계약**이다. 내부 이벤트를 그대로 내보내면 내부 리팩터링이 소비자를 깨뜨린다. 그래서 내부 도메인 이벤트와 외부 **통합 이벤트**를 나누고, 통합 이벤트는 [데이터 계약](/data-engineering/notes/06-data-quality-lineage-contracts)과 호환성 검사(Schema Registry, `buf breaking` — [API 설계 노트 07](/api-design/notes/07-versioning-evolution-governance))로 관리한다. Kafka 의 Schema Registry 호환성 모드는 [Kafka 노트 06](/kafka/notes/06-streams-connect-schema).

## 복사·변환 (copy-and-transform)

업캐스터 체인이 너무 길어지거나 이벤트 구조를 크게 바꿔야 할 때:

```
1. 새 스토어(또는 새 스트림 접두어)를 만든다
2. 옛 이벤트를 순서대로 읽어 변환해 새 스토어에 쓴다 (분할·병합·정리 가능)
3. 그동안 들어오는 새 이벤트도 변환해 따라잡는다
4. 쓰기를 잠깐 멈추고 마지막 꼬리를 옮긴 뒤 새 스토어로 전환
5. 옛 스토어는 읽기 전용으로 보관 (감사 증거)
```

"이벤트는 고치지 않는다" 는 원칙을 깨지 않는다 — 옛 이벤트는 그대로 남고, **새 로그**를 만든 것이다. 대가는 운영 작업과 전환 시점의 위험이다. DB 의 온라인 마이그레이션(확장-축소)과 같은 모양이다 — [SRE 노트 06](/sre/notes/06-capacity-release-change).

## 스냅샷과 프로젝션은 어떻게?

- **스냅샷**: 집합 코드나 상태 모양이 바뀌면 스냅샷 `schema` 를 올리고 옛 스냅샷은 버린다([노트 05](/event-sourcing/notes/05-snapshots-performance)). 다시 만드는 비용만 든다.
- **프로젝션**: 읽기 모델 형식이 바뀌면 재구축한다([노트 04](/event-sourcing/notes/04-projections-replay)). 업캐스터 덕에 프로젝터는 최신 스키마만 처리하면 된다.

## 테스트

진화 규칙은 테스트로 지킨다.

```ts
// 옛 이벤트 픽스처는 지우지 않는다 — 실제 저장된 모양 그대로 보관
import v1 from "./fixtures/MoneyDeposited.v1.json";
test("v1 MoneyDeposited 는 KRW 로 업캐스팅된다", () => {
  expect(upcast(v1).data).toEqual({ amount: 5000, currency: "KRW" });
});
test("모든 이벤트 타입의 모든 옛 스키마가 최신으로 올라간다", () => {
  for (const f of allFixtures()) expect(upcast(f).schema).toBe(LATEST[f.type]);
});
```

옛 이벤트 샘플을 **실제 운영 데이터에서 뽑아** 픽스처로 저장해 두면, 문서에 없던 옛 형식(필드가 문자열이던 시절 등)이 테스트에서 드러난다. 속성 기반으로 "임의의 v1 이벤트를 업캐스팅하면 항상 유효한 v2" 를 검사하는 것도 좋다 — [테스트 전략 노트 05](/testing/notes/05-property-based-testing).

## 심화 — 진화를 배포 절차로 만들기

### 배포 순서: 읽는 쪽 먼저, 쓰는 쪽 나중

새 스키마 이벤트를 **쓰는** 코드와 **읽는** 코드를 한 번에 배포하면, 롤백이 막힌다. 새 코드가 v2 이벤트를 몇 개라도 저장한 뒤 옛 코드로 되돌리면 옛 코드는 v2 를 읽지 못한다(이벤트는 지울 수 없다).

```
배포 1  읽기 지원: 업캐스터·리듀서·프로젝터·다른 서비스 소비자가 v2 를 읽을 수 있음 (쓰기는 여전히 v1)
        ── 모든 인스턴스·소비자에 배포 완료 확인 ──
배포 2  쓰기 전환: 기능 플래그로 v2 쓰기 켜기 (문제 시 플래그만 끄면 v1 쓰기로 복귀)
배포 3  (몇 주 후) v1 쓰기 코드 삭제. v1 업캐스터는 **지우지 않는다** — 옛 이벤트는 영원히 남는다
```

DB 의 확장-축소 마이그레이션과 같은 원리다. 이벤트 소싱에서 다른 점은 "축소" 단계가 없다는 것 — 옛 스키마 읽기 지원은 영구 부채다. 그래서 체인이 길어지면 복사·변환으로 부채를 갚는다.

### 타입 이름은 코드 이름과 분리한다

```ts
// ✗ 클래스 이름을 그대로 저장: 리팩터링으로 이름을 바꾸면 옛 이벤트를 못 읽는다
store.append(stream, [{ type: event.constructor.name, ... }]);

// ✓ 저장용 이름을 명시하고, 바뀐 이름은 별칭 테이블로
const TYPE_ALIASES: Record<string, string> = {
  AmountDeposited: "MoneyDeposited",          // 2025-03 이름 변경
  "billing.PaymentDone": "PaymentAuthorized", // 패키지 이동 전 이름
};
const canonical = (t: string) => TYPE_ALIASES[t] ?? t;
```

번들러의 이름 압축(minify)도 `constructor.name` 을 바꿀 수 있다. 저장 형식에 언어·프레임워크 내부 이름이 새어 나가면 안 된다.

### 1 → N 업캐스터

이벤트 분할은 업캐스터가 배열을 돌려주게 하면 된다.

```ts
type Up = (e: Stored) => Stored[];
const splitAddress: Up = (e) => [
  { ...e, type: "StreetChanged", schema: 1, data: { street: e.data.address.street } },
  { ...e, type: "CityChanged",   schema: 1, data: { city: e.data.address.city } },
];
```

주의: 분할된 이벤트들은 원본과 **같은 version·global_position** 을 공유한다. 프로젝션의 멱등 키를 이벤트 ID 하나로 잡았다면 `id#0`, `id#1` 처럼 하위 번호를 붙여야 둘째가 "이미 처리됨" 으로 버려지지 않는다.

## 모니터링 — 옛 스키마가 얼마나 남았나

```sql
-- 타입·스키마 분포와 마지막 기록 시각: v1 쓰기가 정말 멈췄는지 확인
select type, schema, count(*) as n, max(created_at) as last_written
from events group by type, schema order by type, schema;
```

| 신호 | 의미 |
|---|---|
| `es_upcast_total{type, from_schema}` 카운터 | 재생·로딩에서 옛 스키마를 얼마나 변환하나. 업캐스팅 비용의 근거 |
| v1 의 `last_written` 이 쓰기 전환 이후에도 갱신 | 아직 옛 코드가 도는 인스턴스(혹은 다른 서비스)가 있다 |
| `es_unknown_event_type_total` | 리듀서가 모르는 타입을 만났다 → 롤백된 옛 코드가 새 이벤트를 읽는 중일 가능성 |
| 재생 후 불변식 위반 수 | 조용한 오염(실험의 `undefined` 통화 같은 것)을 잡는 마지막 그물 |

모르는 타입을 만났을 때의 정책도 정해 둔다. 집합 로딩(쓰기 모델)에서는 **예외**가 맞다 — 모르는 사실을 무시하고 결정하면 불변식이 깨진다. 외부 소비자의 프로젝션에서는 **로그 + 메트릭 후 건너뛰기**가 흔하다(관대한 읽기). 같은 시스템 안에서도 위치에 따라 정책이 다르다는 점이 핵심이다. 계약 테스트로 소비자 쪽 깨짐을 미리 잡는 방법은 [테스트 노트 04](/testing/notes/04-contract-testing).

## 흔한 실수와 오해

- **업캐스터에서 DB 를 조회해 값을 채운다**: "당시 사용자 통화" 를 지금 사용자 테이블에서 읽으면, 재생할 때마다 결과가 바뀐다. 업캐스터는 순수 함수 — 모르는 값은 상수 기본값이나 "unknown" 으로.
- **옛 이벤트를 UPDATE 로 고친다**: 감사 증거가 사라지고, 이미 그 이벤트를 받은 외부 소비자와 내 스토어가 서로 다른 과거를 갖게 된다.
- **선택 필드 추가는 항상 안전하다**: 쓰는 쪽에선 그렇지만, 그 필드의 "없음" 을 소비자가 어떻게 해석하는지는 별개다(`discount` 없음 = 0 인가, 모름인가).
- **스키마 레지스트리가 의미 변경도 막아 준다**: 레지스트리는 **형**만 본다. 원 → 센트처럼 같은 int 의 의미 변경은 통과한다.

## 스스로 점검

1. 새 이벤트 스키마를 쓰는 코드를 배포했다가 롤백해야 한다. 왜 위험하고, 어떻게 미리 막나? — 이미 저장된 v2 를 옛 코드가 못 읽는다. 읽기 지원 먼저 배포 → 플래그로 쓰기 전환.
2. 이벤트 타입 이름으로 클래스 이름을 쓰면 안 되는 이유는? — 리팩터링·minify 로 이름이 바뀌면 저장된 이벤트를 못 읽는다. 저장용 이름 + 별칭 테이블.
3. 업캐스터가 순수 함수여야 하는 이유는? — 재생 결과가 언제나 같아야 재구축·감사가 의미 있다.
4. v1 업캐스터를 언제 지울 수 있나? — 저장소에 v1 이벤트가 하나도 없을 때뿐(복사·변환 후). 쓰기를 멈춘 것만으로는 안 된다.

## 실전에서는 어디에 쓰이나

> 이벤트 소싱 시스템을 몇 달 이상 운영하면 반드시 오는 "이벤트 형식을 바꿔야 한다" 는 순간에 등장한다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 해외 결제를 붙이는 커머스 | 통화 필드가 없던 옛 입금 이벤트 | v1 → v2 업캐스터로 currency 기본값 | 옛 이벤트 UPDATE — 감사 증거 훼손 |
| 핀테크 금액 단위 변경 | 원 → 최소 단위 정수 같은 의미 변경 | 새 필드나 새 이벤트 타입 | 같은 필드 의미 변경 — 조용한 100배 오류 |
| 이벤트를 외부에 발행하는 SaaS | 내부 리팩터링이 소비자를 깨지 않게 | 내부 이벤트와 통합 이벤트 분리, 스키마 레지스트리 | 내부 이벤트 그대로 발행 |
| 무중단 배포 조직 | 새 스키마 쓰기 배포를 롤백 가능하게 | 읽기 지원 먼저 배포, 쓰기는 기능 플래그로 전환 | 읽기·쓰기 동시 배포 — 롤백 불가 |
| 오래된 시스템 정리 | 길어진 업캐스터 체인 | 복사·변환으로 새 로그 생성, 옛 로그는 읽기 전용 보관 | 체인을 영원히 유지 |

**이럴 땐 안 맞는다**
- 쓰기 모델의 집합 로딩에서 관대하게 읽는 것 — 모르는 사실을 무시하고 결정하면 불변식이 깨진다. 여기서는 예외가 맞다.
- 스키마 레지스트리가 의미 변경까지 막아 준다고 믿는 것 — 형만 본다. 단위 변경은 그대로 통과한다.

**누가 매일 만나나** — 백엔드가 이벤트에 필드를 추가하는 PR 을 낼 때, 플랫폼·데이터 엔지니어가 통합 이벤트 계약과 호환성 검사를 운영할 때.

**면접·실무 단골 질문**
- Q. 업캐스터가 순수 함수여야 하는 이유는? → 재생 결과가 언제나 같아야 재구축과 감사가 의미 있다.
- Q. 이벤트 타입 이름에 클래스 이름을 쓰면 안 되는 이유는? → 리팩터링·minify 로 이름이 바뀌면 저장된 이벤트를 못 읽는다. 저장용 이름과 별칭 테이블을 둔다.
