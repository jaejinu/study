## nori 는 어떻게 자르는가

한국어 형태소 분석은 "가능한 모든 분할 중 가장 그럴듯한 것" 을 고르는 문제다. nori(Lucene 의 KoreanTokenizer)는 일본어 kuromoji 와 같은 구조다.

1. **사전**: mecab-ko-dic(약 80만 항목). 각 항목은 표면형, 품사, 좌·우 문맥 ID, **단어 비용**.
2. **격자(lattice)**: 입력 문자열의 모든 위치에서 사전에 있는 모든 단어를 노드로 깐다. "복제본의" → `복`, `복제`, `복제본`?, `제본`, `본`, `의` …
3. **연접 비용**: 앞 단어의 우문맥 ID 와 뒤 단어의 좌문맥 ID 사이 비용 행렬(명사 뒤 조사는 싸고, 조사 뒤 조사는 비쌈).
4. **최단 경로**(비터비): 단어 비용 + 연접 비용의 합이 최소인 경로가 분석 결과.

그래서 사전에 `복제본` 이 없으면 `복(명사)+제본(명사)` 가 `복제(명사)+본(명사)` 보다 싸게 나올 수 있다 — 실험 `search-index-notes` 에서 실제로 그렇게 잘렸다. 문맥을 이해하는 것이 아니라 **통계적 비용**으로 고르는 것이다.

```bash
curl -s -X POST localhost:19200/lab-notes/_analyze -H 'Content-Type: application/json' -d '{
  "tokenizer": { "type": "nori_tokenizer", "decompound_mode": "mixed" },
  "text": "복제본의", "explain": true }' | jq '.detail.tokenizer.tokens[] | {token, leftPOS, rightPOS, posType}'
```

### decompound_mode

| 값 | "파이프라인" 결과 | 장단점 |
|---|---|---|
| `none` | 파이프라인 | 정밀, 부분어 검색 불가("파이프" 로 못 찾음) |
| `discard` | 파이프, 라인 | 재현율 ↑, 원형 검색 시 구문 위치가 어긋날 수 있음 |
| `mixed` | 파이프라인, 파이프, 라인 | 둘 다, 색인 크기 ↑ — **대부분의 기본값** |

### 품사 필터 — 무엇을 버릴 것인가

`nori_part_of_speech` 의 `stoptags` 기본값은 조사(J), 어미(E), 기호(S*), 접미사(XS*), 관형사(MM), 부사(MAG) 등을 버린다. 도메인에 따라 조정한다:

- **부사(MAG)**: "빨리 배송" 에서 "빨리" 를 버리면 안 되는 쇼핑 검색 → stoptags 에서 제외.
- **숫자(SN)**: "Redis 7" 의 7, 버전 검색이 중요하면 남긴다(기본은 남김).
- **외국어(SL)**: 영어 토큰은 SL 로 남는다. 영어 어간 처리가 필요하면 `lowercase` 뒤에 `porter_stem` 을 추가하되 한국어 토큰엔 영향 없다.

## 사용자 사전 — 도메인 용어를 가르치기

```json
"tokenizer": {
  "nori_dict": {
    "type": "nori_tokenizer",
    "decompound_mode": "mixed",
    "user_dictionary_rules": [
      "복제본 복제 본",
      "레이트리밋 레이트 리밋",
      "핫키 핫 키",
      "쿠버네티스",
      "카프카"
    ]
  }
}
```

형식: `표면형 [분해1 분해2 ...]`. 분해를 적으면 `mixed` 모드에서 원형과 분해가 함께 나온다. 규칙이 많으면 파일(`user_dictionary: analysis/userdict_ko.txt`)로 두고 모든 노드에 배포한다.

**사전 변경은 리인덱스를 부른다.** 이미 색인된 토큰은 그대로이고 검색 쪽만 새 사전으로 자르면 불일치가 난다. 운영 절차: 사전 변경 → 새 인덱스 → `_reindex` → 별칭 교체([운영 노트](/opensearch/notes/06-operations)). 사전은 코드처럼 버전 관리하고 **검색 로그의 0건 질의**로 후보를 찾는다.

## 동의어

"k8s ↔ 쿠버네티스", "레플리카 ↔ 복제본", "DB ↔ 데이터베이스".

```json
"filter": {
  "my_syn": {
    "type": "synonym_graph",
    "synonyms": [
      "k8s, 쿠버네티스, kubernetes",
      "레플리카, 복제본",
      "pg => postgres, postgresql"
    ]
  }
},
"analyzer": {
  "korean_search": { "tokenizer": "nori_dict", "filter": ["lowercase", "nori_pos", "my_syn"] }
}
```

| 방식 | 장점 | 단점 |
|---|---|---|
| **색인 시** 확장 | 검색이 빠름 | 동의어를 바꾸면 리인덱스, 색인 크기 ↑, 다중 단어 동의어의 위치가 꼬임 |
| **검색 시** 확장 (`search_analyzer` 에만) | 동의어를 언제든 갱신(`_reload_search_analyzers`), 색인 깨끗 | 질의가 약간 무거워짐 — **권장** |

`synonym_graph` 는 "k8s ↔ 쿠버네티스 클러스터" 처럼 단어 수가 다른 동의어의 위치 그래프를 올바르게 만든다(`synonym` 은 구문 질의에서 틀린다). 그래서 검색 시 분석기에만 쓴다.

`,` 는 양방향(모두 같은 그룹), `=>` 는 단방향(왼쪽을 오른쪽으로 치환). "pg 로 검색하면 postgres 문서도" 지만 "postgres 로 검색할 때 pg 를 찾을 필요는 없다" 는 단방향.

## 오타와 자동완성

### fuzzy

```json
{ "match": { "title": { "query": "레디스 복재", "fuzziness": "AUTO", "prefix_length": 1 } } }
```

편집 거리(레벤슈타인) 1~2 이내의 텀을 텀 사전(FST)에서 찾는다. 한국어는 **음절 단위 편집 거리**라 "복재 → 복제" 는 거리 1(재→제)로 잘 잡히지만, 자모 단위 오타("볻제")는 음절 하나가 통째로 달라 거리 1 이어도 의도와 다른 단어가 걸리기 쉽다. `prefix_length: 1` 로 첫 글자는 고정해 폭발을 막는다.

### 자모 분해로 오타·초성 검색

한국어 검색 서비스들이 쓰는 기법: 음절을 **자모로 분해**한 필드를 하나 더 두고 그 필드에서 ngram/fuzzy 를 건다.

```
"복제"  → ㅂㅗㄱㅈㅔ        (자모 필드: 오타 "볻제" = ㅂㅗㄷㅈㅔ 와 편집 거리 1)
"복제"  → ㅂㅈ              (초성 필드: "ㅂㅈ" 입력으로 검색)
```

OpenSearch 에는 내장 자모 필터가 없어 **색인 파이프라인**(ingest pipeline 의 script processor)이나 애플리케이션에서 분해 필드를 만들어 넣는다. 한글 유니코드는 `(코드 − 0xAC00)` 을 `21 × 28` 로 나눠 초성·중성·종성을 계산할 수 있다.

### 자동완성

| 방법 | 원리 | 언제 |
|---|---|---|
| `edge_ngram` 색인 + 일반 검색 | "복제본" → 복, 복제, 복제본 을 색인 | 가장 흔함, 중간 단어도 매치 가능 |
| `search_as_you_type` 타입 | 2·3-gram 서브필드 자동 생성 | 간편 |
| `completion` 제안기 | FST 를 메모리에, 접두사 전용, 매우 빠름 | 검색어 추천(가중치 포함), 정확 접두사만 |

자동완성의 데이터는 **문서 제목이 아니라 과거 검색어**인 경우가 많다(인기 검색어 + 클릭률 가중치).

## 랭킹 학습 (LTR)

BM25 + 부스트 + 감쇠를 손으로 조합하는 데는 한계가 있다. 수십 개의 신호를 **모델이 결합**하게 하는 것이 LTR(Learning to Rank)이다.

```
특징(feature) 예:
  f1 = BM25(title)        f2 = BM25(body)          f3 = kNN 유사도
  f4 = 문서 나이(일)       f5 = 조회수 log           f6 = 질의-제목 정확 일치 여부
  f7 = 클릭률(질의, 문서)  f8 = 레벨(기초/심화)      f9 = 문서 길이

모델: LambdaMART(그래디언트 부스팅 트리) — 순위 지표(nDCG)를 직접 최적화
학습 데이터: (질의, 문서, 관련도 등급) 수천~수만 쌍
```

OpenSearch 에는 **LTR 플러그인**(`opensearch-ltr`, 이 컨테이너에도 설치돼 있다)이 있다: 특징을 질의 템플릿으로 정의 → 특징 값 로깅 → 외부에서 XGBoost/RankLib 로 학습 → 모델을 업로드 → `rescore` 단계에서 상위 N 개를 모델로 재정렬.

```json
POST /lab-notes/_search
{
  "query": { "match": { "body": "복제 지연" } },
  "rescore": { "window_size": 100,
    "query": { "rescore_query": { "sltr": { "params": { "keywords": "복제 지연" }, "model": "notes_lambdamart" } } } }
}
```

### 학습 데이터의 함정 — 클릭은 진실이 아니다

등급을 사람이 다는 것은 비싸서 **클릭 로그**를 쓰고 싶어진다. 그런데:

- **위치 편향**: 1위는 관련 없어도 클릭된다. 3위의 클릭이 1위의 클릭보다 강한 신호다.
- **표시 편향**: 보여 주지 않은 문서는 클릭될 수 없다 → 모델이 현 순위를 강화하는 되먹임.
- **스니펫 편향**: 제목·요약이 좋은 문서가 클릭된다(내용과 별개).

대처: 클릭 모델(위치 보정), 무작위 교란(상위 몇 개를 가끔 섞어 탐색), 클릭 후 체류 시간·재검색 여부를 함께 쓰기. 이것은 [LLM 평가의 편향](/ai-systems/notes/06-evaluation-guardrails-safety) 문제와 같은 구조다.

## 품질을 숫자로 — 오프라인 지표

| 지표 | 정의 | 무엇을 본다 |
|---|---|---|
| **Precision@k** | 상위 k 중 관련 문서 비율 | 첫 화면의 깨끗함 |
| **Recall@k** | 전체 관련 문서 중 상위 k 에 들어온 비율 | RAG 검색기에서 가장 중요(놓치면 LLM 이 모른다) |
| **MRR** | 첫 관련 문서 순위의 역수 평균 | "정답 하나" 형 질의(네비게이션) |
| **nDCG@k** | 등급(0~3)과 순위 할인을 반영, 이상적 순위 대비 비율 | 일반 검색 품질의 표준 |

```
DCG@k  = Σ_{i=1..k} (2^rel_i − 1) / log2(i + 1)
nDCG@k = DCG@k / IDCG@k        (IDCG = 관련도 내림차순으로 놓았을 때의 DCG)

예: 등급 [3, 0, 2] → DCG = 7/1 + 0/1.585 + 3/2 = 8.5
    이상 [3, 2, 0] → IDCG = 7/1 + 3/1.585 + 0 = 8.89    → nDCG@3 = 0.956
```

OpenSearch 는 `_rank_eval` API 로 질의 세트와 등급을 주면 nDCG·MRR·precision 을 계산해 준다 — 분석기·동의어·부스트를 바꿀 때마다 회귀 테스트로 돌린다.

```json
GET /lab-notes/_rank_eval
{
  "requests": [
    { "id": "q1", "request": { "query": { "match": { "body": "복제 지연" } } },
      "ratings": [ { "_index": "lab-notes", "_id": "distributed-systems/04-replication", "rating": 3 },
                   { "_index": "lab-notes", "_id": "redis/11-replication-sentinel-cluster", "rating": 3 },
                   { "_index": "lab-notes", "_id": "postgres/05-operations", "rating": 2 } ] }
  ],
  "metric": { "dcg": { "k": 5, "normalize": true } }
}
```

### 온라인 — A/B 와 인터리빙

오프라인 지표가 오른 변경도 실제 사용자에게는 나쁠 수 있다. 온라인 지표: 클릭률, 0건 비율, 재검색률(첫 결과가 별로였다), 검색 후 전환·체류. **인터리빙**(두 랭커의 결과를 섞어 한 화면에 보여 주고 어느 쪽 문서가 클릭되는지)은 A/B 보다 훨씬 적은 트래픽으로 차이를 검출한다.

## 예시로 보기 — 이 프로젝트에서

실험 `search-index-notes` 가 이 노트의 첫 절을 실증한다:

| 분석기 | "복제본의 지연을 모니터링한다. 파이프라인으로 왕복 시간을 줄였다" |
|---|---|
| standard | 복제본의, 지연을, 모니터링한다, 파이프라인으로, 왕복, 시간을, 줄였다 |
| nori (기본 사전) | **복, 제본**, 지연, 모니터링, 파이프라인, 왕복, 시간, 줄였, 줄이 |
| nori + 사용자 사전 | 복제본의, **복제, 본**, 의, 지연, 모니터링, 파이프라인, 왕복, 시간, 줄였, 줄이 |

사용자 사전 한 줄이 "복제" 를 살렸다. 같은 질의 "복제 지연" 의 결과가 standard 65건 → nori 88건.

이 사이트의 검색 품질 평가 세트를 만든다면: AI 도우미 대화와 `/search` 페이지 질의 로그에서 50개를 뽑아, 질의마다 정답 노트 1~3개를 등급 3/2 로 단 뒤 `_rank_eval` 로 nDCG@5 를 기록한다. 그 다음부터 분석기·동의어·부스트 변경은 그 숫자가 오를 때만 반영한다.

## 실전에서는 어디에 쓰이나

> 한국어 서비스의 검색 품질 문제 — 도메인 용어가 엉뚱하게 잘림, "k8s" 로 "쿠버네티스" 를 못 찾음, 오타·초성 입력, 클릭이 몰리는 순위 — 를 풀 때 등장한다. 기능보다 사전·평가 세트·실험 절차가 핵심이다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 커머스·배달 앱 검색창 | 신조어·브랜드명이 형태소로 잘못 쪼개짐 | 사용자 사전 + 0건 질의 로그로 후보 발굴, 사전 변경 시 리인덱스 | `decompound_mode: none` 으로 쪼개기 끄기 |
| 모바일 앱의 주소록·상품 검색 | 초성("ㄱㅂ")·자모 단위 오타 | 자모 분해 필드(ingest 파이프라인) + ngram·fuzzy | 앱 측 로컬 필터 |
| 기술 문서·개발자 포털 | 약어와 정식 명칭 혼용 | 검색 시 `synonym_graph`, `_reload_search_analyzers` 로 갱신 | 색인 시 동의어(바꾸면 리인덱스) |
| 검색어 추천·자동완성 | 타이핑마다 빠른 접두사 제안 | 과거 검색어 + 인기도 가중치로 `completion` 제안기 | 문서 제목 `edge_ngram` |
| 랭킹 개선을 하는 대형 서비스 | 수십 개 신호 결합과 회귀 방지 | LTR 플러그인 rescore, `_rank_eval` nDCG 회귀 테스트, 인터리빙 | 손으로 부스트 조합 |

**이럴 땐 안 맞는다**
- 클릭 로그를 그대로 정답 라벨로 쓰기 — 위치·표시·스니펫 편향이 현 순위를 강화한다. 위치 보정과 탐색용 교란을 함께 쓴다.
- 평가 세트 없이 LTR 부터 도입 — 개선 여부를 판단할 수 없다. 질의 50~200개 등급 세트와 nDCG 기준선이 먼저다.

**누가 매일 만나나** — 검색 엔지니어는 사전·동의어 PR 과 nDCG 리포트로, 데이터 사이언티스트는 LTR 특징·모델과 A/B 결과로, 프로덕트 매니저는 0건 비율·재검색률 같은 온라인 지표로 만난다.

**면접·실무 단골 질문**
- Q. 동의어는 색인 시와 검색 시 중 어디에 거나? → 대개 검색 시. 사전을 리인덱스 없이 갱신할 수 있고, 다중 단어 동의어는 `synonym_graph` 로 위치 그래프를 올바르게 만든다.
- Q. 오프라인 지표가 올랐는데 배포해도 되나? → 온라인(A/B·인터리빙)으로 클릭률·재검색률을 확인한다. 오프라인 개선이 실제 사용자에게 나쁠 수 있다.
