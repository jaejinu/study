## 두 검색기는 서로 다른 질의에서 실패한다

| 질의 | BM25 | 벡터(임베딩) |
|---|---|---|
| `ERR_CONNECTION_RESET`, `XREADGROUP`, `CVE-2024-3094` | ✓ 정확한 토큰 일치 | ✗ 희귀 토큰은 임베딩 공간에서 뭉개진다 |
| "장애 났을 때 자동으로 되돌리기" (문서엔 "롤백", "selfHeal") | ✗ 같은 단어가 없다 | ✓ 의미가 가깝다 |
| "Redis 복제 지연" | ✓ | ✓ |
| 오타 "레디스 복재" | △ fuzzy 로 일부 | ✓ 어느 정도 |
| 부정 "Kafka 가 **아닌** 메시징" | ✗ | ✗ (둘 다 못한다 — 필터로) |

실무 결론: **둘 다 돌리고 합친다.** 그것이 하이브리드 검색이고, 2024년 이후 RAG 검색기의 기본값이다. [AI 시스템의 RAG 설계](/ai-systems/notes/03-rag-design)와 [임베딩·벡터 검색](/ai-systems/notes/02-embeddings-vector-search)이 벡터 쪽을, 이 노트는 합치는 쪽을 다룬다.

## OpenSearch 의 벡터 검색

```json
PUT /lab-hybrid
{
  "settings": { "index.knn": true },
  "mappings": {
    "properties": {
      "text": { "type": "text", "analyzer": "korean" },
      "subject": { "type": "keyword" },
      "vec": {
        "type": "knn_vector",
        "dimension": 1024,
        "method": {
          "name": "hnsw",
          "space_type": "cosinesimil",
          "engine": "lucene",
          "parameters": { "m": 16, "ef_construction": 128 }
        }
      }
    }
  }
}
```

| 설정 | 의미 | 트레이드오프 |
|---|---|---|
| `engine` | `lucene`(내장, 필터 효율적) / `faiss`(대용량, 양자화) / `nmslib`(구식) | 대부분 lucene 으로 시작, 수억 벡터면 faiss + PQ |
| `space_type` | `cosinesimil`, `l2`, `innerproduct` | 임베딩 모델이 정규화돼 있으면 내적 = 코사인 |
| `m` | HNSW 노드당 이웃 수 | 크면 재현율 ↑, 메모리 ↑ (벡터당 약 `m × 2 × 4B` 그래프) |
| `ef_construction` | 그래프 만들 때 후보 수 | 크면 그래프 품질 ↑, 색인 느림 |
| `ef_search`(질의 시) | 검색할 때 후보 수 | 크면 재현율 ↑, 지연 ↑ |

메모리 계산: 1,000만 × 1024차원 × 4바이트 = **40GB** + 그래프. 벡터 검색은 **메모리 상주**가 전제다(HNSW 는 임의 접근이라 디스크에선 느림). 그래서 양자화(int8, 이진, PQ)와 차원 축소(Matryoshka 임베딩)가 실전의 핵심 손잡이다. 구조 자체는 [HNSW 인덱스](/db-internals/notes/05-index-structures)를 참고.

### 필터와 kNN

"kafka 노트 중에서 의미가 가까운 것" 은 쉬워 보이지만 함정이 있다.

- **사후 필터**: kNN 으로 상위 10 을 뽑고 필터 → kafka 가 0개일 수 있다.
- **사전 필터**: 필터에 맞는 문서만 대상으로 kNN. lucene 엔진은 `knn` 질의 안의 `filter` 를 HNSW 탐색 중에 적용한다(필터가 아주 좁으면 정확 탐색으로 전환).

```json
{ "query": { "knn": { "vec": { "vector": [...], "k": 10, "filter": { "term": { "subject": "kafka" } } } } } }
```

멀티테넌트 RAG(고객별 문서)에서 테넌트 필터는 **반드시 사전 필터**여야 한다. 사후 필터는 결과가 비거나, 더 나쁘게는 구현 실수로 다른 테넌트 문서가 섞인다.

## 점수를 합치는 두 방법

BM25 점수는 0~수십, 코사인 유사도는 0~1. **스케일이 다른 두 점수를 그냥 더하면 BM25 가 이긴다.** 두 해법:

### 1. RRF (Reciprocal Rank Fusion)

점수를 버리고 **순위**만 쓴다.

```
RRF(d) = Σ_{검색기 r}  1 / (k + rank_r(d))        k = 60 (관례)

BM25 1위, kNN 3위 → 1/61 + 1/63 = 0.0323
BM25 없음, kNN 1위 → 0     + 1/61 = 0.0164
BM25 2위, kNN 없음 → 1/62        = 0.0161
```

- **양쪽에 다 있는 문서가 이긴다** — 두 검색기가 동의하는 것이 가장 믿을 만하다는 가정.
- 정규화·튜닝이 거의 필요 없다. `k` 는 상위 순위의 영향력을 조절(작을수록 1위가 압도적).
- 약점: 점수 차이를 버린다. BM25 1위가 압도적으로 정확한 일치(에러 코드)여도 kNN 에 없으면 양쪽에 애매하게 걸린 문서에게 밀릴 수 있다.

### 2. 정규화 + 가중합

```
norm(s) = (s − min) / (max − min)                 각 검색기 결과 안에서 min-max
hybrid(d) = w_bm25 · norm_bm25(d) + w_knn · norm_knn(d)
```

OpenSearch 의 `hybrid` 질의 + `normalization-processor` 검색 파이프라인이 이것을 한다.

```json
PUT /_search/pipeline/hybrid
{ "phase_results_processors": [{ "normalization-processor": {
    "normalization": { "technique": "min_max" },
    "combination": { "technique": "arithmetic_mean", "parameters": { "weights": [0.3, 0.7] } } } }] }

POST /lab-hybrid/_search?search_pipeline=hybrid
{ "query": { "hybrid": { "queries": [
    { "multi_match": { "query": "메시지 순서 보장", "fields": ["title^2", "text"] } },
    { "knn": { "vec": { "vector": [...], "k": 20 } } } ] } } }
```

- 가중치로 "이 도메인은 어휘가 중요"(코드·로그 → BM25 ↑) 를 표현할 수 있다.
- 약점: min-max 는 **각 목록의 1위를 무조건 1.0** 으로 만든다. 한쪽 결과가 전부 쓰레기여도 그 1위가 1.0 이다. 가중치는 평가 세트 없이 정하면 감이다.

| | RRF | 정규화 가중합 |
|---|---|---|
| 튜닝 | 거의 없음(k=60) | 가중치·정규화 방식 |
| 점수 정보 | 버림 | 사용 |
| 강건성 | 높음 | 한쪽이 나쁠 때 약함 |
| 언제 | 기본값, 평가 세트 없을 때 | 평가 세트로 가중치를 튜닝할 수 있을 때 |

## 리랭킹 — 마지막 정밀도

하이브리드로 상위 50~100 을 뽑은 뒤 **크로스 인코더**(질의와 문서를 **함께** 넣어 관련도를 직접 출력하는 모델, 예: bge-reranker, Cohere Rerank)로 다시 정렬한다.

```
1단계 (빠르고 넓게):  BM25 + kNN → RRF → 상위 100      (ms 단위)
2단계 (느리고 정확):  크로스 인코더(질의, 문서) × 100 → 상위 5   (수십~수백 ms)
```

임베딩(바이 인코더)은 질의와 문서를 **따로** 벡터로 만들어 내적하므로 미묘한 상호작용을 놓친다. 크로스 인코더는 모든 쌍을 모델에 넣으니 정확하지만 전체 코퍼스에 쓸 수 없다 — 그래서 2단계. LLM 에게 "이 5개 중 관련 있는 것만" 을 묻는 것도 리랭킹의 한 형태다(비싸다).

## RAG 검색기로 쓸 때의 설계

| 결정 | 지침 |
|---|---|
| **청킹** | 문서 통째가 아니라 의미 단위(이 사이트라면 `##` 섹션). 200~800 토큰, 10~20% 겹침. 청크에 부모 문서 제목·섹션 경로를 붙여 색인(맥락 보존) |
| **필드** | `text`(BM25), `vec`(kNN), `doc_id`·`subject`·`level`·`updated`(keyword/date 필터), `heading_path` |
| **메타데이터 필터** | 권한·테넌트·언어·버전은 사전 필터. 날짜 감쇠로 최신 우대 |
| **k** | 검색 20~50 → 리랭킹 → LLM 에 3~8 청크. 많이 넣는다고 좋지 않다(lost in the middle) |
| **중복 제거** | 같은 문서의 인접 청크가 상위를 독점 → 문서당 최대 2청크 |
| **질의 변환** | 대화 맥락을 반영한 질의 재작성, HyDE(가상 답변으로 검색), 다중 질의 |
| **인용** | 청크 id·문서 링크를 LLM 출력에 강제 → 검증 가능 |

이 사이트의 AI 도우미 `search_notes` 툴을 이 구조로 바꾸면: 섹션 단위 청크 색인 → 하이브리드 + RRF → 상위 6 청크를 근거로 답변 + 노트 링크 인용.

## 평가 없이는 아무것도 바꾸지 마라

검색 개선은 **평가 세트**가 있어야 판단할 수 있다.

1. 실제 질의 50~200개를 모은다(로그, 도우미 대화).
2. 질의마다 정답 문서(또는 등급 0~3)를 단다.
3. 지표: **Recall@k**(정답이 상위 k 안에 있나 — RAG 에 가장 중요), **MRR**(첫 정답의 순위 역수 평균), **nDCG@k**(등급·순위 가중, [노트 07](/opensearch/notes/07-korean-and-ranking)).
4. BM25 / kNN / RRF / 가중합(여러 가중치) / +리랭킹 을 같은 세트로 비교.

전형적 결과: BM25 단독 < kNN 단독 ≈ (도메인에 따라 역전) < 하이브리드 < 하이브리드 + 리랭킹. 차이가 몇 %p 라도 RAG 답변 품질에는 크게 나타난다.

## 예시로 보기 — 이 프로젝트에서

실험 `search-hybrid-rrf` 는 노트 129편을 `text`(제목+요약+태그) + `vec`(1024차원 결정적 해싱 임베딩, [AI 실험](/ai-systems/lab)과 같은 것)로 색인하고 세 질의를 돌린다. 실측 예(질의 "메시지 순서 보장 키"):

| 순위 | BM25 | kNN | RRF |
|---|---|---|---|
| 1 | redis/키 만료와 메모리 축출 | architecture/비동기·메시징과 데이터 일관성 | architecture/비동기·메시징 (bm25 #4, knn #1) |
| 2 | kafka/전달 보장과 설계 패턴 | redis/분산 락 | … |
| 4 | architecture/비동기·메시징 | … | |

- BM25 1위는 "키" 라는 단어 때문에 Redis 키 만료 노트 — **어휘 일치의 함정**.
- kNN 1위는 메시징 노트. 해싱 임베딩은 의미를 모르지만 단어·3-gram 겹침이 많은 쪽을 고른다.
- RRF 1위는 **양쪽 모두에 있는** 메시징 노트 — 두 검색기의 합의가 이긴다.
- 정규화 가중합(OpenSearch `hybrid`)은 min-max 때문에 두 목록의 1위가 같은 0.5 근처로 몰린다.

진짜 임베딩 모델로 바꾸면 kNN 쪽이 "자동으로 되돌리기 → selfHeal/롤백" 같은 의미 일치를 잡기 시작한다. 그때 하이브리드의 이득이 가장 커진다.

## 실전에서는 어디에 쓰이나

> LLM 에 회사 문서를 근거로 답하게 하는 RAG, 그리고 "정확한 키워드" 와 "비슷한 뜻" 을 동시에 잡아야 하는 검색에서 하이브리드가 등장한다. RAG 답변 품질의 상당 부분은 모델이 아니라 검색기에서 정해진다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 사내 문서·위키 AI 도우미 | 에러 코드(정확 일치)와 자연어 질문을 함께 | 섹션 단위 청크에 BM25 + kNN, RRF 융합, 문서 링크 인용 | 벡터 DB 단독(희귀 토큰 약함) |
| B2B SaaS 의 고객별 문서 RAG | 다른 고객 문서가 섞이는 사고 방지 | 테넌트 ID 를 kNN 사전 필터로 | 사후 필터(결과가 비거나 섞임) |
| 고객센터 상담 추천(커머스·통신) | 상위 몇 건의 정밀도 | 하이브리드 상위 50 → 크로스 인코더 리랭킹 → 3~8건 | LLM 에게 전부 넣기(비싸고 lost in the middle) |
| 수억 건 이미지·상품 유사 검색 | 벡터 메모리 비용 | faiss 엔진 + 양자화(PQ·int8), 차원 축소 | lucene 엔진 + 전체 float 벡터 |

**이럴 땐 안 맞는다**
- 평가 세트 없이 가중치 튜닝 — 정규화 가중합의 가중치는 감이 된다. 평가 세트가 없으면 RRF 기본값으로 둔다.
- 부정 조건("Kafka 가 아닌") — BM25·벡터 모두 못 한다. 메타데이터 필터로 표현한다.
- 데이터가 작고 질의가 키워드 위주 — 벡터 색인·임베딩 비용 대비 이득이 작다. BM25 와 동의어 사전으로 시작한다.

**누가 매일 만나나** — ML·AI 엔지니어는 RAG 의 청킹·검색기·리랭커를 고를 때, 백엔드 개발자는 검색 파이프라인과 권한 필터를 연결할 때, 검색 엔지니어는 Recall@k·nDCG 로 변경을 판정할 때 만난다.

**면접·실무 단골 질문**
- Q. RRF 와 정규화 가중합의 차이는? → RRF 는 순위만 써서 튜닝이 거의 없고 강건하다. 가중합은 점수를 쓰지만 min-max 가 각 목록 1위를 무조건 1.0 으로 만든다.
- Q. RAG 검색기에서 가장 중요한 지표는? → Recall@k. 정답 청크가 상위 k 에 없으면 LLM 은 알 수 없다.
