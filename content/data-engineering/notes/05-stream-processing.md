## 끝나지 않는 데이터

[배치](/data-engineering/notes/01-batch-vs-streaming) 는 "어제 데이터" 처럼 **닫힌 구간**을 계산한다. 스트림은 **끝이 없다.** "지금까지의 1분 단위 오류 수" 를 계속 갱신해야 한다. 여기서 질문이 생긴다.

- 1분은 **언제 기준** 의 1분인가? 이벤트가 일어난 시각? 내가 받은 시각?
- 10:00~10:01 구간을 **언제 닫나?** 10:00:59 에 일어난 이벤트가 네트워크 문제로 10:03 에 도착하면?
- 계산 도중 프로세스가 죽으면 **어디서부터** 다시?

## 처리 시간 vs 이벤트 시간

| | 처리 시간 (processing time) | 이벤트 시간 (event time) |
|---|---|---|
| 기준 | 처리기가 이벤트를 받은 시각 | 이벤트에 찍힌 발생 시각 |
| 장점 | 단순, 기다릴 필요 없음 | 결과가 재현 가능, 재처리해도 같음 |
| 단점 | 지연·재처리 시 결과가 달라짐 | 늦은 데이터를 기다려야 함 |

모바일 앱 이벤트는 오프라인이었다가 몇 시간 뒤에 올라오기도 한다. 처리 시간으로 집계하면 "새벽 3시에 사용자 급증" 같은 가짜 신호가 생긴다. **정확한 분석은 이벤트 시간**으로 한다.

## 윈도우

![텀블링 · 슬라이딩 · 세션 윈도우와 워터마크](/diagrams/de-windows-watermark.svg)

| 윈도우 | 모양 | 예 |
|---|---|---|
| **텀블링** | 겹치지 않는 고정 크기 | 1분마다 오류 수 |
| **슬라이딩(호핑)** | 겹치는 고정 크기, 일정 간격 | 최근 5분 평균을 1분마다 |
| **세션** | 활동 사이 간격(gap)으로 끊김 | 사용자 세션(30분 무활동이면 종료) |
| **전역** | 윈도우 없음 | 누적 합계 |

## 워터마크 — "이 시각 이전 이벤트는 다 왔다" 는 추정

이벤트 시간 윈도우를 닫으려면 "10:01 이전 이벤트가 더는 안 온다" 를 알아야 한다. 확실히 알 수는 없으니 **추정**한다.

```
워터마크 = 지금까지 본 최대 이벤트 시각 − 허용 지연(예: 30초)
```

- 워터마크가 10:01:00 을 넘으면 [10:00, 10:01) 윈도우를 닫고 결과를 내보낸다.
- 그 뒤에 10:00:45 이벤트가 오면 **늦은 데이터**다. 선택지: 버린다 / 별도 출력(side output)으로 보낸다 / 이미 낸 결과를 갱신한다(allowed lateness).
- 허용 지연이 길수록 정확하지만 결과가 늦게 나오고 상태를 오래 들고 있다. **지연과 완전성의 교환.**

## 상태 — 스트림 처리의 진짜 어려움

| 연산 | 들고 있어야 하는 상태 |
|---|---|
| 윈도우 집계 | 열린 윈도우마다 부분 합계 |
| 중복 제거 | 최근 본 이벤트 ID 집합 (TTL 필요) |
| 스트림-스트림 조인 | 양쪽의 아직 짝을 못 찾은 이벤트 |
| 스트림-테이블 조인 | 테이블의 현재 상태 |
| 세션 | 사용자별 마지막 활동 |

상태는 메모리나 로컬 디스크(RocksDB, [LSM](/db-internals/notes/03-lsm-tree-compaction))에 두고, 장애 복구를 위해 **체크포인트**로 주기적으로 저장한다.

### 체크포인트와 복구 (Flink 방식)

1. 원천(Kafka)에 **배리어**를 주기적으로 끼워 흘린다
2. 각 연산자는 배리어를 받으면 그 시점의 상태를 스냅샷으로 저장
3. 모든 연산자가 저장하면 체크포인트 완료 — 이때의 Kafka 오프셋도 함께 기록
4. 장애 시: 마지막 체크포인트의 상태를 복원하고, 기록된 오프셋부터 다시 읽는다

상태와 입력 위치가 **함께** 되돌아가므로 엔진 내부적으로는 각 이벤트가 정확히 한 번 반영된다.

## 정확히 한 번의 실체

"정확히 한 번(exactly-once)" 은 마법이 아니다. 두 부분으로 나뉜다.

1. **엔진 내부 상태**: 체크포인트로 입력 위치와 상태를 원자적으로 저장 → 재처리해도 상태는 한 번 반영된 것과 같다
2. **외부 출력(싱크)**: 재처리 구간의 결과가 **다시 나간다.** 다음 중 하나가 필요하다.
   - **멱등 싱크**: 같은 키 upsert (결과 테이블에 `(window_start, service)` 키로 덮어쓰기)
   - **트랜잭션 싱크**: 체크포인트와 함께 커밋되는 2단계 커밋(Kafka 트랜잭션, Flink TwoPhaseCommitSink)

[Kafka 전달 보장](/kafka/notes/04-delivery-guarantees) 과 [분산 트랜잭션](/distributed-systems/notes/06-transactions-coordination) 의 이야기가 여기서 만난다. 실무 결론: **at-least-once + 멱등 싱크**가 가장 단순하고 견고하다.

## 스트림-테이블 이중성

- **스트림 → 테이블**: 변경 이벤트를 키별로 최신만 남기면 테이블이 된다(CDC 의 merge, Kafka 의 compacted topic, KTable).
- **테이블 → 스트림**: 테이블의 변경을 순서대로 내보내면 스트림이 된다(CDC 자체).

실험 [de-cdc-to-lake](/data-engineering/lab/de-cdc-to-lake) 의 "키별 최신 + 삭제 제외" 병합이 정확히 스트림 → 테이블 변환이다.

## 도구의 위치

| 도구 | 성격 | 맞는 곳 |
|---|---|---|
| **Kafka Streams** | 라이브러리(앱 안에 들어감), 상태는 RocksDB + 변경 로그 토픽 | Kafka 안에서 끝나는 변환·집계, JVM 서비스 → [Kafka 노트](/kafka/notes/06-streams-connect-schema) |
| **Apache Flink** | 분산 스트림 엔진, 이벤트 시간·워터마크·체크포인트가 가장 성숙 | 큰 상태, 복잡한 윈도우·조인, SQL |
| **Spark Structured Streaming** | 마이크로배치 기반 | 이미 Spark 를 쓰는 팀, 배치와 코드 공유 |
| **ClickHouse MV** | 적재 시점의 블록 단위 집계 | 단순 집계·롤업. 이벤트 시간 윈도우·늦은 데이터는 질의 시점에 처리 → [MV 노트](/clickhouse/notes/04-materialized-views-aggregation) |
| **RisingWave·Materialize** | 스트리밍 SQL DB | 증분 유지되는 SQL 뷰 |

```sql
-- Flink SQL: 이벤트 시간 1분 텀블링 윈도우, 워터마크 30초
CREATE TABLE logs (
  ts TIMESTAMP(3), service STRING, level STRING,
  WATERMARK FOR ts AS ts - INTERVAL '30' SECOND
) WITH ('connector' = 'kafka', 'topic' = 'app-logs', 'format' = 'json', …);

SELECT window_start, service,
       COUNT(*) AS total, SUM(CASE WHEN level = 'error' THEN 1 ELSE 0 END) AS errors
FROM TABLE(TUMBLE(TABLE logs, DESCRIPTOR(ts), INTERVAL '1' MINUTE))
GROUP BY window_start, window_end, service;
```

## 스트림이 정말 필요한가?

스트림 처리는 운영 비용이 크다(상시 실행, 상태 관리, 재처리 설계). 많은 "실시간" 요구는 다음으로 충분하다.

- 1~5분 마이크로배치
- ClickHouse 에 계속 적재 + 질의 시점 집계(초 단위 응답)
- Prometheus 같은 메트릭 시스템(이미 스트림 집계기다)

## 예시로 보기 — 이 프로젝트에서

"이 사이트의 1분 오류율을 실시간으로, 늦게 온 로그까지 정확히" 를 만든다면:

```
logs/app.jsonl → Alloy → Kafka(app-logs, key=service)
                            └─▶ Flink: 이벤트 시간 1분 텀블링, 워터마크 30초, 허용 지연 5분
                                   └─▶ ClickHouse error_rate_1m (ReplacingMergeTree, 키=(service, window_start))
                                          └─▶ Grafana
```

- 싱크가 `(service, window_start)` 키의 ReplacingMergeTree 라서 재처리·늦은 갱신이 **덮어쓰기**가 된다 → 멱등
- 하지만 지금 이 사이트 규모라면 같은 그래프는 Prometheus 메트릭(`study_action_*`)이나 ClickHouse 질의 시점 집계로 이미 충분하다 — 위 구성은 하루 수억 줄이 될 때의 설계다

## 심화 — 워터마크가 멈추는 이유: 유휴 파티션

워터마크는 연산자마다 **입력 채널들 중 가장 작은 워터마크**를 따른다. 그래야 "모든 입력에서 이 시각 이전은 다 왔다" 가 성립한다. 문제는 한 파티션에 데이터가 안 들어올 때다.

```
Kafka 파티션 0: … 10:05:10, 10:05:40 → 워터마크 10:05:10
Kafka 파티션 1: … 10:05:20          → 워터마크 10:04:50
Kafka 파티션 2: (09:58 이후 이벤트 없음) → 워터마크 09:57:30   ← 이게 전체를 붙잡는다
연산자 워터마크 = min(…) = 09:57:30  → 10:00 윈도우가 영원히 닫히지 않음
```

증상은 "에러는 없는데 결과가 안 나온다" 이고, 상태는 계속 쌓인다. 새벽처럼 트래픽이 적은 시간, 파티션 수를 넉넉히 잡은 토픽에서 흔하다. 해결은 일정 시간 조용한 입력을 워터마크 계산에서 빼는 **유휴(idleness) 설정**이다.

```java
WatermarkStrategy
    .<LogEvent>forBoundedOutOfOrderness(Duration.ofSeconds(30))
    .withTimestampAssigner((e, ts) -> e.tsMillis())
    .withIdleness(Duration.ofMinutes(1));   // 1분간 이벤트 없는 파티션은 무시
```

```sql
-- Flink SQL 에서는 세션 설정으로
SET 'table.exec.source.idle-timeout' = '1 min';
```

## 심화 — 상태 크기를 숫자로 어림하기

스트림 작업의 비용과 장애는 대부분 **상태 크기**에서 온다. 설계 단계에서 어림해 보자(가정치).

| 연산 | 가정 | 상태 크기 어림 |
|---|---|---|
| 중복 제거 (이벤트 ID 보관 10분) | 분당 100만 이벤트, ID+오버헤드 ≈ 60B | 1,000만 × 60B ≈ **600MB** |
| 같은 중복 제거, TTL 없음 | 하루 14.4억 이벤트 | ≈ 86GB 씩 매일 증가 → 결국 장애 |
| 1분 텀블링, 서비스 50개 | 열린 윈도우 = (허용 지연 5분 / 1분 + 1) × 50 | 수백 개 카운터, 무시할 수준 |
| 스트림-스트림 조인 (주문 ↔ 결제, 1시간 창) | 시간당 주문 10만, 행 500B | 양쪽 합쳐 ≈ 100MB |

교훈: **집계는 싸고, 중복 제거·조인은 비싸다.** 그리고 비싼 상태에는 반드시 TTL 을 건다. TTL 이 없는 상태는 "언젠가 터지는 시한폭탄" 이다.

```yaml
# Flink 설정 예 (키 이름은 Flink 버전에 따라 다르니 사용하는 버전 문서로 확인)
execution.checkpointing.interval: 60s
execution.checkpointing.min-pause: 30s       # 체크포인트 사이 최소 휴식 (계속 체크포인트만 하는 것 방지)
execution.checkpointing.timeout: 10min
state.backend.type: rocksdb
execution.checkpointing.incremental: true    # 바뀐 SST 파일만 올림 → 큰 상태에서 필수
table.exec.state.ttl: 1h                     # SQL 작업의 상태 TTL
```

## 심화 — 정확히 한 번의 비용

트랜잭션 싱크는 **체크포인트가 완료될 때 커밋**한다. 그러니 하류가 결과를 보는 시점은 최소 체크포인트 간격만큼 늦어진다.

```
체크포인트 간격 60s  → Kafka 트랜잭션 커밋도 60s 마다
하류 소비자 isolation.level=read_committed → 커밋된 것만 보임 → 결과 지연 0~60s 추가
```

- 하류 소비자가 `read_committed` 가 아니면(기본값 `read_uncommitted`) 중단된 트랜잭션의 결과까지 읽어 정확히 한 번이 깨진다.
- Flink Kafka 싱크의 트랜잭션 타임아웃은 브로커의 `transaction.max.timeout.ms`(기본 15분) 이하여야 한다. 어기면 작업 시작 시 오류가 나고, 맞춰도 체크포인트가 그보다 오래 실패하면 트랜잭션이 중단돼 데이터가 사라질 수 있다.
- Kafka Streams 는 `processing.guarantee=exactly_once_v2` 로 켜고, 이때 `commit.interval.ms` 기본값이 100ms 로 줄어든다(처리량 ↔ 지연).

그래서 다시 실무 결론: 결과 테이블을 키 기반 upsert 로 만들 수 있으면 **at-least-once + 멱등 싱크**가 지연·운영 모두 싸다.

## 모니터링 — 스트림 작업이 아프면 어떻게 보이나

| 증상 | 볼 메트릭 (Flink 이름 예) | 흔한 원인 |
|---|---|---|
| 결과가 안 나옴 | `currentOutputWatermark` 가 멈춤 | 유휴 파티션, 이벤트 시각이 미래로 찍힌 이벤트 |
| 지연이 계속 증가 | Kafka `records-lag-max`, 소비자 그룹 lag | 처리량 부족, 배압 |
| 배압 | `backPressuredTimeMsPerSecond`, `busyTimeMsPerSecond` | 느린 싱크, 핫 키 |
| 체크포인트가 점점 길어짐 | `lastCheckpointDuration`, `lastCheckpointSize` | 상태 증가(TTL 없음), 배압으로 배리어 정렬 지연 |
| 체크포인트 실패 | `numberOfFailedCheckpoints` | 타임아웃, 저장소 장애 → 복구 시 재처리 구간이 길어짐 |
| 늦은 데이터 급증 | `numLateRecordsDropped` | 원천 지연(모바일 오프라인 업로드), 허용 지연이 너무 짧음 |

가장 유용한 단일 지표는 **이벤트 시간 지연 = 현재 시각 − 출력 워터마크**다. "결과가 실제보다 몇 초 늦은가" 를 한 숫자로 보여 주고, 이것을 SLO 로 삼을 수 있다. 핫 키는 서브태스크별 처리량을 나란히 보면 드러난다 — 하나만 100% 바쁘고 나머지는 한가하다면 키 분포 문제다.

## 흔한 실수와 오해

- **처리 시간 윈도우로 만든 뒤 재처리** — 재처리 시각에 모든 이벤트가 몰려 한 윈도우에 들어간다. 재현 가능한 결과가 필요하면 이벤트 시간.
- **이벤트 시각을 그대로 믿음** — 시계가 틀린 기기가 2030년 이벤트를 보내면 워터마크가 미래로 튀어 이후 정상 이벤트가 전부 "늦은 데이터" 가 된다. 수신 시각과의 차이로 상한을 두거나 걸러낸다.
- **"정확히 한 번이면 이메일도 한 번"** — 엔진 밖 부작용(메일·결제 API)은 재처리 때 다시 일어난다. 멱등 키가 필요하다.
- **키 편중 무시** — `key=service` 에서 한 서비스가 트래픽 90% 면 한 서브태스크만 일한다. 키에 접미사를 붙여 나눈 뒤 2단계로 합친다.
- **체크포인트 간격을 너무 짧게** — 큰 상태에서 1초 간격은 체크포인트만 하다 끝난다. 복구 시간 목표(RTO)와 재처리 허용량으로 정한다.

## 스스로 점검

1. 에러는 없는데 새벽에만 윈도우 결과가 안 나온다. 가장 먼저 의심할 것은? — 유휴 파티션 때문에 워터마크가 멈춤. idleness 설정.
2. 중복 제거 상태가 매일 커져 체크포인트가 느려진다. 원인과 해결은? — 상태 TTL 없음. 중복 가능 기간만큼 TTL.
3. Kafka 트랜잭션 싱크를 쓰는데 하류에서 중복이 보인다. 무엇을 확인하나? — 하류 소비자의 `isolation.level=read_committed`.
4. 정확히 한 번 대신 at-least-once + 멱등 싱크를 고르는 이유는? — 체크포인트 간격만큼의 지연과 트랜잭션 운영 부담이 없고, upsert 키만 있으면 결과는 같다.

## 실전에서는 어디에 쓰이나

> "몇 분 늦으면 가치가 없다" 는 요구 — 결제 이상 탐지, 실시간 오류율, 재고 반영 — 에서 이벤트 시간 윈도우와 상태 저장 처리가 등장한다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 핀테크 카드 결제 | 짧은 시간 내 이상 결제 패턴 탐지 | 사용자 키별 슬라이딩 윈도우 집계 + TTL 있는 상태 | 배치 탐지(사후에만 발견) |
| 모바일 게임·앱 이벤트 분석 | 오프라인 후 늦게 올라온 이벤트의 지표 왜곡 | 이벤트 시간 + 워터마크 + 허용 지연, 늦은 데이터는 side output | 처리 시간 집계(가짜 급증) |
| 커머스 주문 ↔ 결제 매칭 | 결제가 안 된 주문 탐지 | 스트림-스트림 조인(1시간 창) | 주기적 배치 조인 |
| 관측 플랫폼 | 서비스별 1분 오류율을 늦은 로그까지 정확히 | Flink 텀블링 윈도우 → `(service, window_start)` 키 upsert 싱크 | Prometheus 메트릭(이미 스트림 집계기) |
| 미디어 스트리밍 서비스 | 시청 세션 단위 지표 | 세션 윈도우(무활동 gap 으로 끊기) | 배치로 사후 세션화 |

**이럴 땐 안 맞는다**
- "실시간" 이라는 말만 있고 실제로는 몇 분이면 되는 리포트 — 상시 실행·상태·재처리 비용이 크다. 1~5분 마이크로배치나 ClickHouse 질의 시점 집계.
- 엔진 밖 부작용(메일·결제 API)에 정확히 한 번을 기대할 때 — 재처리 때 다시 일어난다. 멱등 키로 막는다.

**누가 매일 만나나** — 스트림 플랫폼을 운영하는 데이터 엔지니어가 워터마크 정체·체크포인트 지연·consumer lag 경보를 볼 때, 백엔드 개발자가 Kafka Streams 로 서비스 안 집계를 만들 때.

**면접·실무 단골 질문**
- Q. 워터마크란? → "이 시각 이전 이벤트는 다 왔다" 는 추정(최대 이벤트 시각 − 허용 지연). 길수록 정확하지만 결과가 늦고 상태가 커진다.
- Q. 정확히 한 번은 어떻게 얻나? → 엔진 내부는 체크포인트(상태 + 오프셋), 외부는 멱등 싱크나 트랜잭션 싱크. 실무 기본은 at-least-once + 멱등 싱크.
