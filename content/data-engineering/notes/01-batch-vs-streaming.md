## 데이터 엔지니어링이 푸는 문제

서비스의 데이터는 **운영을 위해** 저장된다. 주문은 [PostgreSQL](/postgres/notes/01-postgres-overview) 에, 세션은 Redis 에, 로그는 Loki 에, 이벤트는 Kafka 에 있다. 각 저장소는 자기 일(트랜잭션, 빠른 조회, 장애 조사)에 최적화돼 있다.

그런데 "지난 분기 국가별 재구매율" 같은 질문은 여러 저장소의 데이터를 **모아서, 정리하고, 넓게 집계**해야 답이 나온다. 운영 DB 에 그 질의를 걸면 운영이 느려진다. 데이터 엔지니어링은 이 간극을 메운다.

```
원천(운영 시스템)          수집             저장(분석용)            변환             소비
PostgreSQL ─┐                                                                   ┌─ 대시보드
Kafka 이벤트 ┼──▶ 배치 덤프 / CDC / 스트림 ──▶ 객체 저장소(Parquet) ──▶ SQL 모델 ──┼─ 분석가 SQL
로그·SaaS  ─┘                              ClickHouse·웨어하우스                └─ ML 피처
```

## ETL 에서 ELT 로

| | ETL (Extract-Transform-Load) | ELT (Extract-Load-Transform) |
|---|---|---|
| 순서 | 꺼내서 → 파이프라인에서 변환 → 적재 | 꺼내서 → 원본 그대로 적재 → 저장소 안에서 SQL 로 변환 |
| 변환 위치 | 별도 처리 서버(Spark, 스크립트) | 웨어하우스·레이크하우스 엔진 |
| 원본 보존 | 변환된 결과만 남기 쉬움 | 원본이 남아 다시 변환 가능 |
| 시대 | 저장·연산이 비쌀 때 | 저장이 싸고 엔진이 강해진 지금 |

지금의 기본은 **ELT** 다. 원본을 객체 저장소나 웨어하우스에 그대로 쌓고, [dbt 같은 SQL 변환](/data-engineering/notes/04-transformation-dbt) 으로 다듬는다. 변환 로직이 틀렸으면 원본에서 다시 돌리면 된다.

## 배치와 스트리밍

| | 배치 | 스트리밍 |
|---|---|---|
| 처리 단위 | 구간(하루치, 한 시간치) | 이벤트 하나 또는 작은 창 |
| 지연 | 분~시간 | 초 이하~초 |
| 정확성 | 구간이 닫힌 뒤 처리하니 쉬움 | 늦게 오는 데이터·순서·중복을 다뤄야 함 |
| 재처리 | 그 구간을 다시 돌리면 됨 | 오프셋을 되감거나 별도 경로 필요 |
| 비용·운영 | 단순, 실행할 때만 자원 | 상시 실행, 상태 관리·장애 복구가 어려움 |
| 예 | 일일 매출 집계, 월말 정산 | 실시간 이상 탐지, 대시보드 초 단위 갱신, 알림 |

> **경험칙:** "몇 분 늦어도 되나?" 를 먼저 묻는다. 대부분의 분석은 시간 단위 배치로 충분하다. 스트리밍은 지연이 곧 가치인 곳(사기 탐지, 재고, 실시간 개인화)에만.

실제로는 둘 사이에 **마이크로배치**(몇 초~몇 분마다 작은 배치)가 넓게 쓰인다. 실험 [de-cdc-to-lake](/data-engineering/lab/de-cdc-to-lake) 도 Kafka 에서 받은 변경을 묶어 Parquet 파일로 쓰는 마이크로배치다.

## 람다와 카파

### 람다 아키텍처

```
          ┌──▶ 배치 계층 (정확, 느림: 하루 한 번 전체 재계산) ──┐
원천 ─────┤                                                  ├──▶ 서빙 (두 결과를 합침)
          └──▶ 속도 계층 (빠름, 근사: 스트림으로 최근만) ───────┘
```

배치가 "정답" 을, 스트림이 "최근 몇 시간" 을 맡는다. 문제는 **같은 로직을 두 번 구현**해야 한다는 것. 둘이 미묘하게 달라 숫자가 안 맞는 일이 흔하다.

### 카파 아키텍처

```
원천 ──▶ 로그(Kafka, 길게 보존) ──▶ 스트림 처리 ──▶ 서빙
                       └── 로직이 바뀌면 처음부터 다시 재생
```

모든 것을 스트림 하나로 처리하고, 재처리가 필요하면 [Kafka](/kafka/notes/01-kafka-overview) 의 로그를 처음부터 다시 흘린다. 코드가 하나라 깔끔하지만, 긴 보존 비용과 대량 재생 시간이 든다.

현실의 많은 팀은 둘을 섞는다: 스트림으로 원본을 레이크에 계속 쌓고(카파식 수집), 분석 모델은 배치로 다시 계산한다(배치식 변환). [레이크하우스](/data-engineering/notes/02-columnar-formats-lakehouse) 가 이 혼합을 쉽게 만든다.

## 원천에서 꺼내는 세 가지 방법

| 방법 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **전체 덤프** | 매번 테이블 전체 `SELECT *` | 가장 단순, 항상 정확 | 크면 느리고 원천 부하 큼 |
| **증분 쿼리** | `WHERE updated_at > 지난번` | 가벼움 | 삭제를 못 봄, `updated_at` 누락·시계 문제 |
| **CDC** | DB 변경 로그(WAL)를 읽음 | 삭제 포함 모든 변경, 원천 부하 적음, 실시간 | 커넥터·슬롯 운영 필요 |

CDC 는 [Debezium 노트](/kafka/notes/08-cdc-outbox-debezium) 에서 자세히 다뤘다. 핵심은 **변경 로그는 "현재 상태" 가 아니라 "일어난 일의 목록"** 이라는 것이다. 분석 저장소에서 현재 상태를 보려면 키별로 최신 이벤트만 남기는 병합이 필요하다.

## 예시로 보기 — 이 프로젝트에서

이 사이트에는 작은 데이터 파이프라인의 부품이 이미 다 있다.

| 역할 | 이 프로젝트 |
|---|---|
| 운영 DB | PostgreSQL (15432, `wal_level=logical`) |
| CDC | Kafka Connect + Debezium (18083) |
| 로그(버퍼) | Kafka (19092) |
| 객체 저장소 | S3 호환 저장소 (실험이 versitygw 컨테이너를 띄움) |
| 파일 포맷 | Parquet |
| 질의 엔진 | DuckDB (프로세스 안), ClickHouse (서버) |

실험 [de-cdc-to-lake](/data-engineering/lab/de-cdc-to-lake) 는 이 부품들을 실제로 잇는다.

1. PG 에 주문 200건을 넣고 Debezium 커넥터를 등록 → 스냅샷 이벤트 200건(`__op = r`)
2. UPDATE 53건, DELETE 10건, INSERT 20건 → 변경 이벤트 83건
3. 소비자가 이벤트를 두 마이크로배치로 묶어 S3 에 Parquet 로 기록
4. DuckDB 가 S3 의 Parquet 를 읽어 **키별 최신 + 삭제 제외** 로 현재 상태를 복원
5. PG 원본과 비교: 행 수 210, amount 합 109,062.12, max(id) 220 이 **정확히 일치**

파일을 그냥 세면 283건이다. 변경 로그와 현재 상태의 차이를 숫자로 보는 것이 이 주제 전체의 출발점이다.
