## 데이터 엔지니어링이 푸는 문제

서비스의 데이터는 **운영을 위해** 저장된다. 주문은 [PostgreSQL](/postgres/notes/01-postgres-overview) 에, 세션은 Redis 에, 로그는 Loki 에, 이벤트는 Kafka 에 있다. 각 저장소는 자기 일(트랜잭션, 빠른 조회, 장애 조사)에 최적화돼 있다.

그런데 "지난 분기 국가별 재구매율" 같은 질문은 여러 저장소의 데이터를 **모아서, 정리하고, 넓게 집계**해야 답이 나온다. 운영 DB 에 그 질의를 걸면 운영이 느려진다. 데이터 엔지니어링은 이 간극을 메운다.

```
원천(운영 시스템)          수집             저장(분석용)            변환             소비
PostgreSQL ─┐                                                                   ┌─ 대시보드
Kafka 이벤트 ┼──▶ 배치 덤프 / CDC / 스트림 ──▶ 객체 저장소(Parquet) ──▶ SQL 모델 ──┼─ 분석가 SQL
로그·SaaS  ─┘                              ClickHouse·웨어하우스                └─ ML 피처
```

## ETL 에서 ELT 로

| | ETL (Extract-Transform-Load) | ELT (Extract-Load-Transform) |
|---|---|---|
| 순서 | 꺼내서 → 파이프라인에서 변환 → 적재 | 꺼내서 → 원본 그대로 적재 → 저장소 안에서 SQL 로 변환 |
| 변환 위치 | 별도 처리 서버(Spark, 스크립트) | 웨어하우스·레이크하우스 엔진 |
| 원본 보존 | 변환된 결과만 남기 쉬움 | 원본이 남아 다시 변환 가능 |
| 시대 | 저장·연산이 비쌀 때 | 저장이 싸고 엔진이 강해진 지금 |

지금의 기본은 **ELT** 다. 원본을 객체 저장소나 웨어하우스에 그대로 쌓고, [dbt 같은 SQL 변환](/data-engineering/notes/04-transformation-dbt) 으로 다듬는다. 변환 로직이 틀렸으면 원본에서 다시 돌리면 된다.

## 배치와 스트리밍

| | 배치 | 스트리밍 |
|---|---|---|
| 처리 단위 | 구간(하루치, 한 시간치) | 이벤트 하나 또는 작은 창 |
| 지연 | 분~시간 | 초 이하~초 |
| 정확성 | 구간이 닫힌 뒤 처리하니 쉬움 | 늦게 오는 데이터·순서·중복을 다뤄야 함 |
| 재처리 | 그 구간을 다시 돌리면 됨 | 오프셋을 되감거나 별도 경로 필요 |
| 비용·운영 | 단순, 실행할 때만 자원 | 상시 실행, 상태 관리·장애 복구가 어려움 |
| 예 | 일일 매출 집계, 월말 정산 | 실시간 이상 탐지, 대시보드 초 단위 갱신, 알림 |

> **경험칙:** "몇 분 늦어도 되나?" 를 먼저 묻는다. 대부분의 분석은 시간 단위 배치로 충분하다. 스트리밍은 지연이 곧 가치인 곳(사기 탐지, 재고, 실시간 개인화)에만.

실제로는 둘 사이에 **마이크로배치**(몇 초~몇 분마다 작은 배치)가 넓게 쓰인다. 실험 [de-cdc-to-lake](/data-engineering/lab/de-cdc-to-lake) 도 Kafka 에서 받은 변경을 묶어 Parquet 파일로 쓰는 마이크로배치다.

## 람다와 카파

### 람다 아키텍처

```
          ┌──▶ 배치 계층 (정확, 느림: 하루 한 번 전체 재계산) ──┐
원천 ─────┤                                                  ├──▶ 서빙 (두 결과를 합침)
          └──▶ 속도 계층 (빠름, 근사: 스트림으로 최근만) ───────┘
```

배치가 "정답" 을, 스트림이 "최근 몇 시간" 을 맡는다. 문제는 **같은 로직을 두 번 구현**해야 한다는 것. 둘이 미묘하게 달라 숫자가 안 맞는 일이 흔하다.

### 카파 아키텍처

```
원천 ──▶ 로그(Kafka, 길게 보존) ──▶ 스트림 처리 ──▶ 서빙
                       └── 로직이 바뀌면 처음부터 다시 재생
```

모든 것을 스트림 하나로 처리하고, 재처리가 필요하면 [Kafka](/kafka/notes/01-kafka-overview) 의 로그를 처음부터 다시 흘린다. 코드가 하나라 깔끔하지만, 긴 보존 비용과 대량 재생 시간이 든다.

현실의 많은 팀은 둘을 섞는다: 스트림으로 원본을 레이크에 계속 쌓고(카파식 수집), 분석 모델은 배치로 다시 계산한다(배치식 변환). [레이크하우스](/data-engineering/notes/02-columnar-formats-lakehouse) 가 이 혼합을 쉽게 만든다.

## 원천에서 꺼내는 세 가지 방법

| 방법 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **전체 덤프** | 매번 테이블 전체 `SELECT *` | 가장 단순, 항상 정확 | 크면 느리고 원천 부하 큼 |
| **증분 쿼리** | `WHERE updated_at > 지난번` | 가벼움 | 삭제를 못 봄, `updated_at` 누락·시계 문제 |
| **CDC** | DB 변경 로그(WAL)를 읽음 | 삭제 포함 모든 변경, 원천 부하 적음, 실시간 | 커넥터·슬롯 운영 필요 |

CDC 는 [Debezium 노트](/kafka/notes/08-cdc-outbox-debezium) 에서 자세히 다뤘다. 핵심은 **변경 로그는 "현재 상태" 가 아니라 "일어난 일의 목록"** 이라는 것이다. 분석 저장소에서 현재 상태를 보려면 키별로 최신 이벤트만 남기는 병합이 필요하다.

## 예시로 보기 — 이 프로젝트에서

이 사이트에는 작은 데이터 파이프라인의 부품이 이미 다 있다.

| 역할 | 이 프로젝트 |
|---|---|
| 운영 DB | PostgreSQL (15432, `wal_level=logical`) |
| CDC | Kafka Connect + Debezium (18083) |
| 로그(버퍼) | Kafka (19092) |
| 객체 저장소 | S3 호환 저장소 (실험이 versitygw 컨테이너를 띄움) |
| 파일 포맷 | Parquet |
| 질의 엔진 | DuckDB (프로세스 안), ClickHouse (서버) |

실험 [de-cdc-to-lake](/data-engineering/lab/de-cdc-to-lake) 는 이 부품들을 실제로 잇는다.

1. PG 에 주문 200건을 넣고 Debezium 커넥터를 등록 → 스냅샷 이벤트 200건(`__op = r`)
2. UPDATE 53건, DELETE 10건, INSERT 20건 → 변경 이벤트 83건
3. 소비자가 이벤트를 두 마이크로배치로 묶어 S3 에 Parquet 로 기록
4. DuckDB 가 S3 의 Parquet 를 읽어 **키별 최신 + 삭제 제외** 로 현재 상태를 복원
5. PG 원본과 비교: 행 수 210, amount 합 109,062.12, max(id) 220 이 **정확히 일치**

파일을 그냥 세면 283건이다. 변경 로그와 현재 상태의 차이를 숫자로 보는 것이 이 주제 전체의 출발점이다.

## 심화 — 지연 예산으로 설계하기

"실시간이 필요하다" 는 말은 숫자로 바꿔야 설계가 된다. 원천에서 대시보드까지 한 이벤트가 지나는 구간마다 지연을 적어 보면 **어디가 병목인지, 스트리밍이 정말 필요한지** 가 보인다. 아래는 이 사이트 규모의 CDC 파이프라인을 가정한 예산이다(측정값이 아니라 설계용 가정치).

| 구간 | 대표 지연 (가정) | 무엇이 결정하나 |
|---|---|---|
| PG 커밋 → WAL 디코딩 | 수십~수백 ms | Debezium 폴링 간격, 긴 트랜잭션 |
| Debezium → Kafka | 수 ms~1초 | 프로듀서 `linger.ms`, 배치 크기 |
| Kafka → 파일 쓰기 | **최대 5분** | 마이크로배치 플러시 주기 |
| 파일 → silver/gold 변환 | 1분~1시간 | 오케스트레이터 스케줄 |
| gold → 대시보드 | 수 초~5분 | 대시보드 캐시 TTL |

합치면 "대략 10분~1시간" 이다. 여기서 Kafka 구간을 아무리 줄여도 변환 스케줄이 1시간이면 끝단 지연은 1시간이다. **가장 긴 구간 하나가 전체를 결정한다.** 그래서 "실시간" 을 원하면 수집만 스트림으로 바꿀 게 아니라 변환·서빙까지 같이 바꿔야 하고, 그 비용이 정말 가치가 있는지 묻게 된다.

### 마이크로배치의 플러시 조건

```ts
// 크기 또는 시간 중 먼저 오는 쪽으로 파일을 닫는다
if (buffer.length >= 50_000 || Date.now() - openedAt >= 5 * 60_000) {
  await writeParquet(`s3://lake/bronze/orders_cdc/day=${day}/batch=${seq}.parquet`, buffer);
  await consumer.commitOffsets(lastOffsets);   // 파일이 써진 *뒤에* 오프셋 커밋
  buffer = []; openedAt = Date.now(); seq++;
}
```

- 오프셋을 파일 쓰기 **뒤에** 커밋하면, 쓰기 직후 죽었을 때 같은 이벤트가 다음 파일에 또 들어간다(at-least-once). 그래서 병합 단계가 키별 최신만 남기는 멱등 연산이어야 한다.
- 5분마다 한 파일이면 하루 288개, 테이블 10개면 2,880개다. 하루 끝에 병합(compaction)하지 않으면 [작은 파일 문제](/data-engineering/notes/02-columnar-formats-lakehouse) 가 된다. 주기를 줄이면 신선도는 좋아지고 파일 수는 늘어난다 — **신선도 ↔ 파일 수** 의 교환.

### CDC 의 숨은 운영 비용 — 복제 슬롯

CDC 커넥터가 멈춰도 PG 는 슬롯이 아직 안 읽은 WAL 을 지우지 못한다. 커넥터가 주말 내내 죽어 있으면 **운영 DB 디스크가 WAL 로 가득 찬다.** 데이터 파이프라인 장애가 운영 장애로 번지는 대표적인 경로다.

```sql
-- 슬롯별로 붙잡고 있는 WAL 양
select slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) as retained_wal
from pg_replication_slots;
```

```
# postgresql.conf (PG 13+): 슬롯이 붙잡을 수 있는 WAL 상한. 넘으면 슬롯이 무효화된다
max_slot_wal_keep_size = 20GB
```

상한을 걸면 운영 DB 는 지키지만 슬롯이 무효화되면 CDC 를 **스냅샷부터 다시** 해야 한다. 어느 쪽을 희생할지는 설계 결정이다. 보통은 운영 DB 를 지키고, 슬롯 WAL 크기에 경보를 건다.

## 모니터링 — 파이프라인이 아프면 어떻게 드러나나

데이터 파이프라인 장애는 대개 **에러가 아니라 조용한 낡음**으로 드러난다. 작업은 "성공" 인데 대시보드 숫자가 어제에서 멈춰 있다. 그래서 성공/실패보다 **신선도와 양**을 본다.

| 무엇을 본다 | 메트릭·질의 예 | 이상 신호 |
|---|---|---|
| 신선도 | `now() - max(event_ts)` 를 테이블별로 | SLA(예: 2시간) 초과 |
| 소비 지연 | `kafka_consumergroup_lag{consumergroup="lake-writer"}` | 계속 증가 = 소비자가 못 따라감 |
| 슬롯 WAL | 위 `retained_wal` | 수 GB 이상, 계속 증가 |
| 처리 행 수 | 파티션별 행 수, 전주 같은 요일 대비 | 갑자기 0 또는 절반 |
| 파일 수 | 파티션별 파일 개수 | 병합 작업이 멈춤 |

```promql
# 신선도 경보: 마지막 성공 적재 후 2시간 넘음
time() - de_last_success_timestamp_seconds{asset="orders_current"} > 2 * 3600
```

작업 로그에는 최소한 `asset`, `partition`, `rows_in`, `rows_out`, `duration_ms`, `run_id` 를 구조화해서 남긴다. "어제 파티션 rows_out=0" 을 로그 질의 하나로 찾을 수 있어야 한다([Loki 로그 노트](/observability/notes/05-logging-loki)).

## 흔한 실수와 오해

- **"스트리밍이 더 최신이니 더 좋다"** — 끝단 지연은 가장 느린 구간이 정한다. 소비자가 하루 한 번 보는 리포트에 스트림은 비용만 늘린다.
- **"CDC 이벤트 수 = 행 수"** — 실험의 283 vs 210 처럼 이벤트는 변경 횟수다. 병합 없이 세면 매출이 부풀려진다.
- **`updated_at` 증분 쿼리는 커밋 순서를 모른다** — 10:00 에 시작해 10:10 에 커밋한 트랜잭션의 행은 `updated_at = 10:00` 이다. 10:05 에 "10:00 이후" 를 읽고 체크포인트를 10:05 로 옮겼다면 이 행은 영원히 빠진다. lookback 창이나 CDC 가 필요한 이유다.
- **"ELT 면 원본은 영원히 보관"** — 개인정보 삭제 요구가 오면 bronze 까지 지워야 한다. 원본 보존 기간과 삭제 절차를 처음부터 정한다.
- **람다의 두 경로를 다른 팀이 따로 구현** — 숫자가 안 맞는 순간 어느 쪽이 맞는지 아무도 모른다. 혼합하더라도 로직은 한 곳(SQL 모델)에 둔다.

## 스스로 점검

1. 끝단 지연이 1시간인 파이프라인에서 Kafka 구간을 1초에서 10ms 로 줄이면 무엇이 좋아지나? — 거의 없다. 병목 구간(변환 스케줄)을 줄여야 한다.
2. CDC 커넥터가 이틀 멈췄을 때 운영 DB 에 생길 수 있는 일과 예방책은? — 슬롯이 WAL 을 붙잡아 디스크가 찬다. `max_slot_wal_keep_size` 와 슬롯 WAL 경보.
3. 마이크로배치에서 오프셋을 파일 쓰기 전에 커밋하면? — 쓰기 직전에 죽으면 그 이벤트가 유실된다(at-most-once).
4. 작업은 매일 성공하는데 대시보드가 틀렸다. 무엇부터 보나? — 신선도(max event_ts), 파티션별 행 수 추이, 원천 쪽 지연.

## 실전에서는 어디에 쓰이나 — 데이터 엔지니어링 지도

> 데이터 엔지니어링은 운영 시스템(DB·이벤트·로그)에 흩어진 데이터를 분석·리포트·ML 이 쓸 수 있는 형태로 옮기고, 그 숫자가 믿을 만하다는 것을 지키는 일이다. "대시보드 숫자가 왜 어제와 다르냐" 는 질문은 결국 이 파이프라인으로 돌아온다.

| 서비스·상황 | 이 주제의 어떤 부분이 | 더 읽기 |
|---|---|---|
| 커머스 일일 매출·재구매율 리포트 | 운영 DB → CDC·덤프 → 레이크 → 일 배치 집계 | 이 노트 |
| 로그·이벤트를 싸게 오래 보관하며 분석 | Parquet 열 포맷, 정렬로 건너뛰기, Iceberg 테이블 | [열 파일 포맷과 레이크하우스](/data-engineering/notes/02-columnar-formats-lakehouse) |
| 매일 새벽 작업 수십 개의 순서·재시도·과거 재계산 | DAG, 논리 날짜, 멱등 파티션 덮어쓰기, 백필 | [오케스트레이션](/data-engineering/notes/03-orchestration) |
| 지표 정의를 코드 리뷰·테스트로 관리 | dbt 모델·증분·테스트·SCD2 | [변환과 dbt](/data-engineering/notes/04-transformation-dbt) |
| 결제 이상 탐지·실시간 오류율 | 이벤트 시간 윈도우, 워터마크, 상태, 정확히 한 번 | [스트림 처리](/data-engineering/notes/05-stream-processing) |
| 원천 스키마 변경으로 대시보드가 조용히 틀림 | 품질 테스트, 격리, 데이터 계약, 계보 | [품질·계보·계약](/data-engineering/notes/06-data-quality-lineage-contracts) |
| 작은 팀이 서버 없이 분석 기반을 만들 때 | 메달리온 계층, DuckDB, 원자적 발행 | [작은 레이크하우스 설계](/data-engineering/notes/07-tiny-lakehouse-design) |
| AI 기능의 토큰 비용·주제별 사용량 기간 비교 | 로그를 bronze 에 쌓고 gold 일 집계 | [작은 레이크하우스 설계](/data-engineering/notes/07-tiny-lakehouse-design) |

**회사 규모에 따라**
- 스타트업: 운영 DB 복제본에 SQL 을 걸거나 cron + 스크립트로 시작한다. 전담자가 없어 관리형 수집 도구 + 웨어하우스 + dbt 정도의 최소 구성이 흔하다.
- 성장기: 작업이 수십~수백 개가 되며 오케스트레이터·CDC·품질 테스트가 필요해지고, "숫자가 안 맞는다" 대응이 데이터 팀 일의 큰 부분이 된다.
- 대규모 조직: 레이크하우스·스트림 처리 플랫폼을 플랫폼 팀이 운영하고, 도메인 팀은 데이터 계약과 계보로 생산자·소비자 관계를 관리한다.

**이럴 땐 안 맞는다**
- 데이터가 작고 질문이 운영 DB 쿼리 몇 개로 끝날 때 — 파이프라인은 운영 부담만 늘린다. 복제본이나 읽기 전용 뷰로 충분하다.
- 요청 처리 중에 결과가 필요한 사용자 기능(실시간 추천 응답 등) — 분석 파이프라인이 아니라 서비스 경로(캐시·온라인 저장소)의 문제다.

**누가 매일 만나나** — 데이터 엔지니어는 새벽 실패 알림·백필·스키마 변경 대응으로, 분석 엔지니어는 dbt 모델과 테스트로 만난다. 백엔드 개발자는 자기 테이블에 CDC 가 걸려 있어 마이그레이션 때 계약을 지켜야 할 때, ML 엔지니어는 피처 테이블의 신선도와 정합성으로 만난다.
