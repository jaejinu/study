## 요구사항

- 1:1·그룹(최대 500명) 채팅, 전송 후 1초 안에 상대에게 보인다.
- 메시지 유실 없음, 대화방 안 순서 보장, 읽음 표시.
- 오프라인 사용자는 모바일 푸시, 다시 접속하면 놓친 메시지 동기화.
- 숫자: 동시 접속 1,000만, 메시지 하루 100억(≈ 11만/s, 피크 30만/s), 메시지 평균 100B.

## 연결 — 서버가 먼저 말해야 한다

| 방식 | 방향 | 특징 |
|---|---|---|
| 롱폴링 | 서버→클라이언트(흉내) | 어디서나 동작, 요청 오버헤드 큼 |
| SSE | 서버→클라이언트 | HTTP 위 단방향, 재연결·이벤트 ID 내장. 이 사이트의 `/api/ask` 스트리밍이 SSE |
| WebSocket | 양방향 | 채팅의 표준, 프록시·LB 설정(업그레이드, 긴 타임아웃) 필요 |

연결 1,000만 개 = 서버 한 대 수십만 연결 × 수십 대. 연결은 메모리(소켓 버퍼)와 파일 디스크립터를 먹는다 — 커널 관점은 [운영체제 노트 05](/os-internals/notes/05-syscalls-interrupts)의 epoll, 프록시 설정은 [Nginx 노트 02](/nginx/notes/02-reverse-proxy-lb).

## 라우팅 — 상대가 어느 서버에 붙어 있나

```
보낸 사람 ─▶ 게이트웨이 A ─▶ 채팅 서비스 ─▶ (저장) ─▶ 수신자 위치 조회 (user → gateway) ─▶ 게이트웨이 B ─▶ 받는 사람
```

| 방법 | 설명 |
|---|---|
| 연결 레지스트리 | 접속 시 Redis 에 `conn:<user> = gateway-B` (TTL + 하트비트) |
| Pub/Sub 채널 | 게이트웨이가 자기에게 붙은 사용자 채널을 구독, 채팅 서비스는 `user:<id>` 에 발행 |
| 일관 해싱 | 사용자 ID 로 게이트웨이를 정해 붙게 함 — 재배치 때 연결 이동 필요 |

Redis Pub/Sub 은 **구독자가 없으면 버려진다**(fire-and-forget). 그래서 "실시간 전달 시도" 에만 쓰고, 진실은 저장소에 둔다 — 실험 [pubsub](/redis/lab/pubsub) 과 [Redis 노트 07](/redis/notes/07-pubsub-streams).

## 순서 — 대화방마다 시퀀스

전역 순서는 필요 없다. **대화방 안 순서**만 지키면 된다.

```
대화방 room-77 의 다음 번호: INCR seq:room-77  →  1043
메시지 저장: (room_id, seq) 기본 키, 서버 시각, 보낸 사람, 클라이언트 메시지 ID
```

- 서버가 번호를 매기므로 두 사람이 동시에 보내도 순서가 하나로 정해진다.
- 클라이언트 시각으로 정렬하면 시계가 틀린 기기의 메시지가 엉뚱한 곳에 끼어든다 — [분산 시스템 노트 02](/distributed-systems/notes/02-time-and-order).
- 대화방이 파티션 단위가 되면 Kafka 의 "같은 키 → 같은 파티션 → 순서 보장" 과 같은 구조다 ([Kafka 노트 02](/kafka/notes/02-topics-partitions)).

## 전달 보장 — 유실 없이, 중복은 클라이언트가

```
클라이언트: client_msg_id = UUID 를 만들어 전송 → 서버 ACK(seq) 를 받을 때까지 재전송
서버:       (room, client_msg_id) 유일 제약 → 재전송된 같은 메시지는 같은 seq 를 돌려줌 (멱등)
수신 측:    마지막으로 받은 seq 를 기억 → 재접속 시 "seq > 1043 인 것 줘" 로 동기화
```

| 단계 | 보장 |
|---|---|
| 보낸 사람 → 서버 | 재전송 + 멱등 키 → 사실상 정확히 한 번 저장 |
| 서버 → 받는 사람 | 실시간 푸시는 최선, **동기화(마지막 seq 이후)** 가 진실 |
| 표시 | 클라이언트가 seq 로 정렬·중복 제거 |

메시지 로그로 Redis Streams 를 쓰면 대화방별 스트림, 소비자 그룹, `XRANGE room-77 <last-id> +` 로 동기화가 자연스럽다 — 실험 [streams](/redis/lab/streams). 대규모 영속 저장은 Cassandra·ScyllaDB 처럼 (room_id, seq) 범위 질의에 강한 저장소를 쓴다.

## 읽음·전달 표시

- 사용자별 "읽은 마지막 seq" 하나만 저장한다(메시지마다 읽음 플래그 X).
- 그룹 채팅의 "N명 읽음" 은 각 멤버의 마지막 읽음 seq 와 비교해 계산 — 500명 그룹이면 비싸므로 근사하거나 요청 시 계산.

## 그룹 채팅 fan-out

메시지 하나를 멤버 500명에게: 저장은 **한 번**(대화방 로그), 전달은 접속 중인 멤버의 게이트웨이로. 뉴스피드의 push 처럼 멤버마다 복사본을 만들지 않는다 — 읽기 쪽이 대화방 로그 하나를 공유하기 때문이다. 대화방이 수만 명(라이브 채팅)이면 전달을 샘플링·묶음·속도 제한한다. 팬아웃 비용 비교는 [노트 04](/system-design/notes/04-news-feed).

## 오프라인과 푸시

```
수신자 연결 없음 → 알림 서비스로 이벤트 → 사용자 설정·방해 금지 시간 확인 → APNs / FCM
```

- 푸시는 **신호**일 뿐, 내용 동기화는 앱이 켜졌을 때 seq 동기화로.
- 푸시 공급자의 토큰 만료·실패율을 관측한다.

## 알림 시스템 일반

| 기능 | 이유 |
|---|---|
| 우선순위 큐 | 보안 알림(로그인 시도)이 마케팅 알림 뒤에 서면 안 된다 |
| 묶음(digest) | "좋아요 37개" 를 한 번에 |
| 빈도 제한 | 사용자당 시간당 N개 — [노트 03 레이트리미터](/system-design/notes/03-rate-limiter) |
| 멱등 | 같은 이벤트로 두 번 보내지 않기(처리 기록) |
| 재시도·DLQ | 공급자 일시 장애 — 실험 [mq-rabbit-dlx-retry](/messaging/lab/mq-rabbit-dlx-retry) |

## 장애 시나리오

| 상황 | 대책 |
|---|---|
| 게이트웨이 한 대 재시작 | 연결 수십만이 동시에 재접속 → 지수 백오프+지터, 재접속 속도 제한 |
| Pub/Sub 메시지 유실 | 클라이언트가 seq 공백을 감지하면 동기화 요청 |
| 대화방 seq 카운터 핫스팟 | 초대형 방은 seq 범위 할당, 또는 (서버시각, 서버ID, 카운터) 조합 |
| 저장소 지연 | 쓰기 경로 타임아웃 → 클라이언트 재전송(멱등이라 안전) |
