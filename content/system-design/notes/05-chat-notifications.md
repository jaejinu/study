## 요구사항

- 1:1·그룹(최대 500명) 채팅, 전송 후 1초 안에 상대에게 보인다.
- 메시지 유실 없음, 대화방 안 순서 보장, 읽음 표시.
- 오프라인 사용자는 모바일 푸시, 다시 접속하면 놓친 메시지 동기화.
- 숫자: 동시 접속 1,000만, 메시지 하루 100억(≈ 11만/s, 피크 30만/s), 메시지 평균 100B.

## 연결 — 서버가 먼저 말해야 한다

| 방식 | 방향 | 특징 |
|---|---|---|
| 롱폴링 | 서버→클라이언트(흉내) | 어디서나 동작, 요청 오버헤드 큼 |
| SSE | 서버→클라이언트 | HTTP 위 단방향, 재연결·이벤트 ID 내장. 이 사이트의 `/api/ask` 스트리밍이 SSE |
| WebSocket | 양방향 | 채팅의 표준, 프록시·LB 설정(업그레이드, 긴 타임아웃) 필요 |

연결 1,000만 개 = 서버 한 대 수십만 연결 × 수십 대. 연결은 메모리(소켓 버퍼)와 파일 디스크립터를 먹는다 — 커널 관점은 [운영체제 노트 05](/os-internals/notes/05-syscalls-interrupts)의 epoll, 프록시 설정은 [Nginx 노트 02](/nginx/notes/02-reverse-proxy-lb).

## 라우팅 — 상대가 어느 서버에 붙어 있나

```
보낸 사람 ─▶ 게이트웨이 A ─▶ 채팅 서비스 ─▶ (저장) ─▶ 수신자 위치 조회 (user → gateway) ─▶ 게이트웨이 B ─▶ 받는 사람
```

| 방법 | 설명 |
|---|---|
| 연결 레지스트리 | 접속 시 Redis 에 `conn:<user> = gateway-B` (TTL + 하트비트) |
| Pub/Sub 채널 | 게이트웨이가 자기에게 붙은 사용자 채널을 구독, 채팅 서비스는 `user:<id>` 에 발행 |
| 일관 해싱 | 사용자 ID 로 게이트웨이를 정해 붙게 함 — 재배치 때 연결 이동 필요 |

Redis Pub/Sub 은 **구독자가 없으면 버려진다**(fire-and-forget). 그래서 "실시간 전달 시도" 에만 쓰고, 진실은 저장소에 둔다 — 실험 [pubsub](/redis/lab/pubsub) 과 [Redis 노트 07](/redis/notes/07-pubsub-streams).

## 순서 — 대화방마다 시퀀스

전역 순서는 필요 없다. **대화방 안 순서**만 지키면 된다.

```
대화방 room-77 의 다음 번호: INCR seq:room-77  →  1043
메시지 저장: (room_id, seq) 기본 키, 서버 시각, 보낸 사람, 클라이언트 메시지 ID
```

- 서버가 번호를 매기므로 두 사람이 동시에 보내도 순서가 하나로 정해진다.
- 클라이언트 시각으로 정렬하면 시계가 틀린 기기의 메시지가 엉뚱한 곳에 끼어든다 — [분산 시스템 노트 02](/distributed-systems/notes/02-time-and-order).
- 대화방이 파티션 단위가 되면 Kafka 의 "같은 키 → 같은 파티션 → 순서 보장" 과 같은 구조다 ([Kafka 노트 02](/kafka/notes/02-topics-partitions)).

## 전달 보장 — 유실 없이, 중복은 클라이언트가

```
클라이언트: client_msg_id = UUID 를 만들어 전송 → 서버 ACK(seq) 를 받을 때까지 재전송
서버:       (room, client_msg_id) 유일 제약 → 재전송된 같은 메시지는 같은 seq 를 돌려줌 (멱등)
수신 측:    마지막으로 받은 seq 를 기억 → 재접속 시 "seq > 1043 인 것 줘" 로 동기화
```

| 단계 | 보장 |
|---|---|
| 보낸 사람 → 서버 | 재전송 + 멱등 키 → 사실상 정확히 한 번 저장 |
| 서버 → 받는 사람 | 실시간 푸시는 최선, **동기화(마지막 seq 이후)** 가 진실 |
| 표시 | 클라이언트가 seq 로 정렬·중복 제거 |

메시지 로그로 Redis Streams 를 쓰면 대화방별 스트림, 소비자 그룹, `XRANGE room-77 <last-id> +` 로 동기화가 자연스럽다 — 실험 [streams](/redis/lab/streams). 대규모 영속 저장은 Cassandra·ScyllaDB 처럼 (room_id, seq) 범위 질의에 강한 저장소를 쓴다.

## 읽음·전달 표시

- 사용자별 "읽은 마지막 seq" 하나만 저장한다(메시지마다 읽음 플래그 X).
- 그룹 채팅의 "N명 읽음" 은 각 멤버의 마지막 읽음 seq 와 비교해 계산 — 500명 그룹이면 비싸므로 근사하거나 요청 시 계산.

## 그룹 채팅 fan-out

메시지 하나를 멤버 500명에게: 저장은 **한 번**(대화방 로그), 전달은 접속 중인 멤버의 게이트웨이로. 뉴스피드의 push 처럼 멤버마다 복사본을 만들지 않는다 — 읽기 쪽이 대화방 로그 하나를 공유하기 때문이다. 대화방이 수만 명(라이브 채팅)이면 전달을 샘플링·묶음·속도 제한한다. 팬아웃 비용 비교는 [노트 04](/system-design/notes/04-news-feed).

## 오프라인과 푸시

```
수신자 연결 없음 → 알림 서비스로 이벤트 → 사용자 설정·방해 금지 시간 확인 → APNs / FCM
```

- 푸시는 **신호**일 뿐, 내용 동기화는 앱이 켜졌을 때 seq 동기화로.
- 푸시 공급자의 토큰 만료·실패율을 관측한다.

| 기능 | 이유 |
|---|---|
| 우선순위 큐 | 보안 알림(로그인 시도)이 마케팅 알림 뒤에 서면 안 된다 |

## 장애 시나리오

| 상황 | 대책 |
|---|---|
| 게이트웨이 한 대 재시작 | 연결 수십만이 동시에 재접속 → 지수 백오프+지터, 재접속 속도 제한 |
| Pub/Sub 메시지 유실 | 클라이언트가 seq 공백을 감지하면 동기화 요청 |
| 대화방 seq 카운터 핫스팟 | 초대형 방은 seq 범위 할당, 또는 (서버시각, 서버ID, 카운터) 조합 |
| 저장소 지연 | 쓰기 경로 타임아웃 → 클라이언트 재전송(멱등이라 안전) |

## 심화 — 연결 수십만 개를 버티는 설정

동시 접속 1,000만을 게이트웨이 50대로 받으면 대당 20만 연결이다. 연결 하나의 비용을 대략 잡아 보자.

| 항목 | 연결당 | 20만 연결 |
|---|---|---|
| 커널 소켓 버퍼(유휴 시 최소) | 수 KB | 1~2GB |
| 앱 객체(사용자 정보, 버퍼, TLS 세션) | 10~30KB | 2~6GB |
| 파일 디스크립터 | 1 | 20만 → 기본 한도 1,024 로는 불가 |

```bash
# 게이트웨이 서버에서 확인·조정할 것
ulimit -n                                   # 프로세스 fd 한도 → systemd 라면 LimitNOFILE=500000
sysctl net.core.somaxconn                   # accept 대기열 (재접속 폭풍 때 넘치면 SYN 드롭)
sysctl net.ipv4.ip_local_port_range         # LB→게이트웨이 구간에서 출발 포트 고갈 주의
ss -s                                       # 현재 TCP 연결 수, TIME-WAIT 수
```

```nginx
# WebSocket 프록시: 업그레이드 헤더와 긴 유휴 타임아웃 (기본 60초면 조용한 채팅방 연결이 끊긴다)
location /ws {
  proxy_pass http://gateways;
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection "upgrade";
  proxy_read_timeout 3600s;
}
```

유휴 타임아웃보다 짧은 주기(예: 25~30초)로 **애플리케이션 하트비트**(ping/pong)를 보내야 중간 LB·NAT 가 연결을 조용히 끊지 않는다. 하트비트가 2번 연속 없으면 서버는 연결 레지스트리에서 사용자를 지운다 — 그래야 "접속 중" 표시가 거짓말을 하지 않는다. 커널 관점은 [리눅스 네트워크 노트 02](/linux-network/notes/02-ip-ports-sockets).

### 재접속 정책 — 지수 백오프 + 완전 지터

```ts
function reconnectDelay(attempt: number) {
  const base = 500, cap = 30_000;
  const exp = Math.min(cap, base * 2 ** attempt);
  return Math.random() * exp;          // full jitter: 0 ~ exp 사이 균등 → 재접속이 시간축에 퍼진다
}
// 서버가 재시작을 예고할 수 있으면 'reconnect_after_ms' 를 무작위로 내려 줘 분산시킨다
```

게이트웨이 한 대(20만 연결)가 재시작할 때 지터가 없으면 20만 건의 TLS 핸드셰이크가 **같은 1초**에 다른 게이트웨이로 몰린다. 지터로 30초에 퍼뜨리면 초당 약 7,000건이다. 배포는 연결을 천천히 비우는(drain) 방식으로 한다.

## 모니터링·로그 — 실시간 시스템에서 볼 것

| 메트릭 | 의미 | 장애 때 모양 |
|---|---|---|
| 게이트웨이별 활성 연결 수 | 부하 분포 | 한 대만 0 으로 → 그 대 장애, 나머지가 계단식 증가 |
| 연결 수립률·종료율 | 재접속 폭풍 감지 | 종료율 급증 직후 수립률 급증 |
| **종단 간 전달 지연** (서버 수신 → 수신자 ACK) | 사용자가 느끼는 "1초" | p99 상승 → 라우팅 조회·Pub/Sub 지연 |
| seq 공백 감지 → 동기화 요청 수 | 실시간 전달 유실률 | 증가 → Pub/Sub 유실, 게이트웨이 버퍼 넘침 |
| 푸시 공급자 응답(성공·무효 토큰·429) | 오프라인 알림 품질 | 무효 토큰 증가 → 앱 업데이트 후 토큰 갱신 누락 |
| 클라이언트 재전송률 | 보낸 사람 쪽 유실·지연 | 증가 → 저장소 쓰기 지연 |

seq 공백 감지 수는 특히 좋은 지표다. "실시간 경로는 최선, 동기화가 진실" 이라는 설계가 실제로 얼마나 자주 구조해 주고 있는지를 숫자로 보여 준다. 0 이 아니어도 괜찮지만, **갑자기 늘면** 실시간 경로가 아프다는 뜻이다.

로그는 메시지 내용을 남기지 않는다(개인정보·종단 간 암호화). `room_id`, `seq`, `client_msg_id`, `gateway`, 단계별 시각만 남겨도 "이 메시지가 어디서 멈췄나" 를 추적할 수 있다 — [관측 노트 06](/observability/notes/06-tracing-otel).

## 흔한 실수와 오해

- **"WebSocket 이면 TCP 라 유실이 없다"** — TCP 는 연결 안에서만 보장한다. 연결이 끊기는 순간 버퍼에 있던 메시지는 사라진다. 앱 수준 ACK·seq 동기화가 필요하다.
- **"접속 중" 상태를 연결 이벤트로만 관리** — 비정상 종료(전파 손실, 배터리)는 close 이벤트가 안 온다. 하트비트 + TTL 로 판정한다.
- **그룹 메시지를 멤버별로 복사 저장** — 500명 방이면 저장량 500배. 대화방 로그 하나 + 멤버별 "마지막 읽은 seq".
- **푸시 알림에 메시지 전문** — 잠금 화면 노출, 크기 제한(APNs 4KB), 종단 간 암호화와 충돌. 푸시는 신호, 내용은 앱이 동기화.
- **배포 때 게이트웨이를 한꺼번에 재시작** — 재접속 폭풍. 롤링 + drain + 서버 지시 재접속 지연.

## 스스로 점검

1. **LB 유휴 타임아웃이 60초인데 조용한 채팅방 연결이 끊긴다. 해결은?** — 30초 주기 하트비트, 프록시 `proxy_read_timeout` 연장.
2. **20만 연결 게이트웨이가 재시작할 때 지터 없이 1초에 몰리는 것과 30초에 퍼뜨리는 것의 차이는?** — 초당 20만 vs 약 7,000 핸드셰이크. TLS CPU·accept 대기열 넘침을 피한다.
3. **"메시지가 늦게 온다" 는 신고를 어떤 메트릭 순서로 보나?** — 종단 간 전달 지연 → 단계별(저장·라우팅 조회·게이트웨이 전송) → seq 공백 동기화 수.
4. **Pub/Sub 유실이 있어도 사용자가 메시지를 잃지 않는 이유는?** — 수신자가 seq 공백을 감지하거나 재접속 때 "마지막 seq 이후" 를 저장소에서 동기화하기 때문이다.

## 예시로 보기 — 이 프로젝트에서
