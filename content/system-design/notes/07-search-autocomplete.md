## 요구사항

- 글자를 칠 때마다 인기 있는 완성 후보 10개.
- p99 < 50ms(사람이 느끼는 즉시), 하루 1회 이상 인기도 반영.
- 숫자: 검색 하루 50억 회, 평균 질의 길이 10글자 → 자동완성 호출 최대 500억/일 ≈ 58만 QPS. 디바운스(타이핑 멈춘 뒤 100ms)로 1/3 이하로 준다.

이 숫자가 말하는 것: **쓰기(인기도 갱신)는 드물고 읽기는 엄청나다.** 읽기 경로에서 계산을 거의 하지 않도록 미리 만들어 둔다.

## 데이터 — 무엇을 추천하나

```
질의 로그 ─▶ (배치, 하루 1회) 정규화·집계 ─▶ (질의, 빈도, 최근성 가중) ─▶ 금지어·개인정보 필터 ─▶ 인덱스 빌드 ─▶ 교체
```

- 실시간 집계는 필요 없다. 몇 시간 늦어도 품질이 크게 다르지 않다. 급상승 검색어만 별도 스트림으로 보정한다([데이터 엔지니어링 노트 05](/data-engineering/notes/05-stream-processing)).
- 인덱스는 **불변 스냅샷**으로 빌드하고 원자적으로 교체한다(블루·그린) — 읽기 경로에 잠금이 없다.

## 세 가지 인덱스

| 방식 | 저장 | 조회 | 인기순 | 갱신 |
|---|---|---|---|---|
| (A) 사전순 ZSET 하나 + ZRANGEBYLEX | 용어 수만큼 | 접두사 범위를 훑고 앱에서 재정렬 | 앱에서 | 쉬움 |
| (B) 접두사마다 상위 K ZSET | 접두사 수 × K | ZREVRANGE 한 번 | 저장 시 | 비쌈(용어 하나가 접두사 여러 개에 영향) |
| (C) 메모리 트라이 + 노드별 상위 K | 노드 수 × K | 메모리 탐색 | 저장 시 | 재빌드 |

```
트라이 (노드마다 상위 K 를 캐시)
(root)
 ├─ k ─ a ─ f ─ k ─ a      top: [kafka(9), kafka-connect(3) …]
 └─ k ─ u ─ b ─ e …        top: [kubernetes(14), kubectl(5) …]
조회 "ku" → 노드 두 단계 이동 → top 그대로 반환 (정렬 없음)
```

### 실측 — 이 사이트의 용어로

[sd-autocomplete](/system-design/lab/sd-autocomplete) 는 모든 주제 노트 233편의 제목 단어와 태그로 사전을 만든다(용어 2,060개, 상위: 심화 40 · 설계 19 · 캐시 18 · 비용 17 · 보안 16). 1~3글자 접두사(2,572종) 1,000회 질의:

| 방식 | p50 | p99 | 메모리 |
|---|---|---|---|
| (A) 사전순 ZSET 1개 | 0.195ms | 0.944ms | 185KB |
| (B) 접두사별 상위 10 ZSET 5,630개 | 0.179ms | 1.394ms | 약 450KB |
| (C) 메모리 트라이 | **0.0006ms** | 0.0030ms | 프로세스 힙 |

- (B) 와 (C) 는 같은 인기순 결과를 돌려줬다.
- (B) 는 (A) 의 **2.4배** 메모리를 쓴다. 용어 2,000개에선 작지만 1억 개면 접두사 수가 폭증해 차이가 커진다.
- (A) 와 (B) 의 p50 은 비슷하다 — 로컬에선 둘 다 **네트워크 왕복**이 지연의 대부분이기 때문이다. (A) 의 진짜 비용은 짧은 접두사("a")에서 범위가 거대해질 때 나온다(LIMIT 로 잘라 인기 후보를 놓칠 수 있다).
- (C) 는 왕복이 없어 300배 빠르지만, 서버마다 복제본을 들고 있어야 하고 빌드·배포가 필요하다.

현실적인 조합: **(C) 를 자동완성 서버의 메모리에** 두고(오프라인 빌드 → 배포), 짧은 접두사 결과는 CDN·브라우저 캐시에. (B) 는 트라이를 쓸 수 없는 서버리스 환경의 대안.

## ZRANGEBYLEX 의 세부

```bash
ZADD ac:lex 0 kafka 0 kafka-connect 0 kubernetes 0 kubectl
ZRANGEBYLEX ac:lex "[ku" "[ku\xff" LIMIT 0 10      # ku 로 시작하는 것
```

- 점수가 모두 같을 때만 사전순 정렬이 보장된다.
- 끝 경계는 접두사 뒤에 0xFF 바이트를 붙인다. UTF-8 한글도 바이트 사전순이라 그대로 동작하지만, "사전순" 이 사람의 가나다 순과 다를 수 있다.
- 인기순으로 다시 정렬하려면 범위를 넉넉히(LIMIT 200) 가져와 앱에서 빈도로 정렬 — 실험의 (A) 가 이렇게 한다.

## 클라이언트와 캐시

| 층 | 방법 |
|---|---|
| 클라이언트 | 디바운스 100~150ms, 이전 결과에서 접두사 필터(“kub” 결과로 “kube” 를 즉시 보여 줌), 요청 취소 |
| 브라우저 | `Cache-Control: max-age=3600` — 같은 접두사 재요청 |
| CDN | 1~2글자 접두사는 전체 트래픽의 큰 비중 → 엣지 캐시 적중률이 높다 |
| 서버 | 메모리 트라이 |

지프 분포 덕에 작은 캐시로 큰 적중률을 얻는 것은 URL 단축기와 같다([노트 02](/system-design/notes/02-url-shortener): 링크 10% 캐시 → 적중 70%).

## 한국어와 오타

- **초성 검색**("ㅋㅍㅋ" → 카프카): 용어를 초성 열로 바꾼 별도 키를 인덱스에 추가.
- **자모 단위 입력 중**("카ㅍ"): 입력 중 음절을 자모로 분해해 접두사로 맞춘다.
- **오타**("kubernets"): 자동완성보다 검색 엔진의 일 — n-gram, 편집 거리, 퍼지 질의. 한국어 형태소·사용자 사전은 [OpenSearch 노트 07](/opensearch/notes/07-korean-and-ranking), 역색인 구조는 [OpenSearch 노트 01](/opensearch/notes/01-inverted-index-analyzers).
- **개인화**: 공통 후보에 사용자의 최근 검색을 섞되, 개인 기록은 기기·세션 단위로 분리.

## 심화 — 노드별 상위 K 트라이를 직접 빌드하기

```ts
type Node = { children: Map<string, Node>; top: [string, number][] };   // top: (용어, 점수) 내림차순, 최대 K
const K = 10;
const newNode = (): Node => ({ children: new Map(), top: [] });

function insert(root: Node, term: string, score: number) {
  let node = root;
  for (const ch of term) {                              // for..of 는 코드 포인트 단위 → 한글 음절 하나가 한 노드
    if (!node.children.has(ch)) node.children.set(ch, newNode());
    node = node.children.get(ch)!;
    pushTop(node, term, score);                         // 지나가는 모든 접두사 노드의 상위 K 갱신
  }
}
function pushTop(node: Node, term: string, score: number) {
  node.top.push([term, score]);
  node.top.sort((a, b) => b[1] - a[1]);
  if (node.top.length > K) node.top.length = K;
}
function suggest(root: Node, prefix: string) {
  let node: Node | undefined = root;
  for (const ch of prefix) { node = node?.children.get(ch); if (!node) return []; }
  return node.top.map(([t]) => t);                      // 정렬·탐색 없음: 접두사 길이만큼 이동이 전부
}
```

조회 비용은 **접두사 길이에만** 비례하고 사전 크기와 무관하다 — 실험에서 0.0006ms 가 나온 이유다. 대신 빌드 비용은 "용어 수 × 평균 길이 × K 정렬" 이고, 메모리는 "노드 수 × K 개 참조" 다.

### 규모를 키우면 — 1억 질의

| 항목 | 추정 |
|---|---|
| 질의 1억 개, 평균 10글자, 접두사 공유로 노드 ≈ 3억 | |
| 노드당 상위 10 참조(8B×10) + 자식 맵 오버헤드(~100B) | ≈ 180B |
| 합계 | **≈ 50GB** — 서버 한 대 메모리로는 빠듯 |

줄이는 방법: (1) 빈도 하위 꼬리(1회 검색)를 잘라 용어를 1/10 로, (2) 깊이 제한(예: 20글자 이후 노드에는 상위 K 를 두지 않음), (3) 첫 1~2글자로 **샤딩**하되 쏠림("a", "s")이 있으니 빈도 기반으로 구간을 나눈다, (4) 상위 K 를 용어 문자열이 아니라 정수 ID 배열로.

### 인기도 점수 — 최근성 가중

```
score(q) = Σ  count(q, day) × 0.5^(age_days / half_life)       half_life = 7일
```

어제 1,000번 검색된 용어는 1,000 × 0.5^(1/7) ≈ 906점, 30일 전 1,000번은 1,000 × 0.5^(30/7) ≈ 51점이다. 반감기가 짧으면 유행에 민감하고, 길면 안정적이다. 매일 전체를 다시 계산하지 않고 `score_today = score_yesterday × 0.5^(1/7) + count_today` 로 점진 갱신할 수 있다.

### 계층별 QPS 를 실제로 계산하면

```
타이핑 이벤트 58만/s
 └ 디바운스 100ms (빠르게 친 글자 묶음)     → 약 1/3  → 19만/s
   └ 클라이언트 접두사 재사용("kub"→"kube")   → 약 1/2  → 10만/s
     └ 브라우저 캐시 (같은 사용자 재입력)       → 약 0.8 → 8만/s
       └ CDN (짧은 접두사가 대부분 적중, 60%)  → 0.4   → 3.2만/s 가 서버까지
```

계수는 서비스마다 다르므로 **실측**으로 채운다. 각 계층에서 요청 수를 메트릭으로 내보내면 이 표가 대시보드가 된다.

## 모니터링·로그 — 빠른 것만큼 "쓸모" 를 본다

| 지표 | 의미 | 이상 징후 |
|---|---|---|
| 서버 p99 지연 | 체감 즉시성 | 트라이 재빌드 중 GC·메모리 2배(구 + 신 인덱스 동시 상주) |
| CDN 적중률(접두사 길이별) | 캐시 효과 | 배포 후 급락 → 캐시 키에 버전·쿼리스트링이 섞였다 |
| **제안 클릭률**(제안이 보인 뒤 선택한 비율) | 품질 | 새 인덱스 배포 후 하락 → 빌드 버그·필터 과잉 |
| 결과 0개 비율 | 사전 커버리지 | 한국어 접두사에서만 높음 → 자모 분해·정규화 문제 |
| 인덱스 나이(마지막 성공 빌드 시각) | 신선도 | 24시간 초과 알림 → 빌드 실패를 아무도 모르는 상황 방지 |
| 차단 목록 적중 수 | 안전 | 급증 → 사회적 사건, 사람 검토 필요 |

자동완성 로그는 **질의 로그 그 자체가 다음 날의 학습 데이터**다. 그래서 로그에 개인정보(전화번호·주소를 검색창에 친 경우)가 섞이면 그대로 추천에 나올 수 있다. 수집 단계에서 패턴 마스킹과 최소 빈도(k명 이상이 검색한 질의만) 기준을 둔다 — k-익명성과 같은 발상. 검색 품질 지표는 [OpenSearch 노트 07](/opensearch/notes/07-korean-and-ranking), LLM 기반 질의 이해와 엮는다면 [AI 시스템 노트 02](/ai-systems/notes/02-embeddings-vector-search).

## 흔한 실수와 오해

- **매 키 입력마다 요청** — 디바운스·요청 취소가 없으면 늦게 도착한 "k" 결과가 "kub" 결과를 덮어쓴다(응답 순서 역전).
- **문자열을 UTF-16 코드 단위로 자르기** — 이모지·일부 문자가 깨진다. 코드 포인트(`for..of`) 또는 정규화(NFC) 후 처리.
- **NFC/NFD 정규화 누락** — macOS 에서 붙여넣은 한글(NFD)은 같은 글자인데 다른 바이트라 접두사가 안 맞는다.
- **자동완성과 검색을 같은 인덱스로** — 자동완성은 "짧은 접두사 → 인기 상위", 검색은 "전체 문서 → 관련도". 요구 지연과 구조가 다르다.
- **빌드 중 제자리 갱신** — 읽기 경로에 잠금·반쯤 만든 상태가 노출된다. 새 인덱스를 다 만든 뒤 포인터만 교체.

## 스스로 점검

1. **트라이 조회 비용이 사전 크기와 무관한 이유는?** — 노드마다 상위 K 를 미리 저장해 두어, 조회는 접두사 길이만큼 이동하고 그 노드의 top 을 반환할 뿐이다.
2. **질의 1억 개로 트라이를 만들면 메모리를 어떻게 줄이나?** — 저빈도 꼬리 제거, 깊이 제한, ID 배열, 빈도 기반 샤딩.
3. **반감기 7일이면 30일 전 1,000회 검색의 점수는?** — 1,000 × 0.5^(30/7) ≈ 51.
4. **새 인덱스를 배포했더니 지연은 같은데 제안 클릭률이 떨어졌다. 의심할 것은?** — 빌드 데이터(필터 과잉, 정규화 변경), 점수 계산 버그. 지연 메트릭만으로는 품질 사고를 못 본다.


## 실전에서는 어디에 쓰이나

> 사용자가 한 글자 칠 때마다 호출되는 기능은 읽기가 압도적으로 많고 지연 예산이 짧다. 그래서 인기 후보를 미리 계산해 두고 캐시 계층으로 대부분을 흡수하는 설계가 검색창 자동완성 전반에 쓰인다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 커머스 검색창 | 상품명·브랜드 추천을 즉시 | 질의 로그 일 배치 집계 → 노드별 상위 K 트라이를 메모리에, 블루·그린 교체 | 매 요청 검색 엔진 접두사 질의 |
| 배달·지도 앱 주소·가게 검색 | 한국어 입력 중 음절과 초성 | 자모 분해 접두사, 초성 키 별도 인덱스 | 완성된 음절로만 매칭 |
| 포털·미디어 급상승 검색어 | 사건 반영이 하루씩 늦음 | 일 배치 + 최근 1시간 실시간 보정 레이어, 지수 감쇠 점수 | 실시간 전면 재계산 |
| 서버리스 SaaS 의 내부 검색 | 서버 메모리에 트라이를 못 둠 | Redis 접두사별 상위 K ZSET 또는 `ZRANGEBYLEX` | 프로세스 메모리 트라이 |
| 문서·개발자 도구 명령 팔레트 | 작은 사전에서 빠른 제안 | 시작 시 메모리 트라이 빌드(수백 KB) | 외부 검색 서비스 |

**이럴 땐 안 맞는다**
- 오타 교정·의미 검색: 접두사 구조로는 못 푼다. n-gram·편집 거리·형태소 분석을 하는 검색 엔진이나 벡터 검색을 쓴다.
- 전체 문서 관련도 검색: 자동완성은 "짧은 접두사 → 인기 상위" 용이다. 검색은 역색인 기반 검색 엔진으로 분리한다.

**누가 매일 만나나** — 검색·추천 백엔드 개발자는 인덱스 빌드와 점수식을 다룰 때, 데이터 엔지니어는 질의 로그 집계·개인정보 마스킹 파이프라인을 운영할 때, 프론트엔드 개발자는 디바운스와 응답 순서 역전을 처리할 때 만난다.

**면접·실무 단골 질문**
- Q. 트라이 조회가 빠른 이유는? → 노드마다 상위 K 를 미리 저장해 조회 비용이 접두사 길이에만 비례한다.
- Q. 58만 QPS 를 서버가 다 받나? → 디바운스, 브라우저 캐시, CDN 이 단계별로 흡수하고 남은 것만 서버로 온다.
