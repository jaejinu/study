## 요구사항

- 팔로우한 사람들의 글을 최신순(또는 랭킹순)으로 보여 준다.
- 타임라인 조회 p99 < 200ms, 글 게시 후 팔로워에게 수 초 안에 보인다.
- 숫자: 일 활성 3억, 하루 글 1억(쓰기 ≈ 1,200/s), 타임라인 조회 하루 30억(≈ 35,000/s), 평균 팔로워 200, **최대 팔로워 1억**.

마지막 숫자가 문제의 전부다. 평균만 보면 쉽다. 분포의 꼬리(셀럽)가 설계를 결정한다.

## 두 방식

```
fan-out on write (push)
  글 게시 ─▶ 팔로워 목록 ─▶ 각 팔로워 타임라인에 postId 를 넣는다 (LPUSH + LTRIM)
  조회      ─▶ 내 타임라인 LRANGE 0 49  (1번)

fan-out on read (pull)
  글 게시 ─▶ 작성자 글 목록에만 넣는다 (1번)
  조회      ─▶ 내가 팔로우하는 N명의 최근 글을 모아 병합 정렬 → 상위 50
```

| | push | pull |
|---|---|---|
| 게시 비용 | 팔로워 수만큼 (셀럽이면 1억) | 1 |
| 조회 비용 | 1 | 팔로이 수만큼 |
| 조회 지연 | 매우 낮음 | 팔로이가 많으면 높음 |
| 저장 | 사용자마다 타임라인 복사본 | 작성자 글 목록만 |
| 새 팔로우 반영 | 과거 글을 백필해야 | 즉시 |
| 비활성 사용자 | 아무도 안 보는 타임라인에 계속 쓴다 | 낭비 없음 |

## 실측 — 멱법칙 그래프에서

[sd-feed-fanout](/system-design/lab/sd-feed-fanout) 은 사용자 1만 명이 각자 20명을 **선호적 연결**(인기 있는 사람이 더 팔로우됨)로 팔로우하는 그래프를 만든다. 팔로워 수 상위 5명은 9,764 · 8,359 · 6,889 · 5,717 · 4,899명, 중앙값은 **4명**이다. 팔로워 1,000명 초과 "셀럽" 은 26명이다. 게시물 2,000개(20%는 인기 작성자)를 올리고 타임라인 300개를 조회했다.

| 방식 | 타임라인 쓰기 | 게시 1건 최악 | 게시 소요 | 조회 명령/타임라인 | 조회 p50 | 조회 p99 |
|---|---|---|---|---|---|---|
| push | **1,357,881** | **9,764** | 4,658ms | 1 | 0.21ms | 1.32ms |
| pull | 2,000 (작성자 목록만) | 1 | — | 20 | 0.24ms | 1.18ms |
| 하이브리드 (셀럽 26명만 pull) | 53,418 | 957 | 585ms | 8.7 | 0.21ms | 1.19ms |

- push 의 쓰기 135만 건 중 대부분은 **셀럽 26명의 글**이 만든다. 하이브리드는 이들만 pull 로 돌려 쓰기를 **25분의 1** 로 줄였다.
- 조회 지연이 셋 다 비슷해 보이는 것은 실험이 명령을 **파이프라인**으로 한 번에 보내기 때문이다(왕복 1번). 실제 비용은 서버가 처리하는 명령 수다: pull 은 타임라인당 20개, 하이브리드는 8.7개(내 타임라인 1 + 팔로우한 셀럽 평균 7.7). 팔로이가 수천 명인 사용자에게 pull 은 수천 명령이 된다.
- 하이브리드의 최악 게시 비용이 957 로 묶인 것은 임계값(1,000) 덕이다. **임계값이 설계 변수**다.

## 하이브리드 설계

```
게시: author.followers > T ? 작성자 글 목록에만 : 팔로워 타임라인에 push (큐 워커가 비동기로)
조회: LRANGE timeline:<me> 0 199
      + 내가 팔로우하는 셀럽들의 최근 글 (셀럽 글 캐시 — 인기 많아 늘 캐시 적중)
      → 병합 → 상위 50
```

| 세부 결정 | 선택지 |
|---|---|
| 타임라인 저장 | Redis LIST(최신순, LTRIM 200) 또는 ZSET(점수=시각/랭킹, 중복 방지) |
| 무엇을 저장 | postId 만 (글 본문은 글 캐시에서 MGET) — 수정·삭제 반영이 쉽다 |
| 길이 | 200~800개로 제한, 더 과거는 pull 로 |
| 비활성 사용자 | 30일 미접속이면 push 대상에서 빼고, 접속 시 pull 로 재구성 |
| 팬아웃 실행 | 게시 API 가 아니라 큐 워커 — 게시 지연과 분리 ([메시징 노트 01](/messaging/notes/01-queue-topic-log-models)) |
| 새 팔로우 | 팔로우한 사람의 최근 글 몇 개를 백필 |

## 랭킹

최신순이 아니라 "관심 있을 법한 순" 이면, 후보 생성(push/pull 로 수백 개) → 점수 매기기(모델) → 다양성·중복 제거 → 상위 N. 후보 생성 단계가 위의 fan-out 이다. 랭킹 모델 서빙은 지연 예산의 대부분을 쓰므로 후보 수를 줄이는 것이 핵심이다 — [MLOps 노트 05](/mlops/notes/05-serving-batching-kv-cache).

## 삭제·차단·수정

- 글 삭제: 타임라인에서 postId 를 지우지 않고(팔로워 수만큼 비싸다) **조회 시 글 캐시에서 '삭제됨' 이면 거른다**.
- 차단: 조회 시 필터. 차단 목록은 사용자별 Set.
- 수정: 타임라인엔 ID 만 있으므로 글 캐시만 갱신.

| 타임라인 Redis 장애 | pull 로 재구성(느리지만 동작), 타임라인은 캐시일 뿐 진실은 글 저장소 |

| 메모리 | 3억 × 200 × 8바이트 ≈ 480GB → 활성 사용자만, 클러스터 샤딩 |

## 심화 — 팬아웃 워커의 처리량과 "게시 후 보이기까지"

비기능 요구사항 "게시 후 수 초 안에 팔로워에게 보인다" 는 팬아웃 큐의 처리량 문제다.

```
하루 글 1억 × 평균 팔로워 200 = 하루 200억 타임라인 쓰기 ≈ 23만 쓰기/s (평균)
피크 ×3 → 70만 쓰기/s
워커 1개: 파이프라인으로 팔로워 1,000명 묶음을 Redis 에 쓰기 ≈ 5ms → 20만 쓰기/s
→ 피크에 워커 4개면 계산상 충분, 실제로는 Redis 샤드 수·네트워크가 한계 → 샤드 수십 개
```

평균 팔로워 200 은 셀럽이 끌어올린 값일 수 있다. 하이브리드로 셀럽을 빼면 평균이 크게 줄어든다 — 실험에서 쓰기 135만 → 5.3만(25분의 1). **분포의 꼬리를 자르면 용량 계획 자체가 바뀐다.**

팬아웃 작업은 팔로워 목록을 **청크**로 나눠 큐에 넣는다.

```ts
// 게시 이벤트 하나 → 팔로워 1,000명 단위 작업 N개 (한 작업이 실패해도 그 청크만 재시도)
for await (const chunk of followersOf(authorId, { batch: 1000, activeWithinDays: 30 })) {
  await queue.add("fanout", { postId, authorId, followerIds: chunk, ts }, { jobId: `${postId}:${chunk[0]}` });
}
// 워커: 파이프라인으로 LPUSH + LTRIM. jobId 가 같으면 큐가 중복을 걸러 재시도에도 멱등
```

ZSET 타임라인이라면 `ZADD timeline:<u> <ts> <postId>` 가 같은 postId 를 다시 넣어도 하나로 남으므로 재시도에 자연스럽게 멱등이다. LIST 는 재시도 시 **중복 항목**이 생길 수 있어 jobId 중복 제거나 조회 시 dedupe 가 필요하다 — LIST 와 ZSET 선택의 숨은 기준이다.

### 메모리 계산 — LIST vs ZSET

| 구조 | 원소 200개, postId 8바이트 | 3억 명이면 |
|---|---|---|
| LIST (listpack/quicklist) | 약 2KB | ≈ 600GB |
| ZSET (작으면 listpack, 128개 초과 시 skiplist+dict) | 작을 때 약 3KB, skiplist 로 바뀌면 10KB 이상 | 수 TB |

`zset-max-listpack-entries`(기본 128)를 넘는 순간 메모리가 몇 배로 뛴다. 타임라인 길이 상한을 이 값 근처로 정하는 것도 방법이다. `MEMORY USAGE timeline:42` 로 실제 크기를 재고 결정한다 — [Redis 노트 12](/redis/notes/12-memory-performance).

### 페이지네이션은 커서로

```http
GET /v1/timeline?limit=50                       → items…, next_cursor = "1729150000123:p-88121"
GET /v1/timeline?limit=50&cursor=1729150000123:p-88121
```

오프셋(`page=3`)은 새 글이 위에 쌓이면 같은 글이 두 번 보이거나 빠진다. "이 시각·ID 보다 오래된 것" 커서를 쓰면 ZSET 에서 `ZREVRANGEBYSCORE timeline:42 (1729150000123 -inf LIMIT 0 50` 한 번으로 이어진다. 셀럽 글 pull 결과와 병합할 때도 같은 커서 기준으로 자른다.

## 모니터링·로그 — 피드가 "느린 것" 과 "늦은 것" 은 다르다

| 증상 | 사용자 체감 | 보는 메트릭 |
|---|---|---|
| 피드가 느리다 | 화면이 늦게 뜬다 | 타임라인 조회 p99, 셀럽 병합 개수, 글 캐시 MGET 미스율 |
| 피드가 늦다 | 친구 글이 몇 분 뒤에 보인다 | **게시→가시성 지연**(time-to-visible), 팬아웃 큐 lag |
| 피드가 틀리다 | 삭제·차단된 글이 보인다 | 조회 시 필터링 수, 글 캐시 무효화 지연 |

게시→가시성 지연은 직접 재야 한다. 팬아웃 작업에 게시 시각 `ts` 를 싣고, 워커가 쓰기를 마칠 때 `now - ts` 를 히스토그램으로 기록한다.

```promql
histogram_quantile(0.99, sum by (le) (rate(feed_fanout_visible_delay_seconds_bucket[5m])))   # SLO: p99 < 5s
sum(feed_fanout_queue_depth)                                                                     # 셀럽 게시 순간 치솟는지
```

셀럽이 글을 올릴 때마다 큐 깊이가 톱니처럼 튀면 임계값 T 가 너무 높다는 신호다. 로그에는 게시 이벤트마다 `author_followers`, `fanout_mode=push|pull`, `chunks` 를 남겨 "어떤 게시가 큐를 막았나" 를 찾는다.

## 흔한 실수와 오해

- **"push 가 빠르니 push"** — 조회만 보면 그렇지만, 셀럽 한 명이 큐를 수 분 막아 **모든 사람의 피드가 늦어진다**. 꼬리 분포를 묻지 않은 설계는 틀린다.
- **타임라인을 진실로 취급** — 타임라인은 재구성 가능한 캐시다. 백업·강한 일관성에 돈을 쓰지 말고, 날아가면 pull 로 다시 만든다.
- **비활성 사용자에게도 계속 push** — 3억 중 절반이 한 달에 한 번 온다면 쓰기의 절반이 낭비다.
- **오프셋 페이지네이션** — 실시간으로 쌓이는 목록에서는 중복·누락이 난다.
- **팔로우 직후 빈 피드** — 새 팔로우 백필을 빠뜨리면 "팔로우했는데 아무것도 안 보인다" 는 문의가 온다.

## 스스로 점검

1. **팬아웃 재시도 시 LIST 와 ZSET 의 차이는?** — ZSET 은 같은 멤버를 다시 넣어도 하나라 멱등, LIST 는 중복이 생겨 jobId 중복 제거·조회 시 dedupe 가 필요하다.
2. **ZSET 타임라인 길이를 128 근처로 묶을 이유가 있나?** — `zset-max-listpack-entries` 를 넘으면 skiplist 로 바뀌어 메모리가 몇 배가 된다.
3. **"친구 글이 5분 늦게 보인다" 를 어떤 메트릭으로 확인하나?** — 게시→가시성 지연 히스토그램과 팬아웃 큐 lag. 조회 p99 는 정상일 수 있다.
4. **피드 API 에서 오프셋 대신 커서를 쓰는 이유는?** — 새 글이 앞에 쌓여도 "이 시점보다 오래된 것" 기준이라 중복·누락이 없다.
