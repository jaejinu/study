## 요구사항

- 팔로우한 사람들의 글을 최신순(또는 랭킹순)으로 보여 준다.
- 타임라인 조회 p99 < 200ms, 글 게시 후 팔로워에게 수 초 안에 보인다.
- 숫자: 일 활성 3억, 하루 글 1억(쓰기 ≈ 1,200/s), 타임라인 조회 하루 30억(≈ 35,000/s), 평균 팔로워 200, **최대 팔로워 1억**.

마지막 숫자가 문제의 전부다. 평균만 보면 쉽다. 분포의 꼬리(셀럽)가 설계를 결정한다.

## 두 방식

```
fan-out on write (push)
  글 게시 ─▶ 팔로워 목록 ─▶ 각 팔로워 타임라인에 postId 를 넣는다 (LPUSH + LTRIM)
  조회      ─▶ 내 타임라인 LRANGE 0 49  (1번)

fan-out on read (pull)
  글 게시 ─▶ 작성자 글 목록에만 넣는다 (1번)
  조회      ─▶ 내가 팔로우하는 N명의 최근 글을 모아 병합 정렬 → 상위 50
```

| | push | pull |
|---|---|---|
| 게시 비용 | 팔로워 수만큼 (셀럽이면 1억) | 1 |
| 조회 비용 | 1 | 팔로이 수만큼 |
| 조회 지연 | 매우 낮음 | 팔로이가 많으면 높음 |
| 저장 | 사용자마다 타임라인 복사본 | 작성자 글 목록만 |
| 새 팔로우 반영 | 과거 글을 백필해야 | 즉시 |
| 비활성 사용자 | 아무도 안 보는 타임라인에 계속 쓴다 | 낭비 없음 |

## 실측 — 멱법칙 그래프에서

[sd-feed-fanout](/system-design/lab/sd-feed-fanout) 은 사용자 1만 명이 각자 20명을 **선호적 연결**(인기 있는 사람이 더 팔로우됨)로 팔로우하는 그래프를 만든다. 팔로워 수 상위 5명은 9,764 · 8,359 · 6,889 · 5,717 · 4,899명, 중앙값은 **4명**이다. 팔로워 1,000명 초과 "셀럽" 은 26명이다. 게시물 2,000개(20%는 인기 작성자)를 올리고 타임라인 300개를 조회했다.

| 방식 | 타임라인 쓰기 | 게시 1건 최악 | 게시 소요 | 조회 명령/타임라인 | 조회 p50 | 조회 p99 |
|---|---|---|---|---|---|---|
| push | **1,357,881** | **9,764** | 4,658ms | 1 | 0.21ms | 1.32ms |
| pull | 2,000 (작성자 목록만) | 1 | — | 20 | 0.24ms | 1.18ms |
| 하이브리드 (셀럽 26명만 pull) | 53,418 | 957 | 585ms | 8.7 | 0.21ms | 1.19ms |

- push 의 쓰기 135만 건 중 대부분은 **셀럽 26명의 글**이 만든다. 하이브리드는 이들만 pull 로 돌려 쓰기를 **25분의 1** 로 줄였다.
- 조회 지연이 셋 다 비슷해 보이는 것은 실험이 명령을 **파이프라인**으로 한 번에 보내기 때문이다(왕복 1번). 실제 비용은 서버가 처리하는 명령 수다: pull 은 타임라인당 20개, 하이브리드는 8.7개(내 타임라인 1 + 팔로우한 셀럽 평균 7.7). 팔로이가 수천 명인 사용자에게 pull 은 수천 명령이 된다.
- 하이브리드의 최악 게시 비용이 957 로 묶인 것은 임계값(1,000) 덕이다. **임계값이 설계 변수**다.

## 하이브리드 설계

```
게시: author.followers > T ? 작성자 글 목록에만 : 팔로워 타임라인에 push (큐 워커가 비동기로)
조회: LRANGE timeline:<me> 0 199
      + 내가 팔로우하는 셀럽들의 최근 글 (셀럽 글 캐시 — 인기 많아 늘 캐시 적중)
      → 병합 → 상위 50
```

| 세부 결정 | 선택지 |
|---|---|
| 타임라인 저장 | Redis LIST(최신순, LTRIM 200) 또는 ZSET(점수=시각/랭킹, 중복 방지) |
| 무엇을 저장 | postId 만 (글 본문은 글 캐시에서 MGET) — 수정·삭제 반영이 쉽다 |
| 길이 | 200~800개로 제한, 더 과거는 pull 로 |
| 비활성 사용자 | 30일 미접속이면 push 대상에서 빼고, 접속 시 pull 로 재구성 |
| 팬아웃 실행 | 게시 API 가 아니라 큐 워커 — 게시 지연과 분리 ([메시징 노트 01](/messaging/notes/01-queue-topic-log-models)) |
| 새 팔로우 | 팔로우한 사람의 최근 글 몇 개를 백필 |

## 랭킹

최신순이 아니라 "관심 있을 법한 순" 이면, 후보 생성(push/pull 로 수백 개) → 점수 매기기(모델) → 다양성·중복 제거 → 상위 N. 후보 생성 단계가 위의 fan-out 이다. 랭킹 모델 서빙은 지연 예산의 대부분을 쓰므로 후보 수를 줄이는 것이 핵심이다 — [MLOps 노트 05](/mlops/notes/05-serving-batching-kv-cache).

## 삭제·차단·수정

- 글 삭제: 타임라인에서 postId 를 지우지 않고(팔로워 수만큼 비싸다) **조회 시 글 캐시에서 '삭제됨' 이면 거른다**.
- 차단: 조회 시 필터. 차단 목록은 사용자별 Set.
- 수정: 타임라인엔 ID 만 있으므로 글 캐시만 갱신.

## 장애와 규모

| 시나리오 | 대책 |
|---|---|
| 셀럽 글 게시 순간 팬아웃 큐 폭증 | 하이브리드, 큐 소비자 자동 확장, 우선순위(활성 사용자 먼저) |
| 타임라인 Redis 장애 | pull 로 재구성(느리지만 동작), 타임라인은 캐시일 뿐 진실은 글 저장소 |
| 핫 키 (셀럽 글 목록) | 복제 키·로컬 캐시 ([Redis 노트 19](/redis/notes/19-performance-tuning)) |
| 메모리 | 3억 × 200 × 8바이트 ≈ 480GB → 활성 사용자만, 클러스터 샤딩 |

## 예시로 보기 — 이 프로젝트에서

```bash
pnpm exec tsx scripts/run-code-lab.mts system-design sd-feed-fanout
# 팔로워 수 상위 5: 9764, 8359, 6889, 5717, 4899 · 중앙값 4 · 셀럽(>1000) 26명
# 쓰기 시 팬아웃: 타임라인 쓰기 1,357,881회 (게시 1건 최악 9,764회)
# 하이브리드(셀럽 26명만 pull): 쓰기 53,418회 (최악 957회)
```

실험은 Redis LIST(`LPUSH`+`LTRIM`)로 타임라인을 만든다. 리더보드처럼 점수 정렬이 필요하면 ZSET — 실험 [zset-leaderboard](/redis/lab/zset-leaderboard).

## 실습 체크리스트

- [ ] 실험의 셀럽 임계값을 500·5,000 으로 바꾸면 쓰기·조회 명령 수가 어떻게 움직일지 예상하기
- [ ] 비활성 사용자 30% 를 push 에서 빼면 쓰기가 얼마나 줄지 계산하기
- [ ] 글 삭제를 "조회 시 필터" 로 처리할 때 필요한 캐시 구조 적기
- [ ] 랭킹 피드에서 후보 생성 개수와 지연의 관계 설명하기
