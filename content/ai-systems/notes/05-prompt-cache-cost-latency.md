## 프롬프트 구조

```
[시스템] 역할·규칙·출력 형식·금지사항           ← 고정, 길다 → 캐시
[참고 자료] 문서, 스키마, 예시(few-shot)        ← 거의 고정 → 캐시
[대화 이력]                                   ← 점진적으로 늘어남 → 접두어 캐시 적중
[현재 요청] 사용자 입력 + 동적 컨텍스트          ← 매번 다름
```

- 지시는 명확·구체·긍정형("~하라"). 출력 형식은 예시로 보여준다.
- 중요한 규칙은 시스템 프롬프트 **앞**과 **끝**에(중간은 덜 주목).
- 구분자(XML 태그, 마크다운 제목)로 섹션을 분리 — 사용자 입력과 지시의 경계가 인젝션 방어의 기본.
- 버전 관리: 프롬프트 변경은 코드 변경. 평가셋으로 회귀 검사.

## 프롬프트 캐싱

Claude API 는 프롬프트의 **접두어**를 캐시해 두고, 다음 요청에서 같은 접두어가 오면 입력 토큰 비용을 **~90% 할인**하고 지연도 줄인다 (캐시 쓰기는 소폭 추가 비용).

```ts
system: [
  { type: "text", text: LONG_SYSTEM_PROMPT },
  { type: "text", text: PRODUCT_DOCS_20K_TOKENS, cache_control: { type: "ephemeral" } },   // 여기까지 캐시
],
messages: [...history, { role: "user", content: question }],
```

- 캐시는 **접두어 일치**로 동작: 캐시 지점 앞의 내용이 한 글자라도 바뀌면 miss. 동적인 것(날짜, 사용자명)은 캐시 지점 **뒤**에.
- 최소 길이(모델별 1024/2048 토큰) 이상이어야 캐시됨. TTL 5분(연장형 1시간).
- 효과 측정: 응답의 `usage.cache_read_input_tokens / input_tokens`. 대시보드에 캐시 적중률.
- RAG 에서 근거가 매번 달라지면 캐시가 안 된다 → 시스템+예시만 캐시하고 근거는 뒤에.

## 응답 캐시

| 종류 | 키 | 적중 조건 | 위험 |
|---|---|---|---|
| 정확 일치 | SHA(모델+프롬프트 전체) | 완전히 같은 요청 | 거의 없음. temperature>0 이면 "같은 답" 이 아닐 수 있음 |
| **시맨틱** | 질문 임베딩 | 유사도 ≥ 임계값 | **오탐**: 비슷해 보이지만 답이 다른 질문 |
| 부분(툴 결과) | 툴 이름+인자 | 같은 조회 | 신선도 |

시맨틱 캐시 설계:
- 임계값은 도메인별로. FAQ 봇 0.9~0.95, 수치·고유명사 민감 도메인은 사용 금지 또는 엔티티 추출 후 정확 일치.
- 캐시 키에 **사용자/테넌트·권한·언어** 를 포함(남의 답을 돌려주면 안 된다).
- TTL + 문서 갱신 시 무효화(출처 문서 ID 로 역인덱스).
- 적중 응답에 "캐시됨" 표시와 👎 시 캐시 삭제.
- 실험실의 **시맨틱 캐시** 실험이 정확 일치 vs 시맨틱의 적중을 보여준다.

## 토큰과 비용

- 한국어는 영어보다 토큰이 많이 든다(글자당 ~1 토큰). 긴 한국어 문서는 비용이 크다.
- 비용 = 입력 토큰 × 단가 + 출력 토큰 × 단가(보통 입력의 5배) + 캐시 쓰기/읽기.
- 측정: 요청마다 `usage` 를 메트릭·로그로. 기능(feature)·사용자별 집계 → 예산 알림.
- 줄이는 순서: (1) 불필요한 컨텍스트 제거 (2) 프롬프트 캐시 (3) 출력 길이 제한·형식 간결화 (4) 응답 캐시 (5) 작은 모델 라우팅 (6) 배치 API (7) 요약으로 대화 압축.

```ts
// 토큰 예산 기반 트리밍
const budget = 8000 - countTokens(system) - countTokens(question) - 512 /* 출력 여유 */;
let ctx = chunks; while (countTokens(ctx) > budget * 0.7) ctx.pop();        // 근거 먼저
let hist = history; while (countTokens(hist) > budget * 0.3) hist.shift();   // 오래된 대화부터
```

## 지연

```
총 지연 = 네트워크 + 큐 대기 + 프롬프트 처리(입력 토큰 비례) + 첫 토큰(TTFT) + 생성(출력 토큰 × 토큰당 시간)
```

- 긴 프롬프트 → TTFT 증가. 캐시가 TTFT 도 줄인다.
- 출력이 길면 생성 시간이 지배. **스트리밍**으로 체감 지연을 TTFT 수준으로.
- 병렬화: 독립적인 LLM 호출(여러 문서 요약)은 `Promise.all`. 레이트 리밋 고려.
- 투기적 실행: 사용자가 타이핑하는 동안 검색을 미리.
- 타임아웃: 모델 호출 30~60s, 스트리밍은 "N초간 토큰 없음" 으로.
- 측정: TTFT p50/p95 와 총 지연을 분리해 대시보드에 ([LLM 관측](/observability/notes/08-llm-observability)).

## 배치와 오프라인

- 즉시 응답이 필요 없는 작업(야간 분류, 임베딩 생성, 요약)은 **Batch API**: 50% 저렴, 24시간 내.
- 큐 + 워커로 레이트 리밋에 맞춰 흘려보내기 (Kafka/Redis Stream 노트).

## 모델 라우팅 예

```ts
function pickModel(req) {
  if (req.kind === "classify" || req.kind === "extract") return "claude-haiku-5-5";
  if (estimateTokens(req) > 50_000 || req.needsReasoning) return "claude-opus-5-5";
  return "claude-sonnet-5-5";
}
```

라우팅 결정과 결과 품질(피드백)을 함께 기록해 규칙을 조정한다.
