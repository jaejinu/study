## RAG 가 푸는 문제

LLM 은 학습 시점 이후의 정보, 사내 문서, 사용자 데이터를 모른다. 전부 프롬프트에 넣기엔 너무 많고 비싸다. **RAG** 는 질문에 관련된 조각만 찾아 프롬프트에 넣는다. 결과의 품질은 대부분 **검색 품질**이 결정한다 — LLM 은 좋은 근거가 있으면 잘 답한다.

![RAG 파이프라인](/diagrams/rag-pipeline.svg)

## 1. 수집과 전처리

- 원본: Markdown, PDF, HTML, DB 레코드, 티켓, 코드.
- 정제: 보일러플레이트(헤더·푸터·내비) 제거, 표는 Markdown 표로, 코드 블록 보존.
- 메타데이터: 출처 URL, 제목, 섹션 경로, 작성일, 권한(누가 볼 수 있나!), 버전.
- 증분 갱신: 문서 해시로 변경 감지 → 해당 청크만 재인덱싱.

## 2. 청킹 — 가장 과소평가되는 단계

| 전략 | 방법 | 적합 |
|---|---|---|
| 고정 길이 | N 토큰 + 겹침 10~20% | 단순, 베이스라인 |
| **구조 기반** | 제목/문단/코드 블록 경계로 | Markdown, 문서 |
| 의미 기반 | 임베딩 변화가 큰 지점에서 분할 | 긴 서술문 |
| 부모-자식 | 작은 청크로 검색, 부모(섹션 전체)를 프롬프트에 | 정밀 검색 + 충분한 맥락 |
| 문장 창 | 문장 단위 검색, 앞뒤 N문장 포함 | Q&A |

- 너무 작으면 맥락 부족, 너무 크면 노이즈·비용. 200~500 토큰에서 시작.
- 청크마다 **헤더 컨텍스트**를 앞에 붙인다: `"[Redis › 캐싱 패턴 › Cache Stampede] 인기 키가 만료되는…"` — 임베딩이 주제를 알게 된다.
- 표·코드는 쪼개지 않는다.
- 이 프로젝트의 미니 RAG 실험은 `## 섹션` 경계 + 450자 + 50자 겹침.

## 3. 검색

```ts
const qVec = await embed(question);                       // 질의 임베딩 (캐시!)
const dense = await knn(qVec, { k: 20, filter: { tenant } });   // 벡터
const sparse = await bm25(question, { k: 20, filter: { tenant } });  // 키워드
const fused = rrf([dense, sparse]);                       // 순위 융합
const reranked = await rerank(question, fused.slice(0, 20)); // cross-encoder
const picked = diversify(reranked, { perDoc: 2 }).slice(0, 5);
```

- **k**: 최종 4~8개. 후보는 20~50개 뽑아 재정렬.
- **다양성**: 같은 문서에서 N개 제한(MMR), 중복 청크 제거.
- **권한 필터**: 검색 단계에서 반드시 (프롬프트에 들어간 뒤엔 늦다).
- **질의 변환**: 대화 맥락을 반영해 질문을 독립형으로 재작성("그건 왜?" → "Redis 파이프라인이 빠른 이유는?"), 복합 질문은 분해, **HyDE**(LLM 이 가상의 답을 생성해 그 임베딩으로 검색).

## 4. 프롬프트 조립

```
system:
  당신은 사내 기술 문서 도우미다. 아래 <근거> 안의 내용만 사용해 답한다.
  각 문장 끝에 근거 번호 [n] 을 붙인다. 근거에 없는 내용은 "문서에서 찾지 못했습니다" 라고 답한다.
  형식: 핵심 답 2~3문장 → 필요 시 단계 → 출처 목록.

user:
  <근거>
  [1] (redis/08-caching-patterns › Cache Stampede) 인기 키가 만료되는 순간 …
  [2] (redis/09-distributed-lock › 올바른 단일 인스턴스 락) SET lock … NX PX …
  </근거>
  <대화>
  (최근 2턴)
  </대화>
  질문: 캐시가 동시에 만료되어 DB 로 요청이 몰리는 문제를 어떻게 막나요?
```

- 근거는 **구분자와 번호**로 명확히. 사용자 입력과 문서를 섞지 않는다(인젝션 완화).
- 토큰 예산: 시스템(캐시) + 근거(≤ 3k) + 대화(≤ 1k) + 질문. 넘치면 근거부터 자른다(순위 낮은 것).
- 시스템 프롬프트와 긴 고정 지시는 **프롬프트 캐시** 대상.

## 5. 생성과 인용

- 인용 번호를 파싱해 UI 에서 출처 링크로. 인용이 없는 문장은 경고.
- 근거에 없는 질문에 "모른다" 를 허용해야 환각이 준다 (평가셋에 "답 없음" 케이스 포함).
- 구조화 출력이 필요하면 JSON 스키마/툴 호출로 형식을 강제.

## 실패 진단

| 증상 | 어디가 문제 | 확인 |
|---|---|---|
| 관련 문서가 있는데 못 찾음 | 청킹(맥락 분리), 임베딩 모델, k 너무 작음 | recall@k 측정, 청크 내용 눈으로 |
| 찾았는데 답이 틀림 | 프롬프트(근거 사용 지시 약함), 모델, 근거 순서 | 근거 그대로 주고 답하게 해 보기 |
| 고유명사·코드 검색 실패 | 벡터만 사용 | 하이브리드(BM25) |
| 오래된 정보 | 인덱스 갱신 누락 | 문서 버전 메타데이터 |
| 다른 사용자 문서 노출 | 권한 필터 없음 | 검색 단계 필터 |
| 느림 | 임베딩 API, 재정렬 | 질의 임베딩 캐시, 재정렬 후보 수 축소 |

## 평가

- **검색**: recall@k, MRR — (질문, 정답 청크) 쌍 100개.
- **근거성(faithfulness)**: 답의 주장이 근거에 있는가 — LLM judge.
- **답변 정확도**: 기대 답과 비교 — judge 또는 사람.
- **"모른다" 정확도**: 근거 없는 질문에 모른다고 하는 비율.
- 도구: Ragas, DeepEval, 자체 스크립트. CI 에서 돌려 회귀 방지 ([LLM 관측 노트](/observability/notes/08-llm-observability)).

## 고급

- **GraphRAG**: 문서에서 엔티티·관계를 추출해 그래프로. "A 와 B 의 관계" 같은 종합 질문에 강함. 비용 큼.
- **에이전틱 RAG**: 모델이 검색을 툴로 여러 번 호출하며 질문을 좁혀 감. 느리지만 복합 질문에 강함.
- **긴 컨텍스트 vs RAG**: 문서가 수십만 토큰 이하이고 질의가 적으면 통째로 넣고 프롬프트 캐시를 쓰는 게 단순할 수 있다. 수백만 문서면 RAG.
- **다중 모달**: 이미지·표를 캡션/텍스트화해 같은 인덱스에.

## 실전에서는 어디에 쓰이나

> RAG 는 "모델이 우리 회사 문서·최신 정보를 모른다" 는 문제를 파인튜닝 없이 풀 때 등장한다. 실제 품질은 모델보다 청킹·검색·권한 필터·인용 같은 파이프라인 설계에서 갈린다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 사내 위키·규정 Q&A | 직원이 흩어진 문서에서 답 찾기 | 구조 기반 청킹 + 헤더 컨텍스트, 근거 번호 인용 | 사내 검색 엔진 — 답 대신 문서 목록만 준다 |
| 고객센터 상담 보조 | 상담원에게 정책·FAQ 근거와 답 초안 제시 | 하이브리드 검색 + 재정렬, "근거 없으면 모른다" | 고정 FAQ 봇 — 바꿔 말한 질문에 약하다 |
| 개발자 문서·API 레퍼런스 도우미 | 코드·함수명이 섞인 질문 | BM25 + 벡터(RRF), 코드 블록은 쪼개지 않음 | 벡터 검색만 — 식별자에 약하다 |
| 금융·법률·의료 문서 검토 | 답의 근거를 반드시 추적 | 문장마다 인용, 근거성(faithfulness) 평가 | 긴 컨텍스트에 전부 넣기 — 문서가 적을 때만 현실적 |
| 멀티테넌트 SaaS 의 AI 기능 | 다른 고객 문서가 답에 섞이는 사고 | 검색 단계에서 테넌트·권한 메타데이터 필터 | 생성 후 필터 — 이미 프롬프트에 들어간 뒤라 늦다 |

**이럴 땐 안 맞는다**
- 문서가 적고(모델 컨텍스트에 들어가는 정도) 질의도 적은 경우 — 통째로 넣고 프롬프트 캐시를 쓰는 편이 단순하다.
- 지식이 아니라 말투·형식·특정 작업 능력을 바꾸고 싶은 경우 — RAG 로는 잘 안 바뀐다. 프롬프트 예시나 파인튜닝을 검토한다.

**누가 매일 만나나** — AI·백엔드 엔지니어는 청크 크기·k·재정렬을 조정하며 recall@k 를 볼 때, 데이터 엔지니어는 문서 수집·증분 재인덱싱 파이프라인을 운영할 때 만난다.

**면접·실무 단골 질문**
- Q. RAG 답이 틀렸을 때 어디부터 보나 → 검색(recall@k, 청크 내용)부터. 근거를 직접 주고도 틀리면 프롬프트·모델 문제다.
- Q. 권한 필터는 어디서 거나 → 검색 단계. 프롬프트에 들어간 뒤에는 막을 수 없다.
