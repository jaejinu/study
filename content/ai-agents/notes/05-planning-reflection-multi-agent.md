## 출발점 — 그냥 툴 루프

[01 에이전트란](/ai-agents/notes/01-what-is-an-agent) 의 루프는 "모델이 툴을 고르고, 결과를 보고, 또 고른다" 가 전부였다. 짧은 작업에는 이걸로 충분하다. 문제는 **작업이 길어질 때**다.

- 5단계가 필요한데 2단계째에서 길을 잃는다.
- 같은 검색을 표현만 바꿔 반복한다.
- 큰 작업의 일부만 하고 "다 했다" 고 끝낸다.
- 컨텍스트가 툴 결과로 가득 차 앞의 목표를 잊는다([메모리](/ai-agents/notes/04-memory-context)).

아래 패턴들은 모두 이 문제를 **루프에 구조를 더해** 푸는 방법이다. 구조는 공짜가 아니다 — 호출 수와 지연이 늘어난다.

## ReAct — 생각을 행동 사이에 끼운다

```text
Thought: 리밸런스 노트를 찾아야 한다. 키워드는 "컨슈머 그룹 리밸런스".
Action: search_notes({"query": "컨슈머 그룹 리밸런스"})
Observation: [{"title": "컨슈머 그룹·오프셋·리밸런스", "href": "/kafka/notes/03-consumer-groups"}, …]
Thought: 첫 결과가 맞다. 본문에서 리밸런스 절을 확인한다.
Action: get_note({"subject": "kafka", "slug": "03-consumer-groups"})
Observation: …
Thought: 충분하다. 요약한다.
Final: …
```

ReAct(Reason + Act)는 행동 전에 **근거를 적게** 해서 다음 행동의 품질을 올린다. 요즘 모델들은 이걸 내장하고 있다 — 툴 호출 전에 짧은 텍스트(또는 숨겨진 추론)를 내고, 확장 사고(extended thinking)를 툴 사이에 끼우는 모델도 있다. 프롬프트로 강제할 때는 생각이 **사용자에게 보이는지**, 로그에 남는지 정해야 한다.

## 계획 후 실행 (plan-and-execute)

```text
[플래너]  목표 → 단계 목록 (예: 1) 관련 노트 찾기 2) 각 노트의 핵심 추출 3) 비교표 작성)
[실행기]  단계마다 툴 루프 (작은 모델도 가능)
[재계획]  단계 결과가 계획과 어긋나면 남은 단계를 다시 짠다
```

| | ReAct (즉흥) | 계획 후 실행 |
|---|---|---|
| 강점 | 짧은 작업, 결과에 따라 즉시 방향 전환 | 긴 작업, 진행 상황이 눈에 보임, 단계별 병렬화 가능 |
| 약점 | 긴 작업에서 목표 상실 | 계획이 틀리면 끝까지 틀림, 과잉 계획 |
| 비용 | 라운드 수만큼 | + 계획 호출 + 재계획 호출 |
| 관측 | 궤적이 길게 한 줄 | 계획 대비 진행률을 지표로 |

계획을 **사용자에게 보여 주고 승인받는** 변형이 실무에서 강력하다. 코딩 에이전트의 "plan mode" 가 이것이다 — 실행 전에 사람이 방향을 고칠 기회를 준다([승인 게이트](/ai-agents/notes/06-guardrails-permissions-approval)).

## 반성 — 스스로 검토하게 한다

| 형태 | 방법 | 효과가 큰 곳 |
|---|---|---|
| 자기 비평 | 답을 낸 뒤 "이 답의 오류·누락을 찾아라" 로 한 번 더 호출 | 사실 확인, 형식 준수 |
| 평가자-최적화자 | 생성자와 평가자(다른 프롬프트·모델)를 분리해 기준을 넘을 때까지 반복 | 번역·글쓰기·코드 |
| 외부 검증기 | 테스트 실행, 스키마 검증, 링크 체크 등 **결정적 검사** | 코드, 구조화 출력 |

가장 믿을 만한 반성은 **모델이 아니라 검증기**다. "링크를 달았나?" 는 모델에게 묻는 것보다 정규식 한 줄이 정확하다. 실험 `agent-tool-loop-budget` 에서 1.5B 모델은 근거 노트를 3번 다 찾고도 답에 링크를 한 번도 달지 못했다. 이럴 때 반성 호출을 더하는 것보다 **호스트가 툴 결과의 href 를 답 아래에 붙이는** 게 싸고 확실하다. 자기 비평은 같은 모델의 같은 맹점을 공유한다는 것도 기억하자([LLM-as-judge 편향](/mlops/notes/02-eval-datasets-metrics)).

## 다중 에이전트 구성

| 패턴 | 구조 | 쓰는 때 |
|---|---|---|
| **라우터** | 분류기 하나가 질문을 전문 에이전트 중 하나로 보냄 | 질문 유형이 뚜렷이 나뉠 때 |
| **병렬화(섹셔닝)** | 독립 하위 작업을 동시에 실행 후 합침 | 여러 출처 조사, 여러 파일 분석 |
| **투표** | 같은 작업을 여러 번 돌려 다수결 | 분류·판정의 신뢰도 |
| **오케스트레이터-워커** | 오케스트레이터가 하위 작업을 동적으로 만들어 워커(서브에이전트)에 위임, 결과 종합 | 작업 분할을 미리 모를 때 |
| **핸드오프** | 대화 주도권을 다른 에이전트에 넘김(상담원 전환처럼) | 고객 지원, 단계별 전문가 |

서브에이전트의 진짜 이점은 **컨텍스트 격리**다. 워커는 깨끗한 창에서 자기 일만 하고 **요약만** 돌려준다. 오케스트레이터의 창은 작게 유지된다. 대가는 "요약에서 빠진 것은 영영 모른다" — 워커에게 무엇을 돌려줄지 명확히 지시해야 한다.

## 비용과 실패 모드

| 패턴 | 호출 수(대략) | 대표 실패 |
|---|---|---|
| 단일 툴 루프 | 라운드 수 | 헤매기, 같은 툴 반복 |
| ReAct | 라운드 수 (+생각 토큰) | 장황한 생각, 생각과 행동 불일치 |
| 계획 후 실행 | 1 + 단계×라운드 + 재계획 | 틀린 계획 고수, 과잉 분해 |
| 반성 | ×2~3 | 무한 수정, 개선 없는 반복 |
| 오케스트레이터-워커 | 1 + 워커 수×워커 라운드 + 종합 | 중복 작업, 결과 충돌, 토큰 폭증(단일 대비 수 배~10배+) |

**책임 소재**도 문제다. 다중 에이전트에서 오답이 나오면 어느 에이전트가 틀렸는지 찾기 어렵다. 트레이스에 에이전트 이름과 부모-자식 관계를 남기지 않으면 디버깅이 불가능하다([노트 07](/ai-agents/notes/07-eval-observability-cost)).

> **원칙**: 다중 에이전트는 "단일 에이전트로 해 봤는데 컨텍스트가 넘치거나 병렬로 하면 확실히 빨라지는" 경우에만. 복잡도를 올리기 전에 툴 설명·검색 품질·검증기부터 고친다.

## 종료 조건 — 패턴과 상관없이 필요하다

| 종료 | 예 |
|---|---|
| 자연 종료 | 모델이 툴 없이 답함 |
| 예산 | 라운드·토큰·시간·비용 상한 → 강제 마무리 |
| 진척 없음 감지 | 같은 툴+같은 인자 반복, 결과 변화 없음 N 회 |
| 검증 통과 | 테스트·스키마·체크 통과 |
| 사람 | 승인 거부, 사용자 중단 |

실험 `agent-tool-loop-budget` 은 예산 종료를 구현한다. 상한에 닿으면 "툴 예산을 다 썼다. 지금까지 정보로 답하라" 를 툴 없이 한 번 더 부른다.

| 루프 상한 | 툴 호출 | 예산 소진 | 총 토큰 | 총 지연 |
|---|---|---|---|---|
| 1 | 1 | 예 (강제 마무리) | 1,440 | 1,289ms |
| 3 | 1 | 아니오 | 2,057 | 2,835ms |
| 6 | 1 | 아니오 | 2,057 | 2,879ms |

이 질문에서 모델은 툴 1회면 충분하다고 판단해 상한 3·6 의 결과가 같았다. **상한은 평균을 바꾸지 않고 최악을 묶는다** — 무한 루프 한 번이 수백 번의 정상 요청보다 비싸다.

## 병렬 툴 호출 — 가장 싼 구조화

다중 에이전트까지 가지 않아도 **한 라운드에 여러 툴을 동시에** 부르게 하면 라운드 수와 지연이 준다. 최근 모델들은 독립적인 호출을 한 응답에 여러 개(`tool_calls` 배열) 낸다.

```ts
// 호스트: 같은 라운드의 tool_calls 는 서로 독립이라고 보고 동시에 실행
const results = await Promise.all(toolCalls.map((tc) => executeTool(tc.function.name, JSON.parse(tc.function.arguments))));
toolCalls.forEach((tc, i) => messages.push({ role: "tool", tool_call_id: tc.id, content: JSON.stringify(results[i].result) }));
```

| | 순차(라운드 3회) | 병렬(라운드 1회) |
|---|---|---|
| 모델 호출 | 3회 + 답 | 1회 + 답 |
| 지연 | 툴 지연의 합 + 모델 3회 | 가장 느린 툴 + 모델 1회 |
| 위험 | — | 서로 의존하는 호출을 병렬로 내면 순서가 꼬임, 쓰기 툴 동시 실행 |

이 사이트의 `/api/ask` 는 한 라운드의 tool_calls 를 **순서대로** 실행한다. 읽기 툴뿐이라 병렬로 바꿔도 안전하다 — 쓰기 툴이 섞이면 [승인 게이트](/ai-agents/notes/06-guardrails-permissions-approval) 를 거쳐 직렬로.

## 예시로 보기 — 이 프로젝트에서

이 사이트에 다중 에이전트가 필요해지는 시나리오를 설계해 보면:

**"이 주제로 2주 학습 계획을 세워 줘"**

1. **플래너**: 주제의 노트 목록·레벨·선수 관계를 보고 일정 초안(`list_experiments`, 노트 목록 툴).
2. **워커(병렬)**: 날짜별로 해당 노트를 읽고 핵심·퀴즈·실험을 추출(`get_note`). 워커마다 깨끗한 창.
3. **개인화**: `get_progress` 로 이미 읽은 노트·자주 틀리는 노트를 반영해 재계획.
4. **검증기**: 모든 링크가 존재하는가, 하루 학습량이 상한(예: 노트 2편)을 넘지 않는가 — 결정적 코드로.
5. **사람 승인**: 계획을 보여 주고 확정.

반대로 지금의 '묻기'(질문 하나에 근거 찾아 답하기)는 **단일 툴 루프 + 검색 증강**이 맞다. 패턴을 더해도 품질보다 지연이 먼저 늘어난다.

## 실전에서는 어디에 쓰이나

> 계획·반성·다중 에이전트는 단일 툴 루프가 긴 작업에서 길을 잃거나 컨텍스트가 넘칠 때 등장한다. 실무에서는 패턴을 더하기 전에 "단일 에이전트 + 검증기" 로 충분한지부터 확인한다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 코딩 에이전트 | 여러 파일 수정에서 방향을 잃음 | 계획 후 실행 + 사람이 계획 승인, 테스트를 외부 검증기로 | 작은 단위로 나눠 사람이 지시 |
| 리서치·보고서 작성 | 여러 출처 조사 | 오케스트레이터-워커로 출처별 병렬 조사, 워커는 요약만 반환 | 병렬 툴 호출 한 라운드 |
| 고객 지원 센터 | 문의 유형별 전문 처리 | 라우터 → 유형별 에이전트, 필요하면 사람에게 핸드오프 | 단일 에이전트 + 유형별 프롬프트 |
| 번역·마케팅 문구 생성 | 품질 기준 맞추기 | 평가자-최적화자 루프, 상한 횟수 | 결정적 검사(길이·금칙어) 후 사람 검수 |

**이럴 땐 안 맞는다**
- 질문 하나에 근거를 찾아 답하는 일 → 단일 툴 루프 + 검색 증강이면 충분하다. 패턴을 더하면 지연만 는다.
- "링크를 달았나" 같은 확인을 반성 호출로 → 같은 모델의 맹점을 공유한다. 정규식·스키마 같은 결정적 검증기가 싸고 정확하다.

**누가 매일 만나나** — AI 애플리케이션 엔지니어가 긴 작업의 실패 궤적을 분석해 구조를 고를 때, 플랫폼 팀이 다중 에이전트 트레이스에 부모-자식 관계를 남기도록 계측할 때.

**면접·실무 단골 질문**
- Q. 다중 에이전트는 언제 쓰나? → 컨텍스트가 넘치거나 병렬화로 확실히 빨라질 때만. 토큰이 수 배로 늘고 책임 소재가 흐려진다.
- Q. 루프 상한은 무엇을 바꾸나? → 평균이 아니라 최악을 묶는다. 무한 루프 한 번이 정상 요청 수백 번보다 비싸다.
