## 한 줄 정의

> **에이전트 = LLM 이 루프를 돌며, 매 턴 "다음에 무엇을 할지(어떤 툴을 어떤 인자로 부를지, 아니면 끝낼지)" 를 스스로 고르는 프로그램.**

세 부품이 있다.

| 부품 | 역할 | 이 사이트에서 |
|---|---|---|
| **LLM** | 다음 행동 결정 + 최종 답 생성 | OpenAI 호환 모델(키가 없으면 로컬 Ollama `qwen2.5:1.5b`), `/assistant` 는 Claude |
| **툴** | 모델이 세상을 보고(읽기) 바꾸는(쓰기) 함수 | `search_notes`, `get_note`, `list_experiments`, `propose_experiment`, `get_progress` (`src/lib/assistant/tools.ts`) |
| **루프** | 툴 결과를 대화에 다시 넣고 모델을 또 부름. 종료 조건과 예산을 가짐 | `/api/ask` 최대 5회, `/api/assistant` 최대 6회 |

LLM 하나만으로는 "말" 밖에 못 한다. 툴이 붙으면 **보고·행동**할 수 있고, 루프가 붙으면 **결과를 보고 다음 수를 바꿀** 수 있다. 이 세 번째 성질이 에이전트를 단순한 "LLM 호출" 과 가른다.

## 툴 호출 한 번은 메시지로 이렇게 보인다

모델은 툴을 "실행" 하지 않는다. 실행은 늘 **호스트(우리 코드)** 가 한다. 모델은 "이 툴을 이 인자로 불러 달라" 는 **구조화된 요청**을 낼 뿐이다.

```jsonc
// 1) 호스트 → 모델: 질문 + 쓸 수 있는 툴 목록(JSON Schema)
{ "messages": [{ "role": "user", "content": "Redis 파이프라인이 RTT 를 어떻게 줄여?" }],
  "tools": [{ "type": "function", "function": { "name": "search_notes", "description": "학습 노트와 실험을 검색한다 …", "parameters": { … } } }] }

// 2) 모델 → 호스트: 답 대신 tool_call
{ "role": "assistant", "content": "",
  "tool_calls": [{ "id": "call_gj4tu8du", "type": "function",
    "function": { "name": "search_notes", "arguments": "{\"query\":\"Redis 파이프라인\"}" } }] }

// 3) 호스트가 실행하고 결과를 tool 메시지로 붙여 다시 모델을 부름
{ "role": "tool", "tool_call_id": "call_gj4tu8du", "content": "[{\"title\":\"파이프라인 — RTT 를 없애라\",\"href\":\"/redis/notes/06-pipelining\", …}]" }

// 4) 모델 → 호스트: 이번엔 tool_call 없이 최종 답 → 루프 종료
```

위 2) 의 `tool_calls` 는 실험 `agent-mcp-server` 에서 로컬 1.5B 모델이 실제로 낸 것이다(입력 161토큰, 출력 25토큰). **`arguments` 는 JSON "문자열"** 이라 호스트가 파싱해야 하고, 파싱이 실패할 수 있다(작은 모델은 종종 깨진 JSON 을 낸다). 그래서 이 사이트의 루프는 파싱 실패를 빈 객체로 받아 넘긴다.

## 루프의 뼈대 — 이 사이트의 `/api/ask`

```ts
// src/app/api/ask/route.ts (요약)
for (let iter = 0; iter < 5; iter++) {                         // ① 예산: 최대 5 라운드
  const res = await client.chat.completions.create({ model, messages, tools: openaiTools, stream: true });
  // 스트림에서 text 와 tool_calls 조각을 모은다 (tool_calls 는 index 별로 이어 붙여야 한다)
  if (calls.size === 0 || finish === "stop") break;            // ② 종료: 툴 요청이 없으면 끝
  messages.push({ role: "assistant", content: text || null, tool_calls: [...] });
  for (const c of calls) {
    const out = await executeTool(c.name, JSON.parse(c.args));  // ③ 실행은 호스트가
    messages.push({ role: "tool", tool_call_id: c.id, content: JSON.stringify(out.result).slice(0, 16000) }); // ④ 결과를 잘라서 되먹임
  }
}
```

뼈대는 이 네 줄이 전부다. 에이전트 엔지니어링의 대부분은 이 네 줄 각각을 **언제·얼마나·무엇을** 로 다듬는 일이다.

| 결정 | 이 사이트의 선택 | 다른 선택지 |
|---|---|---|
| 예산 | 라운드 5회(ask), 6회(assistant) | 토큰·비용·시간 예산, 툴별 호출 상한 |
| 종료 | 모델이 툴을 안 부르면 | "완료" 툴 호출, 검증기 통과, 사람 승인 |
| 실행 | 서버에서 동기 실행, 부작용 툴은 '제안' 만 | 샌드박스, 비동기 작업 큐, 승인 대기열 |
| 되먹임 | 결과 JSON 을 16,000자로 자름 | 요약, 필드 선택, 결과 저장 후 핸들만 전달 |

## 워크플로 vs 에이전트

"LLM 을 여러 번 부른다" 고 다 에이전트는 아니다. **순서를 누가 정하나** 가 기준이다.

| | 워크플로 (코드가 순서를 정함) | 에이전트 (모델이 순서를 정함) |
|---|---|---|
| 예 | 질문 → 검색 → 상위 5개를 붙여 답 생성 (고정 RAG) | 모델이 검색할지, 무엇으로, 몇 번, 노트 전문을 볼지 고름 |
| 예측 가능성 | 높음. 호출 수·비용·지연이 일정 | 낮음. 질문마다 다르고 꼬리가 길다 |
| 디버깅 | 단계별 입력·출력이 고정 | 궤적(trajectory)을 봐야 한다 |
| 강점 | 정해진 문제에 싸고 빠르고 안정 | 열린 문제, 단계 수를 미리 모를 때 |
| 실패 | 경로 밖 질문에 약함 | 헤매기, 반복 호출, 엉뚱한 툴 |

사실 이 사이트의 '묻기' 는 **둘을 섞었다**. 모델이 툴을 쓰기 전에 코드가 먼저 질문으로 관련 노트를 찾아(`searchSmart(question, 5)`) 컨텍스트에 붙인다. 이게 워크플로 부분이다. 그다음에 모델이 더 필요하면 툴을 부른다. 이게 에이전트 부분이다. 작은 모델이 툴 호출에 실패해도 근거가 이미 들어가 있다 — 실무에서 가장 흔하고 튼튼한 형태다.

> **원칙**: 워크플로로 풀리면 워크플로로. 에이전트는 "단계 수와 순서를 미리 모를 때" 만. Anthropic 의 *Building effective agents* 가 같은 말을 한다 — 가장 단순한 해법부터, 복잡도는 측정으로 정당화될 때만 올린다.

## 자율성의 스펙트럼

에이전트냐 아니냐는 이분법이 아니라 연속이다.

| 단계 | 모델이 정하는 것 | 예 |
|---|---|---|
| 0. 단일 호출 | 답 텍스트 | 요약, 번역 |
| 1. 라우터 | 어느 경로로 갈지 하나 | 질문 분류 → 담당 프롬프트 |
| 2. 툴 1회 | 툴 하나와 인자 | 검색 한 번 후 답 |
| 3. 툴 루프 | 툴 순서·횟수·종료 | 이 사이트의 '묻기' |
| 4. 계획 + 실행 | 하위 목표 분해와 재계획 | 코딩 에이전트, 리서치 에이전트 |
| 5. 다중 에이전트 | 하위 에이전트 생성·위임 | 오케스트레이터-워커 |

단계가 올라갈수록 **능력과 함께 실패 표면도 커진다**. 레벨 3 에서 이미 무한 루프, 툴 남용, 인젝션 경로가 생긴다([가드레일](/ai-agents/notes/06-guardrails-permissions-approval)). 레벨 4·5 는 [계획·반성·다중 에이전트](/ai-agents/notes/05-planning-reflection-multi-agent) 에서 다룬다.

## 에이전트를 쓰지 말아야 할 때

- **답의 경로가 정해져 있다**: 폼 입력 → 검증 → 저장. LLM 이 끼어들 이유가 없다.
- **지연 예산이 작다**: 툴 루프 한 라운드는 모델 호출 1회다. 실험에서 로컬 1.5B 로도 툴 1회 + 답 = 약 2.8초였다. 200ms 안에 답해야 하는 경로에는 맞지 않는다.
- **실수가 비싸고 되돌릴 수 없다**: 송금, 삭제, 배포. 에이전트는 "제안" 까지만, 실행은 사람 또는 결정적 코드가([노트 06](/ai-agents/notes/06-guardrails-permissions-approval)).
- **평가할 방법이 없다**: 궤적이 매번 달라 회귀를 못 잡는다. 평가 하네스 없이 에이전트를 운영하면 모델 교체·프롬프트 수정 때마다 눈을 감고 배포하는 셈이다([노트 07](/ai-agents/notes/07-eval-observability-cost), [MLOps 평가 CI](/mlops/notes/07-eval-ci-prompt-regression)).
- **작은 모델만 쓸 수 있다**: 툴 선택·인자 채우기는 모델 능력에 민감하다. 실험 `agent-tool-loop-budget` 에서 1.5B 모델은 근거를 3번 다 찾고도 답에 링크를 한 번도 달지 못했다.

## 에이전트 = 분산 시스템

툴 호출은 **원격 호출**이다. 그래서 [분산 시스템](/distributed-systems/notes/01-why-hard) 과 [API 설계](/api-design/notes/04-errors-retries-deadlines) 의 모든 문제가 그대로 온다.

| 분산 시스템 문제 | 에이전트에서의 모습 |
|---|---|
| 부분 실패 | 툴은 실패했는데 모델은 성공한 줄 알고 답을 지어냄 |
| 재시도와 멱등 | 모델이 같은 쓰기 툴을 두 번 부름 → 중복 실행 |
| 타임아웃·데드라인 | 느린 툴이 전체 응답을 붙잡음, 사용자는 떠났는데 루프는 계속 |
| 백프레셔 | 툴 결과가 너무 커서 컨텍스트 창을 넘침 |
| 관측 | 어느 턴의 어느 툴이 느렸나 → 트레이스가 없으면 모름 |

## 예시로 보기 — 이 프로젝트에서

이 사이트에는 에이전트가 두 개 있다.

| | `/api/ask` (화면 오른쪽 '묻기') | `/api/assistant` (`/assistant` 페이지) |
|---|---|---|
| 모델 | OpenAI 호환 (gpt-5-mini 또는 Ollama) | Claude |
| 컨텍스트 | 현재 노트 본문 + 드래그한 텍스트 + 검색 증강 | 대화만 |
| 루프 | 최대 5 라운드, 스트리밍 중 tool_calls 조립 | 최대 6 라운드, 프롬프트 캐시 |
| 부작용 | 없음 (`propose_experiment` 는 링크만) | 제안 → 사용자가 승인 버튼 → 실행 → 결과를 모델에 되먹임 |
| 관측 | `ask.chat` span, `gen_ai.*` 속성, 토큰·비용 메트릭 | `assistant.chat` span, 캐시 적중 토큰까지 |

실험 `agent-mcp-server` 는 같은 툴 정의를 MCP 서버로 꺼내 로컬 모델이 쓰게 한다. 결과를 미리 보면 다음과 같다.

| 턴 | 모델의 행동 | 입력/출력 토큰 | 지연 |
|---|---|---|---|
| 1 | `search_notes({"query":"파이프라인 RTT","subject":"redis"})` → MCP `tools/call` | 703 / 32 | 213ms + MCP 44ms |
| 2 | 최종 답 | 1,500 / 400 | 2,609ms |

두 번째 턴의 입력이 703 → 1,500 토큰으로 두 배가 됐다. 툴 결과가 대화에 붙었기 때문이다. **에이전트 비용의 본질은 "라운드마다 누적되는 입력"** 이다([노트 07](/ai-agents/notes/07-eval-observability-cost)). 그리고 1.5B 모델의 최종 답은 같은 문장을 반복하다 출력 상한(400토큰)에 걸렸다 — 작은 모델에서 흔한 반복 퇴화다.
