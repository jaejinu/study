## 모델이 보는 것은 이것뿐이다

모델은 툴 코드를 읽지 않는다. 모델에게 보이는 것은 다음 세 가지다.

1. **이름** — `search_notes`
2. **설명** — 자연어 한 문단
3. **입력 스키마** — JSON Schema (`properties`, `type`, `enum`, `description`, `required`)

그리고 호출 후에는 **결과 문자열**을 본다. 이 네 가지가 툴의 "UI" 다. 사람이 쓰는 API 는 문서를 찾아 읽지만, 모델은 이 몇 줄이 전부다. 그래서 툴 설명은 **API 문서가 아니라 프롬프트**로 써야 한다.

## 실측 — 설명만 바꿨더니 툴이 사라졌다

실험 `agent-tool-loop-budget` 은 실행기(`executeTool`)는 그대로 두고 모델이 보는 정의만 바꾼다.

| | 좋은 설명 (사이트의 실제 정의) | 나쁜 설명 |
|---|---|---|
| 이름 | `search_notes`, `get_note` | `search`, `get` |
| 설명 | "학습 노트와 실험을 검색한다. 개념·방법·비교를 물으면 답하기 전에 먼저 호출해 근거를 찾는다. 결과의 href 를 답변에 출처로 인용한다. 여러 단어는 모두 포함된 것만 찾으므로 핵심 단어 1~3개로 질의한다." | "검색", "가져오기" |
| 파라미터 | `query`(설명·예시 포함), `subject`(enum: 26개 주제), `limit`(1~10) | `q`, `a`, `b` (설명 없음) |

결과(질문: "Kafka 컨슈머 그룹의 리밸런스를 노트에서 찾아 요약하고 링크를 달아 줘", 루프 상한 1·3·6 각각):

| 툴 설명 | 툴 호출 | 근거 노트(`/kafka/notes/03-consumer-groups`)를 찾음 | 평균 토큰 |
|---|---|---|---|
| 좋은 설명 | 3회 중 3회 호출 | 3/3 | 1,851 |
| 나쁜 설명 | **0회** | 0/3 | 331 |

나쁜 설명에서 모델은 툴을 **한 번도 부르지 않고** 근거 없이 바로 답했다. 토큰은 적지만 그건 일을 안 했기 때문이다. "무엇을 하는 툴인지 모르면 모델은 툴을 무시한다" — 실행기가 같아도 설명이 나쁘면 툴은 없는 것과 같다.

## 좋은 툴 설명의 구성

```text
[무엇을 한다]         학습 노트와 실험을 검색한다.
[언제 써라]           사용자가 개념·방법·비교를 물으면 답하기 전에 먼저 호출해 근거를 찾는다.
[결과를 어떻게 써라]  결과의 href 를 답변에 출처로 인용한다.
[함정·제약]           여러 단어는 모두 포함된 것만 찾으므로 핵심 단어 1~3개로 질의한다.
[언제 쓰지 마라]      (예) 노트 본문 전체가 필요하면 get_note 를 쓴다.
```

| 요소 | 왜 필요한가 | 빠지면 생기는 일 |
|---|---|---|
| 동사로 시작하는 목적 | 툴 선택의 1차 단서 | 비슷한 툴끼리 헷갈림 |
| "언제 써라" 트리거 | 모델이 툴을 쓸 타이밍을 앎 | 툴을 안 쓰고 지어냄 (위 실측) |
| 결과 사용법 | 인용·후속 행동 유도 | 결과를 받고도 무시 |
| 함정 | 흔한 실패를 미리 차단 | 문장을 통째로 검색어로 넣음 → 결과 0 |
| 형제 툴과의 경계 | 선택 정확도 | `search_notes` 대신 `get_note` 를 추측 slug 로 호출 |

이 사이트의 `search_notes` 설명에 "핵심 단어 1~3개로" 가 들어간 이유도 실제 사고 때문이다. 작은 모델이 질문 문장을 통째로 넣어 AND 검색 결과가 0건이 됐고, 이후 검색 쪽에도 OR 폴백·조사 제거(`searchSmart`)를 넣었다. **툴 설명과 툴 구현은 함께 고친다**.

## 입력 스키마 설계

```json
{
  "type": "object",
  "properties": {
    "query":   { "type": "string", "description": "검색어 (예: '파이프라인 RTT', '격리 수준', 'MOVED')" },
    "subject": { "type": "string", "description": "주제 id 로 범위 제한 (선택)", "enum": ["redis", "kafka", "…"] },
    "limit":   { "type": "integer", "minimum": 1, "maximum": 10, "default": 6 }
  },
  "required": ["query"]
}
```

| 규칙 | 이유 |
|---|---|
| 자유 문자열 대신 **enum** | 모델이 존재하지 않는 값(`"Redis"`, `"레디스"`)을 지어내지 못함 |
| 파라미터마다 **예시** | 형식을 말로 설명하는 것보다 예시 하나가 정확 |
| 필수는 최소, 나머지는 기본값 | 모델이 채울 것이 적을수록 오류가 줄어듦 |
| **이름은 뜻이 드러나게** | `a`, `b` 는 실측처럼 툴을 버리게 만든다 |
| 중첩 객체·긴 배열 피하기 | 작은 모델일수록 깨진 JSON 을 냄 |
| 서버에서 다시 검증 | 스키마는 "힌트" 일 뿐, 모델은 어긴다 |

마지막 줄이 중요하다. 이 사이트의 `executeTool` 은 스키마와 별개로 `ID = /^[a-z0-9-]+$/` 로 subject·slug 를 다시 검사한다. 모델이 `../../etc/passwd` 같은 값을 넣어도 경로가 되지 않게 — 툴 입력은 **신뢰 경계를 넘는 외부 입력**이다([보안 — 입력 검증](/security/notes/08-web-api-llm-security)).

## 결과 설계 — 작게, 구조화, 다음 행동을 담아

```ts
// search_notes 의 결과: 모델이 바로 인용할 수 있는 필드만, 스니펫은 240자로
return { result: hits.map((h) => ({ kind: h.kind, subject: h.subjectName, title: h.title, href: h.href, snippet: h.snippet.slice(0, 240) })) };
```

| 규칙 | 이유 |
|---|---|
| **필요한 필드만** | 결과는 다음 턴 입력 토큰이 된다. 누적되어 비용·지연을 키움 |
| **식별자·링크 포함** | 후속 툴 호출(`get_note(subject, slug)`)과 인용에 필요 |
| 길이 상한 | `/api/ask` 는 16,000자, 실험은 1,600자로 자름. 작은 모델 컨텍스트를 넘지 않게 |
| 빈 결과도 명시적으로 | `[]` 보다 "결과 없음. 더 짧은 검색어로 다시 시도" 가 낫다 |
| 다음 행동 힌트 | "본문이 필요하면 get_note" 처럼 결과 안에 길을 둔다 |

## 오류는 모델이 고칠 수 있게 돌려준다

툴 오류를 예외로 던져 루프를 끝내면 사용자에게 "실패" 만 남는다. 대신 **모델이 읽고 스스로 고칠 수 있는 문장**으로 돌려준다.

```ts
// propose_experiment: 없는 실험 id 를 넣으면
return { result: `실험 ${subject}/${id} 가 없음. list_experiments 로 확인하라.`, isError: true };
```

- `isError: true` 로 표시하면 Anthropic 툴 결과의 `is_error`, MCP 의 `isError` 로 그대로 전달된다. 모델은 "실패했다" 를 안다.
- 메시지에 **복구 방법**(어떤 툴로 무엇을 확인하라)을 넣는다. 작은 모델도 이 힌트는 꽤 잘 따른다.
- 내부 스택 트레이스·비밀은 넣지 않는다. 툴 결과는 결국 사용자 화면에 새어 나갈 수 있다.
- 일시적 실패(타임아웃·429)는 툴 안에서 재시도하고, 모델에게는 최종 결과만. 재시도를 모델에 맡기면 루프 예산을 태운다([API — 재시도와 데드라인](/api-design/notes/04-errors-retries-deadlines)).

## 읽기와 쓰기를 나누고, 쓰기는 멱등하게

| 종류 | 예 | 설계 |
|---|---|---|
| 읽기 | `search_notes`, `get_note`, `get_progress` | 자유롭게 허용. 캐시 가능 |
| 제안 | `propose_experiment` | 부작용 없음. 호스트가 사람에게 승인 UI 를 보여 줌 |
| 쓰기 | (가상) `reset_progress`, `run_experiment` | 기본 비노출. 승인 게이트·멱등 키·감사 로그 |

모델은 **같은 쓰기 툴을 두 번 부를 수 있다**. 스트리밍이 끊겨 재시도하거나, 결과를 못 보고 또 부르거나. 그래서 쓰기 툴은 [멱등 키](/api-design/notes/01-rest-principles) 를 받거나, "이미 처리됨" 을 반환하게 만든다. 이 사이트가 실험 실행을 모델에게 주지 않고 `propose_experiment` 로 바꾼 것도 같은 이유다 — 실험은 실제 Redis 를 멈추고 Docker 를 조작한다. [가드레일](/ai-agents/notes/06-guardrails-permissions-approval) 에서 더 다룬다.

## 툴 개수와 선택 정확도

툴이 많을수록 모델은 고르기 어렵고, 툴 정의 자체가 매 호출 입력 토큰이 된다(이 사이트의 툴 5개 정의만 약 1,600바이트, 실험의 `tools/list` 응답 1,673바이트).

| 툴 수 | 권장 |
|---|---|
| ~10개 | 그대로. 설명 품질에 집중 |
| 10~30개 | 비슷한 툴 병합(파라미터로 구분), 이름에 네임스페이스(`notes_search`, `lab_list`) |
| 30개 이상 | **툴 검색**(질문으로 관련 툴만 골라 노출), 하위 에이전트로 분할([노트 05](/ai-agents/notes/05-planning-reflection-multi-agent)) |

또 하나: 툴 정의는 **매 요청 앞부분에 고정으로** 들어가므로 프롬프트 캐시의 좋은 후보다. `/api/assistant` 는 마지막 툴 정의에 `cache_control` 을 붙여 시스템 프롬프트 + 툴 정의 전체를 캐시한다([프롬프트 캐시·비용](/ai-systems/notes/05-prompt-cache-cost-latency)).

## 예시로 보기 — 이 프로젝트에서

이 사이트의 툴 정의는 한 곳(`src/lib/assistant/tools.ts` 의 `toolDefinitions`)에 있고 세 곳이 재사용한다.

| 사용처 | 형식 변환 |
|---|---|
| `/api/assistant` (Claude) | 그대로 (`input_schema`) |
| `/api/ask` (OpenAI 호환) | `{ type: "function", function: { name, description, parameters: input_schema } }` 로 변환 |
| 실험 `agent-mcp-server` (MCP) | `{ name, description, inputSchema }` 로 변환해 `tools/list` 로 광고 |

**정의 하나, 어댑터 셋**. 툴 설명을 고치면 세 에이전트가 함께 좋아진다. 반대로 한 곳에서만 고치면 같은 질문에 에이전트마다 다른 행동을 한다.

## 실전에서는 어디에 쓰이나

> 툴 설계는 "모델이 툴을 안 쓰고 지어낸다" 거나 "엉뚱한 인자로 부른다" 는 문제를 고칠 때 등장한다. 모델을 바꾸기 전에 툴 이름·설명·스키마부터 보는 것이 실무의 순서다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 사내 지식 검색 도우미 | 모델이 검색 없이 답을 지어냄 | 설명에 "언제 써라" 트리거와 검색어 요령, 결과에 href | 검색 결과를 항상 미리 붙이는 고정 RAG |
| 커머스 고객 상담 에이전트 | 주문 조회 인자 오류 | 주문 상태를 enum 으로, 서버에서 재검증, 고칠 수 있는 오류 문장 | 상담원이 직접 조회 |
| 사내 운영 도구(배포·재시작) | 같은 쓰기를 두 번 실행 | 읽기·제안·쓰기 분리, 쓰기는 멱등 키 + 승인 | 쓰기 툴을 아예 노출하지 않기 |
| 툴 수십 개인 SaaS 통합 봇 | 툴 선택 정확도 저하, 정의 토큰 증가 | 비슷한 툴 병합, 네임스페이스, 툴 검색으로 일부만 노출 | 영역별 서브에이전트로 분할 |

**이럴 땐 안 맞는다**
- 툴 설명을 API 문서처럼 짧게 → 모델이 툴을 무시한다. 설명은 프롬프트로 쓴다.
- 결과로 원본 JSON 전체를 반환 → 다음 라운드 입력이 폭증한다. 필요한 필드만, 큰 것은 핸들로.

**누가 매일 만나나** — AI 애플리케이션 엔지니어가 툴 정의 PR 을 쓰고 궤적을 보며 설명을 고칠 때, 백엔드 개발자가 기존 내부 API 를 툴로 감쌀 때.

**면접·실무 단골 질문**
- Q. 모델이 툴을 부르지 않는다면 무엇부터 보나? → 이름·설명·파라미터 이름. "언제 써라" 트리거와 예시가 있는지.
- Q. 툴 입력 스키마가 있으면 서버 검증은 필요 없나? → 필요하다. 스키마는 힌트일 뿐이고 툴 입력은 신뢰 경계를 넘는 외부 입력이다.
