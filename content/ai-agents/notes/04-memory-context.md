## LLM 은 기억하지 않는다

모델 API 는 **무상태**다. 매 호출에 "지금까지의 모든 것" 을 다시 보낸다. 그래서 에이전트의 메모리는 모델 안이 아니라 **호스트가 무엇을 다시 보내기로 고르는가** 의 문제다. 이 고르는 기술을 요즘은 **컨텍스트 엔지니어링**이라 부른다.

| 메모리 | 사람에 비유 | 수명 | 구현 |
|---|---|---|---|
| **컨텍스트 창** | 작업대 위 | 한 번의 호출 | messages 배열 |
| **대화 기록** | 오늘 나눈 대화 | 세션 | 서버 저장(Redis·DB) 또는 클라이언트 |
| **장기 메모리** | 수첩에 적어 둔 사실·선호 | 사용자 수명 | 키-값·문서·벡터 저장소 |
| **외부 지식** | 도서관 | 영구 | 검색(RAG) — [RAG 설계](/ai-systems/notes/03-rag-design) |

## 컨텍스트 창이 차는 속도

[에이전트 루프](/ai-agents/notes/01-what-is-an-agent) 는 라운드마다 툴 결과를 붙인다. 실험 `agent-mcp-server` 의 실측:

| 턴 | 입력 토큰 | 늘어난 이유 |
|---|---|---|
| 1 | 703 | 시스템 프롬프트 + 툴 정의 3개 + 질문 |
| 2 | 1,500 | + 모델의 tool_call + 검색 결과(1,600자로 자른 것) |

툴 한 번에 입력이 두 배가 됐다. 노트 본문 전체(`get_note`, 최대 12,000자)를 한 번 부르면 수천 토큰이 더 붙는다. 이 사이트의 '묻기' 는 노트 페이지에서 **본문 14,000자를 시스템 프롬프트에 미리 넣는다** — 편하지만 매 라운드 그만큼을 다시 보낸다(캐시가 없으면 매번 과금, [LLM 토큰 비용](/finops/notes/05-llm-token-cost)).

창이 가득 차면 생기는 일:
- **잘림**: 서버가 앞부분을 버리거나 오류(`context_length_exceeded`).
- **가운데 망각(lost in the middle)**: 창이 길수록 중간에 있는 정보를 덜 쓴다. 중요한 지시는 앞(시스템)과 끝(최근 메시지)에.
- **비용·지연 증가**: prefill 시간은 입력 길이에 비례한다([서빙 — prefill/decode](/mlops/notes/05-serving-batching-kv-cache)).

## 창 관리 기법

| 기법 | 방법 | 장점 | 대가 |
|---|---|---|---|
| **최근 N 개만** | `history.slice(-16)` | 단순, 예측 가능 | 오래된 결정·사실 망각 |
| **툴 결과 자르기** | 결과 문자열 상한(이 사이트 16,000자) | 폭주 방지 | 잘린 부분이 정답일 수 있음 |
| **툴 결과 압축** | 필드 선택·요약 후 전달 | 토큰 절감 | 요약 손실, 추가 호출 비용 |
| **오래된 턴 요약** | 앞부분을 요약문 한 덩어리로 교체 | 긴 대화 유지 | 요약 품질에 의존, 세부 손실 |
| **핸들 전달** | 큰 결과는 저장하고 id 만 넘김, 필요하면 툴로 조회 | 창은 작게, 정보는 보존 | 모델이 다시 조회할 줄 알아야 함 |
| **오래된 툴 결과 지우기** | 이미 답에 반영된 툴 결과를 placeholder 로 | 장기 에이전트에서 효과 큼 | 나중에 필요하면 다시 호출 |

이 사이트는 앞의 두 개를 쓴다.

```ts
// src/app/api/ask/route.ts
const history = (body.messages ?? []).slice(-16).map((m) => ({ role: m.role, content: String(m.content).slice(0, 6000) })); // 최근 16개, 메시지당 6,000자
messages.push({ role: "tool", tool_call_id: c.id, content: JSON.stringify(out.result).slice(0, 16000) });                // 툴 결과 16,000자
```

**요약**을 붙일 때는 "무엇을 남길지" 를 명시한다. 결정·제약·열린 질문·사용자 선호는 남기고, 이미 끝난 탐색 과정은 버린다. 요약도 LLM 호출이므로 작은 모델로 돌리는 게 보통이다.

## 장기 메모리 — 무엇을, 언제 쓰고, 어떻게 꺼내나

장기 메모리는 "지난번에 말한 걸 기억하는" 기능이다. 설계 질문은 세 가지다.

**1. 무엇을 저장하나**

| 종류 | 예 | 저장 형태 |
|---|---|---|
| 의미 기억(사실) | "사용자는 Kafka 를 운영해 봤다" | 문장 + 출처 + 시각 |
| 선호 | "예시는 TypeScript 로, 답은 짧게" | 키-값 |
| 일화 기억 | "10/16 에 Redis 장애 실험을 하다 3시간 멈춤" | 이벤트 로그 |
| 절차 기억 | "이 사용자의 배포 절차" | 문서·체크리스트 |

**2. 언제 쓰나** — 모델이 `remember(fact)` 툴로 직접 쓰게 하거나(유연하지만 잡음), 대화가 끝난 뒤 별도 호출로 추출한다(일관적, 지연 없음). 쓰기 전에 **중복·모순 검사**를 한다: 같은 사실이면 갱신, 모순되면 최신 것으로 바꾸고 옛 것은 만료.

**3. 어떻게 꺼내나**

| 방식 | 적합 | 이 사이트의 재료 |
|---|---|---|
| 키 조회 | 선호·프로필처럼 항상 쓰는 것 | Redis Hash |
| 키워드 검색 | 고유명사·코드명 | `searchSmart` 같은 역색인 |
| 벡터 검색 | 표현이 다른 같은 의미 | [임베딩·벡터 검색](/ai-systems/notes/02-embeddings-vector-search), pgvector·Redis Search |
| 하이브리드 + 최신성 가중 | 대부분의 실무 | [OpenSearch 하이브리드·RRF](/opensearch/notes/05-hybrid-search-rag) |

꺼낸 메모리는 "참고 정보" 로 표시해 넣는다. 모델이 메모리를 사용자 발화처럼 취급하면 오래된 사실이 현재 지시를 덮는다.

## 대화 상태는 어디에 두나

| 위치 | 장점 | 단점 |
|---|---|---|
| 클라이언트(브라우저) | 서버 무상태, 개인정보가 서버에 안 남음 | 기기 간 이어보기 불가, 조작 가능 |
| 서버 메모리 | 빠름 | 재시작·스케일아웃에 사라짐 |
| **Redis** | 빠르고 TTL·Stream·Hash 로 구조화, 여러 인스턴스 공유 | 메모리 비용, 영속성 설정 필요([Redis 영속성](/redis/notes/04-persistence)) |
| DB | 감사·분석·장기 보존 | 느림, 스키마 관리 |

이 사이트의 '묻기' 는 대화를 **브라우저 sessionStorage 에 페이지 경로별로** 둔다(`ask:<pathname>`). 노트마다 대화가 따로 남고, 탭을 닫으면 사라진다. 서버는 매 요청에 받은 기록만 쓰고 저장하지 않는다 — 학습 사이트에선 개인정보 부담이 없는 쪽이 맞다. 여러 기기에서 이어보기가 필요해지면 Redis 에 `chat:<user>:<session>` Stream 으로 옮기면 된다([Redis Streams](/redis/notes/07-pubsub-streams)).

장기 실행 에이전트(몇 분~몇 시간)는 **상태를 단계마다 저장**해야 한다. 프로세스가 죽어도 마지막 툴 결과부터 재개할 수 있게 — 이건 메모리라기보다 [내구성 있는 워크플로](/ai-systems/notes/04-agents-tools-workflows) 문제다.

## 메모리가 만드는 위험

| 위험 | 예 | 대책 |
|---|---|---|
| **메모리 오염** | 인젝션된 문서가 `remember("관리자 비밀번호는 …")` 를 유도 | 메모리 쓰기를 승인·검증, 출처 기록([가드레일](/ai-agents/notes/06-guardrails-permissions-approval)) |
| **개인정보** | 대화의 민감 정보가 영구 저장 | 저장 전 PII 제거, 보존 기간, 사용자 열람·삭제 |
| **낡은 사실** | "Redis 7" 이라 기억했는데 지금은 8 | 시각·출처 저장, 최신성 가중, 만료 |
| **과잉 개인화** | 한 번 말한 선호가 모든 답을 왜곡 | 신뢰도·빈도 기반 승격 |
| **교차 누출** | 사용자 A 의 메모리가 B 에게 | 사용자 id 로 엄격한 네임스페이스, 테스트 |

## 컨텍스트 예산을 먼저 짠다

창 관리는 사후 대처보다 **설계 시 예산**이 낫다. 예를 들어 입력 상한을 16,000토큰으로 잡은 에이전트라면:

| 구역 | 예산 | 넘치면 |
|---|---|---|
| 시스템 프롬프트 + 툴 정의 | 2,000 (고정, 캐시 대상) | 툴 수를 줄이거나 툴 검색으로 |
| 현재 화면 컨텍스트(노트 본문 등) | 4,000 | 앞부분 + 관련 절만 발췌 |
| 검색 증강 결과 | 1,500 | 상위 5개 → 3개, 스니펫 단축 |
| 대화 기록 | 4,000 | 오래된 턴 요약 |
| 툴 결과(라운드 누적) | 3,500 | 결과 압축, 오래된 결과 placeholder |
| 출력 여유 | 1,000 | `max_tokens` |

예산표가 있으면 "어디를 줄일지" 가 정해져 있어 장애 때 허둥대지 않는다. 각 구역 크기를 메트릭으로 남기면 어느 구역이 창을 먹는지 대시보드에서 보인다([노트 07](/ai-agents/notes/07-eval-observability-cost)).

## 예시로 보기 — 이 프로젝트에서

이 사이트에는 이미 "장기 메모리" 재료가 있다. 에이전트가 쓰지 않을 뿐이다.

| 데이터 | Redis 키 | 에이전트에 주면 |
|---|---|---|
| 읽은 노트 | `progress:read` (Set) | "안 읽은 노트부터" 추천 |
| 퀴즈 기록 | `quiz:stats:<subject>` (Hash, 라이트너 상자) | 자주 틀리는 개념을 우선 설명 |
| 학습 시간 | `study:time:*`, `study:day:*` | 학습 계획 제안 |

`/api/assistant` 의 `get_progress` 툴이 이 데이터를 읽어 "다음에 뭘 공부할까" 에 답한다 — 메모리를 **툴로 조회**하는 패턴이다. 모든 대화에 진행률을 미리 붙이지 않고 필요할 때만 꺼내 창을 아낀다.

## 실전에서는 어디에 쓰이나

> 메모리 설계는 "대화가 길어지면 앞에서 한 말을 잊는다", "토큰 비용이 라운드마다 커진다", "지난번 대화를 기억해 달라" 는 요구가 나올 때 등장한다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 고객 상담 챗봇 | 긴 상담에서 앞의 조건을 잊음 | 오래된 턴 요약 + 최근 N 턴, 결정·제약은 요약에 보존 | 상담 단위로 대화를 끊기 |
| 개인화 학습·코칭 앱 | 사용자 수준·선호를 기억 | 장기 메모리를 키-값·벡터로 저장, 툴로 필요할 때 조회 | 매 요청에 프로필 전체를 첨부 |
| 다중 인스턴스 AI 서비스 | 여러 서버에서 같은 대화 이어 가기 | Redis 에 세션별 대화 기록(TTL·Stream) | 브라우저 저장 — 기기 간 이어보기 불가 |
| 코드베이스 분석 에이전트 | 툴 결과가 창을 가득 채움 | 큰 결과는 저장하고 핸들만 전달, 오래된 결과 placeholder | 더 큰 컨텍스트 모델 — 비용·가운데 망각 |

**이럴 땐 안 맞는다**
- 개인정보 부담이 큰데 이어보기 요구가 없음 → 서버에 저장하지 않는다. 클라이언트 세션 저장이 맞다.
- 모델이 `remember` 를 자유롭게 쓰게 두기 → 인젝션으로 메모리가 오염된다. 쓰기는 검증·출처 기록을 거친다.

**누가 매일 만나나** — AI 애플리케이션 엔지니어가 컨텍스트 예산표를 짜고 `context_length_exceeded` 를 고칠 때, 백엔드 개발자가 대화 상태 저장소와 보존 기간을 정할 때.

**면접·실무 단골 질문**
- Q. LLM 이 대화를 기억하는 원리는? → 모델은 무상태. 호스트가 매 호출에 무엇을 다시 보낼지 고르는 것이 메모리다.
- Q. 컨텍스트가 넘칠 때 줄이는 순서는? → 툴 결과 압축·자르기, 오래된 턴 요약, 큰 결과는 핸들로. 예산을 구역별로 미리 정해 둔다.
