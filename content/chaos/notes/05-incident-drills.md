[04 게임데이](/chaos/notes/04-gameday-and-automation) 는 **시스템**의 복원력을 시험했다. 이 노트는 그 반대편, **사람**의 복원력이다. 장애는 결국 누군가 터미널 앞에서 "왜 안 되지?" 를 풀어야 끝난다. 그 능력은 읽어서가 아니라 **반복해서 고쳐 봐야** 는다.

이 사이트의 [장애 대응 훈련](/drills) 은 진짜 고장을 전용 컨테이너(`lab-drill-*`)에 만들고, **증상만** 보여 준다. 원인은 직접 찾고, 내 터미널에서 고친 뒤 "채점" 을 누르면 실제 상태를 확인해 복구 시간을 기록한다.

## 왜 실험과 따로 훈련하나

| | 카오스 실험 | 장애 대응 훈련 |
|---|---|---|
| 질문 | 이 시스템은 이 장애를 견디는가? | 나는 이 장애를 몇 분 안에 고치는가? |
| 결과 | 가설 참/거짓, 지표 표 | 통과/실패, MTTR, 사용한 힌트 수 |
| 원인 | 미리 안다 (내가 주입) | **모른다** (증상만 받는다) |
| 반복 가치 | 회귀 탐지 | 기억 → 습관 → 런북 |

실험을 백 번 돌려도 "502 가 뜨면 무엇부터 본다" 가 손에 붙지는 않는다. 훈련은 원인을 가린 채 시계를 돌린다는 점에서 다르다.

## 사고 순서: 관찰 → 가설 → 검증 → 복구 → 기록

1. **관찰** — 증상을 숫자와 메시지로 바꾼다. "느리다" 가 아니라 "`curl -i` 가 502, 응답 2ms" 처럼. 상태 코드·에러 문자열·사용률이 가장 강한 단서다.
2. **가설** — 경로를 따라 의심 구간을 좁힌다. 클라이언트 → 프록시 → 백엔드 → 저장소. "백엔드 로그에 요청이 하나도 없다" 는 문제가 백엔드 **앞**에 있다는 뜻이다.
3. **검증** — 가설을 한 명령으로 확인한다. 설정을 읽고(`nginx -T`, `config get`), 상태를 센다(`pg_stat_activity`, `df -h`, `kubectl describe`).
4. **복구** — 먼저 **완화**(서비스 살리기), 그다음 **원인 제거**. 둘은 다를 수 있다. 롤백은 원인을 몰라도 되는 가장 강력한 완화다.
5. **기록** — 무엇을 봤고 무엇이 틀렸는지 남긴다. 다음 사람의 런북이 된다 ([온콜과 런북](/sre/notes/04-oncall-runbooks)).

> 흔한 실수: 관찰 없이 재시작부터 한다. 재시작은 증거(메모리 상태, 연결 목록, 로그 버퍼)를 지운다. 재시작 전에 한 번은 찍어 두자.

## 훈련 목록과 배우는 것

| 훈련 | 증상 | 연습하는 기술 |
|---|---|---|
| 502 Bad Gateway | 프록시는 502, 백엔드는 "요청 안 옴" | 경로 추적, 프록시 설정 읽기 ([리버스 프록시](/nginx/notes/02-reverse-proxy-lb)) |
| 캐시 쓰기 전부 실패 | SET 만 에러, GET 은 됨 | 메모리 한도와 축출 정책 ([메모리 진단](/redis/notes/12-memory-performance)) |
| DB 새 연결 불가 | CPU 한가, 연결만 실패 | 연결 수 상한, 유휴 세션 찾기 ([PostgreSQL 운영](/postgres/notes/05-operations)) |
| 로그가 안 쌓임 | 쓰기 실패, 메모리·CPU 정상 | 디스크 사용률, 큰 파일 찾기 ([파일시스템](/os-internals/notes/04-filesystem-io)) |
| 배포가 끝나지 않음 | rollout 진행 중, 옛 버전 응답 | Pod 이벤트 읽기, 롤백 ([운영과 디버깅](/kubernetes/notes/08-ops-debugging)) |

각 훈련에는 힌트가 3개 있다. 1번은 "어디를 볼지", 2번은 "무엇을 확인할지", 3번은 거의 답이다. 힌트를 쓴 횟수도 기록에 남는다 — 같은 훈련을 힌트 없이 통과하는 것이 목표다.

## MTTR 을 쪼개서 보기

MTTR(평균 복구 시간)은 한 숫자지만 안에 여러 구간이 있다.

- **TTD**(탐지): 장애 시작 → 누군가 알게 됨. 알림 품질의 문제다 ([번레이트 알림](/sre/notes/03-burn-rate-alerting)).
- **TTA**(인지·착수): 알림 → 사람이 보기 시작. 온콜 체계의 문제다.
- **TTR**(진단+복구): 착수 → 정상. **훈련이 줄이는 구간이 여기다.**

훈련의 기록은 "시작" 을 누른 순간부터 채점 통과까지이므로 TTR 에 해당한다. 막대 그래프에서 시간이 줄어드는지, 힌트 수가 줄어드는지 함께 보자. 시간은 줄었는데 힌트를 계속 쓴다면 외운 것이지 익힌 것이 아니다.

## 안전하게 망가뜨리는 설계

훈련은 일부러 고장을 만든다. 그래서 **원복이 사람에게 달려 있으면 안 된다.**

- **전용 리소스**: 모든 고장은 `lab-drill-*` 컨테이너나 `drill` 네임스페이스에만 만든다. 학습 앱이 쓰는 Redis 나 클러스터의 다른 워크로드는 건드리지 않는다.
- **데드맨 스위치**: 고장을 주입하기 **직전**에, 제한 시간 뒤 전용 리소스를 지우는 분리된 프로세스(`sh -c "sleep N; docker rm -f …"`)를 띄운다. 브라우저를 닫아도, 서버가 죽어도 시간이 되면 정리된다. 정상적으로 통과·포기하면 그 프로세스를 죽여 해제한다. [04 게임데이](/chaos/notes/04-gameday-and-automation) 의 "중단 조건을 사람이 아니라 시스템에" 와 같은 원리다.
- **항상 보이는 탈출구**: "포기하고 원복" 버튼은 훈련 중 언제나 보인다. 누르면 즉시 지우고 해설을 연다. 포기도 기록에 남지만 실패가 아니라 **학습 데이터**다.
- **채점은 실제 상태로**: 채점기는 사용자의 명령을 보지 않는다. HTTP 응답, `SET` 결과, 새 연결 성공, 파일 쓰기, rollout 상태처럼 **증상이 사라졌는지**만 본다. 다른 방법으로 고쳐도 통과다.

## 종합 과제(캡스톤)

훈련이 한 가지 고장이라면, [종합 과제](/capstone) 는 여러 주제를 한 운영 시나리오로 엮는다.

- **관측 가능한 서비스**: 메트릭 노출 → Prometheus 스크레이프 → SLO 레코딩 룰을 promtool 로 테스트 → 번레이트 알림을 실제 Prometheus 에 적용 → 장애를 주입해 알림 수신 → 포스트모템 작성.
- **카나리 배포**: 클러스터 배포 → Argo Rollouts → AnalysisTemplate → 새 버전 카나리 → 분석 통과 후 승격 → 되돌리기.

각 단계에는 자동 검증기가 있고, 프로젝트를 시작한 **이후**에 일어난 알림·분석 실행만 인정한다. 이전에 우연히 받은 알림으로 통과할 수 없다.

## 실전에서는 어디에 쓰이나

> 시스템이 견디는지와 별개로, 장애는 결국 사람이 고쳐야 끝난다. 신규 인원의 온콜 투입, 런북 점검, 복구 시간 단축 목표가 생길 때 이 노트의 훈련 방식이 등장한다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 사내 플랫폼의 온콜 온보딩 | 신규 인원이 첫 장애에서 무엇부터 볼지 모름 | 원인을 가린 훈련(502·디스크 가득·연결 고갈)을 힌트 단계별로 반복 | 선임 옆에서 섀도 온콜 |
| 커머스 운영팀의 MTTR 개선 | 복구가 왜 느린지 모름 | MTTR 을 TTD(알림)·TTA(온콜 체계)·TTR(진단·복구)로 쪼개 측정 | MTTR 한 숫자만 추적 |
| SaaS 런북 점검 | 런북이 실제로 통하는지 | 런북과 대시보드만으로 훈련 → 막힌 단계를 런북에 추가 | 문서 리뷰만 |
| 라이브 방송·게임 이벤트 대비 | 이벤트 중 장애의 완화 속도 | "완화(롤백) 먼저, 원인 제거는 나중" 순서를 손에 익히기 | 이벤트 기간 코드 프리즈 |
| 사내 교육·실습 환경 | 실습 중 망가뜨린 환경이 방치됨 | 전용 리소스 + 데드맨 스위치 + 실제 상태로 채점 | 매번 환경을 손으로 재생성 |

**이럴 땐 안 맞는다**
- 원인을 미리 알려 주는 훈련: 외우기가 될 뿐 진단 능력이 늘지 않는다 → 증상만 주고 시계를 돌린다.
- 다른 사람이 쓰는 공유 환경(Redis·클러스터)에 고장 주입: 훈련이 실제 장애가 된다 → 전용 컨테이너·네임스페이스로 격리.

**누가 매일 만나나** — 온콜에 들어가는 백엔드 개발자·SRE 가 정기 훈련에서, 팀 리드는 TTD·TTR 추세를 보고 알림과 런북 중 어디에 투자할지 정할 때 만난다.

**면접·실무 단골 질문**
- Q. 장애가 나면 바로 재시작하면 안 되나? → 재시작은 증거(메모리 상태, 연결 목록, 로그 버퍼)를 지운다. 한 번 기록해 두고 완화한다.
- Q. MTTR 을 줄이려면 어디부터 보나? → TTD·TTA·TTR 로 쪼개 가장 긴 구간부터 — 알림 품질, 온콜 체계, 진단 숙련도.

## 체크리스트
