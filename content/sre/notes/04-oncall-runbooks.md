## 온콜은 무엇을 위한 것인가

온콜은 "밤에 깨어 있는 사람" 이 아니라 **SLO 를 지키기 위한 마지막 수동 안전장치**다. 자동화가 못 잡는 것을 사람이 잡고, 그 경험을 다음 자동화의 재료로 돌려보낸다. 그러므로 온콜의 설계 목표는 두 가지: **대응 시간**(MTTA/MTTR) 을 SLO 가 요구하는 수준으로, **사람의 부하**를 지속 가능한 수준으로.

### 건강한 온콜의 숫자 (구글 기준)

| 지표 | 기준 | 넘으면 |
|---|---|---|
| 교대(12h)당 페이지 | ≤ 2건 | 알림 튜닝·근본 원인 제거가 1순위 |
| 온콜 시간 비율 | 25% 이하 (최소 8명 로테이션 ≈ 분기당 1~2주) | 인원 충원 또는 범위 축소 |
| 토일 비율 | ≤ 50% | [01](/sre/notes/01-sre-principles-toil) |
| 보상 | 시간 외 대응은 휴가·수당으로 | 없으면 번아웃·이직 |
| 페이지 → 확인(ack) | 5분 이내 (SLO 99.9% 기준) | 에스컬레이션 |

페이지 2건이라는 상한은 경험칙이 아니라 **인지 부하**에서 온다. 한 사건을 제대로 다루는 데(확인·조사·완화·기록) 4~6시간이 든다. 그 이상이면 사건들을 대충 처리하게 되고, 그게 다음 사건을 만든다.

## 로테이션 설계

```
1차(primary)   : 페이지를 받고 5분 안에 ack, 완화 시도
2차(secondary) : 1차가 15분 안에 ack 안 하면 자동 에스컬레이션, 복잡한 사건의 짝
매니저/리드     : 2차도 30분 무응답 또는 심각도 1 이면
```

- **팔로우더선(follow-the-sun)**: 시간대가 다른 팀이 낮 시간만 맡는다. 밤 페이지가 사라진다. 조건: 두 팀의 역량이 대등하고 핸드오프가 문서화돼 있을 것.
- **핸드오프**: 교대 시작 때 15분 — 열린 사건, 이번 주 배포, 침묵(silence) 중인 알림, 알려진 취약점. 글로 남긴다(채널에 고정).
- **온콜 전 체크**: 노트북·VPN·대시보드 접근·런북 위치. "로그인이 안 돼서 30분" 은 흔한 포스트모템 항목이다.
- **온콜 중 개발 금지**는 아니지만, 페이지 2건 넘는 날은 당연히 개발이 안 된다. 그걸 계획에 반영한다(스프린트에서 온콜 인원 제외).

## 에스컬레이션 정책

```
심각도 정의
  SEV1: 사용자 다수 영향, SLO 버짓 급속 소진(번레이트 > 14.4) → 즉시 페이지, 사고 지휘관 지정, 상태 페이지
  SEV2: 일부 기능 저하, 번레이트 6 → 페이지, 1시간 내 완화 목표
  SEV3: 버짓 느린 소진, 중복성 상실(복제본 하나 죽음) → 티켓, 업무 시간
  SEV4: 개선 요청 → 백로그

에스컬레이션 타임아웃
  페이지 → 5분 무응답 → 재알림 → 10분 → 2차 → 15분 → 리드
```

Alertmanager 로 흉내 내기: `repeat_interval` 이 재알림, `routes` 의 `continue: true` 로 같은 알림을 두 수신자에게, `group_wait` 로 2차 지연은 흉내 어렵지만(Alertmanager 는 에스컬레이션 개념이 없다) PagerDuty/Opsgenie 가 그 역할이다. 이 프로젝트의 [alertmanager.yml](/observability/notes/09-alerting-pipeline) 은 severity 로 수신자를 나눈다 — critical 은 `group_wait: 0s`, `repeat_interval: 1h` 가 "5분 무응답 시 재알림" 의 느슨한 버전이다.

## 페이지 피로(alert fatigue)와 알림 품질

알림이 많으면 사람은 **무시하는 법을 배운다**. 그 순간 진짜 장애도 무시된다. 알림 품질을 매주 측정한다:

| 지표 | 계산 | 목표 |
|---|---|---|
| 정밀도 | 조치가 필요했던 페이지 / 전체 페이지 | > 80% |
| 조치율 | 런북대로 뭔가 한 페이지 비율 | 낮으면 그 알림은 티켓으로 강등 |
| 중복률 | 같은 원인으로 여러 번 울린 비율 | 그룹화·억제로 해결 |
| 자동 해결률 | 사람이 손대기 전에 resolved 된 비율 | 높으면 `for` 를 늘리거나 자동 복구에 맡김 |
| 야간 비율 | 22~07시 페이지 비율 | 야간 페이지는 2배로 센다 |

이 프로젝트에서 `study_alerts_received_total{alertname, status}` 로 알림별 firing/resolved 수를 셀 수 있다. `resolved / firing` 이 1에 가깝고 지속 시간이 짧은 알림은 **플래핑** — `for` 를 늘리거나 [번레이트](/sre/notes/03-burn-rate-alerting)로 바꾼다.

### 알림을 줄이는 순서

1. **원인 제거**(가장 좋음): 메모리 알림 → maxmemory-policy 로 축출 자동화.
2. **자동 복구**: Pod 재시작 알림 → liveness probe 가 이미 한다, 알림은 "5분에 3회 이상" 만.
3. **증상 기반으로 통합**: 디스크·CPU·메모리 알림 3개 → SLO 번레이트 1개.
4. **강등**: 페이지 → 티켓 → 대시보드.
5. **삭제**: 6개월간 조치 0 인 알림은 지운다. 두렵다면 먼저 `severity: info` 로.

## 런북 — 좋은 형식

런북은 **새벽 3시의 나**(잠에서 깬, 맥락 없는, 실수하기 쉬운)를 위한 문서다. 형식:

```markdown
# RedisDown
## 증상
redis_up == 0 이 30초 이상. 앱의 진행률 저장·실험 실행이 실패한다 (노트 읽기는 된다).
## 심각도 · SLO 영향
SEV2. redis-connectivity SLO 버짓을 분당 0.14% 소진.
## 확인 (2분)
1. docker inspect -f '{{.State.Status}}' study-redis      → running 이 아니면 §조치 A
2. docker exec study-redis redis-cli ping                 → PONG 이 아니면 §조치 B (hang)
3. docker logs --tail 50 study-redis                      → OOM / "MISCONF" / "Can't save"
4. Grafana → Redis 메모리 패널: maxmemory 근접?
## 조치
A. 컨테이너 중지됨: docker compose up -d redis. 30초 내 redis_up=1 확인.
B. 응답 없음(pause/hang): docker unpause study-redis 또는 docker restart study-redis.
C. MISCONF(RDB 저장 실패): 디스크 확인 → 임시로 config set stop-writes-on-bgsave-error no → 포스트모템.
## 에스컬레이션
15분 내 복구 안 되면 2차. 데이터 유실 의심(AOF 손상)이면 즉시 리드.
## 끝난 뒤
- resolved 알림 확인, 침묵 해제
- 포스트모템 필요? (SEV1·2 는 항상, 또는 같은 원인 2회째)
- 이 런북이 틀렸던 부분 바로 수정 (PR)
```

### 좋은 런북의 조건

- **알림 → 런북 1:1**. `runbook_url` annotation 으로 링크(이 프로젝트 규칙은 이미 그렇게 돼 있다).
- **명령을 복붙할 수 있게**. "로그를 확인한다" 가 아니라 정확한 명령.
- **판단 분기가 적게**. 세 갈래 넘으면 런북이 아니라 교육 자료다.
- **최근 실행 날짜**가 있다. 6개월 안 쓴 런북은 틀렸을 확률이 높다.
- **자동화 후보 표시**. "이 §조치 A 는 스크립트로 가능" 처럼 적어 두면 토일 목록이 된다.

### 나쁜 런북의 징후

"담당자에게 물어본다", "상황에 따라", "보통은 ~하면 된다", 스크린샷만 있는 UI 클릭 절차, 링크가 깨진 대시보드, 런북이 위키 깊은 곳에.

## 런북 → 자동화 승격 경로

```
런북(문서) → 스크립트(pnpm redis:restart) → 알림에 "실행" 버튼(챗옵스)
          → 조건부 자동 실행(3회 연속 실패 시 재시작) → 자가 치유 설계(liveness probe)
```

승격 기준: 같은 런북을 **월 3회 이상** 그대로 실행했다면 스크립트로, 스크립트를 **6개월간 수정 없이** 썼다면 자동 실행으로. 자동 실행에는 반드시 **서킷**(10분에 3회 넘으면 멈추고 사람 호출)을 둔다 — 자동 재시작 루프가 장애를 키우는 사례는 흔하다.

## 예시로 보기 — 이 프로젝트의 온콜 시뮬레이션

실제 온콜은 없지만 흐름을 재현할 수 있다:

1. 알림 규칙의 `runbook_url` 이 노트로 연결된다(RedisDown → Redis 운영 노트). SLO 알림은 이 노트로.
2. 웹훅 수신(`/api/alerts`)이 "페이지 도착" 이고, [관측성 대시보드](/observability)의 최근 알림 카드가 "ack 화면".
3. 실험 `sre-postmortem-timeline` 이 알림·로그·트레이스를 한 타임라인으로 묶는다 — 온콜이 사건 중에 보는 **단일 화면**이 이것이어야 한다.
4. 핸드오프 노트를 흉내 내려면 `logs/app.jsonl` 의 마지막 1시간 경고·에러 요약을 자동 생성하는 스크립트를 만든다(토일 자동화 연습).

## 실전에서는 어디에 쓰이나

> 서비스가 24시간 돌아가야 하는데 사람은 지치지 않아야 할 때 온콜 로테이션·에스컬레이션·런북이 등장한다. 핵심은 "누가, 몇 분 안에, 무엇을 보고, 무엇을 하나" 를 미리 정해 두는 것이다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 글로벌 SaaS | 야간 페이지로 인한 번아웃 | 시간대가 다른 팀 간 팔로우더선 로테이션과 문서화된 핸드오프 | 한 팀 24시간 온콜은 이직을 부른다 |
| 핀테크 결제 운영 | 1차가 못 받을 때 대응 공백 | 페이징 도구(PagerDuty·Opsgenie 등)로 5분·15분 자동 에스컬레이션 | Alertmanager 단독은 에스컬레이션 개념이 없다 |
| 커머스 주문 서비스 | 새벽 3시 맥락 없는 대응 실수 | 알림마다 `runbook_url`, 복붙 가능한 확인·조치 명령 | 위키 깊은 곳의 서술형 문서 |
| 사내 플랫폼 (쿠버네티스 운영) | 반복되는 같은 조치 | 월 3회 이상 실행한 런북을 스크립트 → 챗옵스 버튼 → 서킷 달린 자동 실행으로 승격 | 계속 손으로 실행 |
| 공공 서비스 운영 | 알림이 많아 진짜 장애를 무시 | 정밀도·조치율·중복률을 주간 측정해 강등·삭제 | 알림을 계속 추가만 하기 |

**이럴 땐 안 맞는다**
- 서비스 담당자가 한두 명뿐인 초기 팀: 정식 로테이션을 짤 인원이 없다. 업무 시간 대응 + 야간엔 자동 재시작과 critical 한 개만 둔다.
- 판단 분기가 많은 복잡한 사고: 런북으로 다 담을 수 없다. 런북은 첫 확인까지, 이후는 사고 지휘 체계로 넘긴다.

**누가 매일 만나나** — SRE 와 서비스 백엔드 개발자는 온콜 교대 핸드오프 때, 플랫폼 엔지니어는 알림 규칙에 런북 링크를 붙이고 페이징 도구 라우팅을 설정할 때 만난다.

**면접·실무 단골 질문**
- Q. 알림 피로를 어떻게 줄이나? → 원인 제거 → 자동 복구 → 증상 기반 통합 → 강등 → 삭제 순서로, 정밀도를 측정하면서.
- Q. 좋은 런북의 조건은? → 알림과 1:1, 명령 복붙 가능, 분기 적음, 최근 실행 날짜와 에스컬레이션 기준이 있다.
