## 세 글자의 차이

| | 뜻 | 예 | 누가 정하나 |
|---|---|---|---|
| **SLI** (Indicator) | 서비스 수준을 **재는 지표**. 비율(0~1) 로 표현 | "성공 응답 / 전체 응답" | 엔지니어 |
| **SLO** (Objective) | SLI 의 **목표값** + 기간 | "30일 동안 99.9%" | 제품 + 엔지니어 |
| **SLA** (Agreement) | SLO 를 못 지켰을 때의 **계약상 결과** | "99.5% 미만이면 요금 10% 환불" | 비즈니스·법무 |

SLA 는 SLO 보다 **느슨**해야 한다(내부 목표 99.9%, 외부 약속 99.5%). SLO 를 어기는 것은 팀의 신호이고, SLA 를 어기는 것은 돈이다.

## 좋은 SLI 고르기

SLI 는 **사용자가 느끼는 것**을 재야 한다. CPU 사용률은 SLI 가 아니다 — 사용자는 CPU 를 모른다. 구글의 SLI 메뉴:

| 사용자 여정 유형 | SLI 후보 |
|---|---|
| 요청/응답 (웹·API) | **가용성**(성공 비율), **지연**(임계 이하 비율), 품질(저하 모드 비율) |
| 데이터 처리 (파이프라인) | **신선도**(최신 데이터 나이), 정확성, 커버리지, 처리량 |
| 저장소 | 내구성(유실 없음), 가용성 |

규칙:
1. **사용자에 가까운 곳에서 잰다.** 로드밸런서·게이트웨이가 앱 내부보다 낫다(앱이 죽으면 앱 메트릭도 죽는다). 가장 좋은 건 클라이언트 측 RUM, 하지만 노이즈가 많다.
2. **SLI 는 2~5개면 충분하다.** 많으면 아무도 안 본다. 여정당 가용성 + 지연 하나씩.
3. **비율로 표현한다.** `좋은 이벤트 / 유효한 이벤트`. "유효" 가 중요하다 — 잘못된 요청(4xx 중 클라이언트 잘못)은 분모에서 뺀다. 봇·헬스체크도 뺀다.
4. **명세를 적는다.** "지연 SLI = `/api/*` 에 대한 GET 요청 중 응답이 300ms 이내에 완료된 비율, 로드밸런서 기준, 5xx 는 실패, 429 는 제외".

### 지연은 백분위수가 아니라 "임계 이하 비율" 로

"p99 < 300ms" 는 직관적이지만 SLO 로는 나쁘다: 백분위수는 **집계가 안 된다**(여러 인스턴스의 p99 를 평균 낼 수 없다), 창 크기에 민감하다, 에러 버짓과 연결이 안 된다. 대신:

```
지연 SLI = count(latency ≤ 300ms) / count(all)     → 목표 99%
```

이러면 "100 요청 중 1개는 300ms 를 넘어도 된다" 라는 **버짓**이 생긴다. Prometheus 히스토그램이라면 `le="0.3"` 버킷이 바로 분자다 — 그래서 **버킷 경계를 SLO 임계에 맞춰** 둬야 한다(이 앱의 `study_action_duration_seconds` 버킷 0.25/0.5 는 그 의도).

## 요청 기반 vs 윈도우 기반

| | 요청 기반 (request-based) | 윈도우 기반 (window-based / time-based) |
|---|---|---|
| 정의 | 좋은 요청 / 전체 요청 | 좋은 시간 창 / 전체 시간 창 (예: 1분 창에서 성공률 ≥ 95% 면 "좋은 분") |
| 장점 | 직관적, 트래픽 가중(바쁠 때 장애가 더 아프다) | 트래픽이 적은 시간(새벽)의 장애도 공평하게 반영, 가동률 느낌 |
| 단점 | 새벽 1시간 전면 장애가 낮 5분 장애보다 작게 보일 수 있음 | 창 크기·임계 두 파라미터가 더 생김, 요청 수 적을 때 노이즈 |
| 쓰는 곳 | 대부분의 API | "항상 켜져 있어야 하는" 것(DB 연결, 외부 의존성) |

이 프로젝트에서: 앱 서버 액션은 요청 기반(`study_action_duration_seconds_count{outcome}`), **Redis 연결은 윈도우 기반**(`study_redis_up` 게이지의 `avg_over_time`). 실험 `sre-slo-recording-rules` 가 둘 다 만든다.

## PromQL 로 쓰기 — 레코딩 룰

SLI 는 대시보드·알림·리포트 세 곳에서 똑같이 계산돼야 한다. 같은 식을 세 번 쓰면 언젠가 하나가 달라진다. **레코딩 룰**로 한 번 정의하고 이름으로 쓴다. 이름 규칙은 `level:metric:operations`:

```yaml
groups:
  - name: slo.study-app
    interval: 15s
    rules:
      # 가용성 SLI (요청 기반): 서버 액션 성공 비율, 5m 창
      - record: slo:action_availability:ratio_rate5m
        expr: |
          sum(rate(study_action_duration_seconds_count{outcome!="error"}[5m]))
          / sum(rate(study_action_duration_seconds_count[5m]))
      # 지연 SLI: 250ms 이내 비율
      - record: slo:action_latency_good:ratio_rate5m
        expr: |
          sum(rate(study_action_duration_seconds_bucket{le="0.25"}[5m]))
          / sum(rate(study_action_duration_seconds_count[5m]))
      # Redis 연결 가용성 (윈도우 기반): 5m 동안 연결돼 있던 비율
      # redis_up 은 Redis 가 hang 이면 0 이 아니라 '사라진다' → 스크레이프 성공 여부(up)로 빈자리를 채운다 (아래 함정 참고)
      - record: slo:redis_connectivity:ratio_5m
        expr: avg_over_time((redis_up * 1 or up{job="redis"} * 1)[5m:])
      # 에러율 (1 - SLI), 번레이트 계산의 재료
      - record: slo:action_error:ratio_rate5m
        expr: 1 - slo:action_availability:ratio_rate5m
```

여러 창(5m, 30m, 1h, 6h, 1d, 3d)을 미리 만들어 두면 [번레이트 알림](/sre/notes/03-burn-rate-alerting)이 그걸 쓴다. 창이 길수록 `rate` 비용이 크니 레코딩이 더 중요해진다.

> 함정 1 — **나쁜 상태가 '0' 이 아니라 '없음' 으로 나타난다.** 이 프로젝트에서 실제로 겪었다: `docker pause study-redis`(응답 없는 hang)를 걸자 redis_exporter 의 스크레이프가 타임아웃되어 `redis_up` 이 0 이 되는 대신 **시계열 자체가 사라졌다**(`up{job="redis"}` 만 0). `avg_over_time(redis_up[5m])` 는 빈 구간을 건너뛰고 남은 1 들만 평균하므로 **장애 중에도 SLI 가 100%** 로 보인다. 해법은 `(redis_up * 1 or up{job="redis"} * 1)` — 스크레이프가 실패하면 up 의 0 이 그 자리를 채운다. `* 1` 은 `__name__` 을 지우는 장치다(안 지우면 서브쿼리 창 안에 두 이름이 섞여 "vector cannot contain metrics with the same labelset" 에러). 앱 쪽 `study_redis_up` 도 같은 이유로 사라졌다 — 앱의 `/api/metrics` 자체가 Redis 핑을 기다리며 멈췄기 때문이다.

> 함정 2: `rate()` 의 분모가 0 이면(요청 없음) 결과가 NaN 이다. 트래픽이 없는 시간엔 SLI 가 정의되지 않는다 — 윈도우 기반이 필요한 이유 중 하나이고, 알림에서 `or vector(1)` 같은 처리가 필요한 이유다.

## 에러 버짓

```
에러 버짓 = 1 - SLO
99.9% / 30일 → 0.1% × 43,200분 = 43.2분의 "허용된 실패"
99.9% / 30일, 100만 요청 → 1,000개의 실패 요청
```

| SLO | 연간 허용 다운 | 월간 | 주간 | 하루 |
|---|---|---|---|---|
| 99% | 3.65일 | 7.3시간 | 1.68시간 | 14.4분 |
| 99.9% | 8.76시간 | 43.8분 | 10.1분 | 1.44분 |
| 99.95% | 4.38시간 | 21.9분 | 5분 | 43초 |
| 99.99% | 52.6분 | 4.4분 | 1분 | 8.6초 |

99.99% 면 **사람이 대응할 수 없다**(알림이 울리고 노트북을 여는 데 5분이 걸린다). 그 수준은 자동 페일오버·다중 리전·자동 롤백이 전제다. SLO 를 정할 때 "우리가 그 속도로 대응할 수 있나" 를 먼저 물어야 한다.

### 버짓 정책 — 다 쓰면 무엇이 일어나나

정책이 없는 SLO 는 장식이다. 문서로 합의해 둔다:

```
에러 버짓 정책 (study-app, SLO 99.9%/30d)
1. 버짓 잔여 > 50%: 평소대로. 카나리 비율 25%→100% 를 10분 안에.
2. 버짓 잔여 10~50%: 카나리 단계를 두 배로 늘린다. 금요일 배포 금지.
3. 버짓 소진(< 0%): 기능 배포 동결. 신뢰성 작업(포스트모템 액션, 테스트, 자동화)만.
   해제 조건: 30일 창에서 버짓이 양수로 돌아올 때.
4. 예외: 보안 패치, 버짓 소진의 원인을 고치는 변경.
5. 분쟁: 제품 리드 + SRE 리드가 결정, 기록을 남긴다.
```

버짓이 **남아돈다**면 그것도 신호다: SLO 가 너무 느슨하거나(사용자는 더 기대한다), 너무 보수적으로 배포하고 있다(더 빨리 가도 된다). 카오스 실험으로 버짓을 **일부러 쓰는** 것도 합리적이다 — [장애 실험실](/chaos/notes/01-chaos-principles).

## SLO 를 정하는 절차

1. **사용자 여정**을 고른다("노트 읽기", "실험 실행", "퀴즈 답 저장").
2. 여정마다 SLI 를 명세한다(무엇이 성공인가, 어디서 재나, 무엇을 제외하나).
3. **현재 성능을 측정**한다(2~4주). 목표는 현실에서 출발한다 — 99.5% 인 서비스에 99.99% 를 걸면 첫 날 버짓이 터진다.
4. 사용자 기대와 비용을 놓고 목표를 정한다. "약간 공격적" 이 좋다.
5. 버짓 정책을 합의하고 문서화한다.
6. 대시보드(현재 SLI, 버짓 잔여, 번레이트)와 알림을 만든다.
7. 분기마다 **SLO 리뷰**: 버짓이 늘 남으면 조이고, 늘 터지면 현실화하거나 투자한다.

## 예시로 보기 — 이 프로젝트의 SLO 초안

| 여정 | SLI | 소스 | SLO (30일) | 비고 |
|---|---|---|---|---|
| 서버 액션(읽음·체크·퀴즈 저장) 성공 | `outcome!="error"` 비율 | `study_action_duration_seconds_count` | 99.5% | Redis 꺼짐이 주 원인 → 윈도우 SLI 와 상관 |
| 서버 액션 빠름 | ≤ 250ms 비율 | 같은 히스토그램 `le="0.25"` | 99% | 로컬이라 여유, 운영이면 95% 부터 |
| 앱 ↔ Redis 연결 | `avg_over_time((redis_up * 1 or up{job="redis"} * 1)[…:])` | exporter 게이지 + 스크레이프 성공 | 99.9% | 윈도우 기반, 함정 1 참고 |
| 실험 실행 성공 | `outcome="ok"` 비율 | `study_experiment_runs_total` | — | 실험은 "실패가 정보" 라 SLO 대상 아님. **유효 이벤트에서 제외**하는 예 |
| 알림 전달 | Watchdog 수신 간격 ≤ 2분 | `study_alerts_received_total{alertname="Watchdog"}` | 99% | 메타 모니터링 |

실험 `sre-slo-recording-rules` 는 이 표의 첫 세 줄을 레코딩 룰로 만들어 `promtool check rules` 로 검증하고, Prometheus 에 실제 질의해 현재 SLI 값과 30일 버짓 잔여를 계산한다. 트래픽이 없으면 요청 기반 SLI 가 NaN 이 되는 것을 직접 보게 된다 — 그래서 실험이 먼저 서버 액션을 몇 번 호출한다.

```promql
# 30일 버짓 잔여 비율 (요청 기반)
1 - (1 - sum(increase(study_action_duration_seconds_count{outcome!="error"}[30d]))
         / sum(increase(study_action_duration_seconds_count[30d]))) / (1 - 0.995)
```

## 실습 체크리스트

- [ ] 실험 `sre-slo-recording-rules` 를 돌리고, 출력된 현재 SLI 가 표의 SLO 를 만족하는지 보기
- [ ] 앱에서 노트를 몇 번 "읽음" 토글한 뒤(서버 액션 발생) 요청 기반 SLI 가 NaN 에서 숫자로 바뀌는 것 확인
- [ ] `observability/alert-rules.yml` 에 레코딩 룰 그룹을 추가하고 Grafana 에 "SLI · 버짓 잔여 · 번레이트" 패널 3개 만들기
- [ ] 본인 서비스의 사용자 여정 하나를 골라 SLI 명세(성공 정의·측정 위치·제외 항목)를 한 문단으로 적기
- [ ] 에러 버짓 정책 초안을 팀(또는 자신)과 합의하고 저장소에 커밋
