## SRE 는 "운영을 소프트웨어 엔지니어링으로"

구글이 2003년에 만든 직군 **Site Reliability Engineering** 의 정의는 한 문장이다: *"소프트웨어 엔지니어에게 운영 팀을 설계하라고 하면 나오는 것"*. 서버를 손으로 만지던 시스템 관리자(sysadmin) 모델은 서비스가 커질수록 **사람 수가 트래픽에 비례**해 늘어난다. SRE 는 그 비례를 끊는다 — 반복되는 운영 작업을 코드로 바꾸고, 신뢰성을 **측정 가능한 목표(SLO)** 로 정의해 "얼마나 안정적이어야 하나" 를 느낌이 아니라 숫자로 결정한다.

### DevOps 와의 관계

| | DevOps | SRE |
|---|---|---|
| 정체 | 문화·철학(개발과 운영의 벽 허물기, 자동화, 측정, 공유) | 그 철학의 **구체적 구현** 한 가지 |
| 핵심 질문 | "어떻게 더 자주, 안전하게 배포하나" | "얼마나 신뢰성이 필요하고, 그 안에서 얼마나 빨리 바꿀 수 있나" |
| 도구 | CI/CD, IaC, 모니터링 | SLO·에러 버짓·토일 상한·포스트모템·용량 계획 |
| 비유 | 인터페이스(원칙) | 클래스(구현) |

구글의 표현: `class SRE implements interface DevOps`. 둘은 경쟁하지 않는다. 이 사이트의 [GitHub Actions](/github-actions/notes/01-workflow-basics)·[IaC](/iac/notes/01-why-iac)·[GitOps](/kubernetes/notes/13-gitops-progressive-delivery) 가 DevOps 의 도구라면, 이 주제는 "그 도구로 **무엇을 결정**하나" 를 다룬다.

## SRE 의 핵심 원칙

1. **신뢰성은 기능이다, 그리고 100% 는 잘못된 목표다.** 사용자는 99.99% 와 100% 를 구분하지 못한다(사용자의 와이파이가 더 자주 끊긴다). 마지막 0.01% 를 위한 비용은 기하급수적이고, 그 돈과 시간은 기능 개발에서 빠져나온다. → [SLO 와 에러 버짓](/sre/notes/02-sli-slo-error-budget)
2. **에러 버짓이 개발 속도를 정한다.** SLO 가 99.9% 면 월 43분의 "허용된 불안정" 이 있다. 버짓이 남았으면 공격적으로 배포하고, 다 썼으면 안정화에 집중한다. 개발팀과 운영팀의 영원한 싸움("빨리" vs "안전하게")을 **데이터로 중재**한다.
3. **토일은 50% 를 넘지 않는다.** SRE 의 시간 중 최소 절반은 엔지니어링(자동화, 설계, 도구)이어야 한다. 그렇지 않으면 그 팀은 이름만 SRE 인 운영팀이다.
4. **알림은 사람이 지금 행동해야 할 때만.** 페이지(호출)는 비싸다 — 수면, 집중, 번아웃. 증상(symptom) 기반, SLO 기반 알림. → [번레이트 알림](/sre/notes/03-burn-rate-alerting)
5. **장애는 배움의 기회다 — 블레임리스.** 사람을 탓하면 다음엔 숨긴다. 시스템이 왜 그 실수를 허용했는지 묻는다. → [포스트모템](/sre/notes/05-incident-postmortem)
6. **점진적 변화.** 장애의 70% 는 변경에서 온다. 작게, 카나리로, 되돌릴 수 있게. → [릴리스·변경 관리](/sre/notes/06-capacity-release-change)
7. **용량은 미리.** 유기적 성장(사용자 증가)과 비유기적 성장(마케팅, 신기능)을 예측하고 헤드룸을 둔다. → [성능 공학 07](/performance/notes/07-capacity-planning)

## 토일(toil) — 정확한 정의

토일은 "하기 싫은 일" 이 아니다. 구글의 정의는 여섯 속성이다. **많이 해당할수록 토일**:

| 속성 | 뜻 | 예 (이 프로젝트) |
|---|---|---|
| 수동(manual) | 사람이 손으로 | `docker compose up` 을 매번 손으로 |
| 반복(repetitive) | 두 번째, 세 번째 똑같이 | 매 실험 전에 Redis 상태 확인 |
| 자동화 가능(automatable) | 기계가 할 수 있는데 사람이 | 인증서 갱신, 디스크 정리 |
| 전술적(tactical) | 계획이 아니라 인터럽트 주도 | 알림 받고 Pod 재시작 |
| 지속 가치 없음(no enduring value) | 끝나도 시스템이 나아지지 않음 | 로그 지워서 디스크 확보 |
| 서비스 성장에 비례(O(n)) | 트래픽·사용자·서버 수에 따라 늘어남 | 서버 10대면 10번 패치 |

토일이 **아닌** 것: 운영 작업이어도 설계·자동화·사후 분석처럼 **시스템을 영구히 개선**하는 일. 이메일 답장이나 회의 같은 **오버헤드**도 토일이 아니라 그냥 오버헤드다(없애야 할 대상이긴 하지만 분류가 다르다).

### 왜 50% 인가

- 토일은 **경력을 갉아먹는다**: 반복 작업만 하는 엔지니어는 성장하지 않고 이직한다.
- 토일은 **선형으로 늘어난다**: 자동화가 없으면 서비스가 2배 되면 토일도 2배. 팀 인원을 2배로 뽑는 수밖에 없다.
- 토일은 **장애를 만든다**: 손으로 하는 반복 작업은 언젠가 오타를 낸다(`rm -rf` 의 경로, 잘못된 네임스페이스).
- 50% 는 측정 가능한 **천장**이다. 분기마다 토일 비율을 설문·티켓·온콜 로그로 재고, 넘으면 자동화 프로젝트를 우선순위 1 로 올린다.

## 토일을 찾고 자동화 우선순위를 매기는 법

### 1단계: 가시화

- 온콜 로그·티켓·채팅 채널에서 **"또 그거"** 를 센다. 한 달간 "Pod 재시작" 이 12번이면 그게 1순위 후보.
- 설문: "지난주 시간의 몇 % 가 토일이었나". 숫자가 정확할 필요는 없다, **추세**가 중요하다.

### 2단계: 점수화

```
우선순위 = (빈도 × 회당 시간 × 관련 인원) / 자동화 비용
         + 위험 가중치 (수동 실수가 사고로 이어지는가)
```

| 후보 | 빈도/월 | 회당 | 인원 | 자동화 비용 | 위험 | 점수 |
|---|---|---|---|---|---|---|
| Redis 메모리 알림 받고 키 정리 | 8 | 20분 | 1 | 2일 | 중 | 높음 |
| 인증서 수동 갱신 | 0.3 | 60분 | 1 | 1일 | **높음**(만료=전면 장애) | 높음 |
| 배포 후 수동 스모크 테스트 | 20 | 10분 | 2 | 3일 | 중 | 높음 |
| 월간 비용 리포트 | 1 | 120분 | 1 | 5일 | 낮음 | 낮음 |

### 3단계: 자동화의 단계

1. **문서화** — 런북이 있어야 자동화할 수 있다. 런북 없는 자동화는 아무도 못 고친다.
2. **반자동** — 스크립트 + 사람 승인(`pnpm redis:ha` 처럼 한 명령).
3. **자동** — 트리거(알림·스케줄) → 실행 → 검증 → 보고. 사람은 결과만 본다.
4. **자가 치유** — 시스템이 스스로(Kubernetes 의 readiness/liveness·HPA·ArgoCD selfHeal 이 그 예).
5. **원인 제거** — 토일이 필요 없게 설계를 바꾼다(메모리 알림 → maxmemory-policy 로 자동 축출).

> 자동화에도 비용이 있다. **한 번만 할 일은 자동화하지 않는다.** XKCD 1205 의 표: 하루 한 번 5분 걸리는 일은 5년간 6일을 절약하므로 6일까지 투자할 가치가 있다.

## 운영 부하가 개발 속도를 갉아먹는 방식

```
토일 ↑ → 엔지니어링 시간 ↓ → 자동화 안 됨 → 토일 ↑↑   (악순환)
알림 ↑ → 수면 ↓ → 판단력 ↓ → 장애 대응 실수 → 알림 ↑↑
```

SRE 가 이 고리를 끊는 레버: 토일 상한(50%), 페이지 상한(교대당 2건), 에러 버짓(버짓 소진 시 기능 개발 중단권). 세 가지 모두 **숫자**라서 협상이 가능하다. "운영이 힘들다" 는 협상이 안 되지만 "이번 분기 토일 63%, 온콜 교대당 페이지 7건" 은 된다.

## 예시로 보기 — 이 프로젝트의 운영 작업 분류

| 작업 | 토일? | 현재 | 다음 단계 |
|---|---|---|---|
| 관측 스택 띄우기 (`pnpm obs:up`) | 반자동 | 한 명령 | 앱 시작 시 health 체크 후 자동 안내 |
| Redis 가 죽었을 때 알아차리기 | 자동 | [RedisDown 알림](/observability/notes/09-alerting-pipeline) → 웹훅 | 자동 재시작(compose `restart: unless-stopped`) + 알림은 "재시작 3회 이상" 만 |
| 실험 실패 원인 찾기 | 수동 | 로그 읽기 | 실패 시 trace_id 링크 자동 첨부 (이미 로그에 있음) |
| 노트 링크 깨짐 확인 | 자동화 가능 | 손으로 grep | CI 에 링크 검사 단계 |
| 카나리 승격 판단 | 자동 | [Argo Rollouts 분석](/kubernetes/notes/13-gitops-progressive-delivery) | SLO 기반 판정으로 교체 → [07](/sre/notes/07-slo-driven-automation) |
| kind·minikube·compose 메모리 정리 | 수동·반복 | 사람이 기억 | 안 쓰는 스택 자동 감지 스크립트 |

이 표를 만드는 행위 자체가 SRE 의 첫 걸음이다. "느낌" 이 "목록" 이 되고, 목록은 우선순위가 된다.

## SRE 팀의 모양

- **임베디드**: 제품팀 안에 SRE 1~2명. 맥락이 깊지만 표준화가 어렵다.
- **중앙 플랫폼**: 공용 도구(관측·배포·용량)를 만드는 팀. 이 사이트의 관측 스택·실험 프레임워크가 그 역할.
- **컨설팅/PRR**: 새 서비스가 운영에 들어가기 전 **Production Readiness Review** — SLO 있나, 런북 있나, 알림은, 롤백은, 용량은. 체크리스트는 [06](/sre/notes/06-capacity-release-change).

작은 팀이라면 "SRE 라는 사람" 보다 "SRE 라는 **관행**" 이 먼저다: SLO 하나, 에러 버짓 정책 하나, 포스트모템 템플릿 하나, 토일 측정 하나.

## 실습 체크리스트

- [ ] 지난 2주간 이 프로젝트(또는 본인 업무)에서 한 운영 작업 10개를 적고 토일 6속성으로 점수 매기기
- [ ] 가장 점수 높은 토일 하나를 "문서화 → 반자동" 으로 옮기기 (pnpm 스크립트 하나면 충분)
- [ ] `pnpm obs:up` 뒤 사람이 손으로 확인하는 것(Grafana 열기, 타깃 up 확인)을 스크립트로 자동 검증하게 만들기
- [ ] 다음 노트에서 SLO 를 하나 정의하고, 이 노트의 "에러 버짓이 속도를 정한다" 를 실제 숫자로 바꿔 보기
