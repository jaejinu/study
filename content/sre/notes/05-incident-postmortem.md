## 사고(incident)의 정의와 선언

**사고** = SLO 를 위협하거나 사용자에게 보이는 영향이 있고, 한 사람이 조용히 고칠 수 없는 상황. 선언 기준을 미리 정해 두면 "이게 사고인가" 로 10분을 안 쓴다:

- 번레이트 page 알림(1h 창 > 14.4) 이 울렸다
- 사용자 보고 2건 이상, 또는 내부에서 재현
- 데이터 유실·보안 의심은 규모와 무관하게 즉시
- **의심되면 선언한다**. 선언 취소는 싸고, 늦은 선언은 비싸다.

## 역할 — 고치는 사람이 지휘하면 안 된다

```
사고 지휘관 (IC)      : 전체 그림, 결정, 역할 배정, 다음 공지 시각. 손으로 고치지 않는다.
운영 리드 (Ops lead)   : 실제 조사·완화. 필요하면 여러 명(DB 담당, 앱 담당).
커뮤니케이션 리드      : 상태 페이지·내부 채널·경영진 업데이트. 정해진 주기(30분)로.
기록자 (scribe)        : 타임라인을 실시간으로. 누가 언제 무엇을 했고 무엇을 봤나.
```

왜 분리하나: 디버깅은 **터널 시야**를 만든다. 터미널에 빠진 사람은 "30분째 같은 가설" 을 알아차리지 못하고, 공지를 잊고, 다른 가설을 가진 사람의 말을 못 듣는다. IC 는 15분마다 "지금 가설은? 다른 가설은? 완화 옵션은? 롤백은 가능한가?" 를 묻는 사람이다. 작은 팀에서는 한 명이 IC+커뮤니케이션, 한 명이 운영을 맡는 식으로 **최소 둘**로 나눈다.

## 사고 중의 원칙

1. **완화가 먼저, 원인은 나중.** 롤백·기능 플래그 끄기·트래픽 전환·스케일 아웃·캐시 비우기. "왜" 는 서비스가 돌아온 뒤에. 70% 의 사고는 최근 변경이 원인이므로 **최근 배포 롤백**이 첫 완화 후보다([06](/sre/notes/06-capacity-release-change)).
2. **한 번에 한 변경.** 세 사람이 동시에 세 가지를 바꾸면 무엇이 고쳤는지(또는 망쳤는지) 모른다. 변경은 IC 승인 + 타임라인 기록.
3. **정해진 주기로 공지.** "진행 중, 다음 업데이트 30분 뒤" 도 공지다. 침묵은 사용자와 경영진을 채널로 끌어들여 대응을 방해한다.
4. **교대.** 2시간 넘는 사고는 IC 를 교대한다. 판단력은 소모품이다.
5. **기록.** 채팅 채널 하나에 모든 명령·관찰·결정을 남긴다. 포스트모템의 원재료다. 이 프로젝트에서는 `logs/app.jsonl`(trace_id 포함)·Alertmanager 이력·Tempo 가 자동 기록자다.

### 상태 페이지 문구 예

```
[조사 중] 14:02  일부 사용자의 진행률 저장이 실패하고 있습니다. 원인을 조사 중입니다. 다음 업데이트 14:30.
[완화됨] 14:21   Redis 를 재시작해 저장이 정상화됐습니다. 원인을 계속 확인합니다.
[해결] 15:10     14:00~14:21 사이 저장 실패가 있었습니다. 원인은 메모리 상한 도달로 인한 쓰기 거부였으며, 상한을 조정하고 알림을 추가했습니다.
```

## 포스트모템 — 목적

포스트모템은 **보고서가 아니라 학습 장치**다. 질문은 "누가 잘못했나" 가 아니라 "**시스템이 왜 이 실수를 허용했고, 왜 빨리 못 알아챘고, 왜 복구가 오래 걸렸나**". 작성 조건: SEV1·2 는 항상, 사용자 영향 있는 모든 사고, 데이터 유실, 온콜이 요청하는 것, 같은 원인의 2회째.

### 블레임리스의 정확한 뜻

- 비난 없음 ≠ 책임 없음. 액션 아이템에는 소유자가 있다.
- "A 가 잘못된 설정을 배포했다" → "설정 변경이 리뷰 없이 운영에 갈 수 있었다. 잘못된 값을 검증하는 단계가 없었다."
- 사람은 **합리적으로 행동했다**고 가정한다. 그 시점의 정보·도구·압박에서 그 선택이 왜 합리적으로 보였는지 묻는다. 그래야 다음 사람이 같은 함정에 안 빠진다.
- 블레임이 있는 조직에서는 사고가 **숨겨진다**. 숨겨진 사고는 반복된다.

## 타임라인 재구성

![사고의 시간축](/diagrams/sre-incident-timeline.svg)

타임라인은 포스트모템의 뼈대다. 기억은 믿을 수 없으니 **기계 기록**에서 만든다:

| 소스 | 무엇을 주나 | 이 프로젝트 |
|---|---|---|
| 알림 이력 | 언제 감지됐나, 언제 해결됐나 | Alertmanager API, `/api/alerts` 링버퍼, `study_alerts_received_total` |
| 로그 | 에러의 첫 발생, 메시지, 영향 범위 | Loki `{service="study-app", level=~"warn|error"}` |
| 트레이스 | 느려진 구간, 실패한 호출의 경로 | Tempo 검색 `rootServiceName=study-app`, 지연 상위 |
| 배포 이력 | 변경 시각 | git log, ArgoCD history, Rollout 이벤트 |
| 채팅 | 사람의 결정·가설 | 채널 로그 |
| 메트릭 | 영향 크기(에러율·지연·버짓 소진) | Prometheus 레코딩 룰 |

실험 `sre-postmortem-timeline` 은 앞의 세 소스를 API 로 긁어 **시간순 표** 하나로 합친다. 사고 중엔 이게 온콜의 화면이고, 사고 뒤엔 포스트모템 1장이다. 핵심 세 시각을 뽑는다: **시작**(첫 에러 로그), **감지**(첫 알림), **완화**(에러 중단). 감지 − 시작 = 탐지 시간(TTD), 완화 − 감지 = 복구 시간(TTR). 둘 다 줄이는 것이 액션 아이템의 방향이다.

## 기여 요인 분석

**5 Whys** 는 선형이라 단일 원인을 강요한다. 실제 사고는 여러 요인의 **동시 발생**이다(변경 + 모니터링 공백 + 자동 복구 부재 + 새벽). 대신 **기여 요인 목록**을 만든다:

| 범주 | 질문 | 예 |
|---|---|---|
| 촉발(trigger) | 무엇이 시작했나 | maxmemory 도달로 쓰기 거부 |
| 조건(latent) | 무엇이 그것을 가능하게 했나 | maxmemory-policy 가 noeviction, 알림 임계 80% 가 2분 `for` 로 늦음 |
| 탐지 | 왜 늦게 알았나 | 쓰기 실패가 앱에서 warn 로그만, 메트릭 없음 |
| 복구 | 왜 오래 걸렸나 | 런북 없음, 담당자가 MISCONF 를 처음 봄 |
| 영향 확대 | 왜 커졌나 | 재시도가 큐를 채워 2차 장애 |
| 잘 된 것 | 무엇이 도움됐나 | 트레이스에 trace_id 가 있어 요청 경로를 바로 찾음 |

"잘 된 것" 을 꼭 적는다. 다음에도 그게 작동하도록 지키기 위해서다.

## 액션 아이템의 조건

- **소유자**와 **기한**이 있다. "팀이 검토" 는 액션이 아니다.
- **검증 가능**: "모니터링 개선" ✗ → "쓰기 거부 수를 `redis_rejected_*` 로 수집하고 1분 `for` 알림 추가, 실험으로 검증" ✓
- **우선순위**: 재발 방지(P0) > 탐지 개선(P1) > 복구 단축(P2) > 문서(P3). 전부 P0 면 아무것도 안 된다 — 보통 2~5개.
- **추적**: 백로그에 들어가고 분기 리뷰에서 "지난 포스트모템 액션 완료율" 을 본다. 30% 미만이면 포스트모템은 의식일 뿐이다.

## 템플릿

```markdown
# 포스트모템: Redis 쓰기 거부로 진행률 저장 실패 (2026-10-16)
상태: 리뷰 완료 | 소유자: ___ | 심각도: SEV2 | 영향: 21분간 저장 요청 100% 실패 (약 N건), 읽기는 정상

## 요약 (3문장)
## 영향 (사용자·SLO 버짓: redis-connectivity 30일 버짓의 48% 소진)
## 타임라인 (UTC, 기계 기록 기준)
14:00:12 첫 에러 로그 "OOM command not allowed" (Loki)
14:02:05 RedisMemoryHigh warning 발화 (2분 for 경과)   ← 탐지 2분
14:03:40 온콜 ack, 런북 없음 → 노트 검색
14:21:00 docker restart study-redis → 복구                 ← 복구 17분
## 기여 요인
## 잘 된 것
## 액션 아이템 (소유자, 기한, 검증)
## 배운 것 (한 문단, 다른 팀에게)
```

## 예시로 보기 — 이 프로젝트에서 실제로 일어난 사고

이 노트를 쓰는 도중 진짜 사고가 났다. 실험 `sre-burn-rate-under-chaos` 를 돌리는 중에 실행이 사용자 쪽에서 중단됐고, 실험은 이미 `docker pause study-redis` 를 건 뒤였다. 실험의 정리(cleanup) 훅은 **실험 프로세스가 살아 있어야** 돈다 — 프로세스가 죽었으니 unpause 도 실행되지 않았다. 실험 `sre-postmortem-timeline` 이 기계 기록에서 뽑은 숫자:

| 항목 | 값 |
|---|---|
| 시작 (RedisDown 조건 성립) | 22:33:45 |
| 감지 (첫 웹훅 수신) | 22:33:49 — **TTD 4초** |
| 해결 (resolved) | 다음 날 01:30:35 — **지속 2시간 57분** |
| 같은 알림 반복 통지 | 6회 (repeat_interval) |
| 동반 알림 | StudyAppDown, PrometheusTargetMissing(redis, study-app) |

**기여 요인 (블레임리스)**

- 촉발: 실험 실행이 중간에 중단됐다.
- 조건: 장애 주입과 원복이 **같은 프로세스**에 묶여 있었다. 원복 경로가 주입한 쪽의 생존에 의존했다.
- 탐지: 빨랐다(4초). 알림은 6번 반복됐다.
- 대응: 알림을 받는 사람이 없었다(실험을 돌린 세션이 대기 상태). **감지는 됐는데 행동한 주체가 없는** 전형적인 경우 — 에스컬레이션도, 자동 복구도 없었다.
- 영향 확대: Redis 가 hang 이면 앱의 `/api/metrics` 도 Redis 핑을 기다리며 멈췄다. 그래서 원인 하나가 StudyAppDown·PrometheusTargetMissing 까지 만들었다. Tempo 에는 2시간 53분짜리 `GET /api/metrics` 트레이스가 남았다.
- 잘 된 것: 알림 파이프라인과 타임라인 도구 덕분에 사후에 몇 초 단위로 재구성할 수 있었다.

**액션 아이템**

1. (완료) 실험에 **데드맨 스위치**: pause 직전에 분리된(detached) 프로세스로 "90초 뒤 unpause" 를 장전한다. 주입한 쪽이 죽어도 원복은 일어난다 — [장애 실험실의 안전장치](/chaos/notes/01-chaos-principles)를 코드로.
2. 앱의 `/api/metrics` 가 의존성 확인에 짧은 타임아웃을 두게 한다(메트릭 엔드포인트는 의존성 때문에 막히면 안 된다).
3. Alertmanager 억제 규칙: RedisDown 이 firing 이면 같은 시간대의 StudyAppDown 을 억제하고 본문에 원인 알림을 첨부.
4. RedisDown 이 30분 이상 지속되면 자동으로 `docker unpause`/재시작을 시도하는 반자동 런북([04](/sre/notes/04-oncall-runbooks)).

이 사고 하나가 이 주제의 거의 모든 노트를 관통한다: SLI 정의의 함정([02](/sre/notes/02-sli-slo-error-budget)), 번레이트([03](/sre/notes/03-burn-rate-alerting)), 아무도 받지 않는 알림([04](/sre/notes/04-oncall-runbooks)), 그리고 기계 기록으로 만든 이 타임라인.

## 리뷰와 공유

- 작성자 ≠ 리뷰어. 리뷰에서 블레임 문장을 찾아 고친다("실수로" → "검증 단계 없이").
- 월 1회 **포스트모템 읽기 모임**: 다른 팀의 사고를 읽는다. 같은 함정이 조직 곳곳에 있다.
- 공개 범위는 넓게. 숨길수록 반복된다. 구글·Cloudflare·GitLab 의 공개 포스트모템이 좋은 교재다.

## 실전에서는 어디에 쓰이나

> 사용자가 영향을 받는 장애가 났을 때(대응)와 그 뒤 같은 장애를 막으려 할 때(포스트모템) 이 노트의 구조가 쓰인다. 원인을 빨리 찾는 기술보다 "역할을 나누고, 먼저 완화하고, 기계 기록으로 배우는" 절차의 문제다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 대형 커머스 할인 행사 중 장애 | 여러 명이 동시에 손대며 혼란 | 사고 지휘관(IC)·운영 리드·커뮤니케이션·기록자 분리, 한 번에 한 변경 | 가장 잘 아는 사람이 고치며 지휘 |
| B2B SaaS 상태 페이지 | 고객 문의 폭주와 신뢰 하락 | 30분 주기 공지("조사 중 → 완화됨 → 해결") | 해결될 때까지 침묵 |
| 미디어 스트리밍 장애 회고 | 기억에 의존한 부정확한 타임라인 | 알림 이력·로그·트레이스·배포 이력으로 TTD·TTR 산출 | 참여자 인터뷰만으로 재구성 |
| 핀테크 설정 변경 사고 | 담당자 문책 → 다음 사고 은폐 | 블레임리스 서술, 기여 요인 표, 소유자·기한 있는 액션 아이템 | 5 Whys 로 단일 원인과 책임자 지목 |
| 인프라 회사의 공개 포스트모템 | 고객과 업계에 투명성 확보 | Cloudflare·GitLab 처럼 장애 보고서를 블로그에 공개 | 내부 보고로만 종결 |

**이럴 땐 안 맞는다**
- 영향 없는 단순 알림 하나: 매번 포스트모템을 쓰면 의식이 된다. SEV1·2, 데이터 유실, 같은 원인 2회째로 범위를 정한다.
- 보안 침해 사고: 블레임리스 원칙은 같지만 공개 범위·증거 보존·법무 절차가 다르다. 보안 사고 대응 절차(침해 대응 플레이북)를 따른다.

**누가 매일 만나나** — SRE 와 온콜 개발자는 장애 채널을 열고 IC 를 정할 때, 엔지니어링 매니저는 포스트모템 리뷰와 액션 아이템 완료율을 추적할 때 만난다.

**면접·실무 단골 질문**
- Q. 장애 중 원인 분석과 완화 중 무엇이 먼저인가? → 완화. 최근 배포 롤백·플래그 끄기가 첫 후보이고 원인은 복구 뒤에 찾는다.
- Q. 블레임리스는 책임이 없다는 뜻인가? → 비난이 없을 뿐, 액션 아이템에는 소유자와 기한이 있다.
