## 변경이 장애를 만든다

구글·여러 조사에서 사고의 **60~70% 가 변경**(코드 배포, 설정 변경, 인프라 변경)에서 시작한다. 결론은 "변경하지 말자" 가 아니다 — 변경을 안 하는 조직은 기능을 못 내고, 변경을 모아서 하면 더 큰 장애가 난다. 결론은 **변경을 작고, 관측 가능하고, 되돌릴 수 있게**다.

```
변경 위험 = 변경 크기 × 영향 범위 × (1 - 탐지 확률) × 복구 시간
```

네 항 각각이 레버다: 작은 PR, 카나리(범위), 자동 분석(탐지), 자동 롤백(복구).

## 릴리스 안전장치의 계층

| 계층 | 잡는 것 | 못 잡는 것 | 이 프로젝트 |
|---|---|---|---|
| 단위·통합 테스트 | 로직 오류 | 환경·규모·데이터 문제 | vitest, [테스트 전략](/testing) |
| CI 게이트 | 빌드·린트·타입·취약점 | 운영 동작 | [GitHub Actions](/github-actions/notes/01-workflow-basics) |
| 스테이징 | 통합 문제 | 실제 트래픽 패턴 | minikube/kind |
| **카나리** | 실제 트래픽에서의 회귀 | 느린 누수, 드문 경로 | [Argo Rollouts](/kubernetes/notes/13-gitops-progressive-delivery) 25%→50%→100% |
| 점진 롤아웃 | 리전·셀 단위 영향 제한 | — | 복제본 비율 |
| 기능 플래그 | 코드 배포와 기능 공개 분리, 1초 롤백 | 플래그 폭발·테스트 조합 | 아직 없음 → [07](/sre/notes/07-slo-driven-automation) |
| 롤백 | 모든 것 | 스키마 변경·데이터 이행이 비가역일 때 | `kubectl argo rollouts undo` / ArgoCD history |

**롤백 가능성이 설계 조건**이다. DB 마이그레이션은 **확장-축소(expand/contract)**: 컬럼 추가(구버전과 호환) → 배포 → 코드가 새 컬럼 사용 → 다음 릴리스에서 구 컬럼 제거. 한 릴리스에 "컬럼 이름 변경" 을 넣으면 롤백이 불가능하다.

## 카나리 분석 — 제대로 하기

카나리는 "새 버전 Pod 하나 띄우고 잠깐 보기" 가 아니다. 통계적 비교다:

1. **비교군(baseline)을 같은 시점에 새로 띄운다.** 오래 돌던 안정 버전은 캐시가 데워져 있고 메모리가 쌓여 있어 공정한 비교가 아니다. Kayenta(Spinnaker) 방식: baseline 과 canary 를 동시에 새로 배포.
2. **지표를 미리 정한다.** 에러율·지연 p50/p99·CPU/메모리·로그 에러 수·업스트림 호출 실패율. SLO 의 SLI 가 1순위.
3. **충분한 표본.** 분당 10 요청인 카나리로 1% 에러율 차이를 보려면 수 시간이 필요하다. 표본이 부족하면 "통과" 가 아니라 "판단 불가" 다.
4. **단계마다 판정.** 1% → 5% → 25% → 50% → 100%. 초기 단계는 길게(문제는 보통 초반에 보인다), 후반은 짧게.
5. **자동 판정 + 사람 게이트.** 지표가 명백하면 자동 승격/롤백, 애매하면 사람.

이 프로젝트의 AnalysisTemplate(`k8s/rollouts/web-rollout.yaml`)은 `study_redis_up` 과 `up` 두 지표를 3회 확인한다 — "살아 있나" 수준. SLO 기반 판정(에러율·지연 비율이 baseline 대비 나쁘지 않은가)으로 올리는 것이 [07](/sre/notes/07-slo-driven-automation) 의 내용이다. 실측: 25% → 60초 → 분석 → 50% → 60초 → 100% 에 약 3분.

## 배포 프리즈

연말·대형 이벤트 전 "배포 금지" 는 흔하지만 비용이 있다: 프리즈가 끝나면 **쌓인 변경이 한꺼번에** 나가 더 큰 장애를 만든다. 대안:
- 프리즈 대신 **에러 버짓 기반 속도 조절**([02](/sre/notes/02-sli-slo-error-budget)): 버짓이 넉넉하면 평소대로, 부족하면 자동으로 느려진다.
- 프리즈를 하더라도 "배포 금지" 가 아니라 "**카나리 단계 2배, 야간 금지, 2인 승인**".
- 예외 경로(보안 패치, 장애 수정)는 미리 정의.

## 변경 승인 vs 자동 게이트

변경자문위원회(CAB)식 **사람 승인**은 DORA 연구에서 **속도도 안정성도 개선하지 못하는** 것으로 나타났다. 승인자는 변경 내용을 깊이 모르고, 병목이 되며, "승인됐으니 괜찮겠지" 가 검증을 대체한다. 대신:
- **동료 리뷰**(코드를 아는 사람) + **자동 게이트**(테스트·린트·보안 스캔·카나리 분석·SLO).
- 고위험 변경(스키마, IAM, 네트워크)만 2인 승인 + 변경 창.
- 모든 변경은 **기록**(누가, 무엇을, 언제, 롤백 방법) — git 과 ArgoCD 가 자동으로 해 준다.

## 용량 계획 — SRE 식

[성능 공학 07](/performance/notes/07-capacity-planning) 이 측정과 모델을 다룬다면, 여기서는 **절차**:

1. **수요 예측**: 유기적 성장(추세 외삽) + 비유기적(마케팅 캠페인, 신기능, 신규 리전 — 제품팀에게 분기마다 묻는다).
2. **단위 용량**: 인스턴스 하나가 SLO 안에서 처리하는 QPS. [부하 테스트](/performance/notes/03-k6-load-testing)로 **측정**한다, 추정하지 않는다. 이 앱은 개발 서버 기준 약 37 req/s 에서 포화.
3. **헤드룸**: N+1(인스턴스 하나 죽어도), AZ 하나 손실, 배포 중 일시 용량 감소(롤링 25% 비가용), 트래픽 스파이크 2배. 보통 피크의 60~70% 사용률 목표.
4. **리드타임**: 클라우드도 쿼터·GPU 는 주 단위. 온프렘은 분기 단위. 예측 지평은 리드타임의 2배 이상.
5. **검증**: 용량 계획을 **부하 테스트로 검증**하고 분기마다 재측정. 코드가 바뀌면 단위 용량이 바뀐다 — 성능 회귀 CI.
6. **자동 스케일**은 용량 계획의 대체가 아니라 보완. HPA 는 분 단위, 용량 계획은 월 단위. HPA 상한(maxReplicas)이 곧 용량 계획의 결과다.

## 프로덕션 준비 검토 (PRR)

새 서비스가 온콜 대상이 되기 전, SRE 가 묻는 목록. 이 프로젝트의 web 서비스를 대입:

| 항목 | 질문 | web (kind) |
|---|---|---|
| SLO | 정의·측정·대시보드 있나 | 초안만([02](/sre/notes/02-sli-slo-error-budget)) |
| 알림 | 증상 기반, 런북 연결 | 원인 기반 위주, 런북 일부 |
| 배포 | 카나리·롤백 절차, 롤백 시간 | Rollouts 있음, 롤백 < 1분 |
| 설정 | 코드로 관리, 리뷰 | GitOps ✓ |
| 의존성 | 각 의존성 장애 시 동작(타임아웃·폴백) | Redis 다운 시 읽기는 됨, 저장 실패 — [장애 카탈로그](/chaos/notes/02-failure-catalog) |
| 용량 | 단위 용량·헤드룸·HPA 상한 | 측정됨, HPA 있음 |
| 보안 | non-root, 시크릿, 스캔 | [보안 05](/security/notes/05-container-supply-chain) |
| 데이터 | 백업·복구 리허설 | Redis RDB, 복구 리허설 없음 ✗ |
| 운영 | 런북, 온콜, 에스컬레이션 | 부분 |
| 로그·트레이스 | 구조화, trace_id, 보존 | ✓ |

PRR 은 통과/탈락이 아니라 **갭 목록**이다. 갭은 액션 아이템이 되고, 심각한 갭(백업 없음)은 런칭 차단 조건이다.

## 예시로 보기 — 변경 하나의 여정

"퀴즈 간격 반복 기능 추가" 를 이 틀로:

1. PR 작게(라이브러리 → 액션 → UI 세 PR). 각 PR 에 테스트.
2. CI 통과 → `study:dev2` 이미지 → ArgoCD 가 Rollout 갱신.
3. 카나리 25%: 1분간 `study_action_duration_seconds{action="recordQuiz"}` 의 에러율·p95 를 baseline(기존 액션)과 비교.
4. 통과 → 50% → 100%. 실패 → 자동 롤백 + 알림 + 포스트모템(SEV3).
5. 기능 플래그가 있었다면: 배포는 100% 하되 플래그 off → 내부 사용자만 on → 10% → 100%. 롤백은 플래그 off, 1초.

## 실전에서는 어디에 쓰이나

> 장애 대부분이 배포·설정·인프라 변경에서 시작한다는 사실을 받아들이고, 변경을 멈추는 대신 작게·관측 가능하게·되돌릴 수 있게 만들 때 이 노트가 쓰인다. 용량 계획은 그 변경이 트래픽 증가를 견디는지 미리 확인하는 짝이다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 커머스 연말 시즌 | 프리즈 뒤 쌓인 변경이 한꺼번에 터짐 | 전면 금지 대신 카나리 단계 2배·야간 금지·2인 승인 | 전면 배포 프리즈 |
| 핀테크 DB 스키마 변경 | 롤백 불가능한 마이그레이션 | 확장-축소(expand/contract) 로 두 릴리스에 나눔 | 한 번에 컬럼 이름 변경 |
| 하루 여러 번 배포하는 SaaS | 실제 트래픽에서만 보이는 회귀 | 비교군을 새로 띄운 카나리 분석(Kayenta 방식), 충분한 표본 확보 | Pod 하나 띄우고 눈으로 보기 |
| 게임 신규 시즌 오픈 | 접속 폭주로 인한 서버 포화 | 부하 테스트로 단위 용량 측정, N+1·스파이크 2배 헤드룸, HPA 상한 결정 | 오토스케일만 믿기 (분 단위라 늦다) |
| AI 서비스의 GPU 추론 서버 | 구매·쿼터 리드타임이 주 단위 | 리드타임의 2배 이상 지평으로 수요 예측 | 부족해지면 그때 요청 |
| 사내 플랫폼의 신규 서비스 온보딩 | 준비 안 된 서비스가 온콜에 편입 | PRR 체크리스트로 갭 목록 작성, 백업 없음 같은 갭은 런칭 차단 | 런칭 후 장애로 발견 |

**이럴 땐 안 맞는다**
- 트래픽이 적은 서비스의 정교한 카나리: 표본이 부족해 판정이 불가능하다. 스테이징 검증 + 빠른 롤백 + 기능 플래그가 현실적이다.
- 모든 변경에 변경자문위원회(CAB) 승인: 속도도 안정성도 개선하지 못한다. 동료 리뷰 + 자동 게이트로 바꾸고 고위험 변경만 2인 승인한다.

**누가 매일 만나나** — 백엔드 개발자는 PR 을 쪼개고 마이그레이션을 두 단계로 나눌 때, SRE·플랫폼 엔지니어는 Rollout 단계와 HPA 상한을 정하고 분기 용량 리뷰를 할 때 만난다.

**면접·실무 단골 질문**
- Q. 롤백이 안 되는 배포는 어떻게 하나? → 확장-축소 마이그레이션과 기능 플래그로 "코드 배포" 와 "동작 변경" 을 분리한다.
- Q. 오토스케일이 있는데 용량 계획이 왜 필요한가? → HPA 는 분 단위 반응이고 상한·쿼터·구매 리드타임은 계획으로만 정해진다.
