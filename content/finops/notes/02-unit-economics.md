## 총액은 거짓말을 한다

> 청구서가 무엇으로 구성되는지(컴퓨트·스토리지·네트워크·관리형 서비스, 약정·스팟)는 [클라우드 비용 모델](/finops/notes/01-cloud-cost-model)에서 먼저 정리했다. 이 노트는 그 비용을 **무엇으로 나눠 판단할지**다.

"이번 달 클라우드 비용이 40% 올랐다." 좋은 소식일까 나쁜 소식일까? 알 수 없다. 사용자가 2배 늘었다면 훌륭한 효율 개선이고, 사용자가 그대로라면 사고다.

**단위 비용(unit cost)** = 비용 ÷ 비즈니스 단위. 이것이 FinOps 의 기본 화폐다.

```
              총 비용
단위 비용 = ─────────────
           비즈니스 단위 수 (요청, 활성 사용자, 주문, 처리한 GB, 학습한 노트 …)
```

| 상황 | 총 비용 | 사용자 | 사용자당 비용 | 판단 |
|---|---|---|---|---|
| A | $10,000 → $14,000 | 10만 → 20만 | $0.10 → $0.07 | 규모의 경제, 좋음 |
| B | $10,000 → $14,000 | 10만 → 10만 | $0.10 → $0.14 | 비효율, 조사 필요 |
| C | $10,000 → $9,000 | 10만 → 6만 | $0.10 → $0.15 | 총액은 줄었지만 **나빠짐** |

C 가 핵심이다. 총액만 보는 조직은 C 를 칭찬한다.

## 단위 고르기

좋은 분모의 조건:

1. **비즈니스 가치를 대변한다** — 경영진이 늘리고 싶어 하는 숫자(주문, 활성 사용자, 처리한 문서).
2. **비용과 함께 움직인다** — 그 단위가 늘면 실제로 자원이 더 든다.
3. **측정 가능하다** — 이미 메트릭이나 DB 에 있다.

| 서비스 | 후보 단위 | 비고 |
|---|---|---|
| API 플랫폼 | 요청 1,000건 | 가장 범용. 단, 요청 무게가 다르면 왜곡 |
| 이커머스 | 주문 1건 | 경영진 언어와 일치 |
| SaaS | 활성 테넌트·월 | 가격 정책과 직결([멀티테넌시](/architecture/notes/08-multitenancy-saas)) |
| 데이터 파이프라인 | 처리 GB | 볼륨형 워크로드 |
| LLM 기능 | 대화 1회, 해결된 질문 1건 | 토큰 수보다 "성공한 일" 이 낫다 |
| 이 학습 사이트 | 노트 조회 1회, AI 질문 1회 | `study_note_views_total`, ask 요청 수 |

여러 단위를 계층으로 둔다: 엔지니어는 "요청 1,000건당 $" 로 최적화하고, 경영진은 "활성 사용자당 $" 로 본다.

## 고정비, 변동비, 한계 비용

```
비용
 │                       ╱  변동비 (요청·저장·토큰에 비례)
 │                    ╱
 │                 ╱
 │──────────────╱───────── 고정비 (컨트롤 플레인, 최소 노드, 관리형 DB 최소 사양, 약정)
 │           ╱
 └──────────────────────────── 트래픽
```

- **고정비**는 트래픽이 0 이어도 낸다. 초기 서비스는 단위 비용이 고정비에 지배된다 — 사용자가 적을수록 1인당 비용이 높다.
- **변동비**는 단위에 비례한다. LLM 토큰, 서버리스 호출, egress, 로그 수집이 대표적이다.
- **한계 비용**(사용자 1명을 더 받는 비용)이 의사결정에 중요하다. 무료 플랜 정책, 대량 고객 할인은 한계 비용을 알아야 정할 수 있다.

> **함정:** 무료 사용자의 한계 비용이 LLM 토큰처럼 **선형**이면 성장이 곧 손실이다. 이때 단위 비용을 줄이는 기술(캐시, 작은 모델 라우팅, 출력 제한)이 사업 모델 자체를 바꾼다([LLM 토큰 비용](/finops/notes/05-llm-token-cost)).

## 비용을 메트릭으로 만든다

월말 청구서로는 늦다. 비용을 **Prometheus 시계열**로 만들면 대시보드·알림·SLO 와 같은 도구로 다룰 수 있다.

### 1. 자원 비용을 시계열로

노드(또는 Pod)의 자원에 단가를 곱한다. OpenCost 가 하는 일이 정확히 이것이다([Kubernetes 비용](/finops/notes/03-kubernetes-cost)).

```yaml
# prometheus rules — 가정 단가로 네임스페이스 비용률(USD/시간)
groups:
  - name: cost
    rules:
      - record: namespace:cost_usd_per_hour:allocated
        expr: |
          sum by (namespace) (
            max by (namespace, pod, container) (
              kube_pod_container_resource_requests{resource="cpu"}
              or   # 레이블 집합이 달라 둘 다 남는다 → 바깥 max by 가 컨테이너별 max(요청, 사용)
              rate(container_cpu_usage_seconds_total{container!=""}[5m])
            )
          ) * 0.0316
          +
          sum by (namespace) (
            max by (namespace, pod, container) (
              kube_pod_container_resource_requests{resource="memory"}
              or
              container_memory_working_set_bytes{container!=""}
            )
          ) / 2^30 * 0.0042
```

### 2. 비즈니스 단위로 나눈다

```promql
# 요청 1,000건당 비용 (study 네임스페이스, 1시간 창)
  sum(namespace:cost_usd_per_hour:allocated{namespace="study"})
/
  (sum(rate(study_action_duration_seconds_count[1h])) * 3600 / 1000)
```

이 두 줄이면 "배포 후 요청당 비용이 30% 올랐다" 를 **배포 직후** 알 수 있다. 레코딩 룰의 기본은 [SLI·SLO 노트](/sre/notes/02-sli-slo-error-budget)에서 이미 다뤘다 — 같은 기법을 비용에 쓴다.

### 3. LLM 은 이미 메트릭이 있다

이 사이트는 LLM 호출마다 토큰과 추정 비용을 카운터로 남긴다([LLM 관측](/observability/notes/08-llm-observability)).

```promql
# AI 질문 1회당 비용 (USD)
  sum(increase(study_llm_cost_usd_total[1d]))
/
  sum(increase(study_llm_latency_seconds_count{phase="total"}[1d]))

# 모델별 입력:출력 토큰 비율 — 출력이 비싼 만큼 이 비율이 비용 구조를 말해 준다
sum by (model, kind) (increase(study_llm_tokens_total[1d]))
```

## 공유 비용의 배분

모든 비용이 한 팀·한 기능에 깔끔하게 붙지 않는다.

| 공유 비용 | 배분 기준 예 |
|---|---|
| Kubernetes 컨트롤 플레인, 모니터링 스택 | 네임스페이스별 배분 비용 비율 |
| 공유 DB | 쿼리 시간(pg_stat_statements 의 total_exec_time) 비율 |
| 공유 Kafka | 토픽별 바이트 in/out 비율 |
| 네트워크 egress | 서비스별 응답 바이트(Nginx 로그 `$body_bytes_sent`) |
| 유휴 노드 용량 | 배분 비율대로 나누거나 "플랫폼 비용" 으로 따로 |

정밀함보다 **일관성**이 중요하다. 매달 기준이 바뀌면 추세를 볼 수 없다.

- **쇼백(showback)**: 팀별 비용을 보여만 준다. 문화를 바꾸는 첫 단계.
- **차지백(chargeback)**: 팀 예산에서 실제로 차감한다. 배분 기준이 공정하다는 합의가 먼저다.

## 단위 비용의 함정

단위 비용도 잘못 읽으면 거짓말을 한다.

| 함정 | 예 | 대처 |
|---|---|---|
| **혼합 단위** | 가벼운 조회 요청과 무거운 보고서 생성을 같은 "요청 1건" 으로 | 요청 종류별(가중치) 단위, 또는 단위를 둘로 |
| **지연된 비용** | 이번 달 저장한 데이터의 보존 비용은 다음 달부터 쌓인다 | 저장 단위(GB-월)는 누적으로 따로 본다 |
| **고정비 착시** | 트래픽이 적은 밤에 단위 비용이 치솟는다 | 일·주 단위 창으로, 또는 변동비만 따로 |
| **약정 할인 배분** | 약정 할인을 어느 팀에 반영하나에 따라 팀별 단위 비용이 출렁인다 | 약정 효과는 중앙에서, 팀에는 온디맨드 기준 가격(또는 평균 실효 단가) |
| **품질 무시** | 응답을 짧게 잘라 LLM 비용을 줄였더니 재질문이 늘었다 | "해결된 질문 1건" 처럼 성공한 결과를 분모로 |

마지막 함정이 특히 중요하다. 비용을 줄이는 변경이 **분모(성공)** 를 줄이면 단위 비용은 오히려 오른다. LLM 기능에서는 "토큰당" 이 아니라 "해결된 질문당" 을 단위로 삼아야 캐시·라우팅·출력 제한이 품질을 해치지 않는지 함께 볼 수 있다([AI 평가](/ai-systems/notes/06-evaluation-guardrails-safety)).

## 예시로 보기 — 이 프로젝트에서

실험 두 개가 단위 경제의 재료를 만든다.

**1) 자원 쪽 — `finops-k8s-requests-vs-usage`.** 이 Mac 에서 측정한 kind 클러스터의 `study` 네임스페이스(web·redis·rollout Pod)는 배분 비용이 가정 단가로 **월 약 $7.8**, CPU 요청 270m 중 실제 사용은 20m 안팎(효율 7~10%)이었다. 요청을 사용량에 맞추면 배분 비용의 CPU 부분이 거의 사라진다 — 단위 비용을 낮추는 가장 싼 방법은 코드가 아니라 **requests 재조정**일 때가 많다.

**2) LLM 쪽 — `finops-llm-token-cost`.** "AI 에게 묻기" 패널은 노트 본문을 시스템 프롬프트에 넣는다. CDC 노트(8,834자)를 넣었을 때 입력은 **4,053 토큰**, 질문만이면 **40 토큰**이었다. 하루 2,000 질문 가정의 월 비용은:

| 모델(가정 단가) | 캐시 없음 | 프리픽스 캐시 | 질문 1회당(캐시) |
|---|---|---|---|
| gpt-5 | $342 | $71 | $0.0012 |
| gpt-5-mini | $68 | $14 | $0.00024 |
| gpt-5-nano | $14 | $2.8 | $0.00005 |

같은 기능이 설계 선택(캐시·모델)만으로 **질문당 비용 25배** 차이가 난다. 이 숫자를 "학습자 1명이 하루 20 질문" 같은 단위에 곱하면 가격 정책·무료 한도를 정할 수 있다.

> **팁:** 단위 비용 대시보드에는 항상 **분자(비용)와 분모(단위)를 따로** 그린다. 단위 비용이 튀었을 때 비용이 늘어서인지, 트래픽이 줄어서인지 바로 구분된다.

## 실전에서는 어디에 쓰이나

> 성장하는 서비스의 총 비용은 늘 수밖에 없으니, 실무 판단은 "요청·주문·사용자당 비용" 으로 한다. 가격 정책, 무료 플랜 한도, 배포가 효율을 망쳤는지 판단하는 일이 모두 이 숫자에서 나온다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 이커머스 성장기 | 비용 증가가 정상인지 판단 | 주문 1건당 인프라 비용을 월별 추세로 | 총액 증가율만 보고 절감 압박 |
| AI 기능을 붙인 SaaS | 무료 플랜 한도·가격 결정 | 해결된 질문 1건당 비용, 사용자 1명의 월 한계 비용 | 토큰당 비용 — 품질 저하를 못 본다 |
| 여러 팀이 공유하는 사내 플랫폼 | 공유 비용을 팀에 공정하게 | 네임스페이스 배분 비율로 쇼백, 합의 후 차지백 | 전부 중앙 부담 — 아무도 줄이지 않는다 |
| API 플랫폼 배포 | 배포가 효율을 망쳤는지 즉시 | 비용 레코딩 룰 ÷ 요청 rate = "1,000건당 $" 패널·알림 | 월말 청구서 비교 |
| 데이터 파이프라인 | 볼륨 증가 대비 비용 추세 | 처리 GB 당 비용 | 잡별 실행 시간만 추적 |

**이럴 땐 안 맞는다**
- 요청 무게가 크게 다른 서비스에 "요청 1건" 단일 분모 → 가벼운 요청이 늘면 효율이 좋아진 것처럼 보인다. 종류별 분모나 가중치를 쓴다.
- 트래픽이 아주 적은 초기 서비스 → 고정비가 지배해 단위 비용이 의미 없이 높다. 변동비만 따로 보거나 예산으로 관리한다.

**누가 매일 만나나** — 엔지니어링 리더·PM 은 사용자당 비용으로 가격과 한도를 정하고, 백엔드·SRE 는 배포 후 요청당 비용 그래프를 확인한다. 재무팀은 쇼백·차지백 리포트를 받는다.

**면접·실무 단골 질문**
- Q. 비용이 10% 줄었는데 왜 나빠졌다고 하나? → 분모(사용자·성공 건수)가 더 많이 줄면 단위 비용은 오른다. 분자와 분모를 따로 그려 확인한다.
