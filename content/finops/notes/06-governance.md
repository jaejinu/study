## 기술이 아니라 습관의 문제

앞의 노트들은 **무엇을 줄일 수 있는지**를 다뤘다: requests 재조정([Kubernetes 비용](/finops/notes/03-kubernetes-cost)), 카디널리티·보존([관측 비용](/finops/notes/04-data-observability-cost)), 프롬프트 캐시·라우팅([LLM 토큰](/finops/notes/05-llm-token-cost)). 그런데 한 번 줄인 비용은 6개월 뒤 다시 늘어 있다. 새 서비스, 새 레이블, 켜 두고 잊은 실험 환경 때문이다.

거버넌스는 **비용이 다시 늘지 않게 하는 구조**다. FinOps Foundation 은 이를 세 단계의 반복으로 설명한다.

| 단계 | 질문 | 산출물 |
|---|---|---|
| **Inform** (보이게) | 누가 무엇에 얼마를 쓰나? | 태깅, 배분, 쇼백 대시보드, [단위 비용](/finops/notes/02-unit-economics) |
| **Optimize** (줄이게) | 어디가 낭비인가? | 재조정·약정·아키텍처 개선 백로그 |
| **Operate** (지키게) | 다시 늘지 않게 하려면? | 예산·알림·정책·리뷰 게이트 |

조직 구조는 대개 **중앙 FinOps 팀(작게) + 각 엔지니어링 팀의 책임**이다. 중앙은 도구·데이터·약정 구매를 맡고, 비용을 만드는 결정은 팀이 한다. SRE 가 신뢰성을 다루는 방식([SRE 원칙](/sre/notes/01-sre-principles-toil))과 같은 구조다.

## 태깅: 배분의 전제

태그(레이블)가 없는 비용은 "기타" 로 쌓이고, 기타가 30% 를 넘으면 쇼백은 신뢰를 잃는다.

### 최소 태그 세트

| 태그 | 예 | 용도 |
|---|---|---|
| `team` | payments | 책임자 — 쇼백·차지백 |
| `service` | checkout-api | 단위 비용 계산 |
| `env` | prod / staging / dev | 비프로덕션 비용 비율, 야간 정지 대상 |
| `cost-center` | CC-1042 | 재무 시스템 연결 |
| `owner` | 이메일 또는 팀 채널 | 고아 리소스 연락처 |
| `ttl` (선택) | 2026-11-01 | 실험 환경 자동 삭제 |

Kubernetes 에선 네임스페이스 레이블과 Pod 레이블이 태그 역할을 하고, OpenCost 가 이를 집계 축으로 쓴다.

### 강제하는 방법

말로 하는 정책은 지켜지지 않는다. **만드는 경로에서** 강제한다.

1. **IaC 기본 태그** — Terraform/OpenTofu 프로바이더의 `default_tags` 로 모든 리소스에 자동([IaC 노트](/iac/notes/03-variables-expressions)).
2. **정책 검사** — plan 단계에서 태그 누락을 거부(OPA/Conftest, Sentinel). [IaC 드리프트·정책·테스트](/iac/notes/06-drift-policy-testing)의 규칙 예에 한 줄 추가하면 된다.
3. **클러스터 어드미션** — Kyverno 로 `team` 레이블 없는 Namespace·Deployment 거부.
4. **사후 리포트** — 매주 태그 누락 리소스 목록을 owner 없는 채널에 게시(고아 탐지).

```rego
# conftest — plan JSON 에서 태그 누락 거부
deny[msg] {
  r := input.resource_changes[_]
  r.change.actions[_] == "create"
  tags := object.get(r.change.after, "tags", {})
  not tags.team
  msg := sprintf("%s: team 태그가 없습니다", [r.address])
}
```

## 예산과 알림

예산은 "얼마까지 써도 된다" 가 아니라 **"이 선을 넘으면 사람이 본다"** 는 신호다.

| 알림 종류 | 조건 | 장점 |
|---|---|---|
| 실제 지출 | 월 예산의 50·80·100% 도달 | 단순 |
| **예측 지출** | 현재 추세로 월말 예상이 예산 초과 | 월 중순에 미리 안다 |
| 증가율 | 지난주 대비 +30% | 예산이 없어도 이상을 잡는다 |

SLO 의 번레이트 알림과 같은 사고방식을 쓸 수 있다. **예산 소진 속도**가 평소의 몇 배인지 본다.

```
          실제 일일 지출
번레이트 = ─────────────────  (1 이면 월말에 정확히 예산 소진)
          월 예산 / 일수
```

[번레이트 알림](/sre/notes/03-burn-rate-alerting)의 멀티윈도우 조합(짧은 창 + 긴 창)을 그대로 가져오면, 하루짜리 스파이크에는 조용하고 지속적인 증가에는 빠르게 반응한다.

## 이상 탐지

예산보다 빨리 문제를 잡는 것은 **기준선 대비 이상**이다.

- **기준선**: 같은 요일·같은 시간대의 지난 4주 중앙값(계절성 반영).
- **임계**: 기준선의 2~3배, 또는 절대 증가액(예: 시간당 +$10) — 작은 서비스의 3배는 무시해도 된다.
- **원인 축**: 이상이 뜨면 서비스·리소스 타입·리전·태그별로 쪼개 기여도 상위를 보여 준다. "무엇이 늘었나" 가 알림 본문에 있어야 한다.

흔한 이상의 원인:

| 패턴 | 원인 예 |
|---|---|
| 계단식 증가 | 새 배포가 requests 를 늘림, 새 레이블 추가 |
| 스파이크 | 재시도 폭풍([장애 실험실](/chaos/notes/03-resilience-patterns-verified)), 봇 트래픽, 무한 루프 |
| 서서히 증가 | 보존 정책 없는 스냅샷·로그, 고아 볼륨 |
| 주말에도 같음 | 개발 환경 상시 가동 |

```promql
# 관측 비용의 대리 지표: 활성 시계열이 지난주 같은 시각보다 30% 이상 늘었나
prometheus_tsdb_head_series > 1.3 * (prometheus_tsdb_head_series offset 1w)
```

## 약정 관리 — 중앙이 하는 일

[클라우드 비용 모델](/finops/notes/01-cloud-cost-model)에서 본 Savings Plan·예약은 팀이 아니라 **중앙 FinOps 가 포트폴리오로** 관리한다. 팀마다 약정하면 한 팀의 감소가 다른 팀의 증가를 상쇄하지 못한다.

| 지표 | 정의 | 목표 감 |
|---|---|---|
| **커버리지** | 약정이 덮는 사용량 / 전체 약정 가능 사용량 | 70~85% |
| **활용률** | 실제로 쓴 약정 / 구매한 약정 | 95% 이상 (낮으면 과다 약정) |
| 실효 할인율 | (온디맨드 환산 − 실제 지출) / 온디맨드 환산 | 추세로 본다 |

규칙: 짧은 기간(1년)·유연한 상품(지출 기반 Savings Plan)부터, 분기마다 조금씩 쌓아 올리는 **사다리** 방식으로 산다. 한 번에 3년치를 크게 사면 아키텍처가 바뀔 때 묶인다. 그리고 팀에 보여 주는 단위 비용은 약정 효과를 뺀 **온디맨드 기준**으로 둬서, 팀의 최적화 성과와 중앙의 구매 성과를 섞지 않는다.

## 비용을 SLO 처럼 — "비용 예산"

에러 버짓([SLI·SLO·에러 버짓](/sre/notes/02-sli-slo-error-budget))은 "신뢰성을 얼마나 희생해도 되는가" 를 숫자로 정해 속도와 안정성의 싸움을 끝냈다. 비용에도 같은 장치를 쓸 수 있다.

| 신뢰성 | 비용 |
|---|---|
| SLI: 성공 요청 비율 | 단위 비용: 요청 1,000건당 $ |
| SLO: 99.9% | 목표: 요청 1,000건당 $0.05 이하 |
| 에러 버짓: 0.1% | 비용 여유: 목표까지 남은 차이 |
| 버짓 소진 → 기능 배포 중단, 안정화 | 여유 소진 → 비용 개선을 다음 스프린트 최우선 |

핵심은 **총액이 아니라 단위 비용에 목표를 거는 것**이다. 트래픽 성장은 막을 이유가 없지만, 같은 일을 더 비싸게 하는 것은 막아야 한다.

## 아키텍처 리뷰에 비용 게이트

비용 결정은 설계 단계에서 90% 정해진다. 리뷰 템플릿에 한 칸을 넣자.

- 예상 단위 비용과 근거(부하 모델 × 단가).
- 상시 비용(트래픽 0 일 때)과 최대 비용(상한 장치).
- 데이터 복사 경로와 보존 기간.
- 관측 데이터 추가량(새 메트릭의 예상 시계열 수, 로그 줄 수).

IaC 를 쓴다면 PR 마다 비용 변화를 자동으로 코멘트할 수 있다.

```bash
# Infracost: Terraform/OpenTofu plan 의 월 비용 차이
infracost breakdown --path infra/ --format json --out-file base.json
infracost diff --path infra/ --compare-to base.json
#  + aws_db_instance.main   +$245/월  (db.r6g.large → db.r6g.xlarge)
```

## 예시로 보기 — 이 프로젝트의 최소 거버넌스 세트

학습용이지만 같은 습관을 들여 볼 수 있다.

| 항목 | 지금 상태 | 최소 조치 |
|---|---|---|
| 태깅 | 네임스페이스는 있지만 `team`·`env` 레이블 없음 | `study`·`monitoring` 네임스페이스에 `env=local`, `owner` 레이블 |
| BestEffort | 35개 중 20개 (실험 `finops-k8s-requests-vs-usage`) | LimitRange 기본 requests, 새 차트는 values 로 지정 |
| 관측 볼륨 | 시계열 약 5천, 버킷 36% (실험 `finops-observability-volume`) | 시계열 상한 알림(예: 8천), 새 exporter 추가 시 drop 규칙 리뷰 |
| LLM | 토큰·비용 메트릭 있음 | 시간당 비용 3배 알림, 질문당 입력 토큰 상한 |
| 실험 환경 | kind 클러스터 3개(study, study-netpol, study-tf 는 실험이 지움) | 쓰지 않을 때 `pnpm k8s:netpol:down` 같은 정리 습관 |

> **팁:** 거버넌스의 첫 지표로는 "**배분 안 된 비용 비율**(태그 없음 + 유휴)" 하나만 매주 보자. 이 숫자가 줄어들면 나머지 모든 FinOps 활동이 가능해진다.
