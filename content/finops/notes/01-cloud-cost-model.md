## 비용은 아키텍처의 비기능 요구사항이다

성능·가용성·보안처럼 **비용도 설계가 정한다**. 같은 기능을 월 $300 로도, $30,000 로도 만들 수 있다. 차이는 대개 코드 한 줄이 아니라 "어디에 데이터를 두고, 무엇을 상시로 켜 두고, 무엇을 몇 번 복사하는가" 에서 난다.

FinOps(Financial Operations)는 이 사실을 조직의 습관으로 만드는 일이다. 핵심 원칙은 세 가지다.

| 원칙 | 뜻 | 반대말 |
|---|---|---|
| **가시성** | 누가·무엇이·얼마를 쓰는지 실시간에 가깝게 보인다 | 월말 청구서를 보고 놀란다 |
| **책임** | 비용을 만드는 팀이 비용을 본다 (쇼백·차지백) | 인프라팀 혼자 줄이라고 압박받는다 |
| **단위 경제** | 총액이 아니라 "요청당·사용자당 비용" 으로 판단한다 | 매출이 2배 늘었는데 비용이 2배 늘었다고 혼난다 |

이 주제는 이 세 원칙을 따라 진행한다. 이 노트는 그 전제인 **"무엇에 돈을 내는가"** 다. 다음은 [단위 경제](/finops/notes/02-unit-economics), 그다음 [Kubernetes 비용](/finops/notes/03-kubernetes-cost)이다.

## 청구서의 네 덩어리

### 1. 컴퓨트 — 시간 × 크기

VM·컨테이너·서버리스는 모두 **켜져 있는 시간 × 자원 크기** 다.

| 형태 | 과금 단위 | 꺼져 있으면 | 특징 |
|---|---|---|---|
| VM (EC2, GCE) | 인스턴스·초(최소 1분) | 0 (디스크는 과금) | 가장 싸지만 노는 시간도 낸다 |
| 관리형 Kubernetes 노드 | 노드 VM + 컨트롤 플레인 시간 | 노드 0 이면 컨트롤 플레인만 | Pod 는 공짜, **노드가 돈** |
| Fargate / Cloud Run | vCPU·초 + GiB·초 (요청한 만큼) | 0 | 단가는 VM 의 1.3~2배, 유휴 0 |
| 서버리스 함수 | 호출 수 + GB·초(또는 활성 CPU 시간) | 0 | 트래픽이 적을수록 압도적으로 쌈 |

> **핵심:** 컴퓨트 단가는 대략 **vCPU·시간 $0.02~0.05, GiB·시간 $0.003~0.006** 범위다. 이 사이트 실험의 가정 단가는 vCPU·시간 $0.0316, GiB·시간 $0.0042 다. 노드 한 대(4 vCPU, 16 GiB)를 한 달 켜면 대략 `(4×0.0316 + 16×0.0042) × 730 ≈ $141`.

### 2. 스토리지 — 용량 × 시간, 그리고 요청

| 종류 | 과금 | 함정 |
|---|---|---|
| 블록(EBS, PD) | 프로비저닝한 GB·월 (+ IOPS·처리량) | **쓰지 않아도 크기만큼** 낸다. 분리된 볼륨이 고아로 남는다 |
| 오브젝트(S3, GCS) | 저장 GB·월 + 요청 수 + 꺼내기 | 작은 파일 수백만 개면 요청 비용이 저장 비용을 넘는다 |
| 스냅샷·백업 | 증분 GB·월 | 보존 정책 없으면 영원히 쌓인다 |
| 관리형 DB 스토리지 | GB·월 + I/O | 오토스케일되는 스토리지는 줄지 않는다 |

오브젝트 스토리지는 **저장 등급**(Standard → Infrequent → Archive)으로 10배까지 싸진다. 대신 꺼낼 때 요금과 최소 보존 기간이 붙는다. 로그·백업은 수명 주기 정책으로 자동 이동시키는 것이 기본이다.

### 3. 네트워크 — 가장 자주 놀라는 항목

| 흐름 | 대략 | 비고 |
|---|---|---|
| 인터넷 → 클라우드 (ingress) | 무료 | |
| 같은 AZ 안 | 무료 | 같은 서브넷 Pod 끼리 |
| **AZ 간** | GB당 $0.01 × 양방향 | 다중 AZ 복제·로드밸런서 교차 트래픽 |
| 리전 간 | GB당 $0.02~0.09 | DR 복제, 글로벌 DB |
| **인터넷으로 나가기 (egress)** | GB당 $0.05~0.12 | CDN 을 쓰면 싸진다 |
| **NAT 게이트웨이** | 시간당 + **처리 GB당** | 프라이빗 서브넷 Pod 가 외부 API·이미지 pull 을 할 때마다 |

> **주의:** 다중 AZ 로 Kafka·Redis·DB 를 복제하면 **복제 트래픽이 AZ 간 요금**이 된다. Kafka 의 replication.factor=3 은 쓰기 1GB 당 AZ 간 2GB 를 만든다. 가용성 결정이 곧 비용 결정이다([분산 시스템 — 복제](/distributed-systems/notes/04-replication)).

### 4. 관리형 서비스 — 운영을 사는 비용

관리형 Kafka·Redis·OpenSearch·관측 서비스는 **같은 자원의 VM 보다 1.5~3배** 비싸다. 그 차액으로 사는 것은 패치·백업·장애 대응·업그레이드 같은 운영 노동이다. 결정은 "우리 팀의 운영 시간 단가 × 줄어드는 시간" 과 비교해서 한다.

관측 서비스는 별도로 볼 가치가 있다. 메트릭은 **활성 시계열 수**, 로그는 **수집 GB + 보존 GB-월**, 트레이스는 **스팬 수**로 청구하는 경우가 많다 — 트래픽이 아니라 **카디널리티와 보존**이 비용을 정한다([데이터·관측 비용](/finops/notes/04-data-observability-cost)).

## 할인 구조 — 약속하면 싸진다

| 구매 방식 | 할인 | 약속 | 위험 |
|---|---|---|---|
| 온디맨드 | 0% | 없음 | 가장 비쌈 |
| **Savings Plan / CUD** | 20~50% | 시간당 지출액(달러)을 1·3년 | 사용량이 줄어도 약속한 돈은 낸다 |
| 예약 인스턴스 (RI) | 30~60% | 특정 인스턴스 패밀리·리전 1·3년 | 인스턴스 타입을 바꾸면 쓸모없어진다 |
| **스팟 / 선점형** | 60~90% | 없음 | 2분(또는 30초) 예고로 회수된다 |

사용 패턴별 정석:

```
       ┌────────────── 피크 ──────────────┐
  용량 │      ▲  스팟 (무상태 워커, 배치, CI)  │
       │      ▲  온디맨드 (예측 못 한 버스트)    │
       │──────────────────────────────────────│
       │  Savings Plan (항상 켜져 있는 바닥)     │  ← 지난 3개월 최소 사용량의 70~80%
       └────────────────────────────────────── 시간
```

- **바닥(baseline)** 만 약정한다. 최소 사용량의 70~80% 정도. 100% 를 약정하면 아키텍처 개선(예: 사용량 감소)이 오히려 손해가 된다.
- **스팟**은 "언제 죽어도 되는" 작업에: 큐 소비자, 배치, CI 러너, 상태 없는 웹 Pod(여러 AZ·여러 인스턴스 타입에 분산). Kubernetes 에선 스팟 노드 풀 + PodDisruptionBudget + `terminationGracePeriodSeconds` 로 회수 예고를 처리한다([Kubernetes 스케줄링·오토스케일](/kubernetes/notes/14-scheduling-autoscaling-deep)).
- 상태 있는 것(DB, Kafka 브로커, Redis 프라이머리)은 스팟에 두지 않는다.

## 숨은 비용 체크리스트

청구서에서 "이게 왜 이렇게 크지?" 가 나오는 단골들이다.

| 항목 | 왜 커지나 | 대처 |
|---|---|---|
| NAT 게이트웨이 처리량 | 프라이빗 Pod 가 컨테이너 이미지·외부 API 를 NAT 로 받음 | VPC 엔드포인트, 이미지 캐시(풀스루 레지스트리) |
| AZ 간 트래픽 | 로드밸런서·서비스 메시가 아무 AZ 의 Pod 로 보냄 | 토폴로지 인식 라우팅(`trafficDistribution: PreferClose`) |
| 고아 리소스 | 지운 클러스터의 디스크·스냅샷·로드밸런서·공인 IP | 태깅 + 주기적 청소 작업 |
| 로그 | 디버그 레벨을 켠 채 배포, 요청마다 전문 로그 | 레벨·샘플링·보존 정책 |
| 메트릭 카디널리티 | 사용자 ID·URL 원문 레이블 | 레이블 허용 목록 |
| 과다 프로비저닝 | requests 를 넉넉히 잡아 노드가 늘어남 | 사용량 기반 재조정(VPA 권고) |
| 개발·스테이징 상시 가동 | 밤·주말에도 켜져 있음 | 업무 시간 스케줄(약 65% 절감) |
| LLM 토큰 | 긴 시스템 프롬프트를 매 요청 반복 | 프롬프트 캐시·모델 라우팅([LLM 토큰 비용](/finops/notes/05-llm-token-cost)) |

## 예시로 보기 — 이 프로젝트를 클라우드로 옮기면

로컬에선 전부 Mac 한 대지만, 같은 구성을 클라우드에 올렸다고 가정하고 대략 계산해 보자(가정 단가, 서울 리전 근사).

| 구성 요소 | 로컬 | 클라우드 대응 | 월 추정 |
|---|---|---|---|
| kind 클러스터 (Pod 35개) | kind-study | 관리형 k8s 컨트롤 플레인 + 노드 2대(4 vCPU/16 GiB) | $73 + $282 |
| Redis | study-redis | 관리형 Redis 1 GiB, 복제본 1 | ~$60 |
| PostgreSQL | study-postgres | 관리형 PG 2 vCPU, 50 GB | ~$150 |
| Kafka | study-kafka (KRaft 1대) | 관리형 Kafka 최소 3브로커 | ~$300+ |
| 관측 스택 | Prometheus·Loki·Tempo·Grafana | 관리형 관측(시계열 5천, 로그 수 GB/월) | ~$40 |
| LLM | Ollama (무료) | gpt-5-mini, 하루 2천 질문 | ~$14 (캐시 시) |

실험 `finops-k8s-requests-vs-usage` 는 이 kind 클러스터에서 **어느 네임스페이스가 노드를 얼마나 예약했고 실제로 얼마나 쓰는지**를 계산한다. 이 Mac 에서 측정했을 때 Pod 35개 중 **20개가 requests 가 없는 BestEffort** 였고, CPU 를 예약한 kube-system 은 요청의 6% 만 썼다. 클라우드였다면 "노드 2대 중 1대는 비어 있는데 요금은 내는" 상태다.

> **팁:** 학습용 클라우드 계정에서 같은 걸 해 본다면 처음부터 **예산 알림**(월 $20, $50)과 **리소스 태그**(`project=study`)를 걸어 두자. 비용 통제는 사후가 아니라 설정 단계에서 한다([거버넌스](/finops/notes/06-governance)).

## 비용을 결정으로 바꾸는 질문들

설계 리뷰에서 다음을 묻는 습관이 FinOps 의 시작이다.

1. **상시 vs 요청 시**: 이 컴포넌트는 트래픽이 0 일 때도 돈이 드는가? 스케일 투 제로가 가능한가?
2. **복사 횟수**: 이 데이터는 몇 번 복제되고(복제본·백업·로그·분석 파이프라인), 각각 어디(AZ·리전)로 가는가?
3. **보존**: 얼마나 오래 보관하는가? 그 기간을 누가 정했는가?
4. **단위**: 이 기능의 요청당 비용은? 사용자가 10배 늘면 비용도 10배인가, 100배인가, 2배인가?
5. **약정 가능성**: 이 부하의 바닥은 얼마이고 얼마나 안정적인가?

이 질문에 숫자로 답하려면 비용을 **메트릭**으로 만들어야 한다 — 다음 노트 [단위 경제](/finops/notes/02-unit-economics)의 주제다. 용량 계획 쪽에서 같은 문제를 다룬 [성능 — 용량 계획](/performance/notes/07-capacity-planning)도 함께 보면 좋다.

## 실전에서는 어디에 쓰이나 — FinOps 지도

> FinOps 는 클라우드 비용을 "월말에 재무팀이 놀라는 숫자" 에서 "엔지니어가 설계·배포 때 보는 지표" 로 바꾸는 일이다. 실무에서는 청구서 해석, 단위 비용 대시보드, Kubernetes·관측·LLM 비용 최적화, 그리고 태깅·예산 같은 거버넌스로 나타난다.

| 서비스·상황 | 이 주제의 어떤 부분이 | 더 읽기 |
|---|---|---|
| 청구서에서 NAT·AZ 간 트래픽이 의외로 크다 | 네트워크 과금 구조, 숨은 비용 체크리스트 | 이 노트의 "청구서의 네 덩어리"·"숨은 비용" |
| Savings Plan 을 얼마나 살지 정해야 한다 | 바닥 사용량만 약정, 버스트는 온디맨드, 배치는 스팟 | 이 노트의 "할인 구조" |
| 트래픽이 2배인데 비용이 40% 올랐다 — 잘한 건가 | 요청당·주문당 단위 비용 | [단위 경제](/finops/notes/02-unit-economics) |
| 노드는 계속 늘어나는데 사용률은 낮다 | requests·배분·효율·유휴, right-sizing | [Kubernetes 비용](/finops/notes/03-kubernetes-cost) |
| 관측 SaaS 청구서가 빠르게 커진다 | 활성 시계열·로그 GB·스팬 수, 샘플링 | [데이터·관측 비용](/finops/notes/04-data-observability-cost) |
| AI 기능 출시 후 토큰 비용 급증 | 프롬프트 캐시, 모델 라우팅, 출력 제한 | [LLM 토큰 비용](/finops/notes/05-llm-token-cost) |
| "기타" 비용이 커서 누가 쓴 건지 모른다 | 태깅 강제, 예산·이상 탐지, 비용 리뷰 게이트 | [비용 거버넌스](/finops/notes/06-governance) |

**회사 규모에 따라**
- 스타트업: 계정 하나에서 시작한다. 예산 알림과 태그만 처음부터 걸고, 비싸더라도 관리형 서비스로 운영 시간을 산다 — 대개 사람 시간이 더 비싸다.
- 성장기: 비용이 매출 대비 눈에 띄기 시작한다. 쇼백 대시보드, requests 재조정, 첫 약정 구매, 관측·LLM 비용 관리가 이때 시작된다.
- 대규모 조직: 중앙 FinOps 팀이 약정 포트폴리오·도구·데이터를 맡고, 각 팀은 단위 비용 목표와 차지백을 책임진다. 아키텍처 리뷰에 비용 항목이 들어간다.

**이럴 땐 안 맞는다**
- 월 비용이 작고 엔지니어 시간이 더 비싼 단계 → 정밀 배분·차지백은 과하다. 예산 알림과 태그 정도면 충분하다.
- 총액 절감만 목표로 삼기 → 성장을 막거나 품질을 해친다. 단위 비용으로 판단한다.

**누가 매일 만나나** — 플랫폼·SRE 는 노드·네트워크·관측 비용을, 백엔드는 설계 리뷰에서 "상시로 켜 두나, 몇 번 복사하나" 질문을, ML 엔지니어는 토큰 비용을, 재무·FinOps 담당은 약정과 예산을 본다.
