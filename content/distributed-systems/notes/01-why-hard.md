## 한 대의 컴퓨터는 "결정적" 이다

단일 프로세스에서 함수 호출은 **성공하거나 실패하거나** 둘 중 하나다. 실패하면 예외가 나고, 프로세스가 죽으면 **전부** 죽는다. 메모리 읽기는 수십 ns 에 끝나고, 시계는 하나뿐이다. 프로그래머가 의식하지 않는 이 세 가지 가정 — **전부 아니면 전무(all-or-nothing), 빠르고 예측 가능한 통신, 하나의 시간** — 이 분산 시스템에서는 모두 무너진다.

```
단일 노드                         분산 시스템
----------------------------      --------------------------------------------
함수 호출 → 결과 or 예외          메시지 전송 → 결과 / 예외 / 아무것도 안 옴(영원히?)
프로세스 죽음 = 전체 죽음         노드 1개 죽음 = 나머지는 모름, 계속 동작
메모리 접근 100ns                  네트워크 RTT 0.1ms~100ms, 가끔 10초
시계 하나                           시계 N개, 서로 수십 ms 어긋남, 가끔 거꾸로 감
```

> 분산 시스템의 정의(Leslie Lamport): "내가 존재하는지도 몰랐던 컴퓨터의 고장 때문에 내 컴퓨터를 쓸 수 없게 되는 시스템."

## 부분 실패(partial failure)

가장 중요한 개념 하나만 꼽으라면 **부분 실패**다. 노드 A 가 노드 B 에 "주문 저장해" 를 보내고 응답이 없을 때, A 는 다음 중 무엇이 일어났는지 **알 수 없다**:

1. 요청이 네트워크에서 유실됐다 (B 는 아무것도 모른다)
2. B 가 요청을 받았지만 처리 전에 죽었다
3. B 가 처리를 **완료했지만** 응답이 유실됐다
4. B 가 느릴 뿐이다 (GC 멈춤, 디스크 I/O, 과부하) — 응답이 곧 올 수도

1·2 면 재시도가 맞고, 3 이면 재시도가 **중복**을 만들고, 4 면 재시도가 B 를 더 괴롭힌다. 응답 없음은 이 네 경우를 구분할 정보를 주지 않는다. 이것이 **타임아웃·재시도·멱등성**이 분산 시스템의 기본 어휘가 되는 이유다 ([회복력 패턴](/architecture/notes/04-resilience)).

### 예시: 결제 요청

```
클라이언트 → 결제 서비스: "카드 1234 로 10,000원 결제" … 타임아웃
클라이언트: 재시도? → 3번 경우면 20,000원 결제
클라이언트: 포기?   → 1번 경우면 결제 안 됨
```

해법은 요청에 **멱등 키**(idempotency key, 예: 주문 ID) 를 붙여 서버가 "이미 처리한 키" 를 기억하게 하는 것이다. 그러면 재시도가 안전해진다. 이 패턴은 [멱등성과 정확히 한 번](/distributed-systems/notes/06-transactions-coordination) 에서 깊게 다룬다.

## 분산 컴퓨팅의 8가지 오류 (Fallacies of Distributed Computing)

Peter Deutsch 와 Sun 의 동료들이 1990년대에 정리한, **모두가 처음엔 믿는 거짓 가정**이다.

| # | 오류 | 현실 | 이 프로젝트에서 본 사례 |
|---|---|---|---|
| 1 | 네트워크는 신뢰할 수 있다 | 패킷 유실, 스위치 고장, 케이블 뽑힘, 방화벽 변경 | `chaos-redis-hang` 에서 Redis 가 응답 없음 → 클라이언트 타임아웃 없으면 영원히 대기 |
| 2 | 지연은 0 이다 | 같은 랙 0.1ms, 리전 간 80ms, 대륙 간 200ms | Redis 파이프라인 실험: RTT 가 명령 실행보다 100배 큼 ([파이프라이닝](/redis/notes/06-pipelining)) |
| 3 | 대역폭은 무한하다 | 10Gbps 도 큰 값(1MB) ×10,000 rps 면 포화 | Kafka 배치·압축이 존재하는 이유 |
| 4 | 네트워크는 안전하다 | 평문은 읽히고, 내부망도 침투당한다 | TLS·mTLS, Redis ACL ([보안](/security/notes/02-tls-certificates)) |
| 5 | 토폴로지는 바뀌지 않는다 | Pod 는 매분 재스케줄되고 IP 가 바뀐다 | Kubernetes Service/DNS 가 필요한 이유 ([Service·Ingress](/kubernetes/notes/04-service-ingress)) |
| 6 | 관리자는 한 명이다 | 클라우드·DB팀·네트워크팀·외부 API 각각 다른 정책 | 외부 API 의 레이트리밋이 내 장애가 됨 |
| 7 | 전송 비용은 0 이다 | 직렬화·복사·암호화 CPU, 클라우드 egress 요금 | gRPC/Protobuf vs JSON, 압축 트레이드오프 |
| 8 | 네트워크는 균질하다 | MTU·프록시·로드밸런서·NAT 가 제각각 | 로드밸런서 idle timeout 이 긴 요청을 끊음 |

## 네트워크 모델: 동기 vs 비동기

이론에서 네트워크를 두 극단으로 모델링한다.

- **동기(synchronous) 모델**: 메시지 지연에 **알려진 상한** Δ 가 있고, 프로세스 속도에도 상한이 있다. 상한을 넘으면 "죽었다" 고 확정할 수 있다. 현실에는 없다 — 하지만 데이터센터 안에서 "99.99% 는 Δ 안에 도착" 은 흔하다.
- **비동기(asynchronous) 모델**: 지연 상한이 **없다**. 메시지는 언젠가 도착하지만 언제인지 모른다. 그래서 "느린 노드" 와 "죽은 노드" 를 **구분할 수 없다**. FLP 불가능성 결과([합의](/distributed-systems/notes/05-consensus))가 이 모델에서 나온다.
- **부분 동기(partially synchronous)**: 대부분의 시간은 동기처럼 동작하지만 가끔 비동기 구간이 온다(GC 멈춤, 네트워크 혼잡). 실제 시스템(Raft, Paxos)은 이 모델을 가정한다: **안전성은 항상, 진행(liveness)은 네트워크가 동기적일 때만** 보장.

> 타임아웃은 비동기 네트워크를 억지로 동기처럼 다루는 장치다. 너무 짧으면 멀쩡한 노드를 죽었다고 오판(false positive)하고, 너무 길면 장애 감지가 느려진다. 적응형 타임아웃(측정한 RTT 분포의 p99 + 여유)이 그 절충이다.

## 장애 모델: 무엇이 어떻게 고장 나는가

| 모델 | 정의 | 예 | 다루는 난이도 |
|---|---|---|---|
| **Crash-stop** | 노드가 멈추면 영원히 멈춤 | 전원 차단 후 복구 없음 | 가장 쉬움(이론 가정) |
| **Crash-recovery** | 멈췄다가 **안정 저장소**의 상태로 돌아옴. 메모리는 잃음 | 프로세스 재시작, Pod 재스케줄 | 실제 시스템의 표준 가정. WAL·체크포인트가 필요 |
| **Omission** | 메시지를 보내거나 받는 데 실패 | 패킷 유실, 큐 가득 참 | crash 와 비슷하게 처리 |
| **Timing** | 너무 느리거나 빠름 | GC 멈춤 30초 → 리스가 만료됐는데 리더인 줄 앎 | 매우 위험 — 펜싱 토큰이 필요한 이유 |
| **Byzantine** | **임의로** 잘못 동작, 거짓말 | 버그·악의·비트 플립 | 가장 어려움. 3f+1 노드로 f 개 허용. 블록체인·항공 |

대부분의 인프라(Redis·Kafka·etcd·PostgreSQL)는 **crash-recovery + 비잔틴 아님** 을 가정한다. 내부 시스템끼리 서로 거짓말하지 않는다는 가정이다. 다만 **타이밍 장애**는 모두가 과소평가한다. 다음은 실제로 일어난 일의 전형:

```
t=0   노드 A 가 분산 락을 얻음 (TTL 10s)
t=1   A 가 full GC 로 멈춤 (12초)
t=10  락 만료. 노드 B 가 락 얻음, 파일 쓰기 시작
t=13  A 가 깨어남 — 자기가 락을 가진 줄 알고 파일 쓰기 → 손상
```

A 는 고장 나지 않았다. 단지 느렸다. 이 시나리오를 막는 것이 **펜싱 토큰**이고([분산 락](/redis/notes/09-distributed-lock) 의 Redlock 논쟁), "락을 가졌다" 는 로컬 믿음이 분산 환경에서 얼마나 위험한지 보여 준다.

## 믿을 수 없는 시계

노드마다 수정 진동자(quartz)가 있고 온도·전압에 따라 하루 수십 ms 씩 **드리프트**한다. NTP 가 주기적으로 맞추지만:

- 맞추는 순간 시계가 **뒤로 갈 수** 있다(step). `Date.now()` 의 차이로 경과 시간을 재면 음수가 나온다.
- 리프 초(leap second), VM 일시 정지, 네트워크 지연 때문에 수십~수백 ms 오차가 흔하다.
- 그래서 "타임스탬프가 큰 쪽이 나중 쓰기" (last-write-wins) 는 **데이터를 조용히 잃는다**.

```ts
// 잘못: 벽시계로 경과 시간
const t0 = Date.now(); await work(); const elapsed = Date.now() - t0;   // NTP step 이면 음수/거대값

// 옳음: 단조 시계
const t0 = process.hrtime.bigint(); await work(); const elapsed = Number(process.hrtime.bigint() - t0) / 1e6;
```

시간과 순서는 [다음 노트](/distributed-systems/notes/02-time-and-order) 전체 주제다.

## 그럼에도 분산하는 이유

| 동기 | 설명 |
|---|---|
| **확장성** | 한 대의 한계(CPU·메모리·디스크·네트워크)를 넘는 부하 |
| **가용성** | 한 대가 죽어도 서비스 유지 (복제본, 다중 AZ) |
| **지연** | 사용자 가까운 곳에 데이터 (엣지, 멀티 리전) |
| **격리** | 팀·배포·장애 도메인의 분리 (마이크로서비스) |

대가는 위에서 본 복잡성이다. "분산하지 않아도 되면 하지 마라" 가 첫 번째 원칙이고, 해야 한다면 이 과목이 그 비용을 이해하는 도구다 ([아키텍처 원칙](/architecture/notes/01-principles-tradeoffs)).

## 예시로 보기 — 이 프로젝트에서

각 구성 요소가 어떤 모델을 가정하는지 보면 설계가 보인다.

| 시스템 | 장애 모델 가정 | 부분 실패 대응 | 시계 의존 |
|---|---|---|---|
| **Redis 단일** | crash-recovery(RDB/AOF) | 클라이언트 타임아웃·재연결 (ioredis `retryStrategy`) | 키 만료에 벽시계 사용 — 복제본은 마스터가 보낸 DEL 을 따름 |
| **Redis Sentinel** | 쿼럼으로 마스터 죽음 판정(`down-after-milliseconds`) | 페일오버 중 쓰기 유실 가능(비동기 복제) | 판정 타임아웃이 핵심 매개변수 ([복제·Sentinel](/redis/notes/11-replication-sentinel-cluster)) |
| **Kafka** | 브로커 crash-recovery, 컨트롤러는 KRaft(Raft) 합의 | `acks=all` + ISR 로 유실 방지, 프로듀서 재시도 + 멱등 ([전달 보장](/kafka/notes/04-delivery-guarantees)) | 세션 타임아웃으로 컨슈머 죽음 판정 |
| **PostgreSQL** | crash-recovery(WAL) | 동기 복제면 커밋이 복제본 확인까지 대기 | 트랜잭션 ID 는 논리 카운터, 시계 아님 |
| **Kubernetes** | etcd(Raft) 가 진실, 노드는 하트비트로 판정 | 노드 NotReady → 5분 후 Pod 퇴거(`tolerationSeconds`) | 리스 기반 리더 선출(controller-manager) |

`chaos-redis-hang` 실험([장애 카탈로그](/chaos/notes/02-failure-catalog))은 1번 오류와 4번 경우(느린 노드)를 직접 보여 준다. `docker pause` 로 얼린 Redis 는 TCP 연결이 살아 있어 "죽었다" 는 신호가 전혀 없다. 타임아웃이 없는 클라이언트는 무한 대기하고, 있는 클라이언트는 N초 후 실패한다 — 이것이 "응답 없음은 정보가 아니다" 의 실물이다.

## 설계자의 체크리스트 (이 과목 전체의 지도)

1. 메시지가 유실·지연·중복·순서 바뀜 될 수 있다고 가정했는가? → 재시도 + 멱등 + 순서 보장 수단
2. 노드가 **느린 것**과 **죽은 것**을 구분할 수 없다고 가정했는가? → 타임아웃·리스·펜싱 토큰
3. 시계를 믿지 않았는가? → 논리 시계, 단조 시계, 버전 벡터
4. 동시에 둘이 리더라고 믿을 수 있는가? → 합의·쿼럼·에포크
5. 부분 실패 후 복구 경로가 있는가? → WAL·체크포인트·재처리 가능한 로그
