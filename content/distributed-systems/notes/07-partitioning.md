## 파티셔닝(샤딩)이 필요한 순간

복제는 **같은** 데이터를 여러 곳에 두고, 파티셔닝은 **다른** 데이터를 여러 곳에 둔다. 한 노드의 디스크·메모리·쓰기 처리량을 넘을 때 필요하다. 목표는 **데이터와 부하를 고르게** 나누는 것이고, 실패하면 **skew**(한 노드에 몰림)와 **핫스팟**(특정 키에 몰림)이 생긴다. 보통 복제와 함께 쓴다(파티션마다 리더 + 팔로워).

## 키로 나누는 두 방식

### 범위(range) 파티셔닝

키를 정렬해 연속 구간을 노드에 배정(백과사전 권처럼). HBase, Bigtable, CockroachDB, MongoDB(범위 샤드), PostgreSQL 범위 파티션([파티셔닝](/postgres/notes/06-partitioning-scale)).

- 장점: **범위 질의**가 한 노드에서 끝남(`timestamp BETWEEN`), 정렬 순회 효율.
- 단점: 키가 시간순이면 **최신 구간에 쓰기가 몰림**(타임스탬프 키 = 항상 마지막 노드가 핫). 대책: 키 앞에 다른 요소(센서 ID)를 붙여 `sensor_id:timestamp` — 대신 "모든 센서의 최근 1분" 은 전 노드 질의.
- 경계를 **동적**으로 조정(구간이 커지면 쪼개기, split) — 운영 복잡도.

### 해시 파티셔닝

`hash(key) mod N` 또는 해시 범위를 노드에 배정. 고른 분포가 목표. Cassandra(Murmur3 토큰 링), Redis Cluster(CRC16 슬롯), Kafka(murmur2 → 파티션), DynamoDB.

- 장점: 균등 분포, 핫 범위 없음.
- 단점: **범위 질의 불가**(모든 노드에 흩어짐). `mod N` 이면 N 이 바뀔 때 **거의 모든 키가 이동** → 일관 해싱·슬롯이 필요.
- Cassandra 의 절충: **파티션 키는 해시, 클러스터링 키는 범위** — `(user_id, timestamp)` 면 사용자별로 시간 범위 질의가 한 파티션 안에서 가능.

## 일관 해싱(consistent hashing)

노드와 키를 같은 해시 공간(링, 0~2^32)에 놓고, 키는 시계 방향으로 가장 가까운 노드에 속한다. 노드를 추가/제거하면 **인접 구간의 키만** 이동(평균 K/N 개).

```
링:  0 ────── N1(100) ────── N2(400) ────── N3(800) ────── 2^32
키 h=250 → N2,  h=900 → N1(한 바퀴 돌아)
N4(600) 추가 → 400~600 구간의 키만 N3 에서 N4 로 이동. 나머지는 그대로.
```

문제: 노드가 적으면 구간이 불균등. 해법 **가상 노드(vnode)**: 노드마다 수십~수백 개의 가상 지점을 링에 뿌린다. 분산이 고르고, 노드 제거 시 그 부하가 **모든** 노드에 조금씩 나뉜다. Cassandra 기본 256(최근 16), Riak, Dynamo, 로드밸런서(Ketama, Maglev 는 변형).

## 고정 슬롯 방식 — Redis Cluster 와 Kafka

일관 해싱의 대안은 **파티션 수를 노드 수보다 훨씬 많게 고정**하고, 파티션을 노드에 배정하는 테이블을 관리하는 것이다.

### Redis Cluster: 16384 슬롯

- `slot = CRC16(key) mod 16384`. 각 마스터가 슬롯 범위를 소유(3마스터면 0-5460, 5461-10922, 10923-16383).
- 노드 추가 = **슬롯 이동**(`CLUSTER SETSLOT … MIGRATING/IMPORTING` + `MIGRATE` 키 단위). 온라인으로, 키 단위로 점진적. 이동 중 해당 키 접근은 `ASK` 리다이렉트.
- 클라이언트는 슬롯 맵을 캐시하고 바로 올바른 노드로. 틀리면 `MOVED` 응답으로 갱신(스마트 클라이언트).
- **해시 태그** `{user:42}:cart` → 중괄호 안만 해시 → 같은 슬롯 → 다중 키 명령·트랜잭션 가능. 반대로 모든 키에 같은 태그를 쓰면 한 슬롯에 몰린다(핫스팟 제조기).
- 왜 16384? 하트비트(gossip)에 슬롯 비트맵(2KB)을 실어야 하고, 1000 노드 이상은 어차피 비현실적이라는 설계 판단. [Redis Cluster](/redis/notes/11-replication-sentinel-cluster) 와 `/diagrams/redis-cluster-slots.svg`.

### Kafka: 파티션은 고정, 배정은 이동

- 토픽 생성 시 파티션 수 결정. `partition = murmur2(key) mod P`(키 없으면 sticky 라운드로빈).
- **파티션 수를 늘리면 같은 키가 다른 파티션으로** 가 순서가 깨진다 → 처음부터 넉넉히(보통 처리량/파티션당 처리량 + 여유, 수십~수백). 줄이기는 불가.
- 브로커 추가 시 파티션 **재배치**(`kafka-reassign-partitions`, Cruise Control): 파티션 전체 로그를 복사 → 네트워크 부하 큼, 스로틀 필요.
- 컨슈머 쪽 파티션 배정은 **리밸런스**: 그룹 멤버가 바뀌면 파티션을 재분배. 기본 eager 는 전원 정지 후 재배정(stop-the-world), cooperative-sticky 는 바뀌는 것만 이동. [컨슈머 그룹](/kafka/notes/03-consumer-groups).

| | 일관 해싱(vnode) | Redis 슬롯 | Kafka 파티션 |
|---|---|---|---|
| 단위 수 | 노드당 vnode 수 × 노드 | 16384 고정 | 토픽마다 고정(변경 위험) |
| 배정 정보 | 링(해시로 계산) | 슬롯→노드 테이블(gossip) | 파티션→브로커 테이블(컨트롤러 메타데이터) |
| 이동 단위 | vnode 구간 | 슬롯(키 단위 점진) | 파티션 전체 로그 |
| 다중 키 연산 | 어려움 | 해시 태그 | 같은 키 = 같은 파티션 |

## 핫스팟

해시가 고르게 나눠도 **특정 키**가 폭주하면(유명인 트윗, 세일 상품, `global:counter`) 그 키를 가진 노드만 죽는다. 대책:

| 대책 | 방법 | 비용 |
|---|---|---|
| **키 분할(salting)** | `counter:{0..9}` 10개에 나눠 쓰고 읽을 땐 합산 | 읽기 10배, 핫 키 목록 관리 |
| **로컬 캐시** | 핫 키를 앱 메모리에 짧은 TTL 로 | 약간 stale, 메모리 |
| **복제본 읽기** | 읽기 핫스팟은 복제본으로 분산 | 쓰기 핫스팟엔 무력 |
| 요청 병합 | 같은 키 요청을 묶어 한 번(싱글플라이트) | 지연 약간 |
| 쓰기 배치 | 카운터를 로컬에서 모아 주기적 플러시 | 정확도·지연 |

Redis 의 `--hotkeys`(`redis-cli --hotkeys`, LFU 정책 필요)와 `CLIENT TRACKING`, Kafka 의 파티션별 바이트 메트릭으로 **먼저 측정**한다.

## 요청 라우팅

클라이언트가 "키 k 는 어느 노드?" 를 어떻게 아나.

1. **노드 아무 데나 → 리다이렉트/포워딩**: Redis Cluster 의 MOVED(클라이언트가 다시 보냄), Cassandra 코디네이터(노드가 대신 전달).
2. **라우팅 계층(프록시)**: Twemproxy, Envoy, Vitess(MySQL), Citus 코디네이터. 클라이언트 단순, 프록시가 병목/장애점.
3. **스마트 클라이언트**: 파티션 맵을 클라이언트가 가짐(Kafka, Redis Cluster 의 ioredis/lettuce, Cassandra 드라이버 token-aware). 가장 빠름, 클라이언트 복잡.

맵의 출처: ZooKeeper/etcd(Kafka 과거, HBase), gossip(Cassandra, Redis Cluster), 컨트롤러(Kafka KRaft). 변경 전파 지연 중엔 stale 맵으로 잘못 보내고 리다이렉트로 고친다.

## 보조 인덱스와 조인

파티션 키가 아닌 필드로 찾기(`WHERE color='red'`)는 어렵다.

- **로컬 보조 인덱스(document-partitioned)**: 각 파티션이 자기 데이터의 인덱스. 질의는 **모든 파티션**에 보내 합침(scatter/gather) — 꼬리 지연이 가장 느린 노드. Elasticsearch, Cassandra SAI, MongoDB.
- **전역 보조 인덱스(term-partitioned)**: 인덱스 자체를 인덱스 값으로 파티셔닝. 질의는 한 곳, 쓰기는 **여러 파티션**(비동기 갱신 → 인덱스가 stale). DynamoDB GSI.
- 분산 조인은 데이터 이동(shuffle)이라 비싸다 → 같은 키로 **co-location**(Citus 의 colocated tables, 주문과 주문 항목을 같은 customer_id 로) 하거나 비정규화.

## 리밸런스가 안전하려면

1. 이동 중에도 **읽기·쓰기 가능**(점진적 이동 + 리다이렉트).
2. 이동량 최소(일관 해싱, 슬롯).
3. **자동 리밸런스는 위험**할 수 있다: 노드가 잠깐 느려진 걸 죽었다고 판단해 리밸런스 → 네트워크 부하 → 더 느려짐 → 연쇄. Kafka 는 수동, Cassandra 도 수동 `nodetool`, Redis Cluster 도 수동 reshard. Elasticsearch 는 자동이지만 지연 설정(`delayed_timeout`)으로 완충. 사람이 승인하는 설계가 흔한 이유.
4. 이동 중 **일관성**: 키 이동 후 옛 노드의 사본 삭제, 양쪽에 쓰이지 않게(Redis 는 ASK 로 "새 노드에 한 번만 물어봐").

## 예시로 보기 — 이 프로젝트에서

**`pnpm redis:cluster`**(7001-7006, 마스터 3 + 복제본 3): `redis-cli -c -p 7001` 로 접속해 `SET a 1` 을 치면 `-> Redirected to slot [15495] located at 127.0.0.1:7003` 처럼 MOVED 를 따라간다. `CLUSTER KEYSLOT user:42` 와 `CLUSTER KEYSLOT {user:42}:cart` 로 해시 태그가 같은 슬롯을 만드는 걸 확인. `redis-cli --cluster reshard 127.0.0.1:7001` 로 슬롯 100개를 옮기며 `CLUSTER NODES` 의 `[slot->-node]` 마이그레이션 표시를 본다 ([Cluster 노트](/redis/notes/11-replication-sentinel-cluster)).

**Kafka 파티션 실험**(`/kafka/lab` 의 키·순서 실험): 같은 키가 같은 파티션으로 가서 순서가 지켜지는 것, 키 없는 메시지가 파티션에 흩어지는 것을 본다. 파티션 수를 3 → 6 으로 늘린 뒤 같은 키가 **다른 파티션**으로 가는 것을 직접 확인하면 "파티션 수는 처음에 정한다" 가 왜 규칙인지 체감된다.

**PostgreSQL 파티션 프루닝**(`pg-partition-pruning` 실험): 단일 노드 안의 파티셔닝이지만 원리는 같다 — `WHERE created_at >= …` 가 범위 파티션 하나만 스캔(프루닝). 범위 파티셔닝의 장점(범위 질의 국소화)과 단점(최신 파티션 핫)을 작은 규모로 볼 수 있다. Citus 로 가면 같은 테이블이 노드 간으로 나뉜다.

**이 앱의 키 설계**: `progress:checks:<subject>/<slug>` 는 Cluster 로 가도 노트별로 흩어진다. 만약 `progress:*` 를 한 트랜잭션에 다뤄야 했다면 `{progress}:…` 태그로 한 슬롯에 묶어야 하고, 그러면 진행률 전체가 한 마스터에 몰린다 — 키 설계 = 파티셔닝 설계.

## 실전에서는 어디에 쓰이나

> 데이터나 쓰기 처리량이 한 대를 넘을 때 파티셔닝이 등장한다. 키를 어떻게 고르느냐가 곧 확장성과 핫스팟을 결정하므로, 실무에서는 "샤드 키 설계" 라는 이름으로 가장 오래 고민하는 결정 중 하나다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 대형 커머스 주문 DB | 단일 MySQL·PostgreSQL 의 쓰기 한계 | `customer_id` 해시 샤딩 + 주문·주문 항목 co-location (Vitess·Citus) | 수직 확장·읽기 복제본으로 버티기 |
| 캐시 클러스터 | 메모리 한계를 넘는 캐시 | Redis Cluster 16384 슬롯, 다중 키 연산은 해시 태그 | 클라이언트 측 일관 해싱(Ketama) |
| 이벤트 스트리밍 | 키별 순서 유지 + 병렬 소비 | 키로 Kafka 파티션 결정, 파티션 수를 처음부터 넉넉히 | 파티션 하나(순서 보장, 처리량 한계) |
| SNS·라이브 커머스 | 유명인·인기 상품에 몰리는 핫 키 | 키 salting(`counter:{0..9}`), 로컬 캐시, 요청 병합 | 해당 노드만 증설(근본 해결 아님) |
| IoT·시계열 수집 | 최신 구간에 쓰기 집중 | `sensor_id:timestamp` 복합 키, 시간 범위 파티션 | 순수 타임스탬프 범위 키(마지막 노드가 핫) |
| 로그·상품 검색 | 샤드 간 검색 지연 | 문서 파티션 로컬 인덱스 + scatter/gather, 샤드 수 설계 | 전역 인덱스(쓰기 비용·지연 갱신) |

**이럴 땐 안 맞는다**
- 아직 한 대로 들어가는 데이터: 샤딩은 조인·트랜잭션·운영을 모두 어렵게 한다. 단일 노드 내 파티셔닝(PostgreSQL 범위 파티션)이나 복제본으로 먼저 버틴다.
- 파티션 키가 아닌 필드로 주로 조회하는 워크로드: 매번 전 샤드 질의가 된다. 접근 패턴을 먼저 정하고 키를 고르거나 검색 엔진으로 분리한다.

**누가 매일 만나나** — 백엔드 개발자는 Redis 키·Kafka 메시지 키를 정할 때, 데이터베이스 엔지니어는 샤드 리밸런스와 핫 파티션 지표를 볼 때 만난다.

**면접·실무 단골 질문**
- Q. `hash mod N` 대신 일관 해싱·고정 슬롯을 쓰는 이유는? → N 이 바뀔 때 거의 모든 키가 이동하는 것을 막고 이동량을 최소화한다.
- Q. Kafka 파티션 수를 나중에 늘리면? → 같은 키가 다른 파티션으로 가서 키별 순서가 깨진다.

## 실습 체크리스트

- [ ] `redis:cluster` 에서 `CLUSTER KEYSLOT` 으로 해시 태그를 실험하고, `MSET` 이 다른 슬롯 키에 대해 `CROSSSLOT` 오류를 내는 것을 확인
- [ ] `--cluster reshard` 로 슬롯을 옮기는 동안 다른 터미널에서 `SET/GET` 을 반복해 `ASK` 리다이렉트를 관찰
- [ ] 일관 해싱 링을 100줄 안에 구현하고, vnode 1개 vs 100개일 때 노드 3개의 키 분포 표준편차를 비교
- [ ] Kafka 토픽 파티션을 늘린 뒤 같은 키의 파티션 번호가 바뀌는지 확인
- [ ] 자신의 서비스에서 "유명인 문제" 가 생길 키를 찾고 salting 설계를 적어 본다
