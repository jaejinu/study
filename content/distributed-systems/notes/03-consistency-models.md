## 일관성 모델이란

**일관성 모델**은 "복제된 데이터에 대해 읽기와 쓰기가 어떤 순서로 보이는가" 에 대한 시스템과 클라이언트 사이의 **계약**이다. 강할수록 프로그래머가 편하고(단일 노드처럼 생각 가능), 약할수록 지연이 낮고 가용성이 높다. 모델을 모르고 쓰면 "가끔 옛날 값이 읽힌다" 같은 버그가 재현 불가능한 형태로 나타난다.

```
강함  ┌─ 선형화 (linearizability)      "하나의 복사본, 실시간 순서"
      ├─ 순차 일관성 (sequential)       "하나의 전역 순서, 실시간은 아님"
      ├─ 인과 일관성 (causal)           "인과 관계만 보존"
      ├─ 세션 보장 (RYW, 단조 읽기 …)   "내 세션 안에서만 말이 되게"
약함  └─ 최종 일관성 (eventual)         "언젠가는 같아진다"
```

## 선형화(Linearizability) — "복사본이 하나인 척"

정의: 모든 연산이 **호출과 응답 사이의 어느 한 순간에 원자적으로** 일어난 것처럼 보이고, 그 순간들의 순서가 **실시간 순서**와 일치한다. 쉽게: 쓰기가 완료(응답)된 뒤에 시작한 읽기는 **반드시** 그 쓰기(또는 더 새 값)를 본다.

```
클라이언트 A: ──[ write x=1 ]──────────────
클라이언트 B: ───────────────[ read x ]──── → 반드시 1 (A 의 응답 후 시작했으므로)
클라이언트 C: ────[ read x ]──────────────── → 0 또는 1 (겹치므로 둘 다 OK, 단 한 번 1 을 봤으면 이후 0 불가)
```

- 필요한 곳: 리더 선출, 분산 락, 유일성 제약(계정 이름 중복), 잔액 차감, "정확히 하나의 리더" 보장. 이런 건 **CAS(compare-and-set)** 가 선형화돼야 한다.
- 구현: 단일 리더 + 동기 복제 + 리더에서만 읽기(또는 Raft 의 read index / lease read). etcd·ZooKeeper(쓰기)·Consul·Spanner.
- 비용: 모든 연산이 리더를 거치고 쿼럼 응답을 기다림. 리전 간이면 수십~수백 ms. 네트워크 분단 시 소수 쪽은 **불가용**.

> 함정: "리더에서 읽으면 선형화" 는 리더가 **정말 리더일 때**만. 옛 리더가 분단돼 자기가 리더인 줄 알고 stale 값을 주면 깨진다. Raft 는 읽기 전에 쿼럼 하트비트(read index)로 확인하거나 리스(lease)를 쓴다.

## 순차 일관성(Sequential)

모든 프로세스가 **같은 전역 순서**로 연산을 보되, 그 순서가 실시간과 일치할 필요는 없다. 각 프로세스의 자기 연산 순서는 보존된다. 선형화에서 "실시간" 조건을 뺀 것. 예: ZooKeeper 의 읽기는 팔로워에서 하므로 stale 할 수 있지만 모든 클라이언트가 같은 순서의 상태를 본다(순차 + 세션 보장).

## 인과 일관성(Causal)

**인과적으로 연결된** 쓰기만 순서가 보존되고, 동시(concurrent) 쓰기는 노드마다 다른 순서로 보여도 된다. [happens-before](/distributed-systems/notes/02-time-and-order) 가 바로 이 "인과" 다.

```
A: "저녁 먹을래?" (p1) → B: "좋아!" (p2, p1 을 읽고 씀)
인과 일관성: p2 를 본 사람은 반드시 p1 도 본다. (댓글이 원글보다 먼저 보이는 일 없음)
동시 쓰기: C 가 p1 과 무관하게 "날씨 좋다" 를 쓰면 p1 과의 순서는 자유.
```

분단 중에도 가용한(available) 모델 중 **가장 강한** 모델이다. 구현은 벡터 시계/버전 벡터 또는 의존성 추적(COPS, MongoDB causal sessions). 비용은 메타데이터.

## 세션 보장(Session Guarantees)

전역 모델을 포기하고 **한 클라이언트의 세션 안에서만** 말이 되게 한다. 가장 실용적이고 자주 필요한 네 가지:

| 보장 | 의미 | 깨졌을 때 증상 | 구현 |
|---|---|---|---|
| **Read-your-writes** | 내가 쓴 건 내가 읽는다 | 프로필 수정 후 새로고침하면 옛 값 | 쓴 직후엔 리더에서 읽기, 또는 쓰기의 LSN/버전을 세션에 기억하고 복제본이 그 버전 이상일 때만 응답 |
| **단조 읽기(Monotonic reads)** | 한 번 본 값보다 옛 값은 안 본다 | 새로고침할 때마다 댓글이 생겼다 없어졌다 | 세션을 같은 복제본에 고정(sticky), 또는 마지막 본 버전 이상만 |
| **단조 쓰기** | 내 쓰기는 내가 쓴 순서로 적용 | 수정 → 삭제 했는데 수정이 삭제 뒤에 적용 | 쓰기를 같은 리더로, 순서 번호 |
| **Writes-follow-reads** | 읽은 것에 기반한 쓰기는 그 읽기 이후로 | 원글을 읽고 단 댓글이 원글보다 먼저 복제 | 읽은 버전을 쓰기에 의존성으로 첨부 |

## 최종 일관성(Eventual)

"쓰기가 멈추면 **언젠가** 모든 복제본이 같은 값으로 수렴한다." 그 사이 어떤 순서·어떤 값도 읽힐 수 있다. 사실 보장이라기보다 **liveness 약속**이다. 수렴 방법이 필요하다: LWW(시계 — 위험), 버전 벡터 + 애플리케이션 병합, [CRDT](/distributed-systems/notes/04-replication). DNS, Redis 비동기 복제본 읽기, S3(지금은 강한 일관성으로 바뀜), Cassandra 기본값.

## CAP 정리 — 정확히 무엇을 말하나

Brewer 의 추측(2000)을 Gilbert & Lynch 가 증명(2002). **정확한 진술**:

> 비동기 네트워크에서 **네트워크 분단(P)** 이 일어났을 때, 시스템은 **선형화(C)** 와 **모든 요청에 응답(A)** 을 **동시에** 보장할 수 없다.

흔한 오해 세 가지:

1. "CA/CP/AP 중 둘을 고른다" — 아니다. P 는 **선택이 아니라 현실**이다(네트워크는 분단된다). 선택은 "분단이 일어났을 때 C 를 포기할지 A 를 포기할지" 다.
2. "C" 는 ACID 의 C(제약) 가 아니라 **선형화**다. "A" 는 "99.9% 가용성" 이 아니라 "**모든** 살아 있는 노드가 **모든** 요청에 성공 응답" 이라는 매우 강한 정의다.
3. 분단이 없을 때는 CAP 가 아무 말도 하지 않는다 — 그 공백을 PACELC 가 채운다.

```
분단 발생: 소수 파티션에 요청이 옴
  CP 선택: "리더가 아니라 모릅니다" (에러/타임아웃) → 일관성 유지, 가용성 포기. etcd, ZooKeeper, HBase, 동기 복제 PG
  AP 선택: 로컬 값으로 응답, 나중에 병합     → 가용성 유지, 일관성 포기. Cassandra, DynamoDB(eventual), CouchDB, Redis 비동기 복제본 읽기
```

### PACELC (Abadi, 2012)

**P**artition 이면 **A** vs **C**; **E**lse(정상일 때) **L**atency vs **C**onsistency. 정상 상태에서도 강한 일관성은 동기 복제 = 지연 비용이다.

| 시스템 | 분단 시 | 정상 시 |
|---|---|---|
| etcd / ZooKeeper / Spanner | C | C (쿼럼 대기) |
| Cassandra / Dynamo (기본) | A | L |
| PostgreSQL 동기 복제 | C (복제본 죽으면 커밋 멈춤 — 설정에 따라) | C |
| PostgreSQL 비동기 복제 | A (복제본 읽기 stale) | L |
| Redis Sentinel | A 에 가까움(`min-replicas-to-write` 로 C 쪽으로 조정) | L |
| Kafka (`acks=all`, ISR) | C (ISR 이 `min.insync.replicas` 미만이면 쓰기 거부) | C (ISR 대기) |

## 일관성 모델 vs 트랜잭션 격리 수준

둘은 다른 축이다. **일관성 모델**은 단일 객체의 복제본 간 순서(분산), **격리 수준**은 여러 객체를 묶은 트랜잭션 간 간섭(동시성). 하나로 합친 지도가 Jepsen 의 "consistency models" 그래프다 — 맨 위가 **Strict Serializable**(= 직렬화 + 선형화).

| 축 | 가장 강함 | 예 |
|---|---|---|
| 분산 복제 | 선형화 | etcd CAS |
| 트랜잭션 | 직렬화(Serializable) | PG `SERIALIZABLE` ([MVCC·격리](/postgres/notes/03-mvcc-isolation)) |
| 둘 다 | Strict Serializable | Spanner, CockroachDB(대체로), FoundationDB |

## 어느 모델을 고를까

| 데이터/연산 | 필요한 모델 | 이유 |
|---|---|---|
| 리더 선출, 락, 유일 ID 발급 | 선형화 | 둘이 동시에 성공하면 재앙 |
| 잔액·재고 차감 | 선형화 또는 직렬화 트랜잭션 | 음수 재고 금지 |
| 사용자 프로필 수정 후 표시 | RYW + 단조 읽기 | "저장했는데 안 바뀜" 방지 |
| 댓글·타임라인 | 인과 | 답글이 원글보다 먼저 보이면 안 됨 |
| 좋아요 수, 조회 수, 메트릭 | 최종 | 약간 틀려도 됨, 쓰기 폭주 |
| 캐시 | 최종 + TTL | 원천이 진실 ([캐싱 패턴](/redis/notes/08-caching-patterns)) |

## 예시로 보기 — 이 프로젝트에서

**Redis 복제본 읽기**: `pnpm redis:ha` 의 마스터-복제본은 비동기 복제다. 마스터에 `SET` 직후 복제본에서 `GET` 하면 옛 값이 나올 수 있다(보통 1ms 이내지만 보장 없음). `WAIT 1 1000` 을 쓰면 복제본 1개가 받을 때까지 기다려 RYW 에 가까워지지만 **선형화는 아니다**(페일오버 시 확인받은 쓰기도 잃을 수 있음 — [복제·Sentinel](/redis/notes/11-replication-sentinel-cluster) 의 "쓰기 유실 창"). Redis 는 PACELC 의 PA/EL 이다. 단일 Redis 인스턴스 안에서는 모든 명령이 단일 스레드로 순서화되므로 **그 인스턴스에 대해서는 선형화**다 — 분산 락이 단일 Redis 에서 동작하는 이유이자, 페일오버하면 깨지는 이유.

**PostgreSQL**: 프라이머리에서 읽으면 트랜잭션 격리 수준이 전부다. 읽기 복제본(`hot_standby`)에서 읽으면 `synchronous_commit=remote_apply` 가 아닌 한 stale — 앱이 "쓰기 후 즉시 읽기" 를 복제본으로 보내면 RYW 가 깨진다. 해법: 쓴 직후 N초는 프라이머리로, 또는 `pg_last_wal_replay_lsn()` 을 세션의 쓰기 LSN 과 비교.

**Kafka**: 컨슈머는 **고수준(high watermark)** 까지만 읽는다 = 모든 ISR 에 복제된 메시지만. 그래서 `acks=all` 로 확인된 메시지는 리더가 죽어도 사라지지 않고, 소비자가 본 메시지는 되돌아가지 않는다(단조). 파티션 안에서는 순차 일관성, 파티션 사이는 순서 없음 ([전달 보장](/kafka/notes/04-delivery-guarantees)).

**이 앱의 진행률**: `progress:read` Set 은 단일 Redis 에 쓰고 같은 Redis 에서 읽으니 선형화다. 캐시 없는 단순함의 대가로 Redis 가 죽으면 진행률 기능이 불가용 — 의도적으로 CP 에 가깝게 둔 셈이다(저장 실패 시 UI 가 에러를 보여 준다).
