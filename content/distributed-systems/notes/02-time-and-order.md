## 왜 "순서" 가 문제인가

분산 시스템의 많은 질문이 결국 **순서** 질문이다. "이 쓰기가 저 쓰기보다 먼저였나?", "이 읽기는 그 쓰기 이후인가?", "두 리더 중 누가 최신인가?". 단일 프로세스에서는 프로그램 카운터가 순서를 정해 주지만, 노드가 여럿이면 **공통의 시간축이 없다**.

```
노드 A:  x=1 (10:00:00.050)      노드 B:  x=2 (10:00:00.048)
         A 의 시계가 30ms 빠르다면 실제로는 A 가 나중. 어느 값이 이겨야 하나?
```

## 물리 시계 두 종류

| 종류 | API | 성질 | 용도 |
|---|---|---|---|
| **벽시계(time-of-day)** | `Date.now()`, `clock_gettime(CLOCK_REALTIME)` | 에포크 기준 절대 시각. NTP 가 **앞뒤로 조정**. 리프 초 | 로그 타임스탬프, 사용자에게 보여 줄 시각, 만료 시각 |
| **단조 시계(monotonic)** | `performance.now()`, `process.hrtime`, `CLOCK_MONOTONIC` | 부팅 이후 경과. **절대 뒤로 가지 않음**. 노드 간 비교 불가 | 경과 시간, 타임아웃, 레이트 측정 |

규칙: **경과 시간은 단조 시계로, 시각은 벽시계로.** 벽시계로 타임아웃을 재면 NTP 가 시계를 1초 뒤로 돌릴 때 타임아웃이 1초 길어지거나(앞으로 돌리면) 즉시 만료된다.

### NTP 의 현실

- 일반 데이터센터 NTP 동기화 오차: 수 ms ~ 수십 ms. 공용 인터넷은 100ms 이상도.
- 클라이언트는 서버와의 RTT 를 재서 중간값을 시각으로 추정 → 비대칭 경로면 오차.
- 오차가 크면 **step**(점프), 작으면 **slew**(서서히 조정). step 은 벽시계가 뒤로 갈 수 있는 순간.
- 리프 초: 23:59:60 이 존재. 2012 년 리눅스 커널 버그로 많은 서비스가 다운. Google 은 "leap smearing" 으로 하루에 걸쳐 1초를 녹인다.
- VM 일시 정지·마이그레이션 후 시계가 수 초 튄다.

> 결론: 두 노드의 벽시계 차이로 이벤트 순서를 정하는 설계(Last-Write-Wins)는 **조용히 데이터를 잃는다**. Cassandra 의 LWW 가 유명한 사례.

## happens-before: 순서의 정의 (Lamport, 1978)

Lamport 는 물리 시간 없이 순서를 정의했다. 이벤트 a, b 에 대해 **a → b (a happens-before b)** 는 다음 중 하나일 때:

1. 같은 프로세스에서 a 가 b 보다 먼저 실행됐다
2. a 가 메시지 전송이고 b 가 그 메시지의 수신이다
3. 추이성: a → c, c → b 이면 a → b

a → b 도 b → a 도 아니면 둘은 **동시(concurrent)** 다 — 물리적으로 같은 순간이라는 뜻이 아니라, **서로 영향을 줄 수 없었다**는 뜻이다. 인과(causality)가 순서의 본질이다.

```
P1:  a ──────► b(send m) ──────────────► e
                   \
P2:         c ──────► d(recv m) ──► f

a→b, b→d (메시지), c→d, d→f, a→f (추이). a 와 c 는 동시. e 와 f 도 동시.
```

## Lamport 논리 시계

각 프로세스가 정수 카운터 L 을 가진다:
- 이벤트마다 `L = L + 1`
- 메시지 전송 시 L 을 실어 보냄
- 수신 시 `L = max(L, L_msg) + 1`

**성질**: a → b 이면 L(a) < L(b). 하지만 **역은 성립하지 않는다** — L(a) < L(b) 라고 a → b 는 아니다(동시일 수 있음). 즉 Lamport 시계는 인과 순서와 **일관된 전체 순서**(total order, 동점은 프로세스 ID 로)를 주지만, "동시였는지" 는 알려 주지 않는다.

```ts
class LamportClock {
  private t = 0;
  tick() { return ++this.t; }                       // 로컬 이벤트
  send() { return ++this.t; }                       // 메시지에 실을 값
  recv(remote: number) { this.t = Math.max(this.t, remote) + 1; return this.t; }
}
```

**어디에 쓰나**: 전체 순서가 필요하지만 인과만 보존되면 되는 곳 — 분산 뮤텍스(Lamport 의 원래 용도), 이벤트 로그 정렬, Kafka 의 오프셋도 파티션 안에서는 Lamport 시계와 같은 역할(단조 증가, 인과 일관).

## 벡터 시계: 동시성을 감지한다

N 개 프로세스면 길이 N 의 벡터 V 를 가진다:
- 로컬 이벤트: `V[i] += 1`
- 전송: V 를 실어 보냄
- 수신: `V = max(V, V_msg)` (성분별), 그리고 `V[i] += 1`

**비교**: V(a) ≤ V(b) (모든 성분) 이고 V(a) ≠ V(b) 이면 a → b. 어느 쪽도 ≤ 가 아니면 **동시**.

```
P1: [1,0,0] → send → [2,0,0]
P2: recv [2,0,0] → [2,1,0] → 로컬 → [2,2,0]
P3: 로컬 → [0,0,1]

[2,2,0] vs [0,0,1]: 어느 쪽도 모든 성분이 작지 않음 → 동시. 충돌 가능성 있음!
[2,0,0] vs [2,2,0]: 전자 ≤ 후자 → 전자가 먼저.
```

**용도**: Dynamo/Riak 의 버전 벡터(어떤 복제본이 최신인지, 충돌(sibling)인지 판정), CRDT 의 인과 전달. **비용**: 프로세스 수만큼 커지고, 클라이언트 수가 많으면 폭발 → "dotted version vectors", 노드 단위 벡터로 축소.

| | Lamport | 벡터 |
|---|---|---|
| 크기 | 정수 1개 | 프로세스 수 N |
| a→b ⇒ 비교 | 성립 | 성립 |
| 비교 ⇒ a→b | **불성립** | 성립 |
| 동시 감지 | 불가 | 가능 |
| 주 용도 | 전체 순서, 로그 | 충돌 감지, 복제 |

## 하이브리드 논리 시계 (HLC)

벽시계는 사람이 읽을 수 있고 외부 시스템과 비교 가능하지만 인과를 보장하지 않는다. Lamport 시계는 인과를 보장하지만 벽시계와 무관하다. HLC(Kulkarni et al., 2014)는 둘을 합친다: `(물리 시각 pt, 논리 카운터 c)`.

- 로컬/전송: `l' = max(l, pt_now)`; l 이 안 변하면 `c += 1`, 변하면 `c = 0`
- 수신: `l' = max(l, l_msg, pt_now)`; 같은 l 끼리는 c 를 max+1 로

**성질**: 인과 일관(a→b ⇒ HLC(a) < HLC(b)), 값이 벽시계와 **가깝게 유지**(오차 상한 = 시계 오차 ε), 64비트에 담김(48비트 ms + 16비트 카운터). CockroachDB·YugabyteDB·MongoDB 가 쓴다. "최근 10분 데이터" 같은 시간 범위 질의가 가능하면서 인과도 깨지지 않는다.

## Google Spanner 의 TrueTime

Spanner 는 반대 방향을 택했다: **시계 오차를 작게 만들고 그 오차를 API 로 노출**한다.

- 데이터센터마다 GPS 수신기 + 원자 시계. `TT.now()` 는 `[earliest, latest]` **구간**을 반환(보통 폭 1~7ms).
- 트랜잭션 커밋 시 타임스탬프 s = TT.now().latest 를 고르고, **TT.now().earliest > s 가 될 때까지 기다린다(commit-wait)**. 그러면 커밋이 완료된 시점에는 어느 노드의 시계로도 s 가 과거다 → 타임스탬프 순서 = 실제 순서(외부 일관성, external consistency).
- 비용: 커밋마다 오차 폭(수 ms)만큼 대기. 하드웨어가 있어야 한다.

CockroachDB 는 원자 시계 없이 HLC + "불확실성 구간 재시도" 로 비슷한 효과를 낸다(읽기가 불확실 구간에 걸리면 타임스탬프를 밀어 재시도).

## 순서를 정하는 다른 방법: 단일 리더·시퀀서

이론이 복잡해 보이지만 실무의 가장 흔한 답은 단순하다: **한 곳에서 순서를 매긴다**.

| 시스템 | 순서 결정자 | 순서 번호 |
|---|---|---|
| Kafka 파티션 | 파티션 리더 브로커 | 오프셋(단조 증가 정수) |
| Redis 복제 | 마스터 | 복제 오프셋(`master_repl_offset`) |
| PostgreSQL | 프라이머리 | LSN(WAL 위치), xid |
| Raft/etcd | 리더 | 로그 인덱스 + 텀 |
| Redis Streams | 단일 Redis | 엔트리 ID `밀리초-시퀀스` (벽시계 + 카운터 = HLC 와 유사!) |

단일 리더는 순서를 쉽게 만들지만 **리더가 바뀔 때**가 문제다: 옛 리더가 자기가 리더인 줄 알고 계속 번호를 매길 수 있다 → **에포크/텀**(term)을 번호에 붙여 "구 에포크의 번호는 무효" 로 만든다. Kafka 의 leader epoch, Raft 의 term, Redis Sentinel 의 config epoch 가 모두 이것이다.

## 예시로 보기 — 이 프로젝트에서

**Redis Streams 의 ID**: `XADD s * ...` 가 만드는 `1760596000123-0` 은 `<밀리초>-<시퀀스>`. 같은 밀리초에 여러 항목이면 시퀀스를 올리고, **시계가 뒤로 가면 마지막 ID 의 밀리초를 유지하고 시퀀스만 올린다** — 단조성을 지키는 HLC 식 처리다. [Pub/Sub·Streams](/redis/notes/07-pubsub-streams) 실험에서 ID 를 보면 확인할 수 있다.

**Redis 키 만료와 복제**: 만료는 마스터의 벽시계로 판정하고, 복제본에는 명시적 `DEL` 을 보낸다. 복제본이 자기 시계로 판정하면 시계 차이만큼 마스터와 어긋나기 때문이다. 복제본에서 읽을 때 "논리적으로 만료됐지만 아직 DEL 이 안 온" 키는 만료된 것으로 취급한다(Redis 3.2+).

**Kafka 타임스탬프**: 메시지에 `CreateTime`(프로듀서 벽시계) 또는 `LogAppendTime`(브로커 벽시계)을 기록. 순서는 **오프셋**이 정하고 타임스탬프는 참고용·보존 정책용이다. 시간 윈도우 집계(Kafka Streams)는 이벤트 시간(프로듀서)을 쓰되 **지연 도착**(late arrival)을 grace period 로 허용 — 시계를 못 믿는다는 설계의 반영.

**PostgreSQL 의 xid 와 LSN**: 트랜잭션 가시성은 [MVCC](/postgres/notes/03-mvcc-isolation) 의 xid 스냅샷으로, 복제 위치는 LSN 으로 — 둘 다 **논리 카운터**이고 벽시계는 `now()` 값으로만 쓰인다. `now()` 는 트랜잭션 시작 시각으로 고정된다는 것도 "시계를 순서에 안 쓴다" 의 한 예.

**이 앱의 로그**: `logs/app.jsonl` 의 `ts` 는 벽시계, `trace_id`/span 의 부모-자식 관계는 happens-before 다. Tempo 의 트레이스 뷰는 벽시계로 그리지만 **인과**는 span 관계로 보장된다 — 두 서비스의 시계가 어긋나면 자식 span 이 부모보다 먼저 시작한 것처럼 보이는 일이 실제로 생긴다 ([트레이싱](/observability/notes/06-tracing-otel)).
