## 복제를 왜 하나

같은 데이터를 여러 노드에 두는 이유는 세 가지: **가용성**(노드 하나 죽어도 서비스), **읽기 확장**(읽기를 복제본에 분산), **지연**(사용자 가까운 곳에). 데이터가 변하지 않으면 복제는 쉽다(복사하면 끝). 어려움은 전부 **변경을 어떻게 전파하고, 전파 중에 무엇이 보이는가**에서 온다.

![복제 토폴로지 비교](/diagrams/ds-replication.svg)

## 토폴로지 1: 단일 리더(리더-팔로워)

쓰기는 **리더** 한 곳에만, 리더가 변경 로그를 팔로워에게 보낸다. 읽기는 어디서든. PostgreSQL 스트리밍 복제, Redis 마스터-복제본, Kafka 파티션 리더, MySQL, MongoDB 가 모두 이것.

### 동기 vs 비동기

| 방식 | 커밋 응답 시점 | 내구성 | 지연 | 리더 장애 시 |
|---|---|---|---|---|
| **동기** | 팔로워(들)가 받았다고 확인한 뒤 | 확인된 쓰기는 안 잃음 | 팔로워 RTT 추가, 팔로워 죽으면 **쓰기 정지** | 팔로워가 최신 → 승격해도 유실 0 |
| **비동기** | 리더 로컬 커밋 즉시 | 리더 죽으면 **미전파 쓰기 유실** | 최소 | 승격된 팔로워가 뒤처짐 → 유실 |
| **반동기(semi-sync)** | N 중 1개(또는 k개) 확인 | k 개 동시 장애까지 안전 | 가장 빠른 팔로워 RTT | 확인한 팔로워 승격 |

PostgreSQL: `synchronous_standby_names = 'ANY 1 (s1, s2)'` + `synchronous_commit = on|remote_write|remote_apply`. `remote_apply` 면 복제본에서 읽어도 RYW 보장(가장 느림). Redis: 기본 비동기, `WAIT n t` 로 요청별 반동기, `min-replicas-to-write` 로 "복제본이 너무 뒤처지면 쓰기 거부". Kafka: `acks=all` + `min.insync.replicas` = 반동기의 정식 구현(ISR).

### 복제 로그의 형식

| 형식 | 내용 | 장단점 |
|---|---|---|
| 문장 기반 | SQL 문 그대로 | 작음. `now()`, `random()`, 자동 증가가 비결정적 → 위험(MySQL 초기) |
| **WAL 전달** | 디스크 블록 수준 변경 | PG 스트리밍 복제. 같은 버전·같은 스토리지 엔진이어야 |
| **논리(행) 로그** | 행 단위 before/after | PG 논리 복제(pgoutput), [Debezium CDC](/kafka/notes/08-cdc-outbox-debezium). 버전 다르거나 다른 시스템으로도 |
| 트리거 기반 | 앱 레벨 | 유연하지만 느리고 버그 많음 |

### 팔로워 추가와 따라잡기

새 팔로워는 (1) 리더의 **스냅샷**을 받고 (2) 스냅샷 시점 이후의 로그를 재생해 따라잡는다. 그래서 리더는 스냅샷 위치(PG: LSN, Redis: 복제 오프셋 + replication backlog)를 알아야 하고, 그 이후 로그를 **보존**해야 한다(Redis `repl-backlog-size` 가 작으면 full resync 반복 — [복제](/redis/notes/11-replication-sentinel-cluster)).

### 리더 장애: 페일오버

1. 리더 죽음 **판정**(타임아웃 — 느린 것과 구분 불가, [1장](/distributed-systems/notes/01-why-hard))
2. 새 리더 **선출**(가장 최신 팔로워, 합의 또는 Sentinel 쿼럼)
3. 클라이언트와 팔로워를 새 리더로 **재구성**

함정: 비동기면 옛 리더의 미전파 쓰기 유실 → 외부 시스템과 불일치(GitHub 의 2012 MySQL 사고: 자동 증가 PK 가 재사용돼 Redis 와 어긋남). **스플릿 브레인**: 옛 리더가 살아 돌아와 둘 다 쓰기 수락 → 에포크로 옛 리더 쓰기 거부(STONITH, fencing). 타임아웃이 짧으면 부하 중 불필요한 페일오버, 길면 긴 다운타임.

## 복제 지연이 만드는 이상 현상

비동기 복제에서 복제본 읽기는 **stale** 하다. 증상은 [일관성 모델](/distributed-systems/notes/03-consistency-models) 의 세션 보장 위반 그대로:

- 쓰고 바로 읽으니 없음(RYW 위반) → 쓰기 후 일정 시간 리더 읽기, 또는 버전 비교
- 새로고침마다 과거로 감(단조 읽기 위반) → 세션 고정
- 답글이 원글보다 먼저(인과 위반, 다른 파티션의 복제 지연 차이) → 인과 의존성 추적

지연 모니터링은 필수: PG `pg_stat_replication.replay_lag`, Redis `INFO replication` 의 `slave_repl_offset` 차이, Kafka 의 ISR 이탈(`UnderReplicatedPartitions`).

## 토폴로지 2: 다중 리더

여러 데이터센터에 리더가 하나씩, 리더끼리 비동기로 서로 복제. 멀티 리전 쓰기 지연을 없애고 DC 장애에 강하지만 **같은 데이터를 두 리더가 동시에 수정**하면 충돌한다. 오프라인 앱(캘린더 동기화), 협업 편집(Google Docs)도 본질적으로 다중 리더.

## 토폴로지 3: 무리더(Dynamo 스타일)

리더가 없다. 클라이언트(또는 코디네이터)가 **여러 복제본에 동시에** 쓰고 읽는다. Amazon Dynamo 논문(2007), Cassandra, Riak, Voldemort, ScyllaDB.

### 쿼럼

N 개 복제본, 쓰기가 W 개 확인, 읽기가 R 개 확인. **W + R > N** 이면 읽기 집합과 쓰기 집합이 반드시 겹쳐 최신 값을 적어도 하나는 읽는다(버전으로 최신 고름).

| 설정 | 성질 |
|---|---|
| N=3, W=2, R=2 | 균형. 노드 1개 죽어도 읽기·쓰기 모두 가능 |
| N=3, W=3, R=1 | 읽기 빠름, 쓰기는 모두 살아 있어야 |
| N=3, W=1, R=3 | 쓰기 빠름, 읽기는 모두 살아 있어야 |
| W+R ≤ N | 겹침 없음 → stale 읽기 허용(속도·가용성 우선) |

**쿼럼은 선형화가 아니다**: 쓰기가 일부 복제본에만 도착한 "중간" 상태에서 동시 읽기 두 개가 다른 값을 볼 수 있다(한 읽기는 새 값, 나중 읽기는 옛 값 — 비선형). 또 쓰기가 W 미만으로 실패했을 때 롤백이 없어 일부 복제본엔 남는다. 선형화가 필요하면 합의가 필요하다.

### 복구 메커니즘

- **읽기 복구(read repair)**: 읽을 때 복제본 간 버전이 다르면 최신으로 뒤처진 복제본을 갱신. 자주 읽는 데이터만 복구됨.
- **안티 엔트로피**: 백그라운드로 복제본끼리 **머클 트리**(해시 트리)를 비교해 차이만 동기화. 드물게 읽는 데이터도 결국 수렴.
- **힌트 핸드오프(hinted handoff)**: 목표 노드가 죽어 있으면 다른 노드가 "대신 보관(힌트)" 하고, 돌아오면 넘겨 준다. 쓰기 가용성 ↑, 그러나 힌트 보관 중엔 쿼럼이 "진짜" 가 아니다(sloppy quorum).

## 충돌: 감지와 해결

다중 리더·무리더에서 두 쓰기가 **동시**(인과 무관)면 충돌이다. 선택지:

| 방법 | 동작 | 문제 |
|---|---|---|
| **LWW(Last-Write-Wins)** | 타임스탬프 큰 쪽 승 | 시계 오차로 **확인된 쓰기 유실**. 그래도 가장 흔함(Cassandra) |
| **버전 벡터 + sibling** | 동시 쓰기를 **둘 다 보존**, 읽을 때 앱이 병합 | 앱 복잡. Riak 의 "장바구니 병합"(지운 상품 부활 버그가 Dynamo 논문에) |
| **CRDT** | 자료구조 자체가 병합 규칙을 가짐(교환·결합·멱등) | 표현 가능한 연산이 제한적. 메타데이터 비용 |
| **운영 변환(OT)** | 편집 연산을 변환해 적용 순서 무관하게 | 협업 편집(Google Docs). 구현 극히 까다로움 |
| 충돌 회피 | 같은 키는 항상 같은 리더로(홈 리전) | 리전 장애·사용자 이동 시 다시 충돌 |

### CRDT 맛보기

- **G-Counter**(증가만): 노드별 카운터 벡터, 값 = 합, 병합 = 성분별 max. PN-Counter 는 증가·감소 벡터 두 개.
- **LWW-Register**: (값, 타임스탬프), 병합 = 타임스탬프 큰 쪽 — 역시 시계 의존.
- **OR-Set**(Observed-Remove): 추가마다 고유 태그, 삭제는 "본 태그" 만 제거 → "동시 추가·삭제" 에서 추가가 이김. 장바구니에 알맞다.
- Redis Enterprise 의 Active-Active, Riak, Automerge/Yjs(협업 편집)가 CRDT 기반.

```
OR-Set 예: 노드 A 가 add(x, tagA), 노드 B 가 동시에 remove(x) — B 는 tagA 를 본 적 없음
병합: x 는 {tagA} 로 남음 → "삭제보다 추가 우선" 이 자료구조에 내장
```

## 복제 설계 비교

| 시스템 | 토폴로지 | 동기성 | 충돌 | 페일오버 | 비고 |
|---|---|---|---|---|---|
| **Redis** | 단일 리더 | 비동기(WAIT 로 반동기) | 없음(리더만 씀) | Sentinel 쿼럼 / Cluster 투표 | 복제 백로그, PSYNC |
| **PostgreSQL** | 단일 리더 | 설정 가능(동기/비동기/ANY k) | 없음 | 외부 도구(Patroni — etcd 리스) | WAL 전달 + 논리 복제 |
| **Kafka** | 파티션별 단일 리더 | ISR 반동기(`acks`, `min.insync.replicas`) | 없음 | 컨트롤러(KRaft)가 ISR 중 선출, `unclean.leader.election` 으로 유실 vs 가용성 선택 | leader epoch 로 펜싱 |
| **Cassandra** | 무리더 | 쿼럼 튜닝(ONE/QUORUM/ALL) | LWW(셀 단위 타임스탬프) | 없음(노드 죽어도 쿼럼이면 OK) | 힌트, 읽기 복구, 머클 수리 |
| **etcd** | Raft 리더 | 합의(과반) | 없음 | Raft 선출(초 단위) | 선형화 |
| **CockroachDB** | 범위별 Raft | 합의 | 없음 | Raft | 다중 리전 쓰기도 합의 |

## 예시로 보기 — 이 프로젝트에서

**`pnpm redis:ha`**(6381 마스터, 6382-6383 복제본, Sentinel 26381-26383): `redis-cli -p 6381 INFO replication` 에 `master_repl_offset` 과 각 복제본의 `offset` 이 보인다. 둘의 차가 복제 지연(바이트). `DEBUG SLEEP` 으로 복제본을 멈추고 마스터에 쓰면 차이가 벌어지고, 깨어나면 **부분 재동기(PSYNC)** 로 따라잡는다. 백로그보다 더 뒤처지면 **full resync**(RDB 전송) — `INFO stats` 의 `sync_full` 카운터 증가.

**Sentinel 페일오버 실험**: 마스터를 죽이면 `down-after-milliseconds`(5초) 후 S_DOWN → 쿼럼(2)으로 O_DOWN → 리더 Sentinel 이 가장 최신 복제본을 승격. 그 사이 마스터에 쓰인 미전파 데이터는 사라진다 — 비동기 복제의 "쓰기 유실 창" 을 실제로 측정할 수 있다 ([복제·Sentinel·Cluster](/redis/notes/11-replication-sentinel-cluster)).

**PostgreSQL**: 이 프로젝트의 PG 는 단일 노드지만 `wal_level=logical` 이라 논리 복제 슬롯을 만들 수 있다. [CDC 실험](/kafka/notes/08-cdc-outbox-debezium) 의 Debezium 은 "팔로워 하나" 로서 WAL 을 받는 셈이고, `pg_replication_slots.confirmed_flush_lsn` 과 `pg_current_wal_lsn()` 의 차이가 **복제 지연**이다 — 단일 리더 복제의 모니터링 지표를 그대로 보여 준다.

**Kafka ISR**: `kafka-topics --describe` 의 `Isr:` 목록. 브로커가 1개(이 프로젝트)라 ISR=1, `min.insync.replicas=1` 이고 `acks=all` 이 사실상 `acks=1` 과 같다. 운영에서는 복제 3·min ISR 2 가 표준: 1개 죽어도 쓰기 가능, 2개 죽으면 쓰기 거부(C 선택).

## 실전에서는 어디에 쓰이나

> 서버 한 대가 죽어도 서비스가 살아야 하거나(가용성), 읽기를 나눠야 하거나(확장), 사용자 가까이 데이터를 둬야 할 때(지연) 복제가 등장한다. 실무의 질문은 "얼마나 기다리고, 무엇을 잃을 수 있나" 다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 핀테크 원장 DB (PostgreSQL) | 프라이머리 장애 시 확인된 거래 유실 0 | `synchronous_standby_names = 'ANY 1 (...)'` 반동기 복제 + Patroni 페일오버 | 비동기 복제는 빠르지만 페일오버 시 유실 창 |
| 커머스 상품 조회 | 읽기 트래픽 분산 | 비동기 읽기 복제본 + 복제 지연 모니터링(`replay_lag`) | 캐시 계층으로 읽기 흡수 |
| 이벤트 스트리밍 플랫폼 | 브로커 1대 장애에도 쓰기 유지·유실 없음 | Kafka 복제 3, `min.insync.replicas=2`, `acks=all` | 복제 1 은 디스크 하나에 운명을 맡김 |
| 장바구니·협업 편집·오프라인 앱 | 여러 곳의 동시 수정 병합 | CRDT(OR-Set 등), Automerge·Yjs 같은 라이브러리 | LWW 는 한쪽 수정을 잃는다 |
| 대규모 쓰기 위주 로그·시계열 | 노드 장애에도 쓰기 가용성 | Cassandra 류 무리더 복제, 쿼럼(N=3, W=2, R=2) 튜닝 | 단일 리더는 리더가 쓰기 병목 |

**이럴 땐 안 맞는다**
- 쿼럼으로 선형화를 기대하는 설계: W+R>N 이어도 선형화는 아니다. 락·유일성 같은 연산은 합의 기반 저장소를 쓴다.
- 멀티 리전 다중 리더를 기본값으로: 충돌 해결 비용이 크다. 대부분은 홈 리전 단일 리더 + 원격 읽기 복제본으로 충분하다.

**누가 매일 만나나** — DBA·데이터베이스 엔지니어는 복제 지연 알림과 페일오버 리허설을, 백엔드 개발자는 복제본 읽기로 생긴 stale 데이터 버그를, SRE 는 Redis·Kafka 의 under-replicated 지표를 매일 본다.

**면접·실무 단골 질문**
- Q. 비동기 복제에서 페일오버하면 무엇이 일어나나? → 리더에만 있던 미전파 쓰기가 사라지고, 옛 리더가 돌아오면 스플릿 브레인 위험 → 에포크·펜싱으로 막는다.
- Q. W+R>N 이면 항상 최신 값을 읽나? → 겹치는 복제본이 생길 뿐, 진행 중 쓰기·실패한 쓰기 때문에 선형화는 아니다.
