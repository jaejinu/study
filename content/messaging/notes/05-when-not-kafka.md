## Kafka 가 잘하는 것

먼저 공정하게 정리하자. Kafka 는 [로그 모델](/messaging/notes/01-queue-topic-log-models)의 표준이다.

- 초당 수십만~수백만 이벤트를 디스크에 순차로 쓰고 오래 보존한다.
- 여러 소비자 그룹이 같은 데이터를 **각자의 속도로, 원하면 처음부터** 읽는다.
- 파티션 키로 엔티티별 순서를 보장한다.
- Connect·Streams·Schema Registry 같은 생태계가 넓다([Kafka 심화](/kafka/notes/06-streams-connect-schema)).

이벤트 소싱, CDC, 데이터 파이프라인, 활동 로그 집계, 여러 팀이 같은 이벤트를 구독하는 이벤트 백본. 여기서는 Kafka 가 거의 정답이다.

문제는 Kafka 가 **유명해서** 다른 문제에도 쓰인다는 점이다.

## 신호 1 — 메시지마다 다른 운명이 필요하다 (작업 큐)

이메일 발송, 이미지 변환, 외부 API 호출 같은 작업은 메시지마다 결과가 다르다. 어떤 것은 성공하고, 어떤 것은 5분 뒤에 재시도해야 하고, 어떤 것은 영원히 실패한다.

Kafka 의 소비 위치는 **파티션당 오프셋 하나**다. "m1 은 아직, m2 는 완료" 를 표현할 수 없다. 그래서 m1 이 실패하면 선택지가 셋뿐이다.

| 선택 | 결과 |
|---|---|
| m1 을 계속 재시도 | 그 파티션 뒤의 모든 메시지가 막힌다 (**head-of-line blocking**) |
| m1 을 건너뛰고 커밋 | m1 유실 |
| m1 을 재시도 토픽에 복사하고 커밋 | 재시도 토픽·지연 소비자·DLT 를 직접 만들어야 한다 |

세 번째가 표준 패턴이지만, RabbitMQ 의 [DLX + TTL](/messaging/notes/02-rabbitmq) 이나 JetStream 의 `nak(delay)` 가 브로커 기능으로 주는 것을 코드로 다시 짓는 셈이다. 또 Kafka 는 **파티션 수 이상으로 소비자를 늘릴 수 없다**. 작업이 느려서 워커를 50대로 늘리고 싶은데 파티션이 12개면 38대는 논다.

→ **RabbitMQ, SQS, NATS JetStream(WorkQueue)** 가 맞다. Kafka 4.x 의 Share Group(KIP-932)이 이 공백을 메우려 하지만 아직 새 기능이다.

## 신호 2 — 응답을 기다린다 (요청-응답)

"가격을 계산해서 바로 알려 줘" 는 RPC 다. Kafka 로 하려면 요청 토픽에 보내고, 응답 토픽을 구독하고, 상관 ID 로 짝을 맞추고, 타임아웃을 관리해야 한다. 지연은 배치·폴링 때문에 수 ms~수십 ms 가 붙는다.

→ 직접 호출(**HTTP·gRPC**, [API 설계](/api-design/notes/03-protobuf-grpc))이나 **NATS request-reply** 가 맞다. 비동기여야 할 이유(응답이 몇 분 걸림)가 있으면 작업 큐 + 상태 조회 API(202 Accepted)로.

## 신호 3 — 트래픽이 작다

하루 수천 건, 초당 몇 건인 시스템에 Kafka 클러스터(브로커 3대, 모니터링, 업그레이드, 파티션 관리)를 두는 것은 비용이 크다. KRaft 로 ZooKeeper 는 사라졌지만 여전히 무거운 JVM 시스템이다.

→ 이미 쓰는 저장소를 활용한다.

| 이미 있는 것 | 큐로 쓰는 법 |
|---|---|
| PostgreSQL | `SELECT … FOR UPDATE SKIP LOCKED LIMIT 10` 으로 경쟁 소비자. 비즈니스 쓰기와 **같은 트랜잭션** 에서 작업 등록 가능 — 아웃박스가 공짜 |
| Redis | Streams + 소비자 그룹(`XREADGROUP`, `XACK`, `XAUTOCLAIM`) |
| 클라우드 | SQS·Pub/Sub — 운영이 0 |

PostgreSQL 큐는 과소평가된다. 초당 수백~수천 건까지는 충분하고, 무엇보다 "DB 에 주문 저장 + 후속 작업 등록" 이 원자적이다. 브로커를 쓰면 이것을 위해 [아웃박스 + CDC](/kafka/notes/08-cdc-outbox-debezium) 가 필요하다.

## 신호 4 — 라우팅이 복잡하다

"한국의 VIP 고객 주문 중 결제 수단이 카드인 것만 이 서비스로" 같은 라우팅이다. Kafka 의 라우팅 단위는 토픽이다. 조건이 늘면 토픽이 폭발하거나, 소비자가 전부 읽고 대부분 버린다.

→ **RabbitMQ topic/headers 익스체인지**, **NATS subject 와일드카드**(`orders.kr.vip.>`)가 브로커에서 거른다.

## 신호 5 — 지연이 아주 짧아야 하거나, 엣지다

Kafka 프로듀서는 처리량을 위해 묶어 보내고(`linger.ms`), 소비자는 폴링한다. 튜닝하면 수 ms 까지 내려가지만 기본은 처리량 지향이다. 또 IoT·엣지 장비에 Kafka 를 올리기는 어렵다.

→ **NATS**(리프 노드로 엣지와 클라우드를 잇는다), **MQTT**(IoT 표준).

## 결정표

| 요구 | 1순위 | 대안 | Kafka 가 맞지 않는 이유 |
|---|---|---|---|
| 이벤트를 여러 팀이 오래 재생 | **Kafka** | Pulsar, JetStream(Limits) | — |
| CDC·데이터 파이프라인 | **Kafka** | — | — |
| 작업 큐 (개별 재시도·지연) | RabbitMQ, SQS | JetStream WorkQueue, PG 큐 | 오프셋 하나, head-of-line, 소비자 ≤ 파티션 |
| 요청-응답 | HTTP/gRPC | NATS request-reply | 상관 ID·응답 토픽을 직접 구현 |
| 초당 수십 건, 이미 PG 가 있음 | PG `SKIP LOCKED` | Redis Streams | 운영 비용 대비 이득 없음 |
| 복잡한 라우팅 | RabbitMQ | NATS | 토픽 폭발 |
| 실시간 방송 (잃어도 됨) | NATS core, Redis Pub/Sub | — | 저장·배치 오버헤드가 불필요 |
| 엣지·IoT | NATS, MQTT | — | 무겁다 |
| 우선순위 | RabbitMQ (우선순위 큐 또는 큐 분리) | — | 개념 없음 |

## 반대로 — Kafka 가 꼭 필요하다는 신호

- 같은 이벤트를 **세 팀 이상**이 각자 소비한다.
- "어제 데이터부터 다시 처리" 가 정기적으로 필요하다.
- 처리량이 초당 수만 건을 넘고 계속 는다.
- 이벤트 자체가 기록(감사, 이벤트 소싱)이다.
- 스트림 처리(윈도 집계, 조인)를 한다.

이 중 둘 이상이면 Kafka 의 운영 비용을 낼 가치가 있다.

## 예시로 보기 — 이 프로젝트의 선택

이 학습 사이트에 비동기 처리가 필요해진다고 상상해 보자.

| 기능 | 고를 것 | 이유 |
|---|---|---|
| 실험 실행 요청을 백그라운드로 | **Redis Streams** 소비자 그룹 | Redis 가 이미 있다. 초당 몇 건. 실험은 한 워커만 처리해야 한다 |
| Alertmanager 웹훅 → 알림 저장 | 지금처럼 직접 HTTP + 멱등 처리 | 응답이 필요하고 양이 적다 |
| 노트 변경 → 검색 색인 갱신 | PG 가 있다면 아웃박스, 없다면 Redis Streams | 재처리(전체 재색인)가 필요할 수 있음 |
| 학습 이벤트 분석 파이프라인 | Kafka | 여러 소비자(대시보드·추천·백업), 재생 필요 |

실험 `mq-broker-benchmark` 의 숫자는 이 판단을 바꾸지 않는다. 다섯 경로 모두 초당 수만 건 이상을 처리했다. 이 규모에서는 **처리량이 아니라 모델과 운영 비용**이 선택 기준이다.

## 실전에서는 어디에 쓰이나

> 새 비동기 기능을 만들며 "일단 Kafka" 로 가려는 순간, 요구를 모델·트래픽·운영 비용으로 다시 따져 볼 때 등장한다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 이메일·이미지 변환 작업 | 메시지별 재시도·지연, 워커 수 자유 확장 | RabbitMQ·SQS·JetStream WorkQueue | Kafka — head-of-line, 소비자 ≤ 파티션 |
| 초당 수십 건 사내 백오피스 | 주문 저장과 후속 작업 등록을 원자적으로 | PostgreSQL `SKIP LOCKED` 작업 테이블 | 브로커 + 아웃박스 — 운영 부담 |
| 가격 계산 같은 동기 질의 | 즉시 응답 | HTTP·gRPC, NATS request-reply | 요청·응답 토픽 + 상관 ID 직접 구현 |
| 여러 팀이 소비하는 이벤트 백본·CDC | 재생, 다수 구독, 대용량 | Kafka | 작업 큐 — 재처리 불가 |
| 엣지·IoT 수집 | 가벼운 현장 연결 | NATS, MQTT | Kafka — 장비에 올리기 무거움 |

**이럴 땐 안 맞는다**
- "Kafka 가 꼭 필요한 신호" 가 둘 이상인데 운영이 귀찮아 PG 큐로 버티는 것 — 재생·다수 소비자가 늘면 결국 다시 옮긴다.
- 벤치마크 처리량만으로 고르는 것 — 이 규모에서는 모델과 운영 비용이 기준이다.

**누가 매일 만나나** — 테크 리드·아키텍트가 설계 리뷰에서 브로커를 정할 때, 백엔드가 기존 Kafka 작업 큐의 막힘 장애를 풀 때.

**면접·실무 단골 질문**
- Q. Kafka 로 작업 큐를 만들면 생기는 문제는? → 파티션당 오프셋 하나라 실패 메시지가 뒤를 막고, 재시도 토픽을 직접 만들어야 하며, 소비자를 파티션 수 이상 늘릴 수 없다.
- Q. Kafka 가 꼭 필요하다는 신호는? → 세 팀 이상 소비, 정기적 재처리, 초당 수만 건 이상, 이벤트 자체가 기록, 스트림 처리.

## 실습 체크리스트

- [ ] Kafka 로 이메일 발송 큐를 만들었을 때 한 메일 서버 장애가 다른 메일까지 막는 과정을 오프셋으로 설명하기
- [ ] 파티션 12개 토픽에 워커 50대를 붙이면 몇 대가 일하는지, RabbitMQ 큐라면 어떤지 비교하기
- [ ] PostgreSQL `SKIP LOCKED` 큐를 직접 써 보고(PostgreSQL 실험실 참고), 같은 트랜잭션에서 주문 저장 + 작업 등록이 되는 것 확인하기
- [ ] 내 회사·프로젝트의 메시징 사용처를 위 결정표에 대입해 맞게 고른 것과 아닌 것 찾기
- [ ] "Kafka 가 꼭 필요한 신호" 다섯 개 중 내 시스템에 해당하는 것이 몇 개인지 세어 보기
