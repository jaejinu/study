## 모델 1 — 작업 큐 (경쟁 소비자)

```
생산자 ─→ [ m1 m2 m3 m4 m5 ] ─→ 소비자 A (m1, m3, m5)
                              └→ 소비자 B (m2, m4)
```

- 메시지 하나는 **소비자 하나**만 처리한다. 소비자를 늘리면 처리량이 늘어난다.
- 처리가 끝나면(ack) 메시지는 **사라진다**. 큐는 "해야 할 일 목록" 이다.
- 소비 위치를 **브로커가** 관리한다. 어떤 메시지가 누구에게 나갔고 ack 됐는지 브로커가 안다.
- 메시지 단위로 재시도·지연·dead letter 를 다루기 쉽다.

쓰임: 이메일 발송, 이미지 변환, 결제 후처리, 주문 이행 단계. "누군가 이 일을 한 번 해 줘" 의 세계다.

## 모델 2 — pub/sub 토픽 (팬아웃)

```
생산자 ─→ [토픽 orders.created] ─→ 구독자 A (재고 서비스)  : 모든 메시지
                                ├→ 구독자 B (알림 서비스)  : 모든 메시지
                                └→ 구독자 C (분석)         : 모든 메시지
```

- 메시지 하나가 **구독자 모두**에게 간다.
- 순수 pub/sub(Redis Pub/Sub, NATS core)은 **지금 연결된** 구독자에게만 보낸다. 없던 구독자는 못 받는다. 저장이 없다.
- 생산자는 누가 듣는지 모른다. 새 구독자를 추가해도 생산자 코드를 바꾸지 않는다 — 서비스 분리의 핵심.

쓰임: 이벤트 알림, 캐시 무효화 방송, 실시간 대시보드, 설정 변경 전파.

실전에서는 둘을 합친다. "토픽 → 구독자 그룹마다 큐" 다. RabbitMQ 는 fanout 익스체인지에 서비스마다 큐를 바인딩하고, 각 서비스 안에서는 소비자들이 그 큐를 경쟁해서 읽는다.

## 모델 3 — 로그 (재생 가능한 스트림)

```
오프셋:   0    1    2    3    4    5    6
        [m0] [m1] [m2] [m3] [m4] [m5] [m6] ─→ 계속 추가
                    ↑                   ↑
             분석 그룹 (오프셋 2)    재고 그룹 (오프셋 6)
```

- 메시지는 **append-only 로그**에 쌓이고, 읽어도 **지워지지 않는다**. 보존 기간·크기로만 지운다.
- 소비 위치(오프셋)를 **소비자가** 들고 있다. 브로커는 "그룹 X 는 오프셋 N 까지 읽었다" 를 기록할 뿐이다.
- 그래서 **되감기**(재처리)가 된다. 버그 수정 후 어제부터 다시 처리, 새 서비스가 과거 이벤트 전체로 상태를 재구성.
- 병렬성은 **파티션**으로 나눈다. 파티션 안에서만 순서가 보장된다. 소비자 수는 파티션 수를 넘어 늘어나지 않는다.

쓰임: 이벤트 소싱, CDC([Outbox + Debezium](/kafka/notes/08-cdc-outbox-debezium)), 스트림 처리, 감사 로그, 데이터 파이프라인.

## 한 장으로 비교

| | 작업 큐 | pub/sub 토픽 | 로그 |
|---|---|---|---|
| 한 메시지를 받는 수 | 소비자 1 | 구독자 전부 | 그룹마다 1 |
| 소비 후 | 삭제 | (저장 없음) | 남음 |
| 소비 위치 | 브로커가 메시지별로 | — | 소비자가 오프셋으로 |
| 재처리 | 어렵다 (이미 지워짐) | 불가 | 쉽다 (오프셋 되감기) |
| 순서 | 큐 하나 + 소비자 하나일 때만 | 생산 순서(대체로) | 파티션 안에서 |
| 개별 메시지 재시도·지연 | 쉽다 (nack, DLX, TTL) | — | 어렵다 (한 건 때문에 파티션이 막힘) |
| 느린 소비자 | 큐가 쌓임 | 버려지거나 연결이 끊김 | 랙(lag)이 쌓일 뿐, 다른 그룹에 영향 없음 |
| 대표 | RabbitMQ, SQS, Redis List | Redis Pub/Sub, NATS core, SNS | Kafka, Redis Streams, NATS JetStream, Pulsar |

마지막 줄의 경계는 흐려지고 있다. RabbitMQ 는 **Streams**(로그 큐)를 추가했고, NATS JetStream 은 로그 위에 작업 큐 보존 정책을 얹었고, Kafka 는 **Share Group**(KIP-932)으로 경쟁 소비자 의미를 추가하고 있다. 그래도 각 제품이 **가장 잘하는 기본 모델**은 위 표와 같다.

## 같은 브로커로 다른 모델을 흉내 내면

| 흉내 | 비용 |
|---|---|
| Kafka 로 작업 큐 | 메시지 하나가 실패하면 그 파티션 뒤가 다 막힌다(head-of-line). 재시도 토픽·DLT 를 직접 만들어야 한다. 소비자 수 ≤ 파티션 수 |
| RabbitMQ 로 재처리 | 이미 ack 된 메시지는 없다. 재처리하려면 별도 저장소가 필요 (또는 RabbitMQ Streams) |
| Redis Pub/Sub 로 신뢰성 있는 이벤트 | 구독자가 잠깐 끊기면 그 사이 메시지는 영영 없다. Redis Streams 를 써야 한다 |
| DB 테이블로 큐 | `SELECT … FOR UPDATE SKIP LOCKED` 로 꽤 잘 된다. 처리량이 작고 트랜잭션과 묶어야 할 때 오히려 최선 |

마지막 줄은 과소평가되는 선택지다. 이미 PostgreSQL 이 있고 초당 수백 건이면 큐를 위한 인프라를 늘리지 않는 것이 맞을 수 있다. [Kafka 를 쓰지 말아야 할 때](/messaging/notes/05-when-not-kafka) 에서 더 다룬다.

## 순서 보장 — 생각보다 좁다

"메시지 순서가 보장되나요?" 의 정직한 답은 "어떤 범위에서?" 다.

- **큐 하나 + 소비자 하나**: 순서대로. 하지만 소비자가 하나라 병렬성이 없다.
- **큐 하나 + 소비자 여럿**: 꺼낸 순서는 맞아도 **처리 완료 순서**는 섞인다. A 가 m1 을 천천히, B 가 m2 를 빨리 처리하면 m2 가 먼저 끝난다.
- **재시도가 끼면**: m1 이 실패해 재시도 큐로 갔다 오면 m2, m3 뒤에 처리된다.
- **로그 + 키 기반 파티셔닝**: 같은 키(주문 ID)는 같은 파티션 → 그 키 안에서 순서 보장. 이것이 실무에서 쓸 수 있는 거의 유일한 확장 가능한 순서 보장이다.

그래서 설계는 대개 **"전체 순서" 를 포기하고 "엔티티별 순서" 를 키로 보장**하고, 소비자는 순서가 어긋난 메시지를 견디도록(버전 번호 비교, 멱등 처리) 만든다.

## 예시로 보기 — 이 프로젝트에서

이 프로젝트에는 네 가지 메시징 경로가 다 있다.

| 경로 | 모델 | 어디서 |
|---|---|---|
| Redis Pub/Sub, Streams | pub/sub, 로그 | Redis 실험실의 메시징 실험 |
| Kafka (19092) | 로그 | Kafka 실험실, CDC 실험 |
| RabbitMQ (5673) | 작업 큐 + 익스체인지 | 실험 `mq-rabbit-dlx-retry` |
| NATS (14222) | pub/sub + JetStream 로그 | 실험 `mq-nats-jetstream-ack` |

실험 `mq-broker-benchmark` 는 같은 1만 메시지를 다섯 경로로 흘려 본다. 이 노트북에서 잰 결과의 요지는 이렇다(자세한 표는 [06](/messaging/notes/06-four-brokers-same-workload)).

| 경로 | 보장 | 처리량 (msg/s) | p99 (ms) |
|---|---|---|---|
| NATS core | 저장 없음 | 약 27만 | 4.6 |
| Redis Streams | 메모리 + AOF | 약 16만 | 7.7 |
| Kafka | acks=all | 약 11만 | 21.6 |
| RabbitMQ | persistent + confirm | 약 6.8만 | 10.7 |
| NATS JetStream | 파일 + PubAck + ack | 약 4.5만 | 18.4 |

저장도 ack 도 없는 NATS core 가 가장 빠르고, 디스크에 쓰고 확인을 주고받는 경로일수록 느리다. 보장과 속도는 맞바꾸는 관계다. 표를 볼 때는 늘 **보장 열을 함께** 읽어야 한다.

## 실전에서는 어디에 쓰이나 — 메시징 지도

> 메시징은 "지금 바로 처리하지 않아도 되는 일" 과 "여러 곳이 알아야 하는 사건" 을 서비스 사이에 넘기는 통로다. 실무에서는 브로커 이름보다 모델(작업 큐·pub/sub·로그)을 먼저 고르는 것이 출발점이다.

| 서비스·상황 | 이 주제의 어떤 부분이 | 더 읽기 |
|---|---|---|
| 여러 팀이 같은 이벤트를 각자 속도로 재생 | 로그 모델, 키 기반 순서 보장 | [큐·토픽·로그 모델](/messaging/notes/01-queue-topic-log-models) |
| 주문 후 메일·영수증·포인트 같은 후처리 | 작업 큐, 경쟁 소비자, DLX 지연 재시도 | [RabbitMQ](/messaging/notes/02-rabbitmq) |
| 실시간 위치·센서 방송, 경량 RPC, 엣지·IoT | core NATS, 큐 그룹, request-reply, JetStream | [NATS·JetStream](/messaging/notes/03-nats-jetstream) |
| 결제·재고 이벤트를 중복 없이, "30분 뒤 취소" 작업 | at-least-once + 멱등 소비자, 지연 메시지 | [전달 보장·지연 큐](/messaging/notes/04-delivery-guarantees-delay) |
| 초당 수십 건 사내 서비스에 브로커를 고를 때 | Kafka 가 맞지 않는 신호, PostgreSQL `SKIP LOCKED` 큐 | [Kafka 를 쓰지 말아야 할 때](/messaging/notes/05-when-not-kafka) |
| 주문 → 재고 → 결제 → 배송 사가, 아웃박스 발행 | 브로커별 소비자·아웃박스·사가 구현 차이 | [네 브로커, 같은 워크로드](/messaging/notes/06-four-brokers-same-workload) |
| "주문 메일이 몇 시간째 안 와요" 장애 | 큐 깊이·메시지 나이·재전달률 알림, 트레이스 링크 | [운영과 관측](/messaging/notes/07-operations-observability) |

**회사 규모에 따라**
- 스타트업: 이미 있는 PostgreSQL(`SKIP LOCKED`)·Redis Streams·클라우드 매니지드 큐로 시작한다. 브로커를 운영할 사람이 없기 때문이다.
- 성장기: 서비스가 쪼개지며 RabbitMQ·NATS 같은 브로커로 작업 큐와 이벤트 알림을 나누고, 멱등 소비자·DLQ·큐 깊이 알림이 필수가 된다.
- 대규모 조직: 여러 팀이 공유하는 이벤트 백본(로그 모델)과 작업 큐를 함께 운영하고, 플랫폼 팀이 브로커·스키마·관측을 표준으로 제공한다.

**이럴 땐 안 맞는다**
- 즉시 응답이 필요한 조회·계산 — 응답 큐와 상관 ID 관리가 붙는다. HTTP·gRPC 직접 호출이 낫다.
- 한 서비스 안에서 끝나는 작업 — 브로커보다 트랜잭션과 묶인 DB 작업 테이블이 단순하다.

**누가 매일 만나나** — 백엔드는 비동기 후처리·이벤트 발행 코드를 쓸 때, SRE·플랫폼 엔지니어는 브로커 클러스터와 큐 깊이·랙 알림을 운영할 때, 데이터 엔지니어는 이벤트 로그를 파이프라인으로 가져올 때 이 주제를 만난다.
