## 플랫폼 장애는 곱셈이다

일반 서비스가 30분 멈추면 그 서비스 사용자가 영향을 받는다. 플랫폼이 30분 멈추면 **모든 팀의 배포·프로비저닝·관측이 동시에** 멈춘다. 장애 대응 중인 다른 팀이 핫픽스를 배포하지 못하는 순간 플랫폼 장애는 두 번째 장애를 만든다.

그래서 플랫폼 팀은 자기 플랫폼을 **가장 중요한 서비스처럼** 운영해야 한다. [SRE 원칙](/sre/notes/01-sre-principles-toil)이 플랫폼 자신에게도 그대로 적용된다.

## 사용자 여정 단위로 SLI 를 정한다

"쿠버네티스 API 서버 가용성 99.9%" 는 플랫폼 팀 내부 지표다. 사용자(개발자)가 체감하는 것은 여정이다.

| 사용자 여정 | SLI (좋은 이벤트 / 전체) | SLO 예 |
|---|---|---|
| 코드를 푸시하면 CI 결과를 받는다 | 플랫폼 원인 실패가 아닌 CI 실행 / 전체 CI 실행 | 99.5% (월) |
| CI 가 빨리 끝난다 | 15분 안에 끝난 실행 / 전체 | 95% |
| 배포가 반영된다 | 10분 안에 롤아웃 완료된 배포 / 전체 | 99% |
| DB 를 요청하면 받는다 | 30분 안에 프로비저닝된 요청 / 전체 | 99% |
| 포털·카탈로그를 연다 | 2초 안에 응답한 요청 / 전체 | 99.5% |
| 로그·메트릭을 조회한다 | 쿼리 성공·10초 이내 / 전체 | 99% |

여기서 까다로운 것은 **"플랫폼 원인" 의 분류**다. 테스트 실패로 CI 가 빨간 것은 플랫폼 장애가 아니다. 러너 부족, 캐시 서버 장애, 레지스트리 타임아웃은 플랫폼 장애다. 실패 원인을 자동 분류하는 규칙(로그 패턴·종료 단계)을 먼저 만들어야 SLI 를 셀 수 있다.

```text
CI 실행 결과 분류
├─ success
├─ user_failure     : 테스트·린트·타입 오류 (사용자 코드)
└─ platform_failure : 러너 할당 실패, 이미지 pull 타임아웃, 캐시 서비스 5xx, OOMKilled(러너)
SLI = 1 - platform_failure / (success + user_failure + platform_failure)
```

## 의존하는 바깥 플랫폼

내부 플랫폼은 GitHub, 클라우드, 컨테이너 레지스트리, 패키지 저장소(npm·PyPI)에 의존한다. 이들의 장애를 **내 SLO 에서 뺄 것인가**는 정책 결정이다.

| 선택 | 의미 | 대응 |
|---|---|---|
| 포함 | 사용자 입장에선 어차피 멈춤 → 정직한 SLO | 미러·캐시로 의존도를 낮춘다 (레지스트리 풀스루 캐시, npm 미러) |
| 제외 | 우리가 통제 못 하는 것은 빼고 본다 | 상태 페이지에 외부 원인 표시 |

대부분 **포함**하고, 미러·재시도·우회 경로로 영향을 줄인다. 실제 사례: 공식 이미지가 레지스트리에서 사라지자 `lake:up` 이 실패했다(이 저장소의 MinIO 사례). 미러나 고정 다이제스트가 있었다면 피할 수 있었다.

## 에러 버짓으로 변경 속도를 조절한다

플랫폼 장애의 대부분은 **플랫폼 자신의 변경**에서 온다(클러스터 업그레이드, CI 러너 이미지 교체, 정책 추가). 에러 버짓이 이것을 조절한다([에러 버짓](/sre/notes/02-sli-slo-error-budget)).

| 버짓 상태 | 플랫폼 팀의 행동 |
|---|---|
| 충분 | 업그레이드·새 정책·실험적 기능 출시 |
| 50% 이하 | 위험한 변경은 카나리로만, 변경 동결 창 검토 |
| 소진 | 신뢰성 작업만. 새 기능·마이그레이션 중단 |

### 폭발 반경을 줄이는 플랫폼 변경 방식

| 변경 | 위험 | 줄이는 방법 |
|---|---|---|
| CI 러너 이미지 교체 | 모든 저장소의 빌드가 깨질 수 있음 | 새 라벨로 병행 운영 → 일부 저장소부터 전환 |
| 정책(OPA·Kyverno) 추가 | 모든 배포가 거부될 수 있음 | **audit(경고) 모드로 1~2주** → 위반 목록 해소 → enforce |
| 클러스터 업그레이드 | 워크로드 재스케줄 | 노드 풀 단위 롤링, PDB 확인 |
| 템플릿 변경 | 새로 만들어지는 서비스 전부 | 템플릿 CI(렌더링·빌드), 버전 태그 |
| 공유 재사용 워크플로 변경 | 그것을 쓰는 모든 저장소 | 메이저 버전 태그(`@v3`), 소비자는 고정 |

정책은 특히 조심해야 한다. 정책 하나를 바로 enforce 로 켜는 것은 **모든 팀의 배포를 동시에 멈추는 변경**이다. 이 저장소의 콘텐츠 검사(`tests/content.test.ts`)를 처음 켰을 때도 기존 노트 13곳이 위반으로 걸렸다 — 위반을 먼저 고치거나 규칙을 다듬은 뒤에 CI 에 넣은 이유다.

## 플랫폼 온콜과 지원

| 채널 | 용도 | 응답 기대 |
|---|---|---|
| 페이지(온콜) | 플랫폼 SLO 를 태우는 장애 | 분 단위 |
| 지원 채널(#platform-help) | 사용 질문, 비긴급 문제 | 영업시간 내 |
| 백로그(이슈) | 기능 요청, 개선 | 로드맵 |
| 오피스 아워 | 설계 상담, 마이그레이션 도움 | 주 1회 |

지원 채널의 질문은 데이터다. 같은 질문이 반복되면 문서가 아니라 **제품(플랫폼)** 이 부족한 것이다. 질문을 주제별로 태그해 분기마다 상위 5개를 백로그로 옮긴다. 이것이 [토일](/sre/notes/01-sre-principles-toil)을 줄이는 플랫폼판 방법이다.

## 플랫폼 관측의 구성

| 무엇을 | 어떻게 |
|---|---|
| 파이프라인 단계별 시간·성공률 | CI 이벤트 → 메트릭/로그 ([CI 성능](/github-actions/notes/06-ci-performance)) |
| 러너·빌드 캐시 포화 | 대기 큐 길이, 캐시 적중률 |
| 프로비저닝 요청 수명 | 요청 → 완료 시간 히스토그램, 실패 원인 분류 |
| 클러스터·컨트롤 플레인 | API 서버 지연, etcd, 컨트롤러 큐 ([쿠버네티스 관측](/observability/notes/07-kubernetes-observability)) |
| 포털 | 페이지 응답 시간, 검색 성공률 |
| 사용자 체감 | 정기 설문 + DORA ([DORA](/platform-engineering/notes/05-dora-devex-metrics)) |

## 플랫폼 장애 포스트모템 예시

```text
제목   : CI 러너 이미지 교체 후 2시간 동안 전 저장소 빌드 실패
영향   : 저장소 140개, CI 실행 1,200회 실패(플랫폼 원인), 핫픽스 배포 3건 지연
타임라인
  14:02  러너 이미지 v42 를 기본 라벨(ubuntu-latest-acme)에 반영
  14:05  첫 실패 — "node: command not found"
  14:21  지원 채널 질문 6건 (감지 지연: 플랫폼 원인 실패율 알림 없음)
  14:40  온콜이 이미지 변경을 원인으로 식별
  15:10  v41 로 롤백 (롤백 절차 문서 없음, 수동)
  16:02  캐시 무효화 후 정상화
기여 요인
  - 이미지 교체를 모든 저장소에 동시에 적용 (폭발 반경 = 전체)
  - 이미지 CI 가 "부팅되는지" 만 검사, 대표 저장소 빌드는 안 돌림
  - 플랫폼 원인 실패율 SLI·알림 없음 → 사용자 질문으로 감지
액션 아이템
  - 새 이미지는 canary 라벨로 1일 운영 후 기본 라벨 전환 (소유: 플랫폼, 기한: 2주)
  - 이미지 CI 에 대표 저장소 5개 빌드 추가 (소유: 플랫폼)
  - CI 실패 원인 분류 + 플랫폼 원인 실패율 번레이트 알림 (소유: 플랫폼 SRE)
  - 롤백을 원클릭 워크플로로 (소유: 플랫폼)
```

이 예시의 액션 아이템은 모두 **플랫폼 쪽**에 있다. 사용자 팀에게 "다음엔 조심하세요" 를 요구하는 항목은 없다 — [블레임리스](/sre/notes/05-incident-postmortem)의 원칙이 플랫폼에선 "사용자 탓을 하지 않는다" 로 확장된다.

## 예시로 보기 — 이 프로젝트에서

이 저장소를 "학습자를 위한 플랫폼" 으로 보면, 플랫폼 SLO 를 이렇게 정의할 수 있다.

| 여정 | SLI | 현재 상태로 본 판단 |
|---|---|---|
| 푸시하면 CI 가 결과를 준다 | 성공 또는 사용자 원인 실패 / 전체 | 최근 40회 전부 성공 (실험 `plat-dora-metrics`) |
| CI 가 빨리 끝난다 | 5분 안에 끝난 실행 비율 | 리드타임 p90 약 2.3분 |
| 실험 환경이 뜬다 | `pnpm *:up` 이 성공한 비율 | MinIO 이미지 사건 — 외부 레지스트리 의존이 실제 실패 원인이었다 |
| 장애 주입 실험이 환경을 원상복구한다 | 실험 종료 후 Redis·Kafka 가 정상인 비율 | 데드맨 스위치 도입 전 3시간 정지 사고 1건 → 도입 후 강제 종료 시험에서 60초 내 복구 |
| 노트가 제대로 보인다 | frontmatter 가 파싱되는 노트 비율 | CI 콘텐츠 검사로 100% 강제 |

마지막 두 줄은 이 저장소에서 실제로 일어난 일이 플랫폼 개선으로 이어진 사례다. 3시간 정지 사고의 포스트모템은 [SRE 노트](/sre/notes/05-incident-postmortem)에 있고, 그 결과 생긴 `src/lib/deadman.ts` 는 이제 모든 장애 주입 실험이 쓰는 **플랫폼 기본값**이 됐다. 한 팀(실험 하나)의 사고가 플랫폼 기본값으로 바뀌어 모두를 보호하는 것 — 플랫폼 팀이 포스트모템에서 가장 먼저 찾아야 할 액션 아이템이다.

## 실습 체크리스트

- [ ] 내 조직(또는 이 저장소) 플랫폼의 사용자 여정 세 개를 골라 SLI 를 "좋은 이벤트 / 전체" 형태로 정의하기
- [ ] CI 실패 로그 몇 개를 보고 사용자 원인/플랫폼 원인으로 분류하는 규칙을 써 보기
- [ ] 정책 하나를 audit → enforce 로 전환하는 계획(기간·위반 해소·공지)을 세우기
- [ ] 실험 `plat-dora-metrics` 결과의 리드타임 분포를 보고 "CI 가 빠르다" 는 SLO 의 목표치를 정해 보기
