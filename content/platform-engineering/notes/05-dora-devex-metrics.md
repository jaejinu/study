## 왜 지표가 필요한가

플랫폼 팀은 "개발이 빨라졌다" 를 증명해야 예산을 받는다. 동시에 잘못된 지표는 조직을 망친다(커밋 수, 코드 줄 수, 티켓 처리량). DORA(DevOps Research and Assessment) 연구는 수만 개 조직 설문에서 **조직 성과와 상관있는 소프트웨어 전달 지표 네 개**를 찾았다.

| 지표 | 묻는 것 | 축 |
|---|---|---|
| 배포 빈도 (Deployment Frequency) | 얼마나 자주 프로덕션에 배포하나 | 속도 |
| 변경 리드타임 (Lead Time for Changes) | 커밋이 프로덕션에 도달하기까지 얼마나 걸리나 | 속도 |
| 변경 실패율 (Change Failure Rate) | 배포 중 장애·롤백·핫픽스가 필요했던 비율 | 안정성 |
| 복구 시간 (Failed Deployment Recovery Time, 예전 MTTR) | 실패한 배포로부터 복구하는 데 얼마나 걸리나 | 안정성 |

핵심 발견은 **속도와 안정성이 상충하지 않는다**는 것이다. 상위 조직은 둘 다 좋다. 작은 변경을 자주 배포하면 각 변경의 위험이 작고 원인 파악·되돌리기도 쉽기 때문이다. 최근 보고서는 다섯 번째로 **재작업률(rework rate)** 을 함께 본다.

### 대략의 성과 등급 (연도별로 경계가 조금씩 바뀐다)

| 등급 | 배포 빈도 | 리드타임 | 변경 실패율 | 복구 시간 |
|---|---|---|---|---|
| Elite | 요청 시(하루 여러 번) | 1일 미만 | 낮음(~5%) | 1시간 미만 |
| High | 주 1회~하루 1회 | 1일~1주 | ~10~15% | 1일 미만 |
| Medium | 월 1회~주 1회 | 1주~1개월 | ~15~20% | 1일~1주 |
| Low | 월 1회 미만 | 1개월 이상 | 높음 | 1주 이상 |

## 정의가 숫자를 정한다

같은 저장소에서도 정의를 어떻게 잡느냐에 따라 숫자가 몇 배씩 달라진다.

| 지표 | 선택해야 하는 정의 | 흔한 선택지 |
|---|---|---|
| 배포 빈도 | "배포" 는 무엇인가 | main 병합 / 성공한 CI / 실제 프로덕션 롤아웃 완료 |
| 리드타임 | 시작점은 언제인가 | 첫 커밋 / PR 생성 / PR 병합 / 마지막 커밋 |
| 리드타임 | 끝점은 언제인가 | CI 성공 / 배포 시작 / 롤아웃 100% |
| 변경 실패율 | "실패" 는 무엇인가 | CI 실패 / 롤백 / 핫픽스 / 장애 티켓 연결 |
| 복구 시간 | 시작점 | 배포 시각 / 장애 감지 시각 / 알림 시각 |

**CI 실패는 변경 실패가 아니다.** CI 는 프로덕션에 가기 전에 잡은 것이라 오히려 시스템이 잘 작동한 것이다. DORA 의 변경 실패율은 *프로덕션에 나간 뒤* 문제를 일으킨 배포의 비율이다. 그런데 CI 와 배포가 하나로 붙은 작은 저장소에서는 CI 기록이 유일한 데이터라, 근사치로 쓰되 그 사실을 명시해야 한다.

## 데이터 원천과 계산

```text
Git      : 커밋 시각, PR 생성·병합 시각            → 리드타임 시작점
CI/CD    : 실행 시작·종료·결과, 배포 이벤트          → 배포 빈도, 리드타임 끝점
인시던트 : 장애 시작·감지·해결, 원인 배포 연결       → 변경 실패율, 복구 시간
```

```bash
# 이 저장소에서: main 브랜치 push 로 시작된 CI 실행
gh run list -R jaejinu/study --branch main --event push --limit 200 \
  --json headSha,conclusion,createdAt,updatedAt
# 커밋 시각
git log main --format='%H %cI'
```

리드타임은 **분포**로 봐야 한다. 평균은 오래 묵은 PR 한두 개에 끌려간다. 중앙값과 p90 을 같이 보고, 긴 꼬리의 원인(리뷰 대기, 플래키 테스트 재실행, 배포 창 제한)을 찾는다.

## 숫자 너머 — SPACE 와 개발자 경험

DORA 는 **전달 파이프라인**을 잰다. 개발자가 일하며 겪는 마찰은 잘 안 보인다. SPACE 프레임워크는 다섯 차원을 함께 보라고 권한다.

| 차원 | 예 |
|---|---|
| Satisfaction & well-being | 도구 만족도, 번아웃 |
| Performance | 결과의 품질·영향(코드 양이 아님) |
| Activity | 커밋·PR·배포 수 (단독으로는 위험) |
| Communication & collaboration | 리뷰 대기 시간, 지식 공유 |
| Efficiency & flow | 중단 없이 일한 시간, 대기·인계 횟수 |

실무에서는 **분기 설문 + 시스템 지표**를 같이 본다. "로컬 환경 세팅에 몇 시간 걸렸나", "CI 를 기다리며 컨텍스트를 몇 번 바꿨나" 같은 질문이 플랫폼 백로그로 바로 이어진다.

## 측정의 함정

- **굿하트의 법칙**: 지표가 목표가 되면 좋은 지표가 아니게 된다. 배포 빈도를 목표로 걸면 의미 없는 배포가 늘어난다.
- **팀 간 비교 금지**: 레거시 결제 시스템과 신규 실험 서비스의 리드타임을 같은 잣대로 비교하면 안 된다. 같은 팀의 **추세**를 본다.
- **개인 평가 금지**: DORA 는 시스템(팀+도구+프로세스)의 속성이다. 개인에게 걸면 숫자를 지키려는 행동이 생긴다.
- **작은 표본**: 한 주에 배포 3번이면 실패율 33% 가 한 번의 실패로 나온다. 신뢰 구간을 생각한다.
- **자동 수집만**: 설문 없이 시스템 지표만 보면 "빠르지만 다들 지쳐 있는" 상태를 놓친다.

## DORA 를 대시보드로 — 이벤트를 메트릭으로 바꾸기

스프레드시트로 분기마다 세는 대신, 이벤트가 일어날 때 기록하면 추세를 계속 볼 수 있다.

```text
배포 파이프라인 마지막 단계에서:
  deployments_total{service, env, result="success|rollback"}  += 1
  lead_time_seconds{service, env}   observe(now - first_commit_time)
인시던트 도구 웹훅에서:
  incidents_total{service, caused_by_deploy="true|false"}     += 1
  restore_time_seconds{service}     observe(resolved - started)
```

```promql
# 배포 빈도 (서비스별, 주간)
sum by (service) (increase(deployments_total{env="prod", result="success"}[7d]))

# 리드타임 p50 / p90 (히스토그램)
histogram_quantile(0.5, sum by (le) (rate(lead_time_seconds_bucket{env="prod"}[7d])))
histogram_quantile(0.9, sum by (le) (rate(lead_time_seconds_bucket{env="prod"}[7d])))

# 변경 실패율
sum(increase(incidents_total{caused_by_deploy="true"}[30d]))
  / sum(increase(deployments_total{env="prod", result="success"}[30d]))
```

주의할 점은 [카디널리티](/finops/notes/04-data-observability-cost)다. 커밋 SHA 나 PR 번호를 레이블로 넣으면 시계열이 폭발한다. 개별 이벤트는 로그나 데이터 저장소에 남기고, 메트릭에는 서비스·환경 정도만 둔다.

### 지표를 대화로 바꾸는 법

숫자가 나빠졌을 때 묻는 순서가 있다.

1. **정의가 바뀌었나?** 새 배포 도구가 이벤트를 두 번 보내는 등.
2. **분포의 어디가 변했나?** 중앙값은 그대로인데 p90 만 늘었다면 일부 변경이 막힌 것.
3. **어느 단계에서 기다리나?** 리드타임을 "코딩 → 리뷰 대기 → CI → 배포 대기 → 롤아웃" 으로 쪼갠다. 대개 가장 긴 것은 **사람을 기다리는 시간**이다.
4. **플랫폼이 할 수 있는 일인가?** 리뷰 대기면 팀 관행, CI 대기면 플랫폼, 배포 창 제한이면 조직 정책.

## 플랫폼이 DORA 를 움직이는 지점

| 플랫폼 개입 | 영향받는 지표 |
|---|---|
| CI 캐시·병렬화로 파이프라인 시간 단축 | 리드타임 ([CI 성능](/github-actions/notes/06-ci-performance)) |
| 카나리·자동 롤백 | 변경 실패율의 영향 축소, 복구 시간 ([SLO 기반 자동화](/sre/notes/07-slo-driven-automation)) |
| 기능 플래그 | 배포와 출시 분리 → 배포 빈도↑, 실패율↓ |
| 플래키 테스트 격리 | 리드타임 꼬리 ([플래키 관리](/testing/notes/06-e2e-flaky-management)) |
| 표준 관측·알림 | 감지 시간 단축 → 복구 시간 ([번레이트 알림](/sre/notes/03-burn-rate-alerting)) |

## 예시로 보기 — 이 프로젝트에서

실험 `plat-dora-metrics` 는 이 저장소의 GitHub 기록으로 네 지표를 계산한다. 정의는 이렇게 잡았다.

| 지표 | 이 실험의 정의 | 한계 |
|---|---|---|
| 배포 빈도 | main push 로 시작돼 **성공한 CI** 수 ÷ 관측 기간 | 이 저장소는 실제 배포 단계가 없다 — "배포 가능한 상태" 의 빈도 |
| 리드타임 | 커밋 시각 → 그 커밋의 CI 성공 시각 | PR 없이 main 에 바로 커밋하는 개인 저장소라 리뷰 대기가 0 |
| 변경 실패율 | 실패한 CI ÷ 완료된 CI | CI 실패는 프로덕션 실패가 아니다(위 설명) |
| 복구 시간 | 실패한 CI 종료 → 다음 성공 CI 종료 | 실패가 없으면 계산 불가 |

이 노트를 쓸 때 실측값은 다음과 같았다.

| 항목 | 값 |
|---|---|
| 관측 기간 | 약 17시간 |
| 완료된 main CI | 40회 (전부 성공) |
| 성공 CI 빈도 | 시간당 약 2.4회 |
| 리드타임 중앙값 | 약 1.8분 (p90 약 2.3분) |
| 변경 실패율 | 0% |

숫자만 보면 "Elite 를 넘는 수준" 이다. 그러나 이것이 이 노트의 교훈이다. 이 저장소는 **푸시 전에 로컬에서 타입 검사·린트·콘텐츠 검사를 돌리고**, 리뷰어가 없고, 실제 배포 단계도 없다. 리드타임 2분은 "CI 가 빠르다" 는 뜻이지 "변경이 사용자에게 2분 만에 간다" 는 뜻이 아니다. 지표를 해석할 때는 **정의와 맥락을 숫자와 같이 적는다.**

## 실전에서는 어디에 쓰이나

> 플랫폼·DevOps 투자가 "정말 개발을 빠르고 안전하게 했나" 를 숫자로 보여 줘야 할 때, 그리고 개발자가 어디서 기다리는지 찾을 때 등장한다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 플랫폼 팀의 예산 심사 | CI 개선·카나리 도입의 효과 증명 | 도입 전 기준선 → 리드타임 중앙값·p90, 변경 실패율 추세 비교 | 만족도 설문만 |
| 배포가 느린 대형 커머스 조직 | 리드타임 꼬리의 원인 찾기 | 리드타임을 코딩·리뷰 대기·CI·배포 대기·롤아웃으로 분해 | 개별 PR 사후 분석 |
| 장애가 잦은 핀테크 서비스 | 배포가 장애를 부르는지 확인 | 배포 이벤트와 장애·롤백 티켓을 연결해 변경 실패율·복구 시간 계산 | 장애 건수만 집계 |
| 원격 근무 비중이 큰 SaaS | 숫자는 좋은데 개발자가 지쳐 있는 상태 탐지 | SPACE 관점 분기 설문 + 시스템 지표 병행 | 활동 지표(커밋 수)만 |

**이럴 땐 안 맞는다**
- 개인 성과 평가·팀 간 순위 — 굿하트의 법칙대로 숫자를 지키는 행동만 늘어난다. 같은 팀의 추세를 대화 재료로만 쓴다.
- 배포가 한 주에 몇 번뿐인 작은 표본 — 실패 한 번에 실패율이 수십 %로 튄다. 긴 관측 기간이나 정성 회고를 함께 쓴다.

**누가 매일 만나나** — 엔지니어링 매니저·플랫폼 리드는 분기 리뷰와 로드맵 우선순위를 정할 때, 플랫폼 엔지니어는 배포·CI 이벤트를 메트릭으로 수집하는 파이프라인을 만들 때 만난다.

**면접·실무 단골 질문**
- Q. CI 실패는 변경 실패율에 넣나? → 아니다. 프로덕션에 나간 뒤 장애·롤백·핫픽스가 필요했던 배포의 비율이다. CI 가 잡은 것은 시스템이 잘 작동한 것이다.
- Q. 속도와 안정성은 상충하나? → DORA 연구에서 상위 조직은 둘 다 좋다. 작은 변경을 자주 배포하면 각 변경의 위험과 복구 비용이 작다.
