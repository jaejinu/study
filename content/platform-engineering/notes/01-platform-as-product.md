## 왜 "플랫폼" 이 필요해졌나

DevOps 는 "만든 사람이 운영한다(you build it, you run it)" 를 퍼뜨렸다. 개발 팀이 배포·모니터링·온콜까지 책임지자 배포는 빨라졌다. 그런데 팀이 수십 개가 되자 새로운 문제가 생겼다.

- 팀마다 CI 파이프라인, Dockerfile, Helm 차트, 대시보드, 알림 규칙을 **각자 처음부터** 만든다.
- 같은 실수(시크릿을 env 에 평문으로, 리소스 limit 없음, 로그 레이블 폭발)가 팀마다 반복된다.
- 한 서비스를 띄우는 데 알아야 할 것이 Kubernetes·Terraform·Prometheus·OIDC·네트워크 정책까지 늘어난다.

이 마지막 항목을 **인지 부하(cognitive load)** 라고 부른다. 개발자가 기능을 만드는 것 말고도 머릿속에 들고 있어야 하는 것의 양이다. 플랫폼 엔지니어링은 이것을 줄이는 일이다.

> 플랫폼 = 다른 팀이 자기 일을 더 적은 인지 부하로 해내게 만드는, **셀프서비스 API·도구·문서·지원의 묶음**. 이 묶음을 만들고 운영하는 팀이 플랫폼 팀이다.

## 내부 개발자 플랫폼(IDP)의 구성 요소

| 계층 | 개발자가 하는 일 | 플랫폼이 제공하는 것 | 예 |
|---|---|---|---|
| 개발자 포털 | 서비스·문서·소유자 찾기, 새 서비스 만들기 | 서비스 카탈로그, 템플릿, 검색 | Backstage, Port |
| 통합·배포 | 코드를 푸시하면 테스트·빌드·배포 | 표준 CI/CD 파이프라인, 재사용 워크플로 | GitHub Actions 재사용 워크플로, ArgoCD |
| 인프라 프로비저닝 | "DB 하나 주세요" | 셀프서비스 리소스 API, 정책 | Terraform 모듈, Crossplane |
| 런타임 | 컨테이너 실행 | 표준 클러스터·네임스페이스·기본값 | Kubernetes + 정책(Kyverno) |
| 관측 | 대시보드·알림 | 자동 계측·기본 대시보드·SLO 템플릿 | OTel 자동 계측, Grafana 폴더 |
| 보안·컴플라이언스 | (대개 신경 쓰고 싶지 않음) | 기본값으로 안전하게 | 이미지 스캔, 서명, 시크릿 관리 |

이 표의 핵심은 왼쪽 열이 **짧다**는 것이다. 개발자는 의도만 말하고, 오른쪽 열의 복잡함은 플랫폼이 흡수한다.

## 팀 토폴로지 — 네 가지 팀, 세 가지 상호작용

『Team Topologies』(Skelton & Pais)가 정리한 어휘가 업계 표준이 됐다.

| 팀 유형 | 역할 | 예 |
|---|---|---|
| 스트림 정렬 팀 | 사용자 가치의 흐름 하나를 처음부터 끝까지 책임진다. 대부분의 팀 | 결제 팀, 검색 팀 |
| 플랫폼 팀 | 스트림 정렬 팀이 쓰는 내부 서비스를 제품으로 제공한다 | 배포 플랫폼 팀, 데이터 플랫폼 팀 |
| 지원(enabling) 팀 | 다른 팀의 역량 공백을 일정 기간 메워 주고 떠난다 | SRE 코칭, 보안 챔피언 |
| 복잡한 하위 시스템 팀 | 깊은 전문성이 필요한 부분을 맡는다 | 추천 엔진, 결제 정산 엔진 |

| 상호작용 | 의미 | 언제 |
|---|---|---|
| 협업(collaboration) | 두 팀이 한동안 함께 일한다 | 새 플랫폼 기능을 첫 사용자 팀과 같이 만들 때 |
| X-as-a-Service | 한 팀이 다른 팀의 서비스를 **문서와 API 만으로** 쓴다 | 플랫폼이 성숙한 뒤의 기본 모드 |
| 촉진(facilitating) | 한 팀이 다른 팀이 배우도록 돕는다 | 지원 팀의 기본 모드 |

플랫폼의 목표 상태는 **X-as-a-Service** 다. 플랫폼 팀에게 슬랙으로 물어봐야만 쓸 수 있다면 그것은 플랫폼이 아니라 **티켓 처리 창구**다.

### 예시로 보기 — 티켓 창구 vs 플랫폼

```text
[티켓 창구]
개발자: "#infra 채널) Redis 하나 필요합니다"
인프라 팀: (3일 뒤) "Terraform PR 올렸습니다, 리뷰 부탁"
개발자: "ACL 은 어떻게 하죠?" ... (또 2일)

[플랫폼]
개발자: catalog-info.yaml 에 dependsOn: resource:redis-cache 추가 → PR
플랫폼: 정책 검사(크기·태그·비용 예산) 통과 → 자동 프로비저닝 → 접속 정보는 시크릿으로 주입
       → 기본 대시보드·알림이 서비스 폴더에 생김
```

두 번째 흐름에서 플랫폼 팀은 아무 일도 하지 않았다. 그게 성공이다.

## 인지 부하의 세 종류

| 종류 | 설명 | 플랫폼이 할 일 |
|---|---|---|
| 내재적(intrinsic) | 문제 자체의 어려움 (결제 도메인 규칙) | 건드리지 않는다 — 팀의 본업 |
| 외재적(extraneous) | 문제와 무관하게 환경 때문에 생기는 부담 (YAML 문법, 사내 VPN 설정, 파이프라인 디버깅) | **없앤다** — 플랫폼의 주 대상 |
| 본유적(germane) | 좋은 해법을 만드는 데 쓰는 사고 (설계, 테스트 전략) | 여유를 늘려 준다 |

외재적 부하를 줄이는 대표 수단이 **기본값**이다. 사람은 기본값을 거의 바꾸지 않는다. 그래서 안전하고 관측 가능한 기본값을 템플릿에 넣는 것이 문서를 열 편 쓰는 것보다 효과가 크다([골든 패스와 템플릿](/platform-engineering/notes/03-golden-paths-templates)).

## 플랫폼을 "제품" 으로 운영한다는 것

| 제품 활동 | 플랫폼에서의 모습 |
|---|---|
| 사용자 정의 | 내부 개발자 — 페르소나: 신입, 숙련 백엔드, 데이터 엔지니어 |
| 문제 발견 | 개발자 인터뷰, 지원 티켓 분류, 온보딩 시간 측정 |
| 로드맵 | "Kubernetes 업그레이드" 가 아니라 "새 서비스 첫 배포까지 2일 → 2시간" 처럼 사용자 결과로 |
| 출시·마이그레이션 | 강제 이전보다 더 나은 경로를 만들어 자연 이동 유도, 기한 있는 deprecation |
| 성공 지표 | 채택률, 셀프서비스 비율, 온보딩 시간, DORA 지표([DORA 와 개발자 경험](/platform-engineering/notes/05-dora-devex-metrics)), 만족도(NPS·설문) |
| 지원 | 문서, 예제, 오피스 아워 — 그리고 지원 요청을 제품 백로그로 연결 |

### 흔한 실패 패턴

- **"짓고 나면 오겠지"(build it and they will come)**: 사용자 인터뷰 없이 플랫폼을 설계하면 아무도 안 쓴다. 첫 사용자 팀과 협업 모드로 시작한다.
- **강제(mandate) 로만 채택**: 쓰기 싫은 플랫폼을 강제하면 우회로(섀도 IT)가 생긴다. 플랫폼은 **가장 쉬운 길**이어야 한다.
- **추상화 과잉**: Kubernetes 를 완전히 숨긴 사내 DSL 은 처음엔 쉽지만, 플랫폼이 지원하지 않는 요구 하나로 막힌다. 탈출구(escape hatch)를 둔다.
- **플랫폼 팀이 병목**: 모든 변경이 플랫폼 팀 리뷰를 거치면 다시 티켓 창구다. 정책을 코드로([정책·테스트](/iac/notes/06-drift-policy-testing)) 자동 검사한다.
- **측정 없음**: "좋아졌다" 를 증명하지 못하면 예산을 잃는다. 기준선을 먼저 잰다.

## DevOps·SRE·플랫폼 엔지니어링의 관계

| | 무엇을 최적화하나 | 대표 산출물 |
|---|---|---|
| DevOps | 개발과 운영 사이의 벽 제거, 흐름 | 문화, CI/CD, 협업 관행 |
| SRE | 신뢰성(SLO·에러 버짓·토일 감소) | SLO, 온콜·포스트모템 체계 ([SRE 원칙](/sre/notes/01-sre-principles-toil)) |
| 플랫폼 엔지니어링 | 개발자의 인지 부하와 셀프서비스 | IDP, 골든 패스, 카탈로그 |

세 가지는 경쟁이 아니라 층이다. 플랫폼이 SLO 템플릿·알림 기본값을 제공하면 SRE 관행이 모든 팀에 자동으로 퍼진다.

## 예시로 보기 — 이 프로젝트에서

이 학습 사이트는 그 자체로 아주 작은 IDP 처럼 생겼다.

| IDP 요소 | 이 저장소에서 | 사용자(학습자)가 하는 일 |
|---|---|---|
| 서비스 카탈로그 | `src/lib/subjects.ts` — 주제마다 이름·트랙·설명·메뉴·환경 준비 명령 | 첫 화면에서 주제를 고른다 |
| 셀프서비스 인프라 | `docker-compose.yml` 의 프로파일 + `pnpm *:up` 스크립트 | `pnpm kafka:up` 한 줄로 Kafka 를 띄운다 |
| 환경 점검 | `src/lib/env-checks.ts` 의 주제별 점검 카드 | 무엇이 빠졌는지 대시보드가 알려 준다 |
| 골든 패스 | 노트 frontmatter 규칙, ShellExperiment·CodeExperiment 형식 | 새 주제를 같은 모양으로 추가한다 |
| 정책을 코드로 | `tests/content.test.ts`(CI) — frontmatter·링크·실험 id 검사 | 규칙을 어기면 CI 가 막는다 |
| 안전한 기본값 | `src/lib/deadman.ts` — 장애 주입 실험의 자동 원복 | 실험이 중간에 끊겨도 Redis 가 멈춘 채 남지 않는다 |

실험 `plat-catalog-validate` 는 이 카탈로그(`subjects.ts`)를 읽어 주제마다 노트·퀴즈·실험·환경 점검이 다 갖춰졌는지 **완성도 점수표**를 만든다. 플랫폼 팀이 "어느 서비스가 표준을 안 따르나" 를 보는 스코어카드와 같은 일이다. 자세한 구조는 [이 저장소를 작은 IDP 로 보기](/platform-engineering/notes/07-this-repo-as-idp)에서 다룬다.

## 실전에서는 어디에 쓰이나 — 플랫폼 엔지니어링 지도

> 플랫폼 엔지니어링은 개발 팀이 수십 개로 늘어 "각 팀이 CI·배포·관측·인프라를 처음부터 다시 만드는" 비용이 커질 때, 그 반복을 셀프서비스 제품으로 흡수하는 일이다. 목표는 기술 도입이 아니라 개발자의 인지 부하 감소다.

| 서비스·상황 | 이 주제의 어떤 부분이 | 더 읽기 |
|---|---|---|
| 장애 때 "이 서비스 주인이 누구냐" 로 첫 10분을 잃는 조직 | 서비스 카탈로그와 소유권 강제 | [서비스 카탈로그와 Backstage](/platform-engineering/notes/02-service-catalog-backstage) |
| 새 서비스 하나 띄우는 데 며칠씩 걸리는 성장기 스타트업 | 골든 패스·템플릿에 CI·관측·보안 기본값 내장 | [골든 패스와 템플릿](/platform-engineering/notes/03-golden-paths-templates) |
| "DB 하나 주세요" 티켓이 인프라 팀에 쌓이는 SaaS 회사 | Terraform 모듈·Crossplane 으로 셀프서비스 + 정책 가드레일 | [셀프서비스 인프라](/platform-engineering/notes/04-self-service-infrastructure) |
| 플랫폼 예산을 받으려면 효과를 증명해야 할 때 | DORA 네 지표와 SPACE·설문 | [DORA 지표와 개발자 경험](/platform-engineering/notes/05-dora-devex-metrics) |
| CI·배포 파이프라인 장애로 전사 배포가 멈추는 상황 | 플랫폼 자체의 SLO·에러 버짓·폭발 반경 관리 | [플랫폼 자체의 관측·SLO](/platform-engineering/notes/06-platform-observability-slo) |
| 작은 저장소에서 플랫폼 원리를 직접 연습하고 싶을 때 | 카탈로그·셀프서비스·정책을 코드로의 축소판 | [이 저장소를 작은 IDP 로 보기](/platform-engineering/notes/07-this-repo-as-idp) |

**회사 규모에 따라**
- 스타트업: 별도 플랫폼 팀 없이 시니어 한두 명이 재사용 CI 워크플로와 서비스 템플릿 하나를 관리하는 정도로 충분하다. 포털은 과하다.
- 성장기: 팀이 10개 안팎을 넘으면 플랫폼 팀을 만들고 카탈로그·골든 패스·Terraform 모듈부터 제품처럼 운영한다(첫 사용자 팀과 협업 모드).
- 대규모 조직: 개발자 포털(Backstage 류)·셀프서비스 API·스코어카드·플랫폼 SLO 와 온콜까지 갖춘다. 데이터 플랫폼·ML 플랫폼처럼 플랫폼 팀이 여러 개로 나뉜다.

**이럴 땐 안 맞는다**
- 팀이 하나뿐이고 서비스도 몇 개 — 플랫폼 팀을 두면 오히려 티켓 창구가 하나 더 생긴다. README 와 스크립트로 충분하다.
- 사용자 인터뷰 없이 "포털부터 깔자" 로 시작하는 경우 — 아무도 안 쓰는 플랫폼이 된다. 가장 아픈 반복 작업 하나부터 자동화한다.

**누가 매일 만나나** — 플랫폼 엔지니어는 템플릿·모듈·지원 채널 질문을 다루며, 백엔드·데이터·ML 엔지니어는 새 서비스를 만들거나 DB 를 요청하거나 배포가 막힐 때 플랫폼을 "사용자" 로 만난다. 엔지니어링 매니저는 DORA·설문 결과로 만난다.

**면접·실무 단골 질문**
- Q. DevOps·SRE·플랫폼 엔지니어링의 차이는? → DevOps 는 문화와 흐름, SRE 는 신뢰성(SLO·토일), 플랫폼은 인지 부하와 셀프서비스. 경쟁이 아니라 층이다.
