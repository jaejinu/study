## 처리량을 정하는 세 개의 상한

TCP 연결 하나의 처리량은 다음 중 **가장 작은 값**이다.

| 상한 | 식 | 무엇이 정하나 |
|---|---|---|
| 링크 대역폭 | 병목 링크 속도 | 회선 |
| 윈도 / RTT | min(cwnd, rwnd, 송신 버퍼) / RTT | 버퍼 크기와 지연 |
| 손실 상한 | ≈ MSS / RTT · 1.22 / √p | 손실률과 지연 |

대역폭이 남아도는데 느리다면 대개 둘째나 셋째다.

## BDP — 파이프를 채우려면 얼마나 실어야 하나

**대역폭-지연 곱(BDP)** = 대역폭 × RTT. 파이프 안에 "날아가는 중" 인 데이터 양이다.

```
1 Gbit/s × 100 ms = 100 Mbit = 12.5 MB
```

1Gbit/s 를 100ms 경로로 다 쓰려면 ACK 없이 12.5MB 를 보낼 수 있어야 한다. 윈도·소켓 버퍼가 그보다 작으면 처리량은 `버퍼 / RTT` 에서 멈춘다.

```bash
cat /proc/sys/net/ipv4/tcp_wmem     # 4096  16384  4194304   (최소·기본·최대 송신 버퍼)
cat /proc/sys/net/ipv4/tcp_rmem     # 수신 버퍼 — 자동 조정(autotuning)으로 최대까지 커짐
# 최대 4MB / 0.1s = 40 MB/s = 320 Mbit/s  → 100ms 경로에서 연결 하나의 상한
```

장거리 전송(리전 간 복제, 백업)이 "회선은 10Gbit 인데 연결 하나가 300Mbit 에서 멈춘다" 면 버퍼 최대값을 BDP 이상으로 올리거나 연결을 여러 개 쓴다.

## Mathis 공식 — 손실이 정하는 상한

손실률 p 에서 Reno 류 TCP 의 정상 상태 처리량(Mathis et al., 1997):

```
처리량 ≲ (MSS / RTT) × (1.22 / √p)
```

| RTT | p | 예측(MSS 1448B) |
|---|---|---|
| 25ms | 1% | 5.65 Mbit/s |
| 100ms | 1% | 1.41 Mbit/s |
| 100ms | 5% | 0.63 Mbit/s |

두 가지가 무섭다.

1. **처리량 ∝ 1/RTT.** 서울-버지니아(RTT 180ms)는 서울-도쿄(30ms)보다 같은 손실에서 6배 느리다. 대역폭을 늘려도 소용없다.
2. **처리량 ∝ 1/√p.** 손실 0.01% → 1% 면 처리량이 10분의 1. 손실 1% 는 "작아 보이지만" 장거리에서는 치명적이다.

## 실험 — 9칸 표

실험 `netp-loss-throughput` 은 클라이언트 컨테이너의 송신 방향에 `tc netem` 으로 지연·손실을 걸고 iperf3 로 5초씩 업로드했다(CUBIC).

| 추가 지연 | 손실 | 측정 Mbit/s | 재전송 | 측정 RTT | Mathis 예측 | 측정/예측 |
|---|---|---|---|---|---|---|
| 0ms | 0% | 8922 | 856 | 0.13ms | 제한 없음 | — |
| 0ms | 1% | 7351 | 30757 | 0.27ms | 707 | 10.4× |
| 0ms | 5% | 283 | 6466 | 0.13ms | 316 | 0.9× |
| 25ms | 0% | 320 | 2063 | 26.4ms | 제한 없음 | — |
| 25ms | 1% | 7.72 | 29 | 26.8ms | 5.65 | 1.4× |
| 25ms | 5% | 2.71 | 44 | 27.4ms | 2.53 | 1.1× |
| 100ms | 0% | 95.8 | 2951 | 102ms | 제한 없음 | — |
| 100ms | 1% | 3.70 | 14 | 102ms | 1.41 | 2.6× |
| 100ms | 5% | 1.03 | 28 | 102ms | 0.63 | 1.6× |

읽는 법:

- **같은 링크, 손실 1% 만으로 8.9 Gbit/s → 7.7 Mbit/s(25ms)**. 1000배 차이다. 지연과 손실이 곱해질 때 처리량이 무너진다.
- 지연 25ms·100ms 에서 **측정이 Mathis 예측과 같은 자릿수**(1.1~2.6배)다. CUBIC 은 손실 후 회복이 Reno 보다 빨라 예측보다 조금 높게 나온다.
- RTT 가 거의 0 인 LAN(0ms 행)에서는 공식이 맞지 않는다(10.4×). 재전송이 RTT 0.1ms 안에 끝나 손실이 거의 비용이 아니다. **Mathis 는 장거리 경로의 감각을 주는 공식**이다.
- 손실 0% 의 100ms 행(95.8)은 손실 상한이 아니라 **윈도/RTT 상한과 슬로 스타트** 때문이다([노트 04](/network-protocols/notes/04-congestion-control)).

## 버퍼블로트 — 큐가 깊으면 지연만 늘어난다

병목 앞 큐가 깊으면 손실 기반 TCP 는 큐가 넘칠 때까지 윈도를 키운다. 큐에 쌓인 시간이 그대로 지연이 된다.

```
큐 깊이(시간) = 큐 길이(패킷) × 패킷 크기 / 병목 대역폭
1000 패킷 × 1500B × 8 / 10 Mbit/s = 1.2 초
```

실험 `netp-congestion-control` 의 후반부는 10Mbit/s 병목에 큐 깊이만 바꿔, 업로드로 링크를 채운 동안 ping RTT 를 쟀다.

| 병목 큐 깊이 | 유휴 RTT | 포화 중 RTT | 업로드 |
|---|---|---|---|
| 1000 패킷 (≈ 1.2초 분량) | 0.91ms | **183ms** | 9.45 Mbit/s |
| 20 패킷 (≈ 24ms 분량) | 1.03ms | **47.8ms** | 9.51 Mbit/s |

**처리량은 똑같은데 지연이 4배**다. 깊은 큐는 처리량에 아무것도 보태지 않고, 같은 링크를 쓰는 다른 모든 흐름(화상 통화·게임·DNS)을 기다리게 한다. "누가 업로드만 하면 화상회의가 끊긴다" 의 정체다.

### 해법

| 방법 | 원리 |
|---|---|
| **AQM** — fq_codel, CAKE | 큐에서 오래 기다린 패킷(예: 5ms 이상)을 일찍 버리거나 ECN 표시 → TCP 가 일찍 속도를 줄임. 흐름별 큐(fq)로 작은 흐름을 보호 |
| BBR | 큐를 채우지 않는 속도로 보냄([노트 04](/network-protocols/notes/04-congestion-control)) |
| 버퍼 축소 | 장비 버퍼를 BDP 수준으로 |
| 우선순위 | 지연 민감 트래픽(DSCP)을 앞으로 |

리눅스 기본 qdisc 는 대부분 `fq_codel` 이다. 문제는 대개 **가정용 공유기·모뎀**의 깊은 버퍼다.

## netem 으로 재현하는 법 — 그리고 함정

```bash
tc qdisc replace dev eth0 root netem delay 100ms loss 1%       # 지연·손실
tc qdisc replace dev eth0 root netem delay 50ms 10ms distribution normal   # 지터
tc qdisc replace dev eth0 root netem rate 10mbit limit 1000     # 대역폭 + 큐 깊이
tc qdisc replace dev eth0 root netem loss 1% 25%               # 상관 손실(연달아 손실)
tc qdisc del dev eth0 root                                      # 해제
```

- netem 은 **송신 방향**(egress)에만 걸린다. 왕복 지연을 주려면 한쪽에 RTT 전체를, 또는 양쪽에 절반씩.
- 컨테이너에는 `--cap-add NET_ADMIN` 이 필요하다. 그 컨테이너의 네트워크 네임스페이스에만 적용돼 호스트·다른 컨테이너에는 영향이 없다.
- **세그먼트 오프로드 함정**: veth 는 TSO/GSO 로 64KB 짜리 "슈퍼 패킷" 을 큐에 넣는다. 그러면 `limit 20` 이 20 × 64KB 가 되어 얕은 큐가 깊은 큐가 된다. 실험 준비 때 실제로 겪었다: 오프로드를 켠 채로는 얕은 큐 RTT 가 342ms 였고, `ethtool -K eth0 gso off tso off gro off` 후 42ms 가 됐다. 실험은 그래서 두 컨테이너의 오프로드를 끄고 시작한다.

## 예시로 보기 — 이 프로젝트에서

- 장애 실험([장애 실험실 02](/chaos/notes/02-failure-catalog))이 다루는 "느린 네트워크" 를 정량화한 것이 이 노트다. 지연 100ms·손실 1% 라는 흔한 모바일 조건에서 연결 하나는 수 Mbit/s 에 갇힌다.
- Kafka 클러스터를 리전 간에 복제한다면([Kafka 07](/kafka/notes/07-operations-tuning)) 소켓 버퍼(`socket.send.buffer.bytes`)를 BDP 이상으로 올려야 한다.
- 이 사이트의 앱은 짧은 응답이 대부분이라 처리량보다 **지연(RTT 횟수)** 이 체감을 정한다 — 연결 재사용과 HTTP/2 가 버퍼 튜닝보다 중요하다.

## 실무 시나리오 세 개

**1. 리전 간 백업이 300Mbit/s 에서 멈춘다**
서울 → 버지니아 RTT 180ms, 회선 10Gbit/s. 연결 하나의 상한은 송신 버퍼 4MB / 0.18s ≈ 178Mbit/s. 손실이 0.01% 만 있어도 Mathis 상한은 1448B/0.18s × 1.22/0.01 ≈ 785Mbit/s. → 버퍼 최대를 BDP(10Gbit × 0.18s ≈ 225MB 는 비현실적이므로 수십 MB)로 올리고, **병렬 연결 여러 개**로 나눈다.

**2. 모바일 앱의 이미지 로딩이 느리다**
RTT 100ms, 손실 1%. 이미지 하나 200KB. 슬로 스타트로 200KB 는 약 4 RTT = 400ms + 핸드셰이크 2~3 RTT. 손실이 슬로 스타트 중에 나면 cwnd 가 반토막. → 연결 재사용(HTTP/2·3), 이미지 크기 줄이기(포맷·해상도), CDN 엣지로 RTT 단축([노트 06](/network-protocols/notes/06-load-balancing-cdn)).

**3. 사무실에서 누가 대용량 업로드를 하면 화상회의가 끊긴다**
업링크 20Mbit/s, 공유기 버퍼 깊음 → 버퍼블로트. 업로드가 큐를 채워 모든 패킷이 수백 ms 대기. → 공유기에 SQM(fq_codel·CAKE)을 켜고 대역폭을 실제의 90~95% 로 설정.

## 숫자 감각

| 경로 | RTT | 손실 | 연결 하나의 현실적 처리량 |
|---|---|---|---|
| 같은 데이터센터 | 0.2ms | ~0 | 수 Gbit/s (NIC·CPU 한계) |
| 같은 리전 AZ 간 | 1~2ms | ~0 | 수 Gbit/s |
| 서울 ↔ 도쿄 | 30ms | 0.01% | 수백 Mbit/s~1Gbit/s (버퍼 조정 시) |
| 서울 ↔ 미국 동부 | 180ms | 0.01~0.1% | 수십~수백 Mbit/s |
| LTE | 50~100ms | 0.1~1% | 수~수십 Mbit/s |

## 실전에서는 어디에 쓰이나

> "회선은 넓은데 연결 하나가 느리다", "누가 업로드만 하면 통화가 끊긴다" 같은 증상에서 BDP·Mathis·버퍼블로트 산수가 원인을 짚는다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 클라우드 리전 간 백업·DB 복제 | 넓은 회선에서 연결 하나가 수백 Mbit 에 멈춤 | 소켓 버퍼 최대를 BDP 쪽으로 올리고 병렬 연결 | 회선 증설 — 버퍼 상한이면 효과 없음 |
| 리전 간 Kafka 복제 | 장거리에서 복제 처리량 부족 | 브로커 소켓 버퍼를 BDP 이상으로 | 기본 버퍼 — 윈도/RTT 상한에 갇힘 |
| 모바일 앱 이미지 로딩 | RTT 100ms·손실 1% 에서 느린 로딩 | CDN 엣지로 RTT 단축, 연결 재사용, 이미지 축소 | 원본 직결 — Mathis 상한 그대로 |
| 사무실·재택 화상회의 | 대용량 업로드 중 통화 끊김 | 공유기 SQM(fq_codel·CAKE), 대역폭을 실제의 90~95% 로 | 회선 증설 — 깊은 큐는 그대로 |
| 장애 실험·QA 환경 | 느린 네트워크 조건 재현 | `tc netem` 지연·손실, 오프로드 끄기 | 실제 모바일망 테스트 — 재현성 낮음 |

**이럴 땐 안 맞는다**
- 같은 데이터센터(RTT 0.1ms 대) — Mathis 공식이 맞지 않는다. 손실 비용이 거의 없고 NIC·CPU 가 상한이다.
- 짧은 API 응답 위주 서비스에서 버퍼 튜닝 — 처리량보다 RTT 횟수가 체감을 정하므로 연결 재사용이 먼저다.

**누가 매일 만나나** — SRE·인프라 엔지니어가 "복제가 왜 회선만큼 안 나오나" 를 조사할 때, 데이터 엔지니어가 리전 간 대용량 이관 시간을 견적 낼 때.

**면접·실무 단골 질문**
- Q. 1Gbit/s · RTT 100ms 경로를 연결 하나로 채우려면? → BDP 12.5MB 이상의 윈도·소켓 버퍼가 필요하다.
- Q. 버퍼블로트란? → 깊은 큐가 처리량은 그대로 두고 지연만 늘리는 현상. AQM(fq_codel·CAKE)이나 BBR 로 큐를 비운다.
