## 용량 계획이 답하는 질문

"다음 분기 트래픽 2배를 지금 인프라로 받을 수 있나? 안 되면 무엇을 얼마나 늘려야 하고 비용은?" 추측이 아니라 **측정 + 계산**으로 답하는 것이 용량 계획이다. 네 단계:

1. **부하 모델**: 요청 혼합(엔드포인트 비율), 도착률의 시간 패턴(일 피크/평균 비율, 이벤트 스파이크), 데이터 크기 성장.
2. **단위 용량**: 인스턴스 1개가 SLO 를 지키며 받는 최대 처리량(breakpoint 테스트, [k6](/performance/notes/03-k6-load-testing)).
3. **헤드룸**: 피크 × 안전 계수(1.3~2) + 장애 시 여유(N+1, AZ 하나 손실 시 나머지로 피크 처리).
4. **예측과 재검토**: 성장률로 외삽, 분기마다 다시 측정(코드가 바뀌면 단위 용량도 바뀐다).

## 부하 모델 만들기

운영 데이터에서 뽑는다 — 추측하지 않는다.

| 항목 | 출처 | 예 |
|---|---|---|
| 엔드포인트 혼합 | 액세스 로그/메트릭의 라우트별 비율 | 노트 읽기 85%, 검색 10%, 진행률 쓰기 5% |
| 피크/평균 비율 | 일주일 시계열의 max/avg | 3배 (저녁 피크) |
| 스파이크 | 마케팅 캘린더, 과거 이벤트 | 세일 오픈 10분간 10배 |
| 사용자당 요청 | 세션 로그 | 세션당 20 요청, 평균 체류 5분 |
| 데이터 성장 | DB 크기 추세 | 월 15% → 인덱스가 메모리를 넘는 시점 |

리틀의 법칙으로 동시 사용자 ↔ 도착률 변환: 동시 사용자 10,000 × (20 요청 / 300초) ≈ 670 req/s.

## 단위 용량과 헤드룸

breakpoint 테스트로 "인스턴스 1개의 SLO 내 최대 처리량" 을 얻는다. **SLO 내**가 중요하다 — 포화점이 아니라 "p95 < 300ms 를 지키는 최대" 가 용량이다. 보통 포화점의 60~70%.

```
단위 용량 U = 300 req/s (p95 < 300ms 유지 기준)
피크 λ_peak = 평균 400 × 3 = 1,200 req/s
필요 인스턴스 = ceil(1,200 × 1.5(안전 계수) / 300) = 6
N+1 (하나 죽어도 피크 처리): 6 → 7
AZ 2개에 분산, AZ 하나 손실 시 피크 처리하려면 각 AZ 에 6 → 총 12 (비용 ↑ — 트레이드오프)
```

다운스트림도 같은 계산: 앱 1,200 req/s × 증폭 계수(Redis 명령/요청 20) = 24,000 ops/s → 단일 Redis 로 충분. PG 는 쿼리/요청 × 평균 쿼리 시간으로 커넥션 수([데이터 접근](/performance/notes/05-data-access-bottlenecks)).

## 수직 vs 수평

| | 수직(더 큰 머신) | 수평(더 많은 머신) |
|---|---|---|
| 장점 | 코드 변경 없음, 단일 노드 일관성 유지, 조인·트랜잭션 단순 | 상한 없음(이론상), 장애 격리, 무중단 |
| 한계 | 가장 큰 인스턴스가 상한, 비용 비선형, 재시작 시 전체 중단 | 상태를 나눠야(파티셔닝, 세션 외부화), 조정 비용(USL 의 κ), 운영 복잡 |
| 적합 | DB 프라이머리, 캐시 단일 인스턴스, 초기 단계 | 무상태 앱 서버, 읽기 복제본, 파티션 가능한 데이터 |

규칙: **무상태 계층은 수평, 상태 계층은 먼저 수직 + 읽기 복제 → 정말 필요할 때 파티셔닝**([확장성 패턴](/architecture/notes/02-scalability-patterns), [파티셔닝](/distributed-systems/notes/07-partitioning)). 수평 확장 전에 "서버 1대당 효율" 을 먼저 올리는 게 싸다(프로파일링으로 2배는 흔하다).

## 오토스케일 신호

| 신호 | 장점 | 단점 |
|---|---|---|
| **CPU 사용률** | 쉬움, 기본 HPA | I/O 바운드 앱은 CPU 가 낮아도 느림. Node 단일 스레드는 1코어 100% = 포화인데 평균은 25% 로 보임 |
| **큐 길이 / 대기 중 요청** | 포화를 직접 측정 | 큐가 있어야(메시지 소비자에 최적 — KEDA) |
| **지연 p95** | SLO 와 직결 | 후행 지표(이미 느림), 노이즈 |
| **요청률(RPS/인스턴스)** | 선행 지표, 단위 용량과 직접 연결 | 요청 비용이 균일해야 |
| 예측(스케줄) | 피크 전에 미리 | 패턴이 규칙적일 때만 |

HPA 의 수식: 원하는 복제본 = ceil(현재 복제본 × 현재 값 / 목표 값). **목표를 단위 용량의 60~70%** 에 두어야 스케일 지연(이미지 풀 + 기동 + 워밍업 = 수십 초~분) 동안 버틴다. 스케일 다운은 보수적으로(안정화 창 5분 이상) — 플래핑 방지. 스파이크는 오토스케일로 못 받는다 → 헤드룸 + 부하 차단([Tail at Scale](/performance/notes/08-tail-latency-at-scale)).

## 비용 대비 성능

- **요청당 비용** = 인프라 월 비용 / 월 요청 수. 최적화의 ROI 를 이 숫자로 말한다("p99 30% 개선 + 인스턴스 6 → 4, 월 $800 절감").
- 인스턴스 크기 선택: 큰 인스턴스 몇 개 vs 작은 인스턴스 많이 — 작은 쪽이 장애 단위가 작고 오토스케일 입자가 곱다. 네트워크 대역·메모리 당 비용은 크기별로 다르니 벤치마크로.
- 예약/스팟: 기본 부하는 예약, 피크는 온디맨드/스팟(무상태만).
- **낭비 찾기**: requests 대비 실제 사용(`kube-resource-report`, VPA 추천), 유휴 복제본, 과한 로그 보존, 큰 캐시의 낮은 적중률.

## 성능 예산과 SLO

- **SLO**: "노트 페이지 p95 < 300ms, 가용성 99.9%" 처럼 사용자 관점 목표. 에러 예산(0.1% = 월 43분)을 넘기면 기능보다 안정화 우선([아키텍처 운영](/architecture/notes/07-operations-architecture)).
- **성능 예산**: 엔드포인트별 지연·크기·쿼리 수 상한을 **코드 리뷰 기준**으로. "이 페이지는 DB 왕복 5회 이하, 응답 100KB 이하".
- 예산을 넘는 PR 은 CI 가 막는다 — 아래.

## 성능 회귀 CI

```yaml
# .github/workflows/perf.yml (요지)
jobs:
  perf:
    runs-on: ubuntu-latest
    services: { redis: { image: redis:8-alpine, ports: ["6379:6379"] } }
    steps:
      - uses: actions/checkout@v5
      - run: pnpm install --frozen-lockfile && pnpm build
      - run: pnpm start & npx wait-on http://localhost:3000/api/metrics
      - run: k6 run --summary-export k6.json tests/perf/smoke.js       # thresholds = 성능 예산
      - run: node scripts/perf-compare.mjs k6.json baseline/k6.json     # 기준선 대비 +20% 면 실패
      - uses: actions/upload-artifact@v4
        with: { name: k6, path: k6.json }
```

원칙:
1. **운영 빌드**로, 같은 러너 크기로(노이즈). GitHub 호스티드 러너는 성능이 들쑥날쑥 — 상대 비교(기준선 대비 %)와 넉넉한 임계값(+20~30%), 또는 셀프 호스티드 러너.
2. **기준선**을 main 의 마지막 결과로 저장(아티팩트/캐시)하고 PR 과 비교.
3. 짧게(스모크 1~2분). 긴 테스트는 야간 스케줄.
4. 결과를 PR 코멘트로(표) — [GitHub Actions](/github-actions/notes/02-cache-matrix-artifacts) 의 아티팩트·캐시.
5. 벤치마크 라이브러리 수준(tinybench)의 마이크로 벤치는 별도 — 함수 단위 회귀.

## 예시로 보기 — 이 프로젝트에서

실험 `perf-k6-arrival-rate` 의 측정으로 계산 연습:

- 개발 서버 단위 용량: 포화 ≈ 37 req/s, 25 req/s 에서 p99 63ms 였으니 **SLO(p99 < 100ms) 내 용량 ≈ 25~30 req/s**.
- 가상의 목표: 피크 300 req/s → 300 × 1.5 / 25 = **18 인스턴스**(개발 서버 기준 — 운영 빌드는 10배 이상이라 2~3개).
- Redis: 증폭 계수(`perf-k6-redis-path` 결과) × 300 = 수천 ops/s → 단일 Redis 로 충분. 병목은 앱.
- HPA 목표: 단위 용량의 65% → 인스턴스당 ~16 req/s 에서 스케일. RPS 기반이면 `kubectl autoscale` 대신 커스텀 메트릭(Prometheus Adapter, `sum(rate(study_action_duration_seconds_count[1m]))`).

kind 의 web Deployment 에 HPA 가 있다(`k8s/` + metrics-server, [HPA 실험](/kubernetes/notes/14-scheduling-autoscaling-deep)). `chaos-k8s-pod-kill-under-load` 의 부하를 주며 `kubectl get hpa -w` 로 스케일 결정과 **실제 Ready 까지의 지연**을 재면 "스케일 지연 동안 버틸 헤드룸" 이 얼마인지 체감된다.

CI 는 `.github/workflows/ci.yml` 에 Redis 서비스 컨테이너로 vitest 를 돌리는 구조가 이미 있다. 거기에 위의 perf 잡을 추가하면 된다 — 첫 단계는 `pnpm build && pnpm start` 후 스모크 임계값만.

## 실전에서는 어디에 쓰이나

> "다음 분기 트래픽 2배, 이벤트 날 10배를 받을 수 있나, 비용은?" 이라는 질문이 오면 용량 계획이 등장한다. 인프라 예산, 오토스케일 설정, SLO 협상의 근거가 된다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 커머스 연말 세일 대비 | 피크 × 안전 계수만큼 미리 확보 | breakpoint 로 단위 용량 → 인스턴스 수·N+1·AZ 여유 계산 | 오토스케일만 믿기(스파이크엔 늦음) |
| 알림·이메일 발송 워커 | 백로그에 맞춰 워커 수 조절 | 큐 길이 기반 오토스케일(KEDA) | CPU 기반 HPA 는 I/O 바운드에 둔감 |
| 쿠버네티스 위 무상태 API | 트래픽 추세에 따른 자동 증감 | 단위 용량의 60~70% 를 HPA 목표로, 스케일다운 안정화 창 | 규칙적 패턴은 예측(스케줄) 스케일 |
| 클라우드 비용 절감 요구 | 같은 SLO 를 더 싸게 | 요청당 비용, requests 대비 실사용, 예약 + 스팟 조합 | 일괄 인스턴스 축소 |
| 사내 플랫폼 공통 CI | 성능 회귀가 배포되는 것 방지 | k6 스모크 + main 기준선 대비 +20% 면 실패 | 운영 모니터링으로 사후 발견 |

**이럴 땐 안 맞는다**
- 이벤트성 수십 배 스파이크를 오토스케일만으로 → 스케일 지연(수십 초~분) 동안 무너진다. 사전 증설, 헤드룸, 부하 차단, 대기열로.
- 상태 계층(DB 프라이머리)을 무상태처럼 수평 확장 → 파티셔닝·일관성 비용이 크다. 수직 확장 + 읽기 복제부터.

**누가 매일 만나나** — SRE·플랫폼 엔지니어가 분기 용량 리뷰와 이벤트 대비 회의를 준비할 때, 엔지니어링 매니저가 인프라 예산을 요청당 비용으로 설명할 때.

**면접·실무 단골 질문**
- Q. 단위 용량을 포화점으로 잡으면 안 되는 이유는? → 포화점 근처는 지연이 발산한다. SLO 를 지키는 최대 처리량(보통 포화점의 60~70%)이 용량이다.
- Q. 오토스케일 신호로 CPU 의 한계는? → I/O 바운드나 Node 단일 스레드에선 포화를 못 보여 준다. 큐 길이·RPS·지연을 쓴다.

## 실습 체크리스트

- [ ] 운영 빌드로 breakpoint 테스트를 돌려 "SLO 내 단위 용량" 을 구한다
- [ ] 가상의 피크(평균 3배)와 안전 계수로 필요한 인스턴스 수와 Redis ops/s 를 계산한다
- [ ] HPA 목표를 단위 용량의 65% 로 설정하고 부하 중 스케일 결정 → Ready 지연을 잰다
- [ ] 노트 페이지에 성능 예산(쿼리 수·응답 크기·p95)을 정하고 코드 리뷰 체크리스트에 넣는다
- [ ] CI 에 k6 스모크 + 기준선 비교 잡을 추가해 PR 에서 돈다
