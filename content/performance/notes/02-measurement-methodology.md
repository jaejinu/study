## 측정 없이 추측하지 않는다

성능 작업의 첫 규칙: **먼저 재고, 가설을 세우고, 바꾸고, 다시 잰다.** 경험 많은 엔지니어의 직감도 절반은 틀린다. "DB 가 느릴 거야" 라고 믿고 인덱스를 추가했는데 병목은 JSON 직렬화였던 식이다. 두 번째 규칙: **가장 큰 것부터**. p99 의 80% 를 차지하는 한 구간을 고치면 나머지는 나중에.

## 어디를 볼 것인가 — 세 방법론

### USE (Brendan Gregg) — 자원 중심

모든 **자원**(CPU, 메모리, 디스크, 네트워크, 커넥션 풀, 스레드 풀, 큐)에 대해:

| 항목 | 질문 | 예 |
|---|---|---|
| **U**tilization | 얼마나 바쁜가 | CPU 85%, 디스크 I/O 시간 비율, 풀 사용 중 비율 |
| **S**aturation | 대기 중인 일이 있는가 | 런큐 길이, 디스크 큐 깊이, 풀 대기자 수, 이벤트 루프 지연 |
| **E**rrors | 오류가 있는가 | 네트워크 재전송, OOM kill, 커넥션 거부 |

자원 체크리스트를 **위에서 아래로** 순서대로 보면 놓치지 않는다. 포화(S)가 핵심이다 — 사용률 70% 여도 큐가 쌓이면 문제고, 95% 여도 큐가 없으면 괜찮다.

### RED (Tom Wilkie) — 서비스 중심

각 **서비스/엔드포인트**에 대해 **R**ate(요청률), **E**rrors(오류율), **D**uration(지연 분포). 사용자가 겪는 것을 바로 보여 준다. 마이크로서비스 대시보드의 표준이고, 이 앱의 Grafana RED 패널이 이것이다 ([앱 계측](/observability/notes/03-instrumentation-exporters)).

### 네 가지 골든 시그널 (Google SRE)

지연, 트래픽, 오류, **포화**. RED + USE 의 S. 알림은 이 넷에 건다.

> 조합: RED 로 "어느 서비스가 느린가" 를 찾고, 그 서비스의 자원을 USE 로 훑어 "무엇이 포화인가" 를 찾는다.

## 도구의 역할 분담

| 도구 | 답하는 질문 | 해상도 | 비용 |
|---|---|---|---|
| **메트릭** | 언제부터, 얼마나, 어느 서비스가 | 시계열(초) | 낮음, 항상 켬 |
| **트레이스** | 이 요청의 시간이 **어느 구간**에 쓰였나 | 요청·span(ms) | 샘플링 필요 |
| **로그** | 그때 정확히 무슨 일이 | 이벤트 | 양 많음 |
| **프로파일러** | 이 프로세스의 CPU/메모리가 **어느 함수**에 쓰이나 | 함수·줄(μs) | 높음, 필요할 때 |
| **부하 도구** | 이 부하에서 어떻게 되나 | 실험 | 환경 필요 |

전형적 흐름: 메트릭(RED)이 p99 상승 알림 → 트레이스에서 느린 요청의 span 을 보니 DB 쿼리 1개가 400ms → 그 쿼리의 EXPLAIN → 인덱스. 또는 span 에 빈 구간(어느 자식도 없는 시간)이 크면 **CPU 작업** → 프로파일러. [트레이싱](/observability/notes/06-tracing-otel) 과 [Node 프로파일링](/performance/notes/04-node-web-server-performance).

### 프로파일링 두 종류

- **샘플링**: 주기적으로(1ms) 스택을 찍어 통계. 오버헤드 작고 운영에서도 가능(continuous profiling — Pyroscope, Parca). flame graph 의 원천.
- **계측(instrumentation)**: 함수 진입·종료를 기록. 정확하지만 느리고 결과를 왜곡(관찰자 효과).

## 벤치마크의 함정

벤치마크는 쉽게 **틀린 숫자**를 준다. 흔한 실수:

| 함정 | 증상 | 대책 |
|---|---|---|
| **워밍업 없음** | 처음 수백 요청이 느림(JIT, 커넥션 수립, 캐시 비어 있음) | 워밍업 구간을 결과에서 제외. k6 는 첫 시나리오를 버리거나 `startTime` |
| **캐시 효과** | 같은 키만 반복해 100% 캐시 히트 → 비현실적으로 빠름 | 실제 키 분포(지프, 핫 키 20%) 로 요청 생성 |
| **단일 실행** | 한 번 돌리고 1.3배 빨라졌다고 결론 | 5~10회 반복, 중앙값과 분산 보고. 차이가 분산보다 작으면 "차이 없음" |
| **노이즈** | 노트북에서 재는데 브라우저·Docker 가 CPU 경쟁 | 전용 머신, CPU 고정(governor), 백그라운드 종료, 같은 조건 반복 |
| **부하 도구가 병목** | k6 머신이 100% CPU → 서버가 아니라 도구가 포화 | 도구 머신의 CPU 확인, 분산 실행 |
| **localhost 측정** | 네트워크 지연 0 → 운영과 다름 | 운영과 같은 토폴로지에서 한 번은 잰다 |
| **잘못된 통계** | 평균만 보고, 또는 서로 다른 조건의 p99 를 비교 | 분포 전체, 같은 조건 |
| **죽은 코드 제거** | 마이크로벤치마크에서 결과를 안 쓰면 JIT 가 코드를 제거 | 결과를 소비(blackhole), 벤치마크 라이브러리(tinybench, mitata) 사용 |
| **측정이 측정 대상을 바꿈** | 로깅을 켜니 느려짐 | 오버헤드 측정 후 보정, 샘플링 |

### 재현 가능한 실험 설계

1. **가설**을 적는다: "캐시 TTL 을 60s 로 올리면 p95 가 30% 줄 것".
2. **하나만** 바꾼다. 둘을 바꾸면 무엇이 효과인지 모른다.
3. 같은 **부하 모델**(도착률, 키 분포, 혼합 비율)로 전/후를 잰다.
4. 결과를 **표로** 남긴다(날짜, 커밋, 환경, 숫자). 노트의 "예시로 보기" 처럼.
5. 통계적으로 의미 있는지 본다(반복 측정의 분산).

## 흔한 측정 실수 (서버 쪽)

- **서버 측정 vs 클라이언트 측정**: 서버의 핸들러 시간은 큐 대기·TLS·전송을 빼먹는다. 사용자 지연은 클라이언트에서 잰다(RUM, k6 의 `http_req_duration` 은 클라이언트 관점).
- **집계 간격**: 1분 평균 p99 는 10초 스파이크를 숨긴다. 알림은 짧은 창, 추세는 긴 창.
- **단위 혼동**: `rate()` 는 초당, 히스토그램 버킷은 초 vs ms — 이 앱은 초 단위(prom-client 기본).
- **상관 vs 인과**: "배포 후 느려짐" 이 배포 때문인지 동시에 늘어난 트래픽 때문인지 — 트래픽(Rate)을 같이 본다.

## 예시로 보기 — 이 프로젝트에서

실험 `perf-k6-redis-path` 는 "RED 로 보고 USE 로 좁히기" 의 축소판이다:

1. **RED**: 첫 화면(`/`)을 20 req/s 로 치며 k6 가 p50/p95/p99 와 실패율을 준다.
2. **다운스트림 USE**: 동시에 `redis-cli INFO stats` 로 `instantaneous_ops_per_sec` 를 샘플링하고 전후 `total_commands_processed` 차이를 센다.
3. **증폭 계수** = Redis 명령 수 / HTTP 요청 수. 첫 화면은 주제 16개 × (SMEMBERS 2 + SCAN …) 이라 요청 1개가 Redis 명령 수십 개가 된다. 1000 req/s 면 Redis 는 수만 ops/s — 단일 Redis 의 10만+ ops/s 에는 여유. 즉 **병목은 Redis 가 아니다.**
4. 그럼 어디? `/observability` 의 Tempo 에서 `/` 요청 트레이스를 열면 Redis span 들은 ms 단위이고 나머지(렌더링, 직렬 await)가 대부분이다. → 다음 단계는 Node 프로파일링.

이 앱의 Grafana `study-redis` 대시보드에는 액션 RED 히스토그램(`study_action_duration_seconds`)과 Redis 익스포터 메트릭(`redis_commands_processed_total`, `redis_connected_clients`)이 함께 있어, 부하 실험 중 두 계층을 한 화면에서 볼 수 있다 ([Grafana·알림](/observability/notes/04-grafana-alerting)).

```promql
# 부하 중 Redis ops/s
rate(redis_commands_processed_total[1m])
# 앱 액션 p99
histogram_quantile(0.99, sum(rate(study_action_duration_seconds_bucket[1m])) by (le, action))
# 증폭 계수 (PromQL 로)
rate(redis_commands_processed_total[1m]) / sum(rate(study_action_duration_seconds_count[1m]))
```
