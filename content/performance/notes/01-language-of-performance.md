## 성능은 두 숫자로 시작한다

- **지연(latency)**: 요청 하나가 걸리는 시간. 사용자가 느끼는 것.
- **처리량(throughput)**: 단위 시간에 처리하는 요청 수(req/s, ops/s, MB/s). 시스템이 감당하는 것.

둘은 독립이 아니다. 처리량을 올리면(부하가 늘면) 어느 지점부터 지연이 **비선형으로** 는다. 그 지점이 **포화점(knee)** 이고 성능 공학의 절반은 그 지점을 찾고 미루는 일이다.

```
지연
 │                                      ╱
 │                                   ╱
 │                              ╱
 │────────────────────────╱           ← 포화점(knee) 전까지는 거의 평평
 └──────────────────────────────────── 처리량(부하)
```

용어 몇 개 더: **응답 시간(response time)** = 서비스 시간 + 대기(큐) 시간 + 네트워크. **서비스 시간**은 실제 일하는 시간. 부하가 늘어 느려지는 것은 거의 전부 **대기 시간**이다 — 서비스 시간은 그대로다.

## 평균은 거짓말한다 — 백분위수

요청 100개 중 99개가 10ms, 하나가 2초면 평균은 30ms. "평균 30ms" 는 아무도 경험하지 않은 숫자다. 그래서 **백분위수(percentile)** 를 쓴다.

| 지표 | 의미 | 쓰임 |
|---|---|---|
| **p50 (median)** | 절반의 요청이 이보다 빠름 | "보통" 경험 |
| **p95** | 95% 가 이보다 빠름, 20 요청 중 1개는 더 느림 | SLO 의 흔한 기준 |
| **p99** | 100 중 1개가 더 느림 | 꼬리 지연. 페이지 하나가 API 100개를 부르면 **거의 모든 페이지**가 p99 를 경험 |
| **p99.9 / max** | 극단 | GC 멈춤, 재시도 폭풍, 락 경합의 증거 |

> **꼬리 증폭**: 페이지가 백엔드 호출 N개를 병렬로 하면 페이지 지연 ≈ 그중 가장 느린 것. N=100 이면 p99 를 겪을 확률 = 1 − 0.99^100 ≈ 63%. 꼬리가 곧 사용자 경험이다. [Tail at Scale](/performance/notes/08-tail-latency-at-scale) 에서 대책을 다룬다.

백분위수는 **집계할 수 없다**: 서버 10대의 p99 평균은 전체 p99 가 아니다. 히스토그램(버킷)을 모아 합친 뒤 계산해야 한다 — Prometheus `histogram_quantile(0.99, sum(rate(bucket[5m])) by (le))` 가 그 일을 한다 ([PromQL](/observability/notes/02-prometheus-promql)). 버킷 경계 밖의 값은 보간으로 추정되므로 버킷을 SLO 근처에 촘촘히 둔다.

## 조정 누락(coordinated omission)

Gil Tene 가 이름 붙인, **부하 도구가 느린 응답을 체계적으로 덜 측정하는** 현상.

```
닫힌 모델(VU 루프): 요청 → 응답 기다림 → 다음 요청
  서버가 2초 멈추면 그 동안 VU 는 "기다리느라" 요청을 안 보낸다.
  실제 사용자였다면 그 2초 동안 도착했을 요청 N개가 모두 2초+ 를 겪었을 텐데, 측정엔 느린 요청 1개만 기록된다.
  → p99 가 실제보다 훨씬 낮게 보인다.

열린 모델(도착률): 서버 상태와 무관하게 초당 R개 요청 발생
  멈춤 동안 도착한 요청이 모두 큐에 쌓여 지연으로 기록된다. 현실과 같다.
```

k6 에서는 `constant-arrival-rate` / `ramping-arrival-rate` 실행기가 열린 모델이다. 사용자 수가 고정된 내부 도구(동시 사용자 50명)가 아니면 열린 모델이 맞다. HdrHistogram 같은 도구는 사후 보정도 제공하지만, 처음부터 열린 모델로 재는 게 낫다 ([k6](/performance/notes/03-k6-load-testing)).

## 리틀의 법칙 — 세 숫자의 관계

안정 상태의 어떤 시스템에서든:

> **L = λ × W** — 시스템 안의 평균 요청 수(동시성) = 도착률 × 평균 체류 시간

예시:
- 500 req/s, 평균 응답 40ms → 동시에 처리 중인 요청 = 500 × 0.04 = **20개**. 워커/스레드/커넥션이 20개는 있어야 큐가 안 생긴다.
- p99 가 400ms 로 튀면 그 순간 동시성은 200개 → 풀이 20개면 180개가 **대기**. 꼬리 지연이 풀 고갈을 만들고, 풀 고갈이 꼬리를 더 키우는 되먹임.
- 거꾸로: DB 커넥션 풀이 10개이고 쿼리 평균 5ms → 최대 처리량 ≈ 10 / 0.005 = **2000 qps**. 그 이상은 무조건 대기.
- 반대 방향: "동시 사용자 1000명이 평균 10초마다 클릭" → λ = 100 req/s. 용량 계획의 출발점.

리틀의 법칙은 분포와 무관하게 성립한다(평균만). 그래서 용량 계산의 첫 도구다 ([용량 계획](/performance/notes/07-capacity-planning)).

## 큐잉 이론 직관 — 왜 80% 에서 절벽인가

![포화 곡선과 실측](/diagrams/perf-saturation.svg)

가장 단순한 모델 M/M/1(포아송 도착, 지수 서비스, 서버 1개)에서 **사용률 ρ = λ / μ** (도착률 / 서비스율)일 때:

> 평균 대기 시간 W_q = ρ / (μ − λ) = (ρ / (1 − ρ)) × 서비스 시간

| 사용률 ρ | 대기 ÷ 서비스 시간 | 뜻 |
|---|---|---|
| 50% | 1.0× | 서비스 시간만큼 더 기다림 |
| 70% | 2.3× | |
| 80% | 4× | |
| 90% | 9× | |
| 95% | 19× | |
| 99% | 99× | 사실상 무한 큐 |

**사용률이 80% 를 넘으면 대기 시간이 급격히 는다**는 것이 모든 성능 가이드의 "CPU 80% 알림", "큐 깊이 모니터링" 의 근거다. 변동(burst)이 클수록 더 낮은 사용률에서 절벽이 온다(M/G/1 — 서비스 시간 분산이 대기를 키운다). 서버를 c 개로 늘리면(M/M/c) 같은 사용률에서 대기가 줄어든다 — 풀링의 효과.

```
도착률 λ 가 서비스율 μ 를 넘으면(ρ > 1) 큐가 무한히 자란다.
  → 지연이 "느려지는" 게 아니라 "발산" 한다. 타임아웃·부하 차단이 없으면 전부 죽는다.
```

## 처리량의 상한: 암달과 USL

- **암달의 법칙**: 직렬 부분이 s 이면 아무리 병렬화해도 속도 향상 ≤ 1/s. 10% 가 직렬이면 최대 10배.
- **범용 확장성 법칙(USL, Gunther)**: 경합(contention, σ)에 **일관성 비용**(coherency, κ — 노드 간 동기화)을 더하면 어느 노드 수 이후 처리량이 **오히려 줄어든다**. 락 경합, 캐시 라인 바운싱, DB 복제 동기화가 κ 다. "서버를 늘렸는데 느려졌다" 의 이론.

## 예시로 보기 — 이 프로젝트에서

실험 `perf-k6-arrival-rate` 가 이 노트의 모든 개념을 한 표에 보여 준다 (개발 서버, `/api/metrics`, 실제 측정):

| 목표 req/s | 실제 req/s | p50 | p95 | p99 | max | drop |
|---|---|---|---|---|---|---|
| 10 | 10.1 | 30ms | 35ms | 37ms | 40ms | 0 |
| 25 | 25.0 | 26ms | 42ms | 63ms | 81ms | 0 |
| 50 | **36.8** | **1012ms** | 1688ms | 1720ms | 1734ms | 45 |

읽는 법:
1. 10 → 25 req/s: p50 은 그대로(오히려 약간 빠름 — 워밍업), **p99 는 37 → 63ms** 로 먼저 벌어진다. 꼬리가 먼저 움직인다.
2. 50 req/s: 실제 36.8 req/s 만 달성 = **포화점은 약 37 req/s**(ρ → 1). 요청이 큐에 쌓여 p50 조차 1초. 큐잉 이론의 발산.
3. `drop=45`: 열린 모델이라 VU 가 바닥나 요청을 시작조차 못 한 수. 닫힌 모델이었다면 이 과부하가 "p99 조금 높음" 정도로 보였을 것(조정 누락).
4. 리틀의 법칙 검산: 50 req/s 시나리오에서 동시성 ≈ 36.8 × 1.0s ≈ 37 — maxVUs 200 중 수십 개가 항상 응답 대기 중이었다는 뜻.
5. 서비스 시간 ≈ 27ms 면 이론상 단일 워커 처리량 ≈ 37 req/s. 측정과 일치 — 개발 서버가 요청을 **직렬**로 처리하고 있다는 추론이 가능하다(운영 빌드·멀티 프로세스에서 다시 재 보자).

`perf-k6-smoke` 는 같은 데이터를 임계값(p95 < 500ms)으로 판정한다. p99/p50 비율을 출력하는데, 2~3배면 정상, 10배 이상이면 간헐 지연(GC, 락, 캐시 미스)을 의심한다.

## 실전에서는 어디에 쓰이나 — 성능 공학 지도

> 성능 공학은 "얼마나 빠른가" 보다 "어느 부하까지 약속(SLO)을 지키나" 를 숫자로 답하는 일이다. 출시 전 부하 리허설, 장애 중 병목 찾기, 증설 결정, 비용 논의가 모두 이 노트의 백분위수·리틀의 법칙·큐잉이라는 공통 언어로 이뤄진다.

| 서비스·상황 | 이 주제의 어떤 부분이 | 더 읽기 |
|---|---|---|
| "어제부터 p99 가 튄다" 알림 | RED 로 서비스를, USE 로 자원을 좁히기 | [측정 방법론](/performance/notes/02-measurement-methodology) |
| 커머스 세일·티켓 오픈 직전 | 열린 모델 부하, spike·breakpoint 테스트 | [k6 부하 테스트](/performance/notes/03-k6-load-testing) |
| Node·Next.js API 의 간헐 멈춤 | 이벤트 루프 지연, GC, flame graph | [Node.js·웹 서버 성능](/performance/notes/04-node-web-server-performance) |
| 대부분의 웹 API 지연 | N+1, 커넥션 풀, 캐시 | [데이터 접근 병목](/performance/notes/05-data-access-bottlenecks) |
| 쿠버네티스로 옮긴 뒤 느려진 서비스 | CPU 스로틀링, requests/limits | [시스템 수준](/performance/notes/06-system-level) |
| 다음 분기 인프라 예산 | 부하 모델, 단위 용량, 헤드룸, HPA | [용량 계획](/performance/notes/07-capacity-planning) |
| 팬아웃 많은 마이크로서비스·AI 서비스 | 꼬리 증폭, 헤징, 부하 차단, TTFT | [꼬리 지연과 대규모](/performance/notes/08-tail-latency-at-scale) |

**회사 규모에 따라** — 스타트업은 관리형 APM 의 p95 와 출시 전 스모크 테스트 정도로 시작하고, 병목은 대개 N+1·인덱스 같은 데이터 접근에서 나온다.
성장기에는 SLO 를 정하고 k6 를 CI 에 넣어 회귀를 막으며, 이벤트 시즌마다 breakpoint 테스트로 필요한 인스턴스 수를 계산한다.
대규모 조직에서는 팬아웃 때문에 꼬리가 곧 사용자 경험이 되어 헤징·부하 차단·재시도 예산을 공통 라이브러리로 제공하고, 연속 프로파일링과 요청당 비용을 전담 팀이 관리한다.

**이럴 땐 안 맞는다**
- 트래픽이 거의 없는 사내 도구·초기 MVP 에 정밀한 용량 계획 → 측정 비용이 이득보다 크다. 기본 지표와 스모크 테스트면 충분하다.
- 정합성 버그(중복 결제, 레이스)를 부하 테스트로 찾으려는 것 → 기능·동시성 테스트의 일이다. 부하 테스트는 지연·처리량을 본다.

**누가 매일 만나나** — 백엔드 개발자는 PR 의 성능 게이트가 실패하거나 "평균은 괜찮은데 사용자가 느리다" 는 문의를 받을 때, SRE 는 p99 알림과 용량 리뷰에서, 플랫폼 팀은 커넥션 풀·HPA 기본값을 정할 때 이 언어를 쓴다.
