## 모델을 바꾸는 네 가지 손잡이

LLM 의 동작을 바꾸고 싶을 때 쓸 수 있는 수단은 비용 순서로 네 가지다.

| 손잡이 | 무엇을 바꾸나 | 비용·시간 | 되돌리기 |
|---|---|---|---|
| **프롬프트** | 지시·예시(few-shot)·형식 | 분 단위, 무료에 가까움 | 즉시 |
| **RAG(검색 증강)** | 답할 때 참고할 문서 | 일 단위, 검색 인프라 | 즉시 |
| **파인튜닝** | 모델 가중치 일부 | 일~주, GPU 시간 + 데이터 라벨링 | 이전 모델로 전환 |
| **사전학습** | 모델 전체를 처음부터 | 월, 수백만 달러 | — |

**규칙: 위에서부터 시도하고, 평가로 한계를 확인했을 때만 아래로 내려간다.** 파인튜닝은 마지막 수단에 가깝다. 그런데 의외로 많은 팀이 "우리 데이터로 학습시키면 똑똑해지겠지" 라며 바로 파인튜닝부터 한다.

## 파인튜닝이 잘하는 것과 못하는 것

| 잘하는 것 | 못하는 것 (또는 비효율적) |
|---|---|
| **형식·말투**를 일관되게 (항상 이 JSON 스키마로, 우리 브랜드 말투로) | **새 사실·지식 주입** — 문서를 외우게 해도 환각이 섞이고, 문서가 바뀌면 재학습 |
| 좁은 작업에 특화 (분류·추출·라우팅) — 작은 모델이 큰 모델만큼 | 출처 인용 — 가중치에 녹은 지식은 어디서 왔는지 모른다 |
| 긴 프롬프트를 가중치로 옮겨 **토큰 비용·지연 절감** | 빠르게 바뀌는 정보 |
| 특정 도메인 용어·약어 이해 | 추론 능력의 근본적 향상 |

그래서 흔한 정답은 **"지식은 RAG 로, 행동은 파인튜닝으로"** 다. 이 사이트의 AI 에게 묻기가 노트를 검색해서 컨텍스트에 넣는 것([RAG 설계](/ai-systems/notes/03-rag-design))은 옳은 선택이다. 노트가 바뀌어도 재학습이 필요 없고, 답에 출처 링크를 붙일 수 있다.

### 판단 순서

1. 프롬프트로 시도 → 골든셋 평가 ([평가 노트](/mlops/notes/02-eval-datasets-metrics))
2. 실패 원인이 "정보 부족" 이면 → RAG
3. 실패 원인이 "형식·말투·작업 수행 방식" 이고 프롬프트로 안 고쳐지면 → 파인튜닝 후보
4. 비용·지연이 문제이고 작업이 좁으면 → 작은 모델로 **증류**

## 전체 파인튜닝 vs LoRA

### 전체 파인튜닝 (full fine-tuning)

모든 가중치를 갱신한다. 7B 모델이면 파라미터 70억 개에 대해 가중치·그래디언트·옵티마이저 상태(Adam 은 파라미터당 2개)를 메모리에 들고 있어야 한다.

```
7B × (가중치 2B[bf16] + 그래디언트 2B + Adam 상태 8B[fp32 ×2]) ≈ 7e9 × 12B ≈ 84 GB  (+ 활성값)
```

GPU 여러 장이 필요하고, 결과물도 모델 전체 크기(14GB)다. 작업마다 모델 한 벌씩 저장해야 한다.

### LoRA (Low-Rank Adaptation)

핵심 아이디어: **파인튜닝으로 생기는 가중치 변화 ΔW 는 저랭크(low-rank)** 라고 가정한다. d×d 행렬 W 를 직접 고치는 대신, 작은 두 행렬 A(d×r), B(r×d) 를 학습해 ΔW = A·B 로 둔다(r 은 8~64).

```
원래:   y = W·x                       W: 4096×4096 = 16.8M 파라미터 (동결)
LoRA:   y = W·x + (α/r)·B·(A·x)        A: 4096×16, B: 16×4096 = 131K 파라미터 (학습)
                                       → 이 층에서 학습 파라미터 0.8%
```

| 항목 | 전체 파인튜닝 | LoRA |
|---|---|---|
| 학습 파라미터 | 100% | 0.1~1% |
| GPU 메모리 | 가중치·그래디언트·옵티마이저 전부 | 동결 가중치 + 작은 어댑터의 그래디언트 |
| 결과물 | 모델 전체 (수 GB~수십 GB) | **어댑터 파일 (수~수백 MB)** |
| 여러 작업 | 모델 N 벌 | 베이스 1개 + 어댑터 N 개, 요청마다 교체 가능 |
| 성능 | 기준 | 대부분의 작업에서 비슷 |

어댑터가 작다는 것은 운영에서 큰 차이다. vLLM 같은 서빙 엔진은 **베이스 모델 하나에 여러 LoRA 어댑터를 올려 두고 요청마다 골라 쓰는 것**(multi-LoRA)을 지원한다. 고객사별·작업별 특화 모델을 GPU 한 장으로 서빙할 수 있다.

### QLoRA

베이스 모델을 **4비트로 양자화**해 메모리에 올리고, 그 위에 LoRA 어댑터를 bf16 으로 학습한다. 7B 모델이 약 5GB 에 들어가서 소비자 GPU 한 장으로 학습할 수 있다. 품질 손실은 작업에 따라 작다.

| 기법 | 7B 학습 대략 메모리 |
|---|---|
| 전체 파인튜닝 (bf16 + Adam) | 80GB+ |
| LoRA (bf16 베이스) | 16~20GB |
| QLoRA (4비트 베이스) | 6~10GB |

## 데이터셋 만들기

파인튜닝 결과의 80% 는 데이터가 정한다.

```jsonl
{"messages": [{"role": "system", "content": "너는 사내 지원 봇이다. 항상 JSON 으로 답한다."},
              {"role": "user", "content": "휴가 신청은 어디서 해?"},
              {"role": "assistant", "content": "{\"answer\": \"그룹웨어 > 근태 > 휴가 신청\", \"source\": \"HR-12\"}"}]}
```

| 원칙 | 설명 |
|---|---|
| 서빙과 같은 형식 | 학습 때 시스템 프롬프트·템플릿이 서빙 때와 같아야 한다 (학습-서빙 불일치) |
| 양보다 질 | 형식·말투 학습은 수백~수천 개의 **깨끗한** 예시로 충분. 틀린 예시 하나가 습관이 된다 |
| 다양성 | 같은 유형만 있으면 그 유형만 잘한다. 거절해야 할 질문, 애매한 질문도 섞는다 |
| 평가셋 분리 | 골든셋 문항이 학습 데이터에 섞이면(누수) 평가가 무의미해진다. 해시로 중복 검사 |
| 출처 기록 | 데이터 버전·출처를 실험 추적에 남긴다 ([노트 03](/mlops/notes/03-experiment-tracking-mlflow)) |

## 증류 (distillation)

큰 모델(교사)의 출력을 정답으로 삼아 작은 모델(학생)을 학습시킨다.

```
1. 실제 질의 1만 개 수집
2. 큰 모델로 답 생성 (필요하면 판사로 품질 필터링)
3. 작은 모델을 그 (질의, 답) 쌍으로 파인튜닝
4. 골든셋에서 큰 모델 대비 성능·비용·지연 비교
```

| | 큰 모델 API | 증류한 작은 모델 |
|---|---|---|
| 토큰당 비용 | 높음 | 10~50배 저렴 (자체 서빙) |
| 지연 | TTFT·TPOT 큼 | 작은 모델은 빠르다 — 이 Mac 의 1.5B 는 TPOT 약 6ms |
| 범위 | 범용 | **증류한 작업에만** 강함 |
| 위험 | — | 교사의 오류까지 학습, 분포 밖 질문에 약함 |

좁고 반복적인 작업(분류, 라우팅, 짧은 추출)에서 증류는 비용을 극적으로 줄인다. [프롬프트 캐시·비용](/ai-systems/notes/05-prompt-cache-cost-latency) 의 모델 라우팅과 함께 쓰면: 쉬운 질의는 증류한 작은 모델, 어려운 질의만 큰 모델로.

> **주의:** 상용 API 모델의 출력으로 경쟁 모델을 학습시키는 것은 이용 약관으로 금지된 경우가 많다. 증류 전에 약관을 확인한다.

## 함정

| 함정 | 증상 | 대응 |
|---|---|---|
| 과적합 | 학습 데이터에서는 완벽, 골든셋에서 떨어짐 | 검증 손실 관찰, 조기 종료, epoch 줄이기 |
| **파국적 망각** | 특화 작업은 좋아졌는데 일반 능력(다른 언어, 상식)이 무너짐 | 일반 데이터 섞기, LoRA(베이스 동결), 넓은 회귀 평가 |
| 형식 과적합 | 항상 같은 길이·같은 문장으로 시작 | 데이터 다양성 |
| 평가 누수 | 지나치게 좋은 점수 | 학습·평가 데이터 해시 비교 |
| 베이스 교체 | 베이스 모델 새 버전에 어댑터가 안 맞음 | 어댑터는 특정 베이스 버전에 묶인다 — 레지스트리에 함께 기록 |

## 예시로 보기 — 이 프로젝트에서

이 사이트에 파인튜닝이 필요한가? 실험 [`mlops-eval-harness`](/mlops/lab/mlops-eval-harness) 결과를 보면 1.5B 모델의 퀴즈 키워드 재현율은 약 10% 다. 이건 **지식 부족**(노트 내용을 모름)이 주원인이므로 파인튜닝이 아니라 RAG 가 답이다. 실제로 AI 에게 묻기는 질문으로 노트를 검색해 컨텍스트에 붙인다.

파인튜닝을 고려할 만한 지점은 따로 있다:

| 요구 | 손잡이 |
|---|---|
| 답에 항상 노트 링크를 `[제목](/주제/notes/slug)` 형식으로 | 먼저 프롬프트 + 형식 검사. 1.5B 가 계속 어기면 소량 LoRA 후보 |
| "사이트 밖 내용:" 구분을 지키게 | 프롬프트 + 판사로 준수율 측정 |
| 비용을 낮추고 싶다 | 질의 라우팅: 짧은 정의 질문은 로컬 작은 모델, 설계 질문은 큰 모델 → 그다음 증류 |

로컬에서 LoRA 를 직접 해 보고 싶다면 Apple Silicon 에서는 `mlx-lm` 이 QLoRA 를 지원한다. 퀴즈 카드 300장을 `{"messages": [...]}` JSONL 로 바꿔 qwen2.5 0.5B~1.5B 에 몇 분 학습하고, 같은 골든셋으로 학습 전후를 비교하면 된다 — 단, **학습에 쓴 카드는 평가에서 빼야** 한다.

## 실전에서는 어디에 쓰이나

> LLM 의 동작을 바꾸고 싶을 때 "프롬프트·RAG·파인튜닝·증류 중 무엇으로 풀까" 를 정해야 하는 순간에 등장한다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 사내 지식 QA 봇 | 자주 바뀌는 사내 문서 기반 답변 | RAG 로 검색해 컨텍스트에 넣고 출처 링크 | 문서로 파인튜닝 — 환각·재학습 비용 |
| 고객 상담 티켓 분류·라우팅 | 큰 모델 API 비용·지연 절감 | 큰 모델 출력으로 작은 모델 증류 | 큰 모델 계속 호출 — 토큰 비용 |
| 커머스 상품 설명 생성 | 브랜드 말투·JSON 형식 일관성 | 깨끗한 예시 수백~수천 개로 LoRA | 긴 few-shot 프롬프트 — 토큰 증가 |
| 고객사별 특화 B2B SaaS | 고객사마다 다른 형식·용어 | 베이스 1개 + 고객사별 LoRA 어댑터를 multi-LoRA 서빙 | 고객사별 전체 파인튜닝 — GPU·저장 N 배 |
| 소규모 팀의 실험 | 소비자 GPU 한 장으로 학습 | QLoRA(4비트 베이스 + 어댑터) | 전체 파인튜닝 — 80GB+ 메모리 |

**이럴 땐 안 맞는다**
- 새 사실·자주 바뀌는 정보를 가르치려는 파인튜닝 — 출처를 못 대고 문서가 바뀌면 재학습이다. RAG 를 쓴다.
- 평가 없이 바로 파인튜닝부터 하는 것 — 프롬프트·RAG 의 한계를 골든셋으로 확인한 뒤에 내려간다.
- 상용 API 출력으로 경쟁 모델을 증류하는 것 — 약관으로 금지된 경우가 많다.

**누가 매일 만나나** — AI·백엔드 엔지니어가 프롬프트로 안 고쳐지는 형식·비용 문제를 만났을 때, ML 엔지니어가 GPU 예산과 학습 데이터 라벨링 계획을 세울 때.

**면접·실무 단골 질문**
- Q. 파인튜닝과 RAG 는 각각 언제 쓰나? → 지식은 RAG, 행동(형식·말투·좁은 작업)은 파인튜닝.
- Q. LoRA 가 메모리를 적게 쓰는 이유는? → 베이스 가중치를 동결하고 저랭크 행렬 A·B 만 학습해 그래디언트·옵티마이저 상태가 작다.
