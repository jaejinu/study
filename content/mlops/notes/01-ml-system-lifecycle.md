## 모델은 시스템의 5% 다

2015년 구글 논문 *Hidden Technical Debt in Machine Learning Systems* 의 그림 하나가 MLOps 를 요약한다. 가운데 작은 상자가 "ML 코드" 이고, 그 주변을 데이터 수집·검증·특징 추출·설정·서빙 인프라·모니터링·자원 관리가 훨씬 크게 둘러싼다. **모델을 잘 만드는 일은 시작일 뿐이고, 모델이 매일 올바르게 동작하게 하는 일이 대부분이다.**

![ML 시스템 생애주기](/diagrams/mlops-lifecycle.svg)

전통 소프트웨어와의 차이를 표로 정리하면 이렇다.

| | 전통 소프트웨어 | ML / LLM 시스템 |
|---|---|---|
| 동작을 정하는 것 | 코드 | 코드 + **데이터** + 모델 가중치 + 프롬프트 |
| 버그의 모양 | 예외·크래시·틀린 값 | **조용한 품질 저하** — 200 OK 로 엉뚱한 답 |
| 테스트 | 입력 → 기대 출력 단언 | 골든셋에 대한 **통계적** 지표 (정확도 87% → 84%) |
| 시간에 따른 변화 | 코드를 안 바꾸면 그대로 | 세상(입력 분포)이 바뀌면 같은 모델도 나빠진다 (**드리프트**) |
| 재현 | 같은 커밋 = 같은 바이너리 | 같은 코드라도 데이터·시드·라이브러리 버전이 다르면 다른 모델 |
| 배포 단위 | 바이너리 | 모델 아티팩트(수백 MB~수백 GB) + 서빙 설정 |

"데이터가 코드다" 는 말 그대로다. 학습 데이터에 한 줄의 라벨 오류가 수천 개 섞이면, 그건 코드에 버그가 수천 개 들어간 것과 같다. 그런데 **코드 리뷰처럼 데이터 리뷰를 하는 조직은 드물다.**

## 생애주기 — 여섯 단계와 되돌아가는 화살표

| 단계 | 하는 일 | 산출물 | 흔한 실패 |
|---|---|---|---|
| 1. 문제 정의 | 성공 지표, 오류의 비용(거짓 양성 vs 거짓 음성), 기준선 | 지표·목표값·기준선 | "정확도 높게" 같은 막연한 목표 |
| 2. 데이터 | 수집·라벨링·정제·분할(학습/검증/테스트)·버전 관리 | 데이터셋 v1 + 데이터 카드 | 테스트셋 누수, 시간 순서 무시 분할 |
| 3. 학습 / 적응 | 학습, 파인튜닝, 또는 프롬프트·RAG 설계 | 모델 아티팩트 / 프롬프트 버전 | 실험 추적 없이 "어제 그 설정" 분실 |
| 4. 평가 | 오프라인 지표, 분할별(세그먼트) 성능, 안전성, 비용 | 평가 리포트, 승격 결정 | 평균만 보고 소수 집단 실패를 놓침 |
| 5. 배포 | 레지스트리 등록 → 섀도 → 카나리 → 전체 | 서빙 엔드포인트 | 학습·서빙 전처리 불일치(skew) |
| 6. 관측 | 지연·비용·오류 + **입력·출력 분포**, 사용자 피드백 | 대시보드, 드리프트 알림 | 품질 지표 없이 인프라 지표만 |

중요한 건 화살표가 **6 → 2** 로 돌아간다는 점이다. 관측에서 발견한 실패 사례가 다음 골든셋·학습 데이터가 된다. 이 루프를 자동으로 돌리는 것이 MLOps 의 목표다.

- 실험 추적·재현 → [실험 추적 — MLflow](/mlops/notes/03-experiment-tracking-mlflow)

## LLM 시대에 바뀐 것 — LLMOps

대부분의 팀은 이제 모델을 처음부터 학습하지 않는다. 대신 **API 로 제공되는 거대 모델 + 프롬프트 + 검색(RAG) + 도구** 로 시스템을 만든다. 생애주기의 무게중심이 이동했다.

| 전통 MLOps 의 관심 | LLMOps 의 관심 |
|---|---|
| 특징 공학(feature engineering) | 프롬프트·컨텍스트 공학 |
| 학습 파이프라인·GPU 스케줄링 | 평가 파이프라인, 모델·프롬프트 버전 관리 |
| 정확도·AUC | 정답성·근거성(groundedness)·형식 준수·안전성, **LLM-as-judge** |
| 추론 비용 = 서버 비용 | 추론 비용 = **토큰** (입력·출력·캐시) |
| 모델 드리프트 | 모델 드리프트 + **공급자 모델 교체**(같은 이름, 다른 동작) |

그러나 원칙은 같다. 바꾸는 단위(프롬프트, 모델, 검색 설정)마다 **버전 → 평가 → 승격 → 관측** 을 거친다. 이 사이트의 AI 노트들이 이 원칙의 구체적인 형태다: [LLM 앱 아키텍처](/ai-systems/notes/01-llm-app-architecture), [RAG 설계](/ai-systems/notes/03-rag-design), [평가·가드레일](/ai-systems/notes/06-evaluation-guardrails-safety), [LLM 관측](/observability/notes/08-llm-observability).

## 숨은 기술 부채 — 무엇이 나중에 터지나

논문이 꼽은 부채를 요즘 말로 옮기면 다음과 같다. 대부분 LLM 시스템에도 그대로 적용된다.

### 1. 얽힘 (CACE: Changing Anything Changes Everything)

모델은 입력 신호를 서로 섞어서 쓴다. 특징 하나의 분포를 바꾸면 나머지 특징의 가중치 의미까지 바뀐다. LLM 에서는 **프롬프트의 한 문장**이 다른 지시의 해석을 바꾼다. "간결하게 답하라" 를 추가했더니 JSON 형식 준수율이 떨어지는 식이다.

> **대응:** 변경 단위를 작게, 변경마다 전체 골든셋으로 회귀 평가([노트 07](/mlops/notes/07-eval-ci-prompt-regression)).

### 2. 미선언 소비자 (undeclared consumers)

모델의 출력(점수, 분류)을 다른 팀이 몰래 입력으로 쓰기 시작한다. 모델을 개선했는데 그쪽 시스템이 깨진다. API 계약이 없는 모델 출력은 사실상 공개 API 다.

> **대응:** 모델 출력도 API 처럼 스키마·버전·소비자 목록을 둔다 — [API 버전과 진화](/api-design/notes/07-versioning-evolution-governance) 와 같은 규율.

### 3. 데이터 의존성 부채

코드 의존성은 컴파일러가 잡아 주지만 데이터 의존성은 아무도 안 잡는다. 상류 테이블의 컬럼 의미가 바뀌거나(단위가 원 → 천 원), 로그 수집 버그로 필드가 비면 모델은 **조용히** 나빠진다.

> **대응:** 입력 데이터 검증(스키마·범위·결측률)을 파이프라인 단계로. 이 사이트에서는 [CDC](/kafka/notes/08-cdc-outbox-debezium) 처럼 데이터 흐름을 명시적으로 만드는 것이 도움이 된다.

### 4. 피드백 루프

추천 모델이 보여 준 것만 클릭되고, 그 클릭으로 다시 학습하면 모델은 자기 예측을 강화한다. LLM 에서는 모델이 생성한 텍스트가 웹에 쌓여 다음 학습 데이터가 되는 문제, 사용자 피드백(👍)이 특정 답변 스타일로 쏠리는 문제가 있다.

> **대응:** 탐색(일부 무작위 노출), 피드백 데이터의 출처 표시, 인간 라벨 표본 유지.

### 5. 설정 부채와 파이프라인 정글

실험마다 스크립트를 복사해 붙이다 보면 "어떤 설정으로 프로덕션 모델을 만들었는지" 아무도 모른다.

> **대응:** 실험 추적과 모델 레지스트리([노트 03](/mlops/notes/03-experiment-tracking-mlflow)), 설정을 코드처럼 리뷰.

### 6. 학습-서빙 불일치 (training-serving skew)

학습 때는 파이썬으로, 서빙 때는 다른 언어로 전처리를 다시 구현하면 미묘하게 다르다(토크나이저 버전, 정규화, 시간대). LLM 에서는 평가 때와 서빙 때 **시스템 프롬프트·템플릿이 다른** 형태로 나타난다.

> **대응:** 같은 전처리 코드를 공유, 서빙 요청을 샘플링해 오프라인 평가에 다시 넣어 비교.

## 성숙도 — 우리 팀은 어디쯤인가

| 단계 | 특징 | 다음으로 가려면 |
|---|---|---|
| 0. 수동 | 노트북에서 학습, 파일을 복사해 배포, 평가는 눈으로 | 실험 추적, 골든셋 |
| 1. 파이프라인 자동화 | 학습·평가가 스크립트로 재현됨, 레지스트리 | 지속 학습 트리거, 데이터 검증 |
| 2. CI/CD for ML | 코드·프롬프트·데이터 변경마다 자동 평가 게이트 | 온라인 관측과 자동 재학습 루프 |
| 3. 지속 개선 | 관측 → 실패 사례 수집 → 데이터 → 재학습/재평가가 순환 | (유지) |

대부분의 LLM 기능은 0~1 단계에서 출발한다. **골든셋 하나와 평가 스크립트 하나**만 있어도 0 → 1 로 올라간다. 이 사이트의 실험 [`mlops-eval-harness`](/mlops/lab/mlops-eval-harness) 가 바로 그 최소 형태다.

## 재현성 — "같은 결과" 의 조건

ML 결과를 재현하려면 아래가 모두 같아야 한다.

| 요소 | 고정하는 법 |
|---|---|
| 코드 | git 커밋 해시를 run 에 태그 |
| 데이터 | 데이터셋 버전(해시·스냅샷 ID), 분할 시드 |
| 환경 | 라이브러리 버전 고정(락파일, 컨테이너 이미지 다이제스트) |
| 무작위성 | 시드 고정. 단 GPU 연산·병렬 처리에서는 완전한 결정성이 안 될 수 있다 |
| 모델 | 가중치 해시. API 모델이면 **날짜가 붙은 스냅샷 이름**(`gpt-…-2026-08-01`) |
| 프롬프트 | 프롬프트 템플릿 버전 |

LLM 은 temperature 0 이어도 완전히 결정적이지 않다. 서버의 배칭 구성에 따라 부동소수점 합산 순서가 바뀌어 다른 토큰이 나올 수 있다. 실험 [`mlops-eval-harness`](/mlops/lab/mlops-eval-harness) 를 두 번 돌리면 같은 seed·temperature 0 인데도 판정 1~2건이 달라지는 것을 볼 수 있다. 그래서 평가는 **여러 번 돌려 분포로** 보는 것이 원칙이다.

## 예시로 보기 — 이 프로젝트에서

이 사이트에는 AI 기능이 두 개 있다. 생애주기로 다시 보면 무엇이 부족한지 바로 보인다.

| 단계 | `/assistant`(Claude) · AI 에게 묻기(OpenAI/Ollama) | 상태 |
|---|---|---|
| 문제 정의 | "노트를 근거로 정확히 답한다" | 지표가 정의되지 않음 |
| 데이터 | 노트 본문(검색 증강), 퀴즈 카드 | 퀴즈가 사실상 골든셋 역할을 할 수 있다 |
| 적응 | 시스템 프롬프트 + 검색 증강 + 툴 | 프롬프트가 코드에 하드코딩, 버전 없음 |
| 평가 | 없음 → `mlops-eval-harness` 로 시작 | 키워드 재현율·판사 점수·위치 편향 |
| 배포 | 환경 변수로 모델 교체(`OPENAI_MODEL`) | 레지스트리 없음 |
| 관측 | 토큰·비용·지연 메트릭(`study_llm_*`), 트레이스 | 품질 지표(근거 인용률, 👍) 없음 |

실험 [`mlops-ollama-serving`](/mlops/lab/mlops-ollama-serving) 은 6단계(관측)의 인프라 쪽 지표 — TTFT·TPOT·처리량 — 를 직접 재 본다. 이 Mac 에서 qwen2.5 1.5B 는 출력 약 160 토큰/초, 같은 입력을 다시 보내면 접두 캐시로 TTFT 가 347ms → 13ms 로 줄었다.

## 실전에서는 어디에 쓰이나 — MLOps 지도

> MLOps 는 모델을 "한 번 잘 만드는" 일이 아니라, 모델·프롬프트·데이터·세상이 바뀌어도 매일 올바르게 동작하게 하는 운영 체계다. 직접 학습하든 API 모델을 쓰든 같은 루프(버전 → 평가 → 승격 → 관측)를 돈다.

| 서비스·상황 | 이 주제의 어떤 부분이 | 더 읽기 |
|---|---|---|
| 첫 AI 기능을 붙이며 어디부터 손댈지 정할 때 | 생애주기 여섯 단계, 숨은 기술 부채, 성숙도 단계 | [ML 시스템 생애주기](/mlops/notes/01-ml-system-lifecycle) |
| 사내 문서 QA 챗봇의 출시 전 품질 확인 | 골든셋, 지표, LLM-as-judge 와 그 편향 | [평가 데이터셋과 지표](/mlops/notes/02-eval-datasets-metrics) |
| 여러 사람이 모델을 고치다 "어제 그 설정" 을 잃을 때 | 실험 추적, 모델 레지스트리, 별칭 승격·롤백 | [실험 추적 — MLflow](/mlops/notes/03-experiment-tracking-mlflow) |
| 고객 상담 분류를 더 싸고 빠르게 | 프롬프트 → RAG → 파인튜닝 판단, LoRA·증류 | [파인튜닝·증류](/mlops/notes/04-finetuning-distillation) |
| 자체 GPU 로 LLM API 를 제공할 때 | prefill·decode, 연속 배칭, KV 캐시, 양자화 | [LLM 서빙](/mlops/notes/05-serving-batching-kv-cache) |
| 추천·검색·LLM 기능이 200 OK 로 조용히 나빠질 때 | 드리프트 탐지, 대리 지표, 가드레일, 품질 알림 | [모델 관측과 드리프트](/mlops/notes/06-model-observability-drift) |
| 프롬프트 한 줄 수정이 장애가 되는 LLM 기능 | 평가 CI, 회귀 게이트, 안전 문항 | [평가 CI 와 프롬프트 회귀 테스트](/mlops/notes/07-eval-ci-prompt-regression) |

**회사 규모에 따라**
- 스타트업: API 모델 + 프롬프트 + RAG 로 시작한다. 골든셋 하나, 평가 스크립트 하나, 토큰 비용 대시보드가 MLOps 의 전부인 경우가 많다.
- 성장기: AI 기능이 늘면서 실험 추적·프롬프트 버전 관리·평가 CI 가 필요해지고, 비용 때문에 작은 모델 라우팅·증류를 검토한다.
- 대규모 조직: 플랫폼 팀이 자체 서빙 클러스터·모델 레지스트리·평가 인프라를 운영하고, 제품 팀은 그 위에서 평가 게이트와 품질 SLO 를 지킨다.

**이럴 땐 안 맞는다**
- 규칙 몇 개로 풀리는 문제(정해진 조건 분기, 계산) — ML 은 데이터·평가·관측의 지속 비용을 낳는다. 일반 코드·규칙 엔진이 낫다.
- 오류 하나가 치명적인데 사람 검토를 둘 수 없는 결정 — 확률적 출력에 맡기지 않고 결정적 로직과 사람 승인을 둔다.

**누가 매일 만나나** — ML 엔지니어는 학습·평가·배포 파이프라인에서, 백엔드는 LLM API 를 붙이고 비용·지연·품질을 볼 때, 데이터 엔지니어는 학습·평가 데이터의 품질과 버전을 관리할 때 이 주제를 만난다.
