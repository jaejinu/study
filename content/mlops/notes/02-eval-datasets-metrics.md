## 평가는 ML 의 단위 테스트다

일반 코드에서 테스트가 하는 일은 "이 변경이 기존 동작을 깨지 않았나" 를 빠르게 알려 주는 것이다. ML·LLM 시스템에서는 **평가(eval)** 가 그 역할을 한다. 차이는 결과가 통과/실패가 아니라 **숫자의 분포**라는 점이다.

| 테스트 | 평가 |
|---|---|
| `expect(fee(30000, true)).toBe(0)` | "골든셋 200문항에서 정답률 87.5% (±2.3%)" |
| 하나라도 실패하면 빨간불 | 기준선 대비 **유의미하게** 나빠지면 빨간불 |
| 결정적 | 확률적 — 같은 입력에도 출력이 흔들린다 |

평가 없이 프롬프트를 고치는 것은 테스트 없이 리팩터링하는 것과 같다. "좋아진 것 같다" 는 느낌은 보통 **고친 그 사례 하나**만 보고 내린 결론이다.

## 골든셋 만들기

골든셋은 *입력 + 기대하는 답(또는 판단 기준)* 의 고정된 목록이다.

### 어디서 모으나

| 출처 | 장점 | 단점 |
|---|---|---|
| 실제 사용자 질의 (로그 샘플) | 현실 분포 | 개인정보 정리 필요, 정답을 따로 만들어야 함 |
| 실패 사례 (👎, 고객 문의) | 약점을 정확히 겨냥 | 분포가 치우침 → 별도 묶음으로 관리 |
| 전문가가 쓴 문항 | 정답 품질 높음 | 비싸고 느림 |
| LLM 이 생성한 합성 문항 | 싸고 빠름 | 생성 모델의 편향이 섞임, 반드시 사람이 검수 |
| **이 사이트의 퀴즈 카드** | 질문·정답 쌍이 이미 있음 | 정답이 짧고 표현이 특정 |

### 크기와 신뢰 구간

정답률 p 를 n 문항으로 잴 때 95% 신뢰 구간은 대략 **p ± 1.96·√(p(1−p)/n)** 이다.

| n | p = 0.8 일 때 ± |
|---|---|
| 10 | ±25%p |
| 50 | ±11%p |
| 200 | ±5.5%p |
| 1000 | ±2.5%p |

10문항으로 "80% → 90% 로 좋아졌다" 는 말은 잡음과 구분이 안 된다. 실험 [`mlops-mlflow-tracking`](/mlops/lab/mlops-mlflow-tracking) 에서 temperature 0·0.7·1.2 를 5문항으로 비교했더니 0.7 이 이겼는데, 이건 거의 확실히 잡음이다. **두 시스템을 비교할 때는 같은 문항에 대한 쌍대 차이**를 보면 분산이 줄어든다(쌍체 검정).

### 누수와 분할

- **학습·튜닝에 쓴 문항을 평가에 쓰지 않는다.** 프롬프트를 고치면서 계속 들여다본 문항(개발셋)과, 승격 결정에만 쓰는 문항(테스트셋)을 나눈다.
- 시간이 중요한 데이터는 **시간으로 분할**한다(과거로 학습, 미래로 평가).
- 골든셋도 **버전**이 있다. 문항을 추가·수정하면 점수가 바뀌므로, 비교는 같은 버전끼리만.

### 세그먼트별로 보기

평균 87% 가 "모든 질문에서 87%" 가 아니다. 주제·언어·질문 길이·사용자 유형별로 나눠 보면, 평균은 좋아졌는데 특정 세그먼트가 크게 나빠진 경우가 흔하다. 평가 리포트는 항상 **세그먼트 표**를 같이 낸다.

## 지표 — 무엇을 재는가

### 정답이 하나인 문제 (분류·추출)

| 지표 | 정의 | 언제 |
|---|---|---|
| 정확도 | 맞힌 수 / 전체 | 클래스가 균형일 때 |
| 정밀도 | 양성이라 한 것 중 진짜 양성 | 거짓 양성이 비쌀 때 (스팸 필터) |
| 재현율 | 진짜 양성 중 찾아낸 비율 | 놓치면 비쌀 때 (사기 탐지) |
| F1 | 정밀도·재현율의 조화 평균 | 둘 다 중요할 때 |
| 정확 일치(EM) | 출력 문자열이 정답과 같음 | 추출·짧은 답 |

### 정답이 여러 형태인 문제 (생성)

| 지표 | 원리 | 한계 |
|---|---|---|
| BLEU / ROUGE | 정답과 n-gram 겹침 | 같은 뜻 다른 표현에 0점, 한국어 어절·조사에 특히 약함 |
| 키워드 재현율 | 정답의 핵심 단어가 답에 있나 | 싸고 결정적이지만 동의어·풀어쓰기를 놓친다 |
| 임베딩 유사도 | 정답·답변 벡터의 코사인 | "반대 의미" 도 높은 점수가 나올 수 있다 |
| 형식 검사 | JSON 파싱, 정규식, 길이 | 내용은 안 본다 — 하지만 **가장 신뢰할 수 있는** 지표 |
| LLM-as-judge | 다른 LLM 이 루브릭으로 채점 | 판사의 편향을 물려받는다 |

실험 [`mlops-eval-harness`](/mlops/lab/mlops-eval-harness) 에서 1.5B 모델의 평균 키워드 재현율은 **10%** 였지만 같은 답변에 대한 판사 점수는 **평균 6.4/10** 이었다. 두 지표가 이렇게 어긋나는 문항을 직접 읽어 보는 것이 평가 설계의 출발점이다. 키워드 지표는 "자연어로 풀어 쓴 정답" 을 못 알아보고, 판사는 "그럴듯하지만 틀린 답" 에 후하다.

## LLM-as-judge — 설계와 편향

### 좋은 판사 프롬프트의 요소

1. **루브릭**: 점수별 기준을 글로 정의한다. "10 = 정답의 핵심 개념을 모두 정확히, 5 = 일부 누락, 0 = 틀리거나 무관".
2. **참조 답**: 가능하면 정답을 같이 준다(참조 기반). 판사가 스스로 정답을 아는 척하지 않게.
3. **척도**: 0~10 보다 **이진(맞음/틀림) 또는 3단계**가 일관성이 높다. 세밀한 척도는 판사마다 다르게 쓴다.
4. **이유 먼저, 점수 나중** (chain-of-thought): 근거를 쓰게 한 뒤 마지막 줄에 점수. 단, 파싱 규칙을 엄격히.
5. **형식 강제**: 구조화 출력(JSON 스키마)으로 받는다. 실험에서는 "숫자 하나만" 지시가 10/10 지켜졌지만, 큰 판사일수록 설명을 덧붙이려 한다.

### 알려진 편향

| 편향 | 현상 | 대응 |
|---|---|---|
| **위치 편향** | 쌍대 비교에서 먼저(또는 나중에) 나온 답을 선호 | A/B 순서를 바꿔 두 번 묻고, 일치할 때만 승패로 센다 |
| **길이 편향** | 길고 자세한 답을 더 좋게 평가 | 길이를 통제하거나 루브릭에 "간결성" 명시 |
| **자기 선호** | 판사 자신(같은 모델 계열)이 쓴 답을 선호 | 평가 대상과 다른 모델 계열·더 큰 모델로 판사 |
| **말투 편향** | 자신감 있는 말투, 마크다운 서식에 후함 | 서식 제거 후 채점 |
| **정답 누설에 둔감** | 참조 답을 그대로 베낀 답에 높은 점수 | 표절 검사 별도 |

### 직접 잰 위치 편향과 자기 선호

실험 [`mlops-eval-harness`](/mlops/lab/mlops-eval-harness) 는 사람이 쓴 정답과 모델의 답을 A/B 로 두 번(순서를 바꿔) 비교시킨다. qwen2.5 1.5B 를 판사로 쓴 결과:

| 측정 | 값 |
|---|---|
| 순서를 바꾸면 판정이 뒤집힌 비율 | **22%** (9건 중 2건) |
| 첫 번째(A) 를 고른 비율 | 61% |
| 두 순서 모두 사람의 정답을 고른 비율 | **0%** |
| 두 순서 모두 **자기(모델) 답**을 고른 비율 | **78%** |

결론은 분명하다. 이 판사는 다섯 번 중 한 번은 **자리**를 보고, 일관된 판정의 거의 전부는 **자기 답**을 고른다. 작은 모델을 자기 자신의 판사로 쓰면 평가가 아니라 자기 칭찬이 된다.

> **실무 규칙:** (1) 판사는 평가 대상보다 강하고 다른 계열의 모델, (2) 순서 교차 필수, (3) 판사 자체를 사람이 라벨링한 표본(50~100건)으로 **판사의 정확도**를 먼저 잰다. 판사와 사람의 일치율(코헨의 카파)이 낮으면 그 판사의 점수는 의미가 없다.

## 쌍대 비교 vs 절대 점수

| | 절대 점수 (0~10) | 쌍대 비교 (A vs B) |
|---|---|---|
| 질문 | "이 답은 몇 점인가?" | "어느 쪽이 더 나은가?" |
| 판사 일관성 | 낮다 (척도 해석이 흔들림) | 높다 |
| 결과 | 시스템별 평균 점수 | 승률, Elo/Bradley-Terry 순위 |
| 쓰임 | 회귀 게이트(기준선 이상인가) | 두 후보 중 승자 고르기 |

새 프롬프트가 기존보다 나은지 결정할 때는 쌍대 비교가, 매 배포마다 "최소 기준" 을 지키는지 볼 때는 절대 점수나 이진 판정이 맞다.

## 오프라인 평가와 온라인 평가

| | 오프라인 | 온라인 |
|---|---|---|
| 데이터 | 고정 골든셋 | 실제 트래픽 |
| 지표 | 정답성·형식·안전성 | 👍/👎, 재질문율, 작업 완료율, 이탈 |
| 속도 | 분 단위, 배포 전 | 일~주 단위, 배포 후 |
| 방법 | 평가 스크립트, CI | A/B 테스트, 섀도 배포, 카나리 |

오프라인 평가로 **나쁜 것을 막고**, 온라인 평가로 **좋은 것을 확인**한다. 둘이 어긋나면(오프라인은 올랐는데 사용자 지표는 내려감) 골든셋이 현실을 대표하지 못한다는 신호다 — [모델 관측과 드리프트](/mlops/notes/06-model-observability-drift).

## 예시로 보기 — 이 프로젝트에서

이 사이트의 퀴즈 `content/*/quiz.json` 은 `{note, q, a}` 형태다. 바로 골든셋으로 쓸 수 있다.

```ts
// 실험 mlops-eval-harness 의 골든셋 선택 — 매번 같은 문항 (결정적)
const subjects = ["redis", "kafka", "postgres", "kubernetes", "docker", "observability"];
for (let i = 0; out.length < n; i++)
  for (const s of subjects) { const cards = await loadQuiz(s); if (cards[i * 2]) out.push(cards[i * 2]); }
```

```ts
// 위치 편향 측정: 같은 두 답을 순서만 바꿔 묻는다
const p1 = pick(await ask(gold, answer));   // A=정답, B=모델
const p2 = pick(await ask(answer, gold));   // A=모델, B=정답
const flip = winner(p1) !== winner(p2);     // 판정이 뒤집혔나
```

AI 에게 묻기 패널을 평가하려면 문항을 이렇게 늘리면 된다: 퀴즈 질문을 그대로 묻고 (1) 답변에 해당 노트 링크가 포함되었는지(형식 검사), (2) 정답 키워드 재현율, (3) 강한 판사의 이진 정답 판정. 세 지표가 모두 있어야 프롬프트 수정의 효과를 말할 수 있다.

> 함께 읽기: 평가가 생애주기의 어디에 있는지는 [ML 시스템 생애주기](/mlops/notes/01-ml-system-lifecycle), 평가를 CI 로 자동화하는 법은 [평가 CI](/mlops/notes/07-eval-ci-prompt-regression).

## 실전에서는 어디에 쓰이나

> 프롬프트 수정, 모델 교체, 출시 승인처럼 "좋아졌나 나빠졌나" 를 숫자로 말해야 하는 모든 순간에 골든셋과 지표가 등장한다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 사내 문서 QA 챗봇 | 모델 교체 전후 정답성 비교 | 실제 질의 로그 + 전문가 정답으로 골든셋, 강한 판사의 이진 판정 | 데모 질문 몇 개 — 잡음과 구분 불가 |
| 핀테크 사기 탐지 | 놓치면 비싼 사례를 제대로 측정 | 재현율 중심, 시간 순 분할 | 정확도 — 불균형 클래스에서 착시 |
| 이메일 스팸 필터 | 정상 메일 오차단 방지 | 정밀도 중심, 언어·발신 유형별 세그먼트 표 | 평균 F1 하나만 |
| 상담 요약 SaaS | 두 프롬프트 중 승자 고르기 | 쌍대 비교 + 순서 교차, 승률 | 0~10 절대 점수 — 척도 해석이 흔들림 |
| 검색·추천 서비스 | 오프라인 지표가 실제 만족을 대표하는지 확인 | 오프라인 골든셋 + 온라인 A/B 지표 대조 | 오프라인만 — 대표성 미확인 |

**이럴 땐 안 맞는다**
- 형식·포함 검사로 판단할 수 있는 것을 LLM 판사에 맡기는 것 — 판사 편향과 비용만 더해진다.
- 10~20 문항으로 작은 차이를 결론 내는 것 — 신뢰 구간이 ±20%p 대다. 문항을 늘리거나 쌍체 비교를 쓴다.

**누가 매일 만나나** — ML·AI 엔지니어가 프롬프트·모델 변경 PR 의 근거를 낼 때, PM·도메인 전문가가 골든셋 정답과 루브릭을 만들 때.

**면접·실무 단골 질문**
- Q. LLM-as-judge 의 대표 편향과 대응은? → 위치·길이·자기 선호. 순서 교차, 다른 계열의 강한 판사, 사람 라벨로 판사 정확도를 먼저 잰다.
- Q. 정확도만 보면 안 되는 경우는? → 클래스 불균형(사기·스팸). 정밀도·재현율·F1 과 세그먼트별 표를 함께 본다.

## 실습 체크리스트
