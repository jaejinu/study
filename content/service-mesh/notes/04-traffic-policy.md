## 정책은 호출하는 쪽에서 실행된다

재시도·타임아웃·부하 분산은 모두 **클라이언트 프록시(outbound)** 의 일이다. 서버 프록시는 인가와 메트릭을 맡는다.

```
[앱 A] ─▶ [프록시 A: 엔드포인트 선택(EWMA) → 타임아웃 시계 시작 → 보냄 → 5xx 면 재시도 → 연속 실패 Pod 격리]
                                                     │
                     [프록시 B1] [프록시 B2] [프록시 B3(고장)]
```

그래서 정책을 거는 곳은 **호출받는 Service**(또는 그 Service 에 붙은 HTTPRoute)지만, 실제로 적용되는 곳은 그 Service 를 부르는 모든 메시 클라이언트다. 메시 밖 클라이언트에는 적용되지 않는다.

## 재시도

```bash
kubectl annotate svc web retry.linkerd.io/http=5xx retry.linkerd.io/limit=2
# 선택: retry.linkerd.io/timeout=300ms (시도 하나당 시간 상한)
#       retry.linkerd.io/grpc=unavailable,deadline-exceeded (gRPC 상태 코드)
```

| 설정 | 의미 | 주의 |
|---|---|---|
| `http: 5xx` (또는 `502,503,504`, `gateway-error`) | 어떤 응답이 재시도 대상인가 | 500 은 앱 버그일 수 있다 — 다시 보내도 같다 |
| `limit: 2` | 원 요청 + 최대 2번 | 3회면 장애 시 부하가 최대 3배 |
| `timeout` | 시도별 시간 상한 | 전체 타임아웃보다 작아야 재시도할 시간이 남는다 |

### 언제 재시도해도 되나

재시도는 **같은 요청을 두 번 실행해도 결과가 같을 때만** 안전하다.

- GET·HEAD·PUT·DELETE 는 의미상 멱등이다. POST 는 아니다.
- 메시는 기본적으로 **본문이 있는 요청**도 재시도할 수 있게 본문을 버퍼링한다(크기 제한 있음). 즉 POST /payments 를 재시도할 수 있다 — 서버가 멱등 키로 중복을 막지 않으면 결제가 두 번 된다([API 설계 04](/api-design/notes/04-errors-retries-deadlines), 실험 `api-idempotency-key`).
- 그래서 재시도는 **경로 단위**(HTTPRoute 에 어노테이션)로 거는 것이 좋다: `GET /items` 에는 걸고 `POST /orders` 에는 걸지 않는다.

### 재시도 폭풍과 재시도 예산

장애가 넓게 퍼지면 재시도가 부하를 키운다. 서비스 3단 호출에 각 단계가 3번씩 재시도하면 맨 아래는 **3³ = 27배** 요청을 받는다([장애 실험실 03](/chaos/notes/03-resilience-patterns-verified)의 `chaos-retry-storm` 실측).

막는 방법:

| 방법 | 원리 |
|---|---|
| **재시도 예산** | 재시도를 "원 요청의 20% 까지" 같은 비율로 제한. 장애가 크면 재시도가 자동으로 줄어든다(Linkerd 의 옛 ServiceProfile `retryBudget`, Envoy 의 `retry_budget`) |
| 한 층에서만 재시도 | 보통 가장 바깥(게이트웨이)이나 가장 안쪽 한 곳 |
| 지수 백오프 + 지터 | 재시도 간격을 벌리고 흩뜨린다 |
| 재시도 가능 응답 제한 | 429·503 은 "기다리라" 는 신호 — `Retry-After` 를 존중 |

## 타임아웃

```bash
kubectl annotate svc whoami timeout.linkerd.io/request=500ms
```

실험 `mesh-retry-budget` 의 실측:

| 설정 | 응답 | 걸린 시간 |
|---|---|---|
| 타임아웃 없음 | 200 | 2004ms |
| `timeout.linkerd.io/request=500ms` | **504** | 503ms |

타임아웃이 하는 일은 **호출자를 지키는 것**이다. 느린 의존성 하나 때문에 호출자의 스레드·커넥션·사용자가 모두 묶이는 것을 끊는다. 하지만 서버는 그 요청을 계속 처리하고 있다. 끝까지 일을 멈추게 하려면 **데드라인 전파**(gRPC `grpc-timeout` 헤더, [API 설계 04](/api-design/notes/04-errors-retries-deadlines))가 필요하다 — 메시는 여기까지 해 주지 않는다.

타임아웃 값 정하기: 서버의 p99 지연보다 약간 길게, 그리고 **호출 체인 아래로 갈수록 짧게**. 바깥 1s, 중간 800ms, 안쪽 500ms. 거꾸로면 바깥이 이미 포기한 요청을 안쪽이 계속 처리한다.

## 장애 축적 — 메시의 서킷 브레이커

```bash
kubectl annotate svc web balancer.linkerd.io/failure-accrual=consecutive \
        balancer.linkerd.io/failure-accrual-consecutive-max-failures=3
# 선택: …-min-penalty=1s  …-max-penalty=60s  (격리 시간, 지수 백오프)
```

엔드포인트 하나가 **연속 3번 실패**하면 부하 분산 후보에서 잠시 뺀다. 격리 시간이 지나면 시험 요청 하나를 보내고(half-open), 성공하면 되돌린다. 실패하면 격리 시간이 늘어난다. 라이브러리 서킷 브레이커([장애 실험실 03](/chaos/notes/03-resilience-patterns-verified)의 `chaos-circuit-breaker`)와 같은 상태 기계를 **엔드포인트 단위로** 돌리는 것이다.

| 비교 | 라이브러리 서킷 브레이커 | 메시 장애 축적 |
|---|---|---|
| 단위 | 의존성 전체(예: "재고 서비스") | 엔드포인트(Pod) 하나 |
| 효과 | 의존성 전체가 죽으면 빨리 실패 | 나쁜 Pod 만 피하고 나머지로 보냄 |
| 전체 장애 시 | 즉시 실패(폴백 실행) | 모든 Pod 가 격리되면 결국 실패 |

둘은 상호 보완이다: 메시는 "Pod 하나가 이상하다" 를, 앱은 "서비스 전체가 죽었다" 를 다룬다.

## 실험 결과 — 정상 2 · 고장 1

실험 `mesh-retry-budget` 은 http-echo 정상 Pod 2개와 **항상 503** 을 내는 Pod 1개를 같은 Service 뒤에 두고 60번씩 불렀다.

| 정책 | 200 | 실패 | 성공률 | p50 | p99 |
|---|---|---|---|---|---|
| 정책 없음 | 40 | 20 | 67% | 1ms | 6ms |
| 재시도 5xx · 최대 2회 | 60 | 0 | **100%** | 1ms | 35ms |
| 장애 축적(연속 3회), 재시도 없음 | 57 | 3 | **95%** | 1ms | 4ms |

- **재시도**는 실패를 지연으로 바꿨다: 성공률 100% 의 대가로 p99 가 6ms → 35ms.
- **장애 축적**은 실패를 처음부터 피해 지연이 늘지 않았다. 대신 격리되기 전 3번의 실패는 그대로 사용자에게 갔다.
- 운영에서는 **둘을 함께** 쓴다: 장애 축적으로 나쁜 Pod 를 빨리 빼고, 그 사이의 실패를 재시도로 흡수한다.

## 부하 분산 — EWMA 와 P2C

kube-proxy(iptables)는 연결 단위로 무작위 분산한다. HTTP/2·gRPC 처럼 연결 하나에 요청이 몰리는 프로토콜에서는 한 Pod 에 쏠린다([gRPC 03](/api-design/notes/03-protobuf-grpc)의 HTTP/2 다중화). 메시 프록시는 **요청 단위로** 분산한다.

Linkerd 의 알고리즘:

1. **P2C(Power of Two Choices)**: 엔드포인트 중 무작위로 2개를 뽑는다.
2. 둘 중 **EWMA(지수 가중 이동 평균) 지연 × 진행 중 요청 수** 가 작은 쪽으로 보낸다.

느려진 Pod 는 EWMA 가 커져 자연히 덜 선택된다. 전체를 정렬하지 않고 2개만 비교하므로 엔드포인트가 많아도 빠르고, 모든 클라이언트가 같은 "최고의 Pod" 로 몰리는 떼 현상(herding)도 피한다. 꼬리 지연을 줄이는 기법들([성능 08](/performance/notes/08-tail-latency-at-scale))과 같은 계열이다.

실험의 "정책 없음" 단계에서 고장 Pod 로 간 비율은 실행마다 23%(14/60)~33%(20/60)로 흔들렸다 — 503 은 빨리 오므로 EWMA 는 오히려 그 Pod 를 "빠르다" 고 볼 수 있다. **빠른 실패는 부하 분산기를 속인다.** 장애 축적이 필요한 이유다.

## 예시로 보기 — 이 프로젝트에서

- 이 사이트 앱의 Redis 클라이언트(ioredis)는 앱 안에서 타임아웃·재연결을 한다. 메시를 붙여도 Redis(6379)는 opaque TCP 라 HTTP 재시도 정책이 적용되지 않는다 — 데이터 저장소 호출의 복원력은 여전히 앱 몫이다.
- `/api/ask` 처럼 LLM 을 부르는 경로에 메시 재시도를 걸면 토큰 비용이 재시도 횟수만큼 곱해진다. 비멱등·고비용 경로에는 재시도를 걸지 않는다.

## 정책 값을 데이터로 정한다

정책 값은 감으로 정하지 않는다. 프록시 메트릭이 근거다([노트 05](/service-mesh/notes/05-observability)).

| 정책 | 근거 메트릭 | 정하는 법 |
|---|---|---|
| 타임아웃 | 서버의 p99·p99.9 지연(`response_latency_ms_bucket`) | p99.9 의 1.5~2배. 너무 짧으면 정상 요청까지 끊는다 |
| 재시도 상한 | 실패율, 실패의 상관성 | 일시 실패(배포·Pod 교체)면 1~2회, 지속 실패면 재시도 무의미 |
| 재시도 대상 | 실패 응답의 상태 코드 분포 | 503·504·연결 실패만. 500 은 대개 앱 버그 |
| 장애 축적 임계 | Pod 별 연속 실패 패턴 | 3~7회. 너무 작으면 정상 Pod 도 잠깐씩 빠진다 |

## 조합 레시피

| 상황 | 권장 조합 |
|---|---|
| 읽기 API, 일시 실패가 잦음(배포 중) | 타임아웃 + 재시도(5xx, 1~2회) + 장애 축적 |
| 쓰기 API(멱등 키 없음) | 타임아웃만, 재시도 없음 |
| 쓰기 API(멱등 키 있음) | 타임아웃 + 재시도(연결 실패만) |
| 비싼 다운스트림(LLM·외부 결제) | 짧은 타임아웃 + 재시도 없음 + 앱의 폴백 |
| 지연 민감·멱등 읽기 | 헤징(복제 요청, [성능 08](/performance/notes/08-tail-latency-at-scale)) — 메시 지원 여부 확인 |

## 재시도 증폭 계산

호출 체인 A → B → C, 각 홉이 최대 r 번 재시도(원 요청 포함 r+1 회)면, C 가 받는 최대 요청 수는 (r+1)². r=2 면 9배, 3단이면 27배.

```
정상 시 C 의 요청률 1,000 rps
C 가 503 을 내기 시작 → B 가 3배(1+2) → A 도 B 의 실패를 보고 3배 → C 는 최대 9,000 rps
```

장애가 난 서비스에 9배 부하를 퍼붓는 것이 재시도 폭풍이다. 그래서 **재시도는 한 층에서만**, 그리고 **예산으로 상한**을 둔다.
