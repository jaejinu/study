## 왜 이 숫자부터인가

데이터베이스의 모든 구조 — B-tree, LSM, WAL, 버퍼 풀, 열 저장 — 는 한 가지 사실에 대한 답이다: **메모리는 빠르지만 휘발하고, 디스크는 영속하지만 느리며, 디스크는 "큰 덩어리를 순서대로" 읽고 쓸 때만 빠르다.** 숫자를 몸으로 알면 각 설계가 왜 그렇게 생겼는지 저절로 보인다.

## 지연 숫자 (2020년대 서버 기준, 자릿수 감각)

| 작업 | 지연 | 사람 시간으로 환산 (1ns = 1초) |
|---|---|---|
| L1 캐시 참조 | 1 ns | 1초 |
| L2 캐시 참조 | 4 ns | 4초 |
| L3 캐시 참조 | 15 ns | 15초 |
| 메인 메모리 참조 | 80~100 ns | 1.5분 |
| 메모리 4KB 순차 읽기 | ~0.5 µs | 8분 |
| NVMe SSD 4KB 임의 읽기 | 20~100 µs | 6시간~1일 |
| NVMe SSD 1MB 순차 읽기 | ~150 µs | 2일 |
| 같은 데이터센터 왕복 | ~500 µs | 6일 |
| SATA SSD 4KB 임의 읽기 | ~150 µs | 2일 |
| **fsync (NVMe, 전원 보호 캐시 없음)** | 0.1~2 ms | 1~23일 |
| HDD 탐색 + 4KB 읽기 | 5~10 ms | 2~4개월 |
| 클라우드 네트워크 블록 스토리지(EBS 등) 4KB | 0.5~2 ms | 6~23일 |
| 대륙 간 왕복 | 150 ms | 5년 |

세 가지를 기억하면 된다.

1. **메모리와 디스크는 1,000배 차이**(100ns vs 100µs). 그래서 자주 쓰는 데이터는 메모리에 둔다 — [버퍼 풀](/db-internals/notes/02-btree-pages-buffer-pool), OS 페이지 캐시, Redis 자체.
2. **fsync 는 밀리초**. 커밋마다 fsync 하면 단일 스레드 커밋은 초당 수백~수천 건이 상한이다. 그래서 그룹 커밋과 "fsync 를 언제 할 것인가" 의 손잡이가 존재한다([WAL](/db-internals/notes/04-wal-checkpoint-recovery)).
3. **네트워크 왕복이 SSD 읽기보다 느리거나 비슷**하다. 원격 DB 에 쿼리 하나 = SSD 몇 번 읽기. [Redis 파이프라이닝](/redis/notes/06-pipelining)이 왜 중요한지의 근거.

## 순차 vs 임의

### HDD — 탐색의 물리학

HDD 는 회전하는 원판 위의 헤드다. 임의 읽기 = 헤드 이동(탐색, ~4ms) + 원하는 섹터가 돌아올 때까지 대기(회전 지연, 7200rpm 에서 평균 ~4ms). 순차 읽기는 헤드가 한 번 자리를 잡으면 원판이 도는 대로 읽힌다(~200MB/s).

```
4KB 임의 읽기:  ~100 IOPS × 4KB = 0.4 MB/s
순차 읽기:                        200 MB/s        → 500배
```

이 500배가 1970년대부터 데이터베이스 설계를 지배했다. B-tree 의 "높이를 낮게"(탐색 횟수 최소화), 로그 구조의 "추가만"(순차 쓰기), 정렬된 SSTable 이 모두 여기서 나왔다.

### SSD — 탐색은 없지만 순차가 여전히 유리한 이유

SSD 는 기계 부품이 없어 임의 읽기도 빠르다. 그런데도 순차가 유리하다.

| SSD 의 단위 | 크기 | 성질 |
|---|---|---|
| **페이지** | 4~16KB | 읽기·쓰기 단위. 덮어쓰기 불가 |
| **블록(erase block)** | 수백 페이지(수 MB) | 지우기 단위. 쓰기 전에 블록 통째로 지워야 함 |
| **FTL**(Flash Translation Layer) | 컨트롤러 펌웨어 | 논리 주소 → 물리 페이지 매핑, 가비지 컬렉션, 마모 평준화 |

"덮어쓰기" 는 실제로 **새 페이지에 쓰고 옛 페이지를 무효 표시**한다. 무효 페이지가 섞인 블록은 FTL 이 살아 있는 페이지를 다른 곳에 옮긴 뒤 지운다(SSD 내부 GC). 그래서:

- **임의 작은 쓰기**는 블록 여기저기에 무효 페이지를 흩뿌려 SSD 내부 GC 를 부르고, 내부에서 데이터를 또 복사한다 → **SSD 자체의 쓰기 증폭**. 지연 스파이크와 수명 단축.
- **순차 큰 쓰기**는 블록을 통째로 채우고 통째로 무효화되니 GC 가 싸다.
- 읽기도 큰 순차 읽기가 내부 병렬성(여러 칩·채널)을 다 쓴다. 4KB 임의 읽기 IOPS × 4KB 보다 순차 처리량이 몇 배 높다.

LSM 트리가 SSD 시대에 다시 인기를 얻은 이유가 이것이다([LSM 노트](/db-internals/notes/03-lsm-tree-compaction)).

## 페이지 — 모든 저장의 단위

디스크(와 OS)는 바이트 단위로 읽지 않는다. **페이지**(4KB, DB 는 보통 8KB 또는 16KB) 단위다. 1바이트를 읽어도 페이지 하나를 읽고, 1바이트를 바꿔도 페이지 하나를 쓴다.

이것이 데이터베이스 설계의 핵심 제약이다:

- 한 페이지에 **관련 있는 것을 많이** 넣을수록 I/O 당 얻는 것이 많다 → B-tree 노드 = 페이지 하나, 노드당 키 수백 개(팬아웃 ↑, 높이 ↓).
- 행 하나 바꾸는 데 페이지 하나를 쓴다 → **쓰기 증폭**의 근원. 실험 `dbi-write-amplification` 에서 108바이트 행 커밋 하나가 4~9KB 쓰기를 만들었다(40~80배).
- 열 저장이 분석에 강한 이유: 한 열의 값만 페이지에 빽빽이 → 그 열을 읽는 질의는 필요한 페이지만([쿼리 실행기](/db-internals/notes/07-query-execution-columnar)).

## OS 페이지 캐시와 직접 I/O

애플리케이션이 `read()` 하면 커널은 먼저 **페이지 캐시**(남는 RAM 전부)를 본다. 있으면 메모리 복사, 없으면 디스크에서 읽어 캐시에 넣고 복사. `write()` 는 페이지 캐시의 페이지를 **더럽힐(dirty)** 뿐 디스크에 쓰지 않고 바로 돌아온다. 커널이 나중에(기본 30초 내, 또는 dirty 비율 초과 시) 백그라운드로 내려 쓴다.

| 방식 | 누가 캐시를 관리하나 | 예 |
|---|---|---|
| 버퍼드 I/O(페이지 캐시) | 커널 | PostgreSQL(이중 캐시: shared_buffers + 페이지 캐시), Kafka(거의 전부 페이지 캐시에 맡김), Lucene/OpenSearch, SQLite |
| 직접 I/O(`O_DIRECT`) | DB 가 직접(버퍼 풀) | MySQL InnoDB(권장 설정), Oracle, ScyllaDB |
| mmap | 커널이 페이지 폴트로 | LMDB, 옛 MongoDB(MMAPv1). 제어가 어려워 DB 엔 비권장 |

PostgreSQL 은 `shared_buffers` 를 RAM 의 25% 정도로 두고 나머지는 페이지 캐시가 맡게 한다 — 같은 페이지가 두 군데 있을 수 있는 대신 구현이 단순하다. [Kafka](/kafka/notes/05-internals-storage-replication) 는 아예 자체 캐시 없이 페이지 캐시 + `sendfile`(제로 카피)에 기댄다. 순차 추가·순차 읽기라 커널의 미리 읽기(readahead)가 완벽히 맞기 때문이다.

## fsync — 영속의 대가, 그리고 거짓말

`write()` 가 돌아왔다고 데이터가 디스크에 있는 게 아니다. 전원이 나가면 페이지 캐시의 dirty 페이지는 사라진다. **`fsync(fd)`** 는 그 파일의 dirty 페이지를 디스크에 쓰고, **디스크 장치의 휘발성 쓰기 캐시까지 비우라고(FLUSH)** 명령한 뒤, 완료되면 돌아온다.

| 계층 | fsync 가 뚫어야 하는 것 |
|---|---|
| 애플리케이션 버퍼(stdio, 드라이버) | `write()` 로 먼저 커널에 넘겨야 |
| 커널 페이지 캐시 | fsync 가 쓰기 요청 |
| 장치 쓰기 캐시(DRAM) | FLUSH/FUA 명령 |
| NAND | 실제 영속 |

비용: NVMe 에서 0.1~2ms, 클라우드 블록 스토리지에서 1~5ms. 커밋마다 하면 그게 커밋 지연의 대부분이다.

그리고 **거짓말**들:

- **macOS** 의 `fsync()` 는 장치 캐시를 비우지 않는다. 진짜는 `fcntl(F_FULLFSYNC)`. 그래서 이 Mac 의 실험 수치(`dbi-write-amplification` 의 커밋 지연 0.04~0.2ms)는 Linux 서버보다 낙관적이다. SQLite 는 `PRAGMA fullfsync` 로 이걸 선택할 수 있다.
- 전원 보호 커패시터가 있는 **엔터프라이즈 SSD** 는 캐시를 비운 척해도 안전하다(정전 시 캐시를 NAND 로 흘려 넣을 전력이 있다). 그래서 fsync 가 수십 µs 로 빠르다. 소비자용 SSD 는 그렇지 않다.
- **fsync 실패의 의미**(2018 "fsyncgate"): Linux 는 fsync 가 EIO 로 실패하면 dirty 페이지를 **깨끗하다고 표시하고 버린다**. 다시 fsync 해도 성공이 돌아온다 — 데이터는 이미 없는데. PostgreSQL 은 그 뒤로 fsync 실패 시 **즉시 PANIC** 하고 WAL 로 복구하도록 바꿨다.
- Docker Desktop 의 가상 디스크도 호스트까지 FLUSH 를 전달하는 방식에 따라 수치가 크게 달라진다. 실험 `dbi-wal-vs-aof` 에서 PostgreSQL `synchronous_commit=on/off` 차이가 커밋당 0.06ms 로 작게 나온 이유다.

## 세 가지 증폭

저장 엔진 비교의 공용어다.

| 증폭 | 정의 | 높아지는 원인 |
|---|---|---|
| **쓰기 증폭(WA)** | 실제 디스크 쓰기 바이트 / 논리적으로 쓴 바이트 | 페이지 단위 쓰기, 로그 + 데이터 이중 쓰기, 컴팩션·머지, SSD 내부 GC |
| **읽기 증폭(RA)** | 질의 하나에 읽은 페이지 수 | 여러 레벨·파일을 뒤지기(LSM), 인덱스 → 힙 왕복, 블룸 필터 오탐 |
| **공간 증폭(SA)** | 디스크 사용량 / 실제 데이터 크기 | 죽은 튜플·버전(MVCC 블로트), 컴팩션 전 중복, 페이지 채움률 |

**RUM 추측**(Read, Update, Memory): 셋을 동시에 최소화하는 구조는 없다. B-tree 는 읽기에, LSM 은 쓰기에, 해시는 점 조회에 최적이고 대가를 다른 곳에서 치른다. 저장 엔진 선택은 워크로드가 어느 증폭을 견딜 수 있는지의 선택이다.

## 예시로 보기 — 이 프로젝트에서

**실험 `dbi-write-amplification`**(Node 22 내장 SQLite): 108바이트 행을 2,000번 각각 커밋.

| 모드 | 커밋 p50 | 커밋당 디스크 쓰기 | 쓰기 증폭 |
|---|---|---|---|
| 롤백 저널 / FULL | ~0.17 ms | ~8.8 KB | ~80× |
| 롤백 저널 / NORMAL | ~0.13 ms | ~8.8 KB | ~80× |
| WAL / FULL | ~0.04 ms | ~4.3 KB | ~40× |
| WAL / NORMAL | ~0.01 ms | ~4.3 KB | ~40× |
| WAL / FULL, 2,000행을 **한 트랜잭션** | 전체 1 ms | 행당 ~120 B | ~1.1× |

읽는 법: 롤백 저널은 커밋마다 원본 페이지를 저널에 복사하고(4KB+) 데이터 페이지를 덮어쓴다(4KB) — 페이지 두 장. WAL 은 바뀐 페이지를 로그 끝에 한 장. 그리고 **배치하면 페이지 하나에 수십 행이 같이 들어가** 증폭이 거의 사라진다. "작은 트랜잭션을 많이" 가 왜 비싼지, 그룹 커밋이 왜 존재하는지가 이 표 하나에 있다.

**실험 `dbi-wal-vs-aof`**: PostgreSQL `synchronous_commit` 과 Redis `appendfsync` 로 같은 질문(커밋 전에 fsync 하나?)을 다른 엔진에서.

```bash
# 이 Mac 의 Docker VM 이 보고하는 디스크와 페이지 캐시
docker run --rm alpine sh -c 'cat /proc/meminfo | grep -E "^(MemTotal|Cached|Dirty)"; cat /sys/block/vda/queue/rotational 2>/dev/null'
```
