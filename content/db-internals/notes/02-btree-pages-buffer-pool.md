## 왜 이진 트리가 아닌가

균형 이진 트리(레드블랙)는 메모리에서 훌륭하지만, 노드 하나에 키 하나라 높이가 log₂N 이다. 10억 개면 높이 30 — **디스크 읽기 30번**. 앞 노트의 숫자로 30 × 100µs = 3ms, HDD 면 300ms.

B-tree 는 **노드 하나 = 페이지 하나(8KB)** 에 키를 수백 개 넣는다. 팬아웃(자식 수) F 이면 높이는 log_F N.

| 키 크기(+포인터) | 페이지당 키 (팬아웃) | 높이 3 이 담는 키 | 높이 4 |
|---|---|---|---|
| 16 B (bigint) | ~400 | 400³ = 6,400만 | 256억 |
| 40 B (UUID 문자열) | ~180 | 580만 | 10억 |

거의 모든 실제 인덱스는 **높이 3~4** 다. 그리고 루트와 2단계 노드는 늘 메모리(버퍼 풀)에 있으니 점 조회는 **디스크 읽기 1~2번**. 이것이 B-tree 가 50년째 기본값인 이유다.

## B+tree — 실제로 쓰는 변형

데이터베이스의 "B-tree" 는 거의 모두 **B+tree** 다.

```
                 [ 루트: 30 | 60 ]                 ← 내부 노드: 키 + 자식 포인터만 (값 없음 → 팬아웃 ↑)
            /          |          \
   [10|20]          [40|50]          [70|80]        ← 내부 노드
   /  |  \          /  |  \          /  |  \
 [리프]⇄[리프]⇄[리프]⇄[리프]⇄ ...                    ← 리프: 키 → 값(또는 행 주소), 형제끼리 연결 리스트
```

- 내부 노드에 값이 없어 팬아웃이 크다.
- 모든 값은 리프에 있고, 리프가 **양방향 연결 리스트**라 범위 질의(`between`, `order by ... limit`)는 시작 리프를 찾은 뒤 옆으로 걷기만 하면 된다.

## 슬롯 페이지 — 페이지 안은 어떻게 생겼나

가변 길이 레코드를 페이지에 넣는 표준 구조:

```
┌────────────────────────────────────────────────────────┐
│ 페이지 헤더 (LSN, 체크섬, 여유 공간 시작/끝, 플래그)       │
├────────────────────────────────────────────────────────┤
│ 슬롯 배열 → [1][2][3][4] ...      (앞에서부터 자람)       │
│                                                          │
│                  ... 여유 공간 ...                        │
│                                                          │
│ ... [튜플 4][튜플 3][튜플 2][튜플 1]  (뒤에서부터 자람)     │
└────────────────────────────────────────────────────────┘
```

- 슬롯은 (오프셋, 길이). 외부에서는 **(페이지 번호, 슬롯 번호)** 로 레코드를 가리킨다 — PostgreSQL 의 **ctid**. 레코드가 페이지 안에서 옮겨져도(압축) 슬롯만 고치면 주소가 유지된다.
- 페이지 헤더의 **LSN** 은 "이 페이지에 마지막으로 반영된 WAL 위치" — 복구 때 이 페이지에 어떤 로그를 다시 적용할지 판단한다([WAL 노트](/db-internals/notes/04-wal-checkpoint-recovery)).
- 체크섬은 토른 페이지(8KB 중 일부만 써진 상태)·비트 부패를 잡는다.

## 탐색, 삽입, 분할

**탐색**: 루트에서 시작해 각 노드 안에서 이진 탐색으로 자식을 고르고 리프까지. 노드 하나 = 페이지 읽기 하나.

**삽입**: 리프를 찾아 정렬 위치에 넣는다. 공간이 없으면 **분할**:

1. 새 페이지를 할당한다.
2. 키의 절반(일반적으로)을 새 페이지로 옮긴다.
3. 부모에 새 페이지를 가리키는 키(구분자)를 추가한다.
4. 부모도 가득 찼으면 부모도 분할 — 루트까지 올라가면 **높이가 1 증가**.

분할은 **페이지 세 개를 쓰는** 비싼 작업이고(WAL 도 그만큼), 직후 두 페이지는 반쯤 빈다.

### 오른쪽 끝 분할 최적화

키가 단조 증가하면(`bigserial`, 시간순 ID) 항상 맨 오른쪽 리프에만 삽입된다. 50:50 으로 쪼개면 왼쪽 반은 영원히 반쯤 빈 채 남는다. 그래서 PostgreSQL·InnoDB 는 **맨 오른쪽 리프의 분할은 꽉 채운 채(fillfactor 만큼) 넘기고 새 페이지에 새 키만** 넣는다. 결과: 순차 키 인덱스는 리프가 ~90% 찬다.

### 무작위 키의 분할 폭풍

UUID v4 처럼 무작위 키는 **모든 리프가 분할 후보**다. 실험 `dbi-btree-pageinspect` 에서 같은 20,000개 키를 넣었을 때:

| | 리프 페이지 | 평균 채움률 | 크기 |
|---|---|---|---|
| 순차 키 | 55 | 89.6% | 456 kB |
| 무작위 키 | 69 | 71.5% | 568 kB |
| 순차 키 + fillfactor 50 | 98 | 50.6% | 800 kB |

무작위 삽입은 중간 분할 후 페이지가 50% 에서 다시 차오르다 또 분할되므로 평균이 이론값 ln2 ≈ 69% 근처로 수렴한다. 작은 테이블에선 25% 차이지만 진짜 비용은 다른 데 있다:

- **캐시 지역성 상실**: 순차 키는 최근 페이지(맨 오른쪽 몇 장)만 뜨겁다. 무작위 키는 인덱스 **전체**가 작업 집합이 된다. 인덱스가 버퍼 풀보다 크면 삽입마다 디스크 읽기.
- **WAL 폭증**: PostgreSQL 은 체크포인트 후 페이지를 처음 수정할 때 **페이지 전체**를 WAL 에 쓴다(full page write). 무작위 키는 체크포인트마다 거의 모든 리프를 처음 건드린다.
- 해법: **UUID v7 / ULID**(앞부분이 시간) — 전역 유일 + 시간순. [PostgreSQL 인덱스 노트](/postgres/notes/02-indexes-explain)와 같은 결론.

### fillfactor

`CREATE INDEX ... WITH (fillfactor = 70)` 은 처음 만들 때(그리고 오른쪽 분할 때) 30% 를 비워 둔다. 나중에 들어오는 중간 삽입·갱신이 분할 없이 들어간다. 테이블(힙)의 fillfactor 는 PostgreSQL 의 **HOT 갱신**(같은 페이지 안에 새 버전을 넣으면 인덱스를 안 고쳐도 됨)을 가능하게 한다. 읽기 전용이면 100, 갱신이 잦으면 70~90.

## 클러스터드 vs 힙 + 보조 인덱스

| | PostgreSQL (힙) | MySQL InnoDB (클러스터드) |
|---|---|---|
| 행이 사는 곳 | **힙**(순서 없는 페이지 더미) | **기본 키 B+tree 의 리프** 자체 |
| 보조 인덱스 리프 값 | 행 주소 **ctid** | 행의 **기본 키** |
| 보조 인덱스로 조회 | 인덱스 → ctid → 힙 페이지 1번 | 인덱스 → PK → **PK 트리를 다시 탐색** |
| 기본 키 범위 질의 | 힙이 흩어져 있으면 임의 I/O | 리프가 PK 순이라 순차 |
| 행이 움직이면 | 모든 인덱스의 ctid 갱신(그래서 HOT 이 중요) | 보조 인덱스는 PK 를 가리키니 그대로 |
| 큰 PK 의 대가 | 없음 | 모든 보조 인덱스에 PK 가 복사됨 → UUID PK 면 전부 커짐 |

InnoDB 에서 "PK 는 작고 단조 증가하게" 가 철칙인 이유가 이것이다. PostgreSQL 에서 Index Only Scan 이 중요한 이유도 — 힙을 안 가면 왕복이 하나 준다(단, visibility map 이 all-visible 이어야. [MVCC 노트](/db-internals/notes/06-mvcc-gc-comparison)).

## pageinspect 로 실제 페이지 보기

```sql
CREATE EXTENSION pageinspect;

SELECT root, level FROM bt_metap('lab_seq_idx');
-- root = 3, level = 1   → 높이 2 (루트 + 리프)

SELECT type, live_items, free_size FROM bt_page_stats('lab_seq_idx', 3);
-- type r(oot), live_items 55   → 리프 55장을 가리키는 하향 포인터 55개

SELECT itemoffset, ctid, data FROM bt_page_items('lab_seq_idx', 3) LIMIT 3;
-- (1,0)  ""                         ← 첫 항목: "음의 무한대" (가장 왼쪽 자식)
-- (2,1)  6f 01 00 00 00 00 00 00    ← 키 0x016f = 367 이상은 블록 2
-- (4,1)  dd 02 00 00 ...            ← 키 733 이상은 블록 4

SELECT itemoffset, ctid, data FROM bt_page_items('lab_seq_idx', 1) LIMIT 3;
-- (2,1)  6f 01 ...   ← 리프의 첫 항목은 high key (이 페이지의 상한, 오른쪽 형제의 최소 키)
-- (0,1)  01 00 ...   ← 키 1 → 힙 0번 페이지 1번 튜플
-- (0,2)  02 00 ...
```

`data` 는 리틀 엔디언 바이트다(`6f 01` = 0x016f = 367). 내부 노드의 `ctid` 는 힙 주소가 아니라 **자식 페이지 번호**(블록, 오프셋 무시)라는 점이 헷갈리는 부분이다.

## 버퍼 풀 — 페이지를 메모리에 두는 곳

DB 는 디스크 페이지를 메모리의 **프레임**에 올려 두고 재사용한다. 질의는 버퍼 풀을 통해서만 페이지를 본다.

```
요청: 페이지 (rel 16384, 블록 42)
  → 해시 테이블에서 찾기 ─ 있음 → 핀(pin) 증가, 사용
                         ─ 없음 → 희생 프레임 고르기(교체 정책)
                                  → dirty 면 먼저 디스크에 쓰기 (WAL 규칙: 그 페이지 LSN 까지 WAL fsync 가 먼저)
                                  → 디스크에서 읽어 올리기
```

### 교체 정책

| 정책 | 방식 | 문제/장점 |
|---|---|---|
| LRU | 가장 오래 안 쓴 것 | **순차 스캔 오염**: 큰 테이블 한 번 훑기가 뜨거운 페이지를 전부 밀어냄 |
| **Clock sweep** (PostgreSQL) | 프레임마다 사용 카운트(최대 5), 시계 바늘이 돌며 0 이면 희생·아니면 1 감소 | LRU 근사, 락 경합 적음 |
| LRU + midpoint (InnoDB) | 새 페이지는 리스트 중간(old 구간)에 삽입, 일정 시간 후 다시 쓰이면 young 으로 | 스캔 저항 |
| 2Q / LRU-K / ARC | 한 번 쓰인 것과 두 번 이상 쓰인 것을 분리 | 스캔 저항 + 빈도 반영 |

PostgreSQL 은 큰 순차 스캔·VACUUM·COPY 에 **링 버퍼**(256KB 정도의 작은 전용 영역)를 써서 버퍼 풀 전체가 오염되지 않게 한다. [Redis 의 LRU/LFU 축출](/redis/notes/03-keys-expiration) 도 같은 문제의 다른 답(샘플링 근사)이다.

```sql
CREATE EXTENSION pg_buffercache;
SELECT c.relname, count(*) AS buffers, round(100.0 * count(*) / (SELECT setting::int FROM pg_settings WHERE name='shared_buffers'), 1) AS pct
FROM pg_buffercache b JOIN pg_class c ON b.relfilenode = pg_relation_filenode(c.oid)
GROUP BY c.relname ORDER BY buffers DESC LIMIT 10;
```

### 래치와 동시성

여러 스레드가 같은 B-tree 를 동시에 수정하면? 페이지마다 가벼운 **래치**(짧은 뮤텍스, 트랜잭션 락과 다름)를 잡는다.

- **래치 크래빙**: 자식의 래치를 잡은 뒤 부모의 래치를 놓는다. 자식이 "안전"(분할이 안 일어날 만큼 여유)하면 위쪽을 전부 놓는다.
- **B-link tree**(Lehman-Yao, PostgreSQL 이 사용): 모든 노드에 오른쪽 형제 포인터 + high key. 분할 중인 노드를 읽던 탐색이 "내가 찾는 키가 high key 보다 크네" 하면 오른쪽 형제로 이동하면 된다 — 읽기가 분할을 기다리지 않는다. 위 pageinspect 에서 본 **high key** 가 이것이다.

## 실전에서는 어디에 쓰이나

> 테이블의 PK 를 고르고, 인덱스가 왜 커졌는지, 캐시 적중률이 왜 떨어졌는지 설명해야 할 때 B-tree 페이지와 버퍼 풀이 등장한다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 커머스 주문 테이블 | 전역 유일 ID 와 삽입 성능을 동시에 | UUID v7·ULID 처럼 시간이 앞에 오는 키로 오른쪽 끝 삽입 유지 | UUID v4 는 분할 폭풍·FPI 증가, 시퀀스는 샤드 간 유일성을 따로 챙겨야 한다 |
| MySQL 기반 SaaS | 보조 인덱스가 너무 커짐 | InnoDB 는 PK 가 모든 보조 인덱스에 복사되므로 작은 단조 증가 PK + 별도 공개 ID 열 | PostgreSQL 힙 구조는 PK 크기 영향이 작다 |
| 핀테크 잔액·한도 테이블 | 잦은 UPDATE 마다 인덱스 갱신 | 테이블 fillfactor 70~90 으로 HOT 갱신 유도, 인덱스 열은 갱신하지 않게 | 이력을 추가 전용 테이블로 분리 |
| 사내 리포트 배치 | 큰 스캔이 운영 쿼리 캐시를 밀어냄 | 링 버퍼·스캔 저항 교체 정책 확인, `pg_buffercache` 로 점유 측정 | 리포트를 복제본·분석 저장소로 |
| 게임 랭킹 조회 | 정렬된 상위 N | `(score DESC, id)` B-tree 로 `order by … limit` 을 리프 순회로 | 메모리 정렬 집합(Redis ZSET) |

**이럴 땐 안 맞는다**
- 쓰기가 압도적인 이벤트·로그 적재 — 제자리 갱신과 페이지 단위 쓰기가 병목이다. LSM 계열이나 추가 전용 저장소([03](/db-internals/notes/03-lsm-tree-compaction)).
- `like '%중간%'`, 배열 포함, 다차원 근접 질의 — 정렬 순서로는 못 푼다. GIN·GiST 같은 다른 구조([05](/db-internals/notes/05-index-structures)).

**누가 매일 만나나** — 백엔드 개발자가 마이그레이션에서 PK 타입과 인덱스를 정할 때, DBA 가 "인덱스가 테이블보다 크다" 거나 버퍼 적중률 하락의 원인을 찾을 때.

**면접·실무 단골 질문**
- Q. UUID v4 를 PK 로 쓰면 왜 느려지나? → 모든 리프가 분할 후보가 되고 작업 집합이 인덱스 전체로 커지며, 체크포인트 뒤 full page write 가 늘어난다.
- Q. 클러스터드 인덱스와 힙 + 보조 인덱스의 차이? → InnoDB 는 행이 PK 리프에 있어 보조 인덱스가 PK 로 재탐색하고, PostgreSQL 은 ctid 로 힙을 직접 가리킨다.
