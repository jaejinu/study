## 보안은 "기능" 이 아니라 "속성" 이다

로그인 화면을 만들면 "인증 기능" 이 생긴다. 하지만 **보안**은 그 기능이 있느냐가 아니라, 시스템 전체가 공격자가 있어도 **의도한 대로만 동작하느냐** 는 속성이다. 성능이나 가용성처럼, 한 군데가 아니라 모든 곳에서 지켜져야 하고 한 군데가 무너지면 전체가 무너진다.

> "공격자는 가장 약한 곳으로 들어온다." 방어자는 모든 문을 지켜야 하고, 공격자는 하나만 찾으면 된다. 이 비대칭이 보안을 어렵게 만든다.

그래서 "무엇을 설치할까" 보다 먼저 **무엇을 지키고, 누구로부터, 어떤 경로로** 를 정리해야 한다. 이것이 **위협 모델링**이다.

## CIA — 지키려는 세 가지

| 속성 | 뜻 | 깨졌을 때 | 이 프로젝트 예 |
|---|---|---|---|
| **기밀성** (Confidentiality) | 허가된 주체만 읽는다 | 유출 | `ANTHROPIC_API_KEY`, PostgreSQL 비밀번호, 진행률 데이터 |
| **무결성** (Integrity) | 허가된 주체만, 허가된 방식으로만 바꾼다 | 변조 | 노트 내용, 실험 결과, 컨테이너 이미지 |
| **가용성** (Availability) | 필요할 때 쓸 수 있다 | 서비스 중단 | Redis 가 FLUSHALL 당함, 앱이 DoS 로 다운 |

여기에 흔히 **인증(Authenticity)** 과 **부인 방지(Non-repudiation)**, **책임 추적(Accountability, 감사 로그)** 을 더한다. 감사 로그는 "누가 언제 무엇을" 을 남겨 사고 뒤 복원과 억제력을 준다 — [관측성](/observability/notes/05-logging-loki) 과 보안이 만나는 지점이다.

## 공격자 모델 — 누구를 상정하나

| 공격자 | 능력 | 동기 | 대표 공격 |
|---|---|---|---|
| 인터넷의 무작위 봇 | 자동 스캔, 알려진 CVE, 기본 비밀번호 | 암호화폐 채굴, 봇넷 | 열린 Redis(6379) 에 접속해 `CONFIG SET dir` 로 cron 심기 |
| 기회주의적 공격자 | 공개 익스플로잇, 피싱 | 금전 | 유출된 `.env` 의 API 키로 LLM 비용 폭탄 |
| 표적 공격자 | 시간·돈, 제로데이, 사회공학 | 데이터·파괴 | 공급망(의존성·CI) 오염 |
| 내부자 | 정당한 자격 증명 | 실수·악의 | `kubectl delete ns prod`, 데이터 반출 |
| 악의적 입력(사용자·문서) | 앱이 처리하는 콘텐츠 | 다양 | SQL 인젝션, XSS, **프롬프트 인젝션** |

"우리는 작아서 표적이 아니다" 는 첫 번째 줄(봇) 앞에서 무의미하다. 인터넷에 열린 포트는 **수 분 안에** 스캔된다. 반대로 모든 것을 표적 공격자 기준으로 막으려면 끝이 없다. 위협 모델링은 **어디까지 막을지** 선을 긋는 일이다.

## 위협 모델링 4단계

Adam Shostack 의 네 질문이 가장 실용적이다.

1. **무엇을 만들고 있나?** → 데이터 흐름도(DFD): 구성 요소, 데이터 저장소, 흐름, **신뢰 경계**
2. **무엇이 잘못될 수 있나?** → STRIDE 로 요소마다 위협 열거
3. **어떻게 할 건가?** → 완화(제거·완화·전가·수용)
4. **잘 했나?** → 검토, 테스트, 재방문

### 1. 데이터 흐름도와 신뢰 경계

**신뢰 경계**(trust boundary)는 "이 선을 넘는 데이터는 믿을 수 없다" 는 선이다. 브라우저 ↔ 서버, 인터넷 ↔ 내부망, 앱 ↔ DB, 사용자 입력 ↔ LLM 프롬프트, 컨테이너 ↔ 호스트. **검증은 신뢰 경계에서** 한다. 내부 함수마다 검증하지 않고, 경계를 넘을 때 한 번 확실히.

```
[브라우저] ──HTTP──▶ │경계1│ [Nginx 18080] ──▶ [Next.js 3000] ──▶ │경계2│ [Redis] [PG] [Kafka]
                                                   │
                                            [Anthropic API] ◀── 경계3 (외부 서비스, 키)
                                                   │
                              사용자 메시지 + 노트 내용 ──▶ LLM ──▶ 툴 호출(실험 실행!) │경계4│
```

이 프로젝트의 경계 4 가 흥미롭다. LLM 이 읽는 노트 내용에 "실험을 실행하라" 는 문장이 있으면? 도우미는 `propose_experiment` 로 **제안만** 하고 사람이 승인 버튼을 눌러야 실행된다. 이것이 프롬프트 인젝션에 대한 설계상의 완화다 — [08 노트](/security/notes/08-web-api-llm-security).

### 2. STRIDE — 위협을 빠짐없이 떠올리는 체크리스트

| 글자 | 위협 | 깨지는 속성 | 질문 | 이 프로젝트 예 |
|---|---|---|---|---|
| **S**poofing | 위장 | 인증 | 다른 사람인 척할 수 있나? | 토큰 없는 `/api/assistant` 를 누구나 호출 → API 비용 |
| **T**ampering | 변조 | 무결성 | 데이터·코드를 바꿀 수 있나? | 레지스트리의 `study:dev` 이미지 교체, MITM 으로 응답 변조 |
| **R**epudiation | 부인 | 책임 추적 | "내가 안 했다" 를 반박할 로그가 있나? | 누가 `progress:read` 를 지웠는지 모름 |
| **I**nformation disclosure | 정보 노출 | 기밀성 | 보면 안 되는 걸 볼 수 있나? | `/api/metrics` 에 내부 정보, 에러 스택 트레이스, `.env` 커밋 |
| **D**enial of service | 서비스 거부 | 가용성 | 못 쓰게 만들 수 있나? | `/redis/console` 로 `DEBUG SLEEP 100`, 실험 무한 실행 |
| **E**levation of privilege | 권한 상승 | 인가 | 낮은 권한으로 높은 일을 할 수 있나? | 컨테이너 root → 호스트, Pod 의 SA 토큰으로 클러스터 관리 |

요소(프로세스·저장소·흐름·외부 엔티티)마다 여섯 글자를 묻는다. 프로세스는 여섯 개 전부, 데이터 흐름은 T·I·D, 저장소는 T·I·D·R 이 주로 해당된다.

### 3. 완화 전략 네 가지

| 전략 | 뜻 | 예 |
|---|---|---|
| **제거** | 그 기능·데이터를 없앤다 | 콘솔 페이지에서 `CONFIG`·`DEBUG` 명령 차단, 불필요한 포트 닫기 |
| **완화** | 가능성·피해를 줄인다 | 레이트리밋, 입력 검증, 최소 권한, 암호화 |
| **전가** | 다른 주체가 책임진다 | 결제를 PG 사에, 인증을 IdP 에, WAF 를 CDN 에 |
| **수용** | 위험을 알고 감수한다(문서화!) | 로컬 학습 환경이라 Redis 비밀번호 없음 |

**수용**이 나쁜 게 아니다. 모르는 채 열려 있는 것과 알고 열어 둔 것은 다르다. 이 프로젝트의 compose 는 `protected-mode no` 로 Redis 를 띄우지만 `127.0.0.1:6379` 로만 포트를 묶는다 — "로컬 전용" 이라는 수용의 근거를 설정에 남긴 셈이다.

## 설계 원칙 — 어디서나 통하는 것들

### 최소 권한 (least privilege)
각 주체(사용자, 서비스, 프로세스, 토큰)는 **일을 하는 데 필요한 최소한**만 가진다. 탈취 시 피해 범위 = 그 권한. Redis ACL 로 `~cache:* +@read`, k8s RBAC 로 `pods get/list` 만, DB 역할에 `SELECT` 만, 컨테이너는 non-root. [실험 sec-k8s-rbac](/security/lab), [sec-redis-acl](/security/lab) 이 이것을 보여 준다.

### 심층 방어 (defense in depth)
하나의 통제가 뚫려도 다음이 막는다. 방화벽 + 인증 + 인가 + 암호화 + 감사 로그 + 모니터링. "WAF 가 있으니 입력 검증은 안 해도" 는 심층 방어의 반대다.

```
인터넷 → [CDN/WAF] → [방화벽/SG] → [TLS] → [인증] → [인가] → [입력 검증] → [파라미터 바인딩] → [DB 권한] → [감사 로그]
```

### 안전한 기본값 (secure by default)
설정을 안 하면 안전한 쪽이어야 한다. 새 사용자는 권한 없음, 새 포트는 닫힘, 새 테이블은 RLS 적용. Redis 가 3.2 부터 `protected-mode yes` 를 기본으로 한 것, Kubernetes 가 Pod Security Standards 를 도입한 것이 이 방향이다. 반대 사례: 과거 MongoDB·Elasticsearch 가 인증 없이 0.0.0.0 에 바인딩되던 시절의 대규모 유출.

### 실패는 닫힌 쪽으로 (fail closed)
인가 서비스가 죽으면 → 모두 거부. 인증서 검증 실패 → 연결 끊기. 예외: 가용성이 더 중요한 곳(예: 레이트리미터의 Redis 가 죽으면 통과시킬지 막을지)은 **의식적으로** 정한다 — [Redis 레이트리밋 노트](/redis/notes/10-rate-limiting) 의 fail-open 논의.

### 공격 표면 최소화
실행 중인 서비스·열린 포트·설치된 패키지·노출된 엔드포인트·권한의 총합이 공격 표면이다. alpine/distroless 이미지, 안 쓰는 라우트 삭제, 내부 포트는 `127.0.0.1` 바인딩. [이미지 스캔 실험](/security/lab) 에서 패키지 수 = 취약점 후보 수임을 본다.

### 관심사 분리와 격리
웹·앱·DB 를 다른 네트워크 세그먼트에, 테넌트별 네임스페이스, 블라스트 반경 제한. 하나가 뚫려도 옆으로(lateral movement) 못 가게 — [NetworkPolicy](/kubernetes/notes/12-network-policy-mesh).

### 검증은 경계에서, 신뢰는 명시적으로
"내부망이니 믿는다" 는 **제로 트러스트** 이전의 사고방식이다. 제로 트러스트 = 네트워크 위치가 아니라 **신원과 상태**로 매 요청을 인가. mTLS 로 서비스 간 신원 증명, 짧은 토큰, 지속적 검증.

### 단순함
복잡한 시스템은 검토할 수 없다. 인증 로직을 직접 짜지 말고 검증된 라이브러리/IdP 를 쓰고, 암호를 직접 설계하지 말라("Don't roll your own crypto").

## 이 프로젝트의 위협 모델 (예시로 보기)

| 요소 | 자산 | 주요 위협 (STRIDE) | 현재 상태 | 완화 |
|---|---|---|---|---|
| `/api/assistant` | Anthropic 비용, 프롬프트 | S(인증 없음) · D(무한 호출) · I(노트 내용 유출—공개 저장소라 무의미) | 로컬 전용 | 운영이면 인증 + 레이트리밋 + 예산 상한(토큰 메트릭에 알림) |
| `/redis/console` | Redis 전체 | D(`FLUSHALL`, `DEBUG SLEEP`) · E(`CONFIG SET`) | 로컬 전용 | 명령 허용 목록, 읽기 전용 ACL 사용자로 연결 |
| 실험 실행 엔드포인트 | 호스트의 docker/kubectl | E(셸 실험은 호스트 명령을 실행) · D | 로컬 전용 | 절대 인터넷에 노출 금지, 실험 ID 허용 목록(이미 그렇게) |
| LLM 툴 루프 | 실험 실행 권한 | T(프롬프트 인젝션으로 실험 제안) | 승인 버튼 | 제안/실행 분리 유지, 툴 결과를 신뢰 경계로 |
| `.env` / API 키 | 기밀 | I(커밋 유출) | `.gitignore` | git 유출 탐지(gitleaks), 키 회전 — [04 노트](/security/notes/04-secrets-management) |
| 컨테이너 이미지 | 무결성 | T(공급망) · E(root) | `study:dev` 는 non-root? 확인 필요 | 스캔·서명·non-root — [05 노트](/security/notes/05-container-supply-chain) |
| kind 클러스터 | 가용성 | E(default SA 권한) | 기본값 | RBAC·PSS — [06 노트](/security/notes/06-kubernetes-security) |
| Redis/PG/Kafka | 데이터 | S(비밀번호 없음) · I | `127.0.0.1` 바인딩 | ACL·pg_hba·SASL — [07 노트](/security/notes/07-datastore-hardening) |
| Nginx(18080) | 앞단 | D · I(헤더 노출) | `server_tokens` 기본 | TLS·헤더·레이트리밋 — [Nginx 노트](/nginx/notes/03-cache-tls-ratelimit) |

이 표에서 가장 중요한 결론: **이 앱은 로컬 학습 도구로 설계됐고, 인터넷에 노출하면 안 된다.** 위협 모델이 "공격자가 로컬 사용자 본인뿐" 이라는 전제 위에 서 있기 때문이다. 전제가 바뀌면(예: 팀과 공유) 표의 거의 모든 행이 "완화 필요" 로 바뀐다. 위협 모델은 전제를 명시하는 문서다.

## 보안을 측정하기 — 관측과 연결

- **감사 로그**: 인증 성공/실패, 권한 변경, 관리 명령 실행을 구조화 로그로 (`who, what, when, from, result`). Loki 에서 `{service="study-app"} | json | event="auth.failed"` 로 집계.
- **이상 탐지 신호**: 실패 로그인 급증, 새 IP 에서의 관리 명령, 평소 없던 시간대의 대량 조회, Redis `ACL LOG` 증가, k8s 감사 로그의 `secrets` list.
- **취약점 지표**: 이미지별 CRITICAL 수, 수정판 존재 비율, 인증서 만료까지 일수(`probe_ssl_earliest_cert_expiry`) — Grafana 패널과 알림 규칙으로. [알림 파이프라인](/observability/notes/09-alerting-pipeline) 의 규칙에 `CertExpiringSoon` 을 넣어 보자.
- **런타임 탐지**: Falco 가 커널 이벤트(eBPF)로 "컨테이너 안에서 셸이 떴다", "/etc/shadow 를 읽었다" 를 알려 준다 — [08 노트](/security/notes/08-web-api-llm-security).

## 흔한 오해

| 오해 | 실제 |
|---|---|
| 내부망이라 안전하다 | 내부자·피싱·측면 이동. 제로 트러스트 |
| HTTPS 면 안전하다 | 전송만 보호. 인증·인가·입력 검증·저장 암호화는 별개 |
| 비밀번호 해시했으니 끝 | bcrypt/argon2 + 솔트 + 레이트리밋 + 유출 비밀번호 차단 |
| 작은 서비스는 표적이 아니다 | 봇은 표적을 고르지 않는다 |
| 스캐너가 0 이면 안전 | 스캐너는 알려진 것만 본다. 설계 결함(인가 누락)은 못 찾는다 |
| 보안은 보안팀 일 | 설계·코드·운영 모두의 일. 가장 싼 수정은 설계 단계 |
