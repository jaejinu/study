## 데드락 — 서로를 영원히 기다린다

```
스레드 1: lock(A) … lock(B)        스레드 2: lock(B) … lock(A)
   A 보유, B 대기  ─────→  B 는 스레드 2 가 보유
   ↑                                  │
   └──── A 는 스레드 1 이 보유 ←── B 보유, A 대기
```

[데드락 실험](/concurrency/lab/conc-deadlock)은 워커 1 이 A→B, 워커 2 가 B→A 순서로 락을 잡게 한다. 둘 다 첫 락을 쥔 채 50ms 쉬어서 상대도 자기 첫 락을 잡게 만든 뒤 두 번째 락을 요청한다. 진짜 블로킹 락이면 영원히 멈추므로 실험은 두 번째 락에 500ms 타임아웃을 두고, 타임아웃을 데드락 신호로 쓴다.

## 네 조건 — 코프먼 조건

데드락은 다음 넷이 **모두** 성립할 때만 생긴다. 하나만 깨도 사라진다.

| 조건 | 의미 | 깨는 방법 | 비용 |
|---|---|---|---|
| 상호 배제 | 자원을 한 번에 하나만 쓴다 | 공유 가능한 자원으로 (읽기 전용, 불변, 원자 연산) | 모든 자원에 가능하진 않음 |
| 점유와 대기 | 하나를 쥔 채 다른 것을 기다린다 | 필요한 락을 **한 번에 전부** 잡거나, 못 잡으면 다 놓기 | 동시성 감소 |
| 비선점 | 남이 쥔 자원을 빼앗을 수 없다 | 타임아웃·tryLock 실패 시 스스로 놓기, DB 는 희생자 abort | 재시도 로직 필요 |
| **순환 대기** | 대기 관계가 원을 이룬다 | **전역 락 순서** — 모두 같은 순서로 잡는다 | 순서 규칙을 지켜야 함 |

가장 실용적인 것이 **순환 대기 깨기**다. 실험의 두 번째 라운드에서 두 워커가 모두 A→B 순서를 따르면 둘 다 두 락을 얻는다. 순서가 같으면 원이 생길 수 없다.

### 락 순서를 정하는 방법

```java
// 계좌 이체 — 두 계좌 락을 항상 id 가 작은 쪽부터
void transfer(Account a, Account b, long amt) {
  Account first = a.id < b.id ? a : b, second = a.id < b.id ? b : a;
  synchronized (first) { synchronized (second) { a.withdraw(amt); b.deposit(amt); } }
}
```

자연 키(id, 주소)가 없으면 `System.identityHashCode` 같은 값으로 정하고, 같으면 세 번째 "타이 브레이커" 락을 쓴다. PostgreSQL 에서도 같은 원리로 **여러 행을 갱신할 때 항상 같은 순서**(예: `ORDER BY id FOR UPDATE`)로 잠그면 데드락이 사라진다([PostgreSQL 04](/postgres/notes/04-locks-deadlocks)).

## 감지하고 회복하기

순서를 강제할 수 없는 시스템(데이터베이스처럼 임의의 트랜잭션이 들어오는 곳)은 **감지 후 회복**을 쓴다.

**대기 그래프(wait-for graph)**: 노드 = 트랜잭션(스레드), 간선 T1 → T2 = "T1 이 T2 가 쥔 것을 기다린다". **그래프에 순환이 있으면 데드락.**

| 시스템 | 방식 |
|---|---|
| PostgreSQL | 락을 `deadlock_timeout`(기본 1초) 넘게 기다리면 대기 그래프를 검사, 순환이면 한 트랜잭션을 `deadlock detected` 로 abort |
| MySQL InnoDB | 즉시 감지(또는 lock_wait_timeout), 되돌리기 비용이 작은 쪽을 희생 |
| Java | `jstack`, JFR 이 `Found one Java-level deadlock` 출력, `ThreadMXBean.findDeadlockedThreads()` |
| Go | 모든 고루틴이 막히면 런타임이 `fatal error: all goroutines are asleep - deadlock!` |

### 타임아웃과 tryLock

```java
if (lockA.tryLock(500, MILLISECONDS)) {
  try {
    if (lockB.tryLock(500, MILLISECONDS)) { try { work(); } finally { lockB.unlock(); } }
    else { /* 못 잡았다 → A 도 놓고 백오프 후 재시도 */ }
  } finally { lockA.unlock(); }
}
```

타임아웃은 데드락을 **끝내지만**, 재시도 타이밍이 같으면 다음 문제를 만든다.

## 라이브락 — 움직이지만 진전이 없다

두 스레드가 데드락을 피하려고 동시에 락을 놓고, 동시에 다시 잡고, 다시 충돌하고… 좁은 복도에서 서로 비켜 주다 계속 같은 쪽으로 움직이는 두 사람과 같다. CPU 는 바쁘지만 일은 끝나지 않는다.

해법은 **무작위성**이다 — 재시도 대기에 지터(무작위 지연)를 넣는다. 이더넷의 지수 백오프, 이 사이트 [재시도 폭풍 실험](/chaos/lab/chaos-retry-storm)의 지터, Raft 의 무작위 선거 타임아웃([분산 시스템 05](/distributed-systems/notes/05-consensus))이 모두 같은 처방이다.

## 기아 — 늘 밀린다

**기아(starvation)**: 시스템은 진행하지만 특정 스레드가 계속 기회를 못 얻는다.

| 원인 | 예 | 처방 |
|---|---|---|
| 불공정 락 | 막 깨어난 스레드보다 계속 도착하는 새 스레드가 락을 가로챔(barging) | 공정 락(`new ReentrantLock(true)`) — 처리량은 떨어짐 |
| 읽기-쓰기 락 | 읽기가 끊이지 않아 쓰기가 영원히 대기 | 쓰기 선호 정책 |
| 우선순위 스케줄링 | 높은 우선순위가 계속 있어 낮은 쪽이 안 돎 | 에이징 (기다린 만큼 우선순위 올리기) |
| CAS 경합 | lock-free 루프에서 한 스레드만 계속 실패 | 백오프, wait-free 구조 |

[스핀락 vs 뮤텍스 실험](/concurrency/lab/conc-cas-spinlock)의 스핀락은 공정성이 전혀 없다. 누가 다음에 잡을지는 캐시 라인을 먼저 가져가는 코어가 정한다. 처리량은 좋을 수 있지만 꼬리 지연(p99)은 나빠질 수 있다 — 공정성과 처리량은 교환 관계다.

## 우선순위 역전 — 화성에서 생긴 일

1997년 화성 탐사선 **패스파인더**가 반복적으로 재부팅됐다. 원인은:

1. 낮은 우선순위 작업 L 이 공유 버스의 뮤텍스를 잡았다.
2. 높은 우선순위 작업 H 가 같은 뮤텍스를 기다렸다.
3. 그 사이 **중간 우선순위** 작업 M 들이 L 보다 우선이라 계속 실행되어 L 이 락을 풀 기회를 얻지 못했다.
4. H 가 너무 오래 기다리자 워치독이 시스템을 리셋했다.

**높은 우선순위 작업이 낮은 우선순위 작업에게 사실상 밀린 것**이 우선순위 역전이다. 해법은 **우선순위 상속**: 락을 쥔 L 이 그 락을 기다리는 가장 높은 우선순위(H)를 잠시 물려받아 M 보다 먼저 실행되게 한다. 패스파인더는 지구에서 VxWorks 뮤텍스의 우선순위 상속 옵션을 켜는 패치로 고쳐졌다. 리눅스는 `PTHREAD_PRIO_INHERIT`, 실시간 커널의 rt_mutex 가 이것을 지원한다.

일반 서버에서는 이 형태가 **스레드 풀 고갈**로 나타난다. 중요한 요청이 덜 중요한 작업이 쥔 커넥션·락을 기다리는 동안, 풀은 덜 중요한 작업으로 가득 차 있다. 벌크헤드(작업 종류별 풀 분리)가 처방이다.

## 분산 시스템의 데드락

| 형태 | 예 | 처방 |
|---|---|---|
| 분산 락 순서 | 서비스 A 가 Redis 락 X 후 Y, 서비스 B 가 Y 후 X | 락 순서 규칙, 락 TTL |
| 동기 호출 순환 | A → B → A 동기 호출, 각자 스레드 풀이 가득 | 비동기화, 타임아웃, 순환 의존 제거 |
| 분산 트랜잭션 | 2PC 참여자들이 서로의 행을 잠금 | 타임아웃·abort ([분산 시스템 06](/distributed-systems/notes/06-transactions-coordination)) |

분산에서는 대기 그래프를 한 곳에서 볼 수 없으므로 **타임아웃이 사실상 유일한 감지기**다. 그리고 TTL 로 풀리는 락은 "락 주인이 아직 살아 있는데 풀리는" 반대 문제를 만든다 — [펜싱 토큰](/distributed-systems/lab/ds-fencing-token)이 그 처방이다.

## 흔한 실수

| 실수 | 결과 | 바로잡기 |
|---|---|---|
| 락 안에서 외부 콜백 호출 | 콜백이 다른 락을 잡아 순서가 깨짐 | 락을 놓은 뒤 콜백 |
| 타임아웃 없는 원격 락·호출 | 상대가 죽으면 영원히 대기 | 모든 대기에 타임아웃 |
| 재시도에 지터 없음 | 라이브락, 재시도 폭풍 | 지수 백오프 + 무작위 지터 |
| 같은 스레드 풀에서 하위 작업을 기다림 | 풀이 가득 차면 스스로 데드락 (스레드 풀 고갈) | 하위 작업은 별도 풀, 또는 비동기 |
| DB 트랜잭션에서 행을 임의 순서로 갱신 | 동시 트랜잭션 간 데드락 | 항상 같은 키 순서로 잠금 |

## 실전에서는 어디에 쓰이나

> 자원 여러 개를 잡는 코드 — 계좌 이체, 재고 이동, 여러 행 갱신, 서비스 간 동기 호출 — 에서 데드락이, 재시도 로직에서 라이브락이, 공유 풀에서 기아가 등장한다.

| 어디서 | 무엇을 풀려고 | 어떻게 쓰나 | 다른 선택지 |
|---|---|---|---|
| 핀테크 계좌 이체 | 반대 방향 동시 이체의 데드락 | 계좌 id 순서로 잠금(`ORDER BY id FOR UPDATE`) | DB 데드락 감지 후 재시도에만 의존 |
| 커머스 재고 일괄 갱신 | 여러 행을 임의 순서로 UPDATE | 항상 같은 키 순서, 트랜잭션 짧게 | 행마다 별도 트랜잭션 |
| MSA 동기 호출 | A → B → A 호출로 양쪽 스레드 풀 고갈 | 순환 의존 제거, 모든 호출에 타임아웃, 비동기화 | 풀 크기 증가(지연만 늦춘다) |
| API 클라이언트·게이트웨이 재시도 | 동시 재시도 충돌과 재시도 폭풍 | 지수 백오프 + 무작위 지터 | 고정 간격 재시도 |
| 작업 종류가 섞인 서버 | 중요한 요청이 덜 중요한 작업 뒤에 밀림 | 작업 종류별 풀 분리(벌크헤드) | 단일 공유 풀 |

**이럴 땐 안 맞는다**
- 분산 환경에서 대기 그래프로 감지하기 — 전체 그래프를 한 곳에서 볼 수 없다. 타임아웃, TTL 리스, 펜싱 토큰을 쓴다.
- 처리량이 중요한 곳에 무조건 공정 락 — 공정성은 처리량을 깎는다. 꼬리 지연이 문제일 때만 고른다.

**누가 매일 만나나** — 백엔드 개발자가 `deadlock detected` 로그를 받고 갱신 순서를 고칠 때, SRE 가 스레드 덤프에서 "모든 스레드가 같은 풀을 기다림" 을 볼 때.

**면접·실무 단골 질문**
- Q. 데드락의 네 조건과 가장 실용적인 해법은? → 상호 배제·점유와 대기·비선점·순환 대기. 전역 락 순서로 순환 대기를 깬다.
- Q. 라이브락은 어떻게 푸나? → 재시도 대기에 무작위 지터를 넣어 대칭을 깬다.
