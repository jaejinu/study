## 두 단어부터 정확히

| | 동시성 (concurrency) | 병렬성 (parallelism) |
|---|---|---|
| 정의 | 여러 작업이 **진행 중인 상태를 겹쳐서** 다루는 구조 | 여러 작업을 **같은 순간에 실제로** 실행 |
| 필요한 것 | 작업을 나누고 전환하는 방법 | 코어(또는 기계)가 여러 개 |
| 코어 1개에서 | 가능 (번갈아 실행) | 불가능 |
| 주된 목적 | 기다리는 동안 다른 일 하기 (지연 숨기기) | 계산을 나눠 빨리 끝내기 (처리량) |
| 예 | Node 의 이벤트 루프가 요청 1만 개를 다룸 | 이미지 1,000장을 코어 8개가 나눠 변환 |

롭 파이크의 정리가 가장 짧다: **동시성은 구조이고, 병렬성은 실행이다.** 잘 짜인 동시성 구조는 코어가 늘면 병렬로 돌 수 있지만, 동시성이 있다고 저절로 빨라지지는 않는다.

> 이 사이트의 서버(Next.js, Node)는 **스레드 하나**로 수백 개의 요청을 동시에 다룬다. 요청 대부분이 Redis·파일·네트워크를 **기다리는** 시간이기 때문이다. 반대로 실험의 CPU 계산은 그 스레드를 막는다 — 그래서 무거운 계산은 워커 스레드로 보낸다([성능 공학 04](/performance/notes/04-node-web-server-performance)).

## 실행 단위 네 가지

| 단위 | 누가 전환하나 | 메모리 | 생성 비용 | 대표 |
|---|---|---|---|---|
| 프로세스 | OS 스케줄러 (선점) | 각자 독립 주소 공간 | 큼 (ms) | Nginx 워커, PostgreSQL 백엔드 |
| OS 스레드 | OS 스케줄러 (선점) | 주소 공간 공유, 스택은 각자 | 중간 (수십 µs, 스택 수 MB 예약) | Java 플랫폼 스레드, Node worker_threads |
| 이벤트 루프 + 콜백 | 프로그램 (협력적, await 지점에서만) | 한 스레드 안 | 거의 0 | Node, Redis, Nginx 워커 내부 |
| 코루틴·가상 스레드·고루틴 | 런타임 (보통 협력적, 블로킹 지점에서) | 공유 | 매우 작음 (KB) | Go, Kotlin, Java 21 가상 스레드 |

선점(preemptive) 전환은 **언제든** 끼어들 수 있어 공유 데이터가 위험하고, 협력적(cooperative) 전환은 **정해진 지점에서만** 바뀌어 안전하지만 한 작업이 양보하지 않으면 전체가 멈춘다. Node 개발자가 "락이 필요 없다" 고 느끼는 이유가 협력적 전환이고, 동기 루프 하나가 서버 전체를 세우는 이유도 같은 성질이다([운영체제 01](/os-internals/notes/01-processes-threads-context-switch) 의 컨텍스트 스위치).

## 소통 방식 두 가지

**공유 메모리**: 같은 변수를 여러 실행 단위가 읽고 쓴다. 빠르지만 동기화(락·원자 연산)가 필요하고 버그가 숨는다. 2~5편이 이 세계다.

**메시지 전달**: 데이터를 복사(또는 소유권 이전)해 보낸다. 받는 쪽만 그 데이터를 만진다. 느릴 수 있지만 추론이 쉽다. 액터(Erlang·Akka), CSP 채널(Go), 워커의 postMessage 가 여기다. 7편에서 다룬다.

```js
// 공유 메모리 — 같은 버퍼를 두 스레드가 본다
const sab = new SharedArrayBuffer(4);
new Worker(code, { workerData: { sab } });       // 워커도 같은 메모리

// 메시지 전달 — 값이 복사된다 (structured clone)
worker.postMessage({ orderId: 42 });              // 받은 쪽 객체는 별개
```

"메모리를 공유해서 통신하지 말고, 통신해서 메모리를 공유하라" 는 Go 의 속담은 두 번째를 기본으로 하라는 권고다. 분산 시스템은 애초에 공유 메모리가 없으므로 메시지 전달밖에 없다 — 이 주제의 끝(7편)이 [분산 시스템](/distributed-systems/notes/01-why-hard)의 시작과 맞닿는 이유다.

## 얼마나 빨라질 수 있나 — 암달의 법칙

프로그램에서 병렬화할 수 있는 비율을 p, 코어 수를 N 이라 하면 속도 향상은

```
S(N) = 1 / ((1 − p) + p / N)          N → ∞ 이면  S → 1 / (1 − p)
```

| 병렬 비율 p | 코어 4 | 코어 16 | 코어 64 | 상한 (∞) |
|---|---|---|---|---|
| 50% | 1.6배 | 1.9배 | 2.0배 | 2배 |
| 90% | 3.1배 | 6.4배 | 8.8배 | 10배 |
| 95% | 3.5배 | 9.1배 | 15.4배 | 20배 |
| 99% | 3.9배 | 13.9배 | 39.3배 | 100배 |

**순차 부분 5%** 가 코어 64개의 효과를 15배로 묶는다. 순차 부분은 대개 여기 있다: 락으로 보호되는 임계 구역, 공유 카운터, 결과 합치기, 메모리 대역폭, 그리고 **조정 자체**(스레드 생성·종료, 작업 분배).

실제로는 암달보다 더 나쁘다. 코어가 늘면 **경합 비용**(같은 캐시 라인을 코어끼리 빼앗기)과 **조정 비용**이 늘어 어느 지점부터는 코어를 더 넣을수록 **느려진다**. 이것을 정량화한 것이 닐 건서의 **범용 확장성 법칙(USL)**: 처리량이 N 에서 최고점을 찍고 내려간다([성능 공학 07](/performance/notes/07-capacity-planning)).

### 구스타프슨의 법칙 — 문제를 키우면 얘기가 달라진다

암달은 **같은 문제**를 빨리 푸는 경우다. 현실에서는 코어가 늘면 **더 큰 문제**를 푼다(더 많은 사용자, 더 큰 데이터). 이때 순차 부분은 거의 그대로이고 병렬 부분만 커지므로 확장성이 훨씬 좋다. 웹 서버가 "코어를 늘리면 처리량이 거의 비례해 는다" 고 말할 수 있는 것은 요청끼리 독립적이어서다.

## 예시로 보기 — 이 프로젝트에서

[경합 조건 실험](/concurrency/lab/conc-race-condition)은 워커 4개가 공유 카운터 하나를 100만 번씩 올린다. 세 가지가 동시에 드러난다.

1. **정확성**: 일반 대입(`a[0] = a[0] + 1`)은 갱신을 잃는다. 2편의 주제.
2. **원자 연산의 비용**: `Atomics.add` 는 정확하지만, 네 코어가 같은 캐시 라인을 번갈아 독점하느라 단일 스레드보다 오히려 느릴 수 있다. 공유 카운터는 **순차 부분 그 자체**다 — 암달의 1 − p.
3. **해법의 방향**: 워커마다 지역 카운터를 두고 마지막에 한 번 합치면 공유가 사라진다. 병렬 프로그래밍의 첫 번째 기술은 락이 아니라 **공유를 없애는 설계**다.

이 사이트의 다른 실험도 같은 이야기를 한다.

| 실험 | 동시성 관점 |
|---|---|
| [Redis 분산 락](/redis/notes/09-distributed-lock) | 프로세스(기계) 사이의 임계 구역 — 3편의 락이 네트워크로 나간 것 |
| [펜싱 토큰](/distributed-systems/lab/ds-fencing-token) | 락을 쥔 쪽이 멈추면? — 6편의 "락은 조언일 뿐" |
| [PostgreSQL 격리 수준](/postgres/notes/03-mvcc-isolation) | DB 가 대신 처리해 주는 동시성 제어 |
| [이벤트 소싱 낙관적 동시성](/event-sourcing/lab/es-optimistic-concurrency) | 락 대신 버전 비교(CAS) — 4편의 CAS 가 테이블 행으로 |

## 동시성 버그가 어려운 이유

- **비결정성**: 같은 입력이어도 스레드 실행 순서(인터리빙)가 매번 다르다. 버그가 1만 번에 한 번 난다.
- **관찰이 바꾼다**: 로그·디버거를 붙이면 타이밍이 바뀌어 버그가 사라진다(하이젠버그).
- **조합 폭발**: 스레드 2개가 각 10단계를 가지면 가능한 인터리빙이 18만 가지가 넘는다.
- **하드웨어와 컴파일러**: 코드에 적은 순서대로 실행된다는 보장도 없다(5편 메모리 모델).

그래서 이 분야의 도구는 "테스트를 많이 돌리기" 보다 **구조로 불가능하게 만들기**(불변 데이터, 소유권, 메시지 전달, 락 순서 규칙)와 **도구로 찾기**(ThreadSanitizer, Java 의 jcstress, 모델 검사 — [분산 시스템 08](/distributed-systems/notes/08-verification-and-practice))에 무게를 둔다.
