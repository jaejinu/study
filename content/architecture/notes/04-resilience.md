## 전제: 모든 것은 실패한다

네트워크 지연, 의존 서비스 다운, 디스크 꽉 참, 배포 중 Pod 종료, GC 멈춤. 복원력은 "실패를 막는 것" 이 아니라 **실패가 번지지 않게** 하는 것이다.

## 타임아웃

없으면 요청이 영원히 걸려 스레드·커넥션을 잡아먹고 **연쇄 장애**가 된다.

- 모든 외부 호출에 타임아웃: 연결(1~3s), 읽기(의존성의 p99 × 2~3).
- **예산 전파**: 사용자 요청 전체 2s 면, 하위 호출에 남은 시간을 넘긴다 (gRPC deadline, `AbortSignal.timeout`).
- 타임아웃 후 상대가 작업을 계속할 수 있다(이미 결제됨?) → 멱등 키로 재확인.

```ts
const res = await fetch(url, { signal: AbortSignal.timeout(remainingMs) });
```

## 재시도

- 재시도는 **일시적** 오류(네트워크, 503, 429, 데드락)에만. 400/404/인증 오류는 재시도하지 않는다.
- **지수 백오프 + 지터**: 100ms, 200ms, 400ms … + 무작위. 지터가 없으면 모든 클라이언트가 동시에 재시도해 **재시도 폭풍**(thundering herd)이 된다.
- 횟수 제한(2~3회), 총 시간은 타임아웃 예산 안에.
- 멱등하지 않은 요청(POST 결제)은 멱등 키 없이는 재시도 금지.
- 재시도 예산: 전체 요청의 10% 이상이 재시도면 재시도를 멈춘다(의존성이 과부하라는 뜻).

```ts
async function withRetry<T>(fn: () => Promise<T>, { tries = 3, base = 100 } = {}) {
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (e) {
      if (i >= tries - 1 || !isTransient(e)) throw e;
      await sleep(base * 2 ** i + Math.random() * base);     // 지터
    }
  }
}
```

## 서킷브레이커

의존성이 죽었는데 계속 호출하면 타임아웃만 쌓인다. 서킷브레이커는 실패율이 임계를 넘으면 **즉시 실패**로 전환해 의존성이 회복할 시간을 준다.

![서킷브레이커 상태](/diagrams/circuit-breaker.svg)

```
CLOSED (정상) ─실패율 > 50% (최근 20건)─▶ OPEN (즉시 실패, 폴백) ─30s 후─▶ HALF-OPEN (시험 호출 몇 건)
   ▲                                                                        │ 성공 → CLOSED
   └────────────────────────────────────────────────────────────── 실패 → OPEN
```

- 상태는 인스턴스별(메모리) 또는 공유(Redis) — 공유하면 전체가 동시에 열려 폭풍을 막는다.
- OPEN 일 때 **폴백**: 캐시된 값, 기본값, 기능 축소("추천을 불러올 수 없습니다").
- 라이브러리: resilience4j(JVM), opossum(Node), Polly(.NET). 서비스 메시(Istio/Linkerd)는 프록시 레벨에서.

## 벌크헤드 (격리)

배의 격벽처럼, 한 의존성의 장애가 전체 스레드/커넥션을 삼키지 않게 **자원을 나눈다.**
- 의존성별 커넥션 풀·동시성 제한(세마포어): 결제 API 는 최대 50 동시, 추천 API 는 20.
- 중요 트래픽과 배치 트래픽을 다른 Pod/노드에 (Kubernetes PriorityClass, 별도 Deployment).
- 테넌트별 격리: 큰 고객 하나가 큐를 독점하지 않게 테넌트별 레이트 리밋.

## 부하 차단과 우아한 저하

- 과부하 시 **일부 요청을 빨리 거절**(503 + Retry-After)하는 것이 전부를 느리게 하는 것보다 낫다. 큐 길이/지연 기반 적응형 제한(Netflix concurrency-limits).
- 우선순위: 로그인·결제 > 검색 > 추천. 과부하 시 낮은 것부터 끈다(기능 플래그).
- 읽기 전용 모드: DB 리더 장애 시 레플리카로 읽기만 제공.
- 정적 폴백 페이지: 캐시된 홈페이지.

## 헬스체크 설계

| 종류 | 의미 | 확인 |
|---|---|---|
| liveness | 프로세스가 살아 있나 | 데드락 아님, 이벤트 루프 응답 |
| readiness | 트래픽 받을 수 있나 | 의존성 연결(DB·Redis) 준비, 워밍업 완료 |
| startup | 초기화 끝났나 | 긴 부팅 |

readiness 에 **의존성 전체**를 넣으면 Redis 장애 시 모든 Pod 이 동시에 빠져 전면 장애가 된다. 핵심 의존성만, 그리고 캐시 가능하게. ([k8s probe](/kubernetes/notes/03-pod-deployment))

## 데이터 계층의 복원력

- 복제 + 자동 failover ([Sentinel 실험](/redis/lab/sentinel-failover)) — 승격 중 수 초 쓰기 실패를 앱이 재시도로 흡수.
- 커넥션 끊김 재연결(클라이언트 라이브러리 설정), DNS 재해석.
- 백업·복구 연습, 멀티 AZ.

## 카오스 엔지니어링

가설 → 실험(의존성 지연 주입, Pod 강제 종료, 네트워크 분단) → 관측 → 개선. 작게, 운영 시간 외, 중단 스위치와 함께. 이 프로젝트의 [자가 치유 실험](/kubernetes/lab/k8s-self-healing)과 [failover 실험](/redis/lab/sentinel-failover)이 작은 카오스 실험이다. 도구: Chaos Mesh, Litmus, Gremlin.
