## 아키텍처란

"어떻게 쪼개고, 어떻게 연결하고, 무엇을 포기할지" 의 결정 집합. 좋은 아키텍처는 정답이 아니라 **맥락에 맞는 트레이드오프**다. 같은 채팅 서비스도 사용자 100명과 1억 명은 다른 구조다.

## 요구사항을 숫자로

| 항목 | 질문 | 예 (이 사이트) | 예 (결제 API) |
|---|---|---|---|
| 처리량 | 초당 요청, 피크/평균 비율 | 1 rps | 2,000 rps, 피크 10배 |
| 지연 | p50/p99 목표 | 500ms 면 충분 | p99 < 300ms |
| 가용성 | 연간 허용 다운타임 | 상관없음 | 99.95% (4.4h/년) |
| 일관성 | 읽기가 최신이어야 하나 | 아니오 | 잔액은 예 |
| 데이터 | 크기, 증가율, 보존 | MB | TB, 7년 |
| 내구성 | 유실 허용 | 캐시 날아가도 OK | 0 |
| 비용 | 월 예산 | 0 | $X |
| 팀 | 인원, 운영 역량 | 1명 | 20명, 온콜 |

**비기능 요구사항(NFR)** 이 구조를 결정한다. 기능은 어떤 구조에서도 만들 수 있다.

가용성 표: 99% = 3.65일/년, 99.9% = 8.8h, 99.99% = 53분, 99.999% = 5분. 9 하나 더하기마다 비용은 수 배.

## CAP 와 PACELC

네트워크 분단(P)이 일어나면 **일관성(C)** 과 **가용성(A)** 중 하나를 포기해야 한다. 분단은 반드시 일어나므로 실질 선택은 CP vs AP.

- CP: 분단 중 일부 요청 거부 (ZooKeeper, etcd, 동기 복제 DB). 정확성 우선.
- AP: 분단 중에도 응답, 나중에 수렴 (DynamoDB 기본, Cassandra, DNS). 가용성 우선.

**PACELC**: 분단이 없을 때(E)도 **지연(L) vs 일관성(C)** 을 고른다. 동기 복제는 느리고 비동기는 stale.

예: Redis 복제는 비동기(EL) — 빠르지만 failover 시 마지막 쓰기 유실 가능 ([Sentinel 실험](/redis/lab/sentinel-failover)). PostgreSQL 동기 복제(`synchronous_commit=on` + standby)는 커밋 지연↑, 유실 0.

## 일관성 모델

| 모델 | 보장 | 예 |
|---|---|---|
| 강한(선형화) | 쓰기 완료 후 모든 읽기가 최신 | 단일 DB 리더, etcd |
| 순차 | 모든 노드가 같은 순서로 봄 | |
| 인과 | 원인→결과 순서 유지 | 댓글이 글보다 먼저 보이지 않음 |
| Read-your-writes | 내가 쓴 건 내가 바로 봄 | 프로필 수정 후 새로고침 |
| 단조 읽기 | 과거로 돌아가지 않음 | 레플리카 고정(session affinity) |
| 최종(eventual) | 언젠가 수렴 | 캐시, DNS, 피드 |

대부분의 서비스는 "강한 일관성이 필요한 작은 핵심(잔액, 재고, 인증)" + "최종 일관성으로 충분한 나머지(피드, 통계, 추천)" 로 나뉜다. 핵심에 강한 일관성 비용을 쓰고 나머지는 캐시·비동기로.

## 지연·처리량·비용

- **지연**은 RTT 와 직렬 단계 수가 지배 ([Redis 파이프라인](/redis/notes/06-pipelining), [네트워크 노트](/linux-network/notes/01-layers-tcpip)). 단계를 줄이거나 병렬화.
- **처리량**은 병목 자원이 결정 — DB 커넥션, 단일 파티션, 락. 샤딩·파티셔닝으로 병렬성 확보.
- **비용**은 과잉 프로비저닝과 데이터 전송에서 샌다. 캐시가 가장 싼 확장.
- 리틀의 법칙: 동시 요청 수 = 처리량 × 지연. p99 지연이 2배면 같은 처리량에 커넥션·스레드가 2배 필요.

## 단순함의 가치

- 모놀리스로 시작해 **경계가 보일 때** 쪼갠다. 마이크로서비스는 조직 규모 문제의 해법이지 성능 해법이 아니다.
- 지루한 기술(PostgreSQL, Redis, 큐 하나)을 깊게. 새 기술은 한 번에 하나.
- 제거할 수 있는 컴포넌트가 최고의 컴포넌트. 운영 비용은 컴포넌트 수에 비례.
- "나중에 필요할 것" 을 위한 설계는 대개 틀린다. 대신 **바꾸기 쉽게**(인터페이스, 데이터 소유권 명확).

## 의사결정 기록 (ADR)

```markdown
# ADR-007: 세션 저장소로 Redis 사용
상태: 승인 (2026-10-16)
맥락: 웹 서버 3대가 세션을 공유해야 함. 세션은 유실돼도 재로그인으로 복구 가능. p99 < 5ms.
결정: Redis Hash + TTL 24h. Sentinel 로 HA. 영속성은 AOF everysec.
대안: PostgreSQL 세션 테이블(지연·부하), sticky session(배포 시 유실), JWT(폐기 어려움).
결과: 로그인 상태 유지·강제 로그아웃 가능. Redis 장애 시 전원 재로그인(허용). 운영 컴포넌트 +1.
```

ADR 은 "왜" 를 남긴다. 6개월 뒤의 나와 팀이 같은 논쟁을 반복하지 않게.

## 이 사이트의 아키텍처 (예시)

```
브라우저 ─▶ Next.js (서버 컴포넌트 + 서버 액션)
              ├─ content/*.md (파일) ── 노트
              ├─ Redis ── 진행률, 실험 대상, 벡터 검색
              ├─ docker/kubectl/kafkajs/pg ── 실험 실행
              └─ OTel → Tempo, JSON 로그 → Loki, /api/metrics → Prometheus
```

결정: 노트는 DB 가 아니라 **파일**(git 이 버전·리뷰, 빌드 불필요). 진행률은 Redis(학습 대상이자 가볍다). 실험은 서버에서 실행(브라우저에 권한 없음). 포기한 것: 다중 사용자, 인증, 수평 확장 — 개인 학습 사이트에 불필요.
